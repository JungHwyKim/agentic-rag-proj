# 기록 형식 설계

상태: 구현됨 (커밋 예정)
관련 기록: [task_log/2026-08-17-기록형식-md전환.md](../task_log/2026-08-17-기록형식-md전환.md)

## 확정된 것

- **`task_log/` 기록은 `.md` 다.** `YYYY-MM-DD-<주제>.md` — 근거: 같은 저장소의 `plan_log/` 가
  이미 전부 `.md` 였고, 두 기록 폴더가 형식이 갈려 있을 이유가 없다. `.txt` 는 GitHub·에디터에서
  링크·표·강조가 죽는다
- **옮길 때 문장은 한 글자도 안 고친다.** 더할 수 있는 것은 마크업(`#`, `|`, 코드펜스, 줄머리 `- `)뿐이고,
  기록은 그때의 사실이라 다듬는 순간 거짓이 된다 — 근거: 무손실 대조 스크립트로 7개 전부 확인했다
- **표로 재구성하려면 원문에 열 이름이 이미 있어야 한다.** 없으면 열 이름을 지어내야 하므로
  코드펜스에 원문 그대로 둔다 — 근거: `routing-diff` 의 "실데이터 표 9개" 블록처럼 열 이름 없이
  들여쓰기로만 계층을 만든 블록이 실제로 여럿이다
- **정렬로만 표현된 대응 관계는 표로 옮길 때 말로 남긴다** — 근거: splitter 기록의
  `100자 미만 청크  6 / 0 / 3 / 3` 은 바로 위 4행에 순서로 대응하는데, 표로 바꾸면 그 단서가 사라진다.
  이번 변환에서 **유일하게 텍스트를 더한 자리**이고 검증 스크립트에 화이트리스트로 남겼다
- **파일명은 확장자만 바꾼다.** `phase1` `routing-diff-시행령개정안` 에 날짜를 소급해 붙이지 않는다 —
  근거: INDEX 링크와 `plan_log/*.md` 상호참조를 더 어긋나게 만들 뿐이고, 얻는 것은 이름의 균일함뿐이다

2회차(작업 트리 줄끝)에서 더해진 것.

- **기록 파일의 작업 트리 줄끝은 규칙이 아니다 — 읽어서 감지한다** — 근거: `core.autocrlf=true`
  가 커밋 때 정규화해 **HEAD 는 전부 LF** 다(2026-08-28 확인: 세 INDEX·CLAUDE.md·`loop.py`
  모두 CRLF 0). 작업 트리 값은 그 파일을 **마지막으로 쓴 도구의 자국**일 뿐이라 git 에 안 보이고
  남에게도 안 간다. 스크립트는 `NL = "
" if "
" in s else "
"` 으로 감지하고,
  **진짜 위험한 상태인 «한 파일 안에 섞임» 만 검사한다**(`s.replace(NL, "").count("
") == 0`)
## 미결

- **`plan_log/` 쪽 형식은 손대지 않았다.** 이미 `.md` 이고 회차 누적 구조라 이번 규칙(표/펜스 판정)이
  그대로 적용되는지 안 봤다 — 정하려면: 다음 회차를 쓸 때 정렬 블록이 실제로 나오는지 본다
- **`task_log/INDEX.md` 한 줄 요약이 계속 길어진다.** 지금 항목당 3~5줄이라 "색인만 훑어도 보인다"는
  목적에서 멀어지는 중 — 정하려면: 항목이 10개를 넘길 때 다시 본다

## 안 하기로 한 것

- **확장자만 `git mv` 하고 본문은 그대로 두기** — 이유: 바이트는 완벽히 보존되지만 읽으라고 만든
  문서가 안 읽히게 된다. `1.`~`7.` 절 제목이 하나의 순서목록으로 뭉치고, 공백 정렬 블록이 한 줄로
  흐르고, `_hookutil` 같은 밑줄 식별자가 기울임이 된다. 그러면 `.md` 로 바꾼 값이 없다
- **문장까지 다듬는 전면 재작성** — 이유: 기록의 값어치는 그때 무엇을 알았고 무엇을 몰랐는지에 있다.
  지금 아는 것으로 문장을 고치면 과거 기록이 아니라 현재의 요약이 된다 / 다시 볼 조건: 없음
- **`.txt` 를 계속 쓰되 `.md` 만 새로 추가하기** — 이유: 같은 폴더에 두 형식이 섞이면 다음 세션이
  어느 쪽을 따라야 하는지 매번 판단해야 한다. 훅은 확장자를 안 보므로(`task_log_check.py` 는 경로
  접두사만, `is_recordable()` 은 `.py` 여부만) 섞여도 안 막힌다 — 즉 아무도 안 알려준다

- **세 `INDEX.md` 의 작업 트리 줄끝을 손으로 통일하기** — 이유: **통일할 것이 없다.** 저장소는
  이미 통일돼 있고(HEAD 전부 LF) 갈린 것은 각자 머신의 작업 트리뿐이다. 게다가 **안 남는다** —
  다음 `Path.write_text()` 한 번이나 checkout 한 번이면 다시 갈린다. 실제로 2026-08-28 하루에
  `task_log/INDEX.md`·`verify_log/INDEX.md` 가 LF 에서 CRLF 로 뒤집혔는데 그 커밋(`ee5b046`)의
  stat 은 `1 +` 였다 — **줄끝은 커밋된 적이 없다** / 다시 볼 조건: 없음
- **`.gitattributes` 로 `*.md text eol=lf` 를 못 박기** — 이유: 이것은 **지속되는** 유일한 손잡이지만
  (checkout 자체를 고정한다) 저장소 전체·모든 세션의 작업 트리를 바꾸는 변경이다. 지금 이 문제가
  내는 대가는 «스크립트가 줄끝을 상수로 가정하면 깨진다» 하나이고, 그건 감지 두 줄로 공짜로
  막힌다 — 값이 비용을 못 넘는다 / **다시 볼 조건: 감지를 넣고도 줄끝으로 또 깨질 때**

## 1회차 — 2026-08-17 · task_log 를 .md 로 옮긴다

**물은 것**

`plan_log` 와 `task_log` 에 저장된 기록 `.txt` 를 데이터 변질 없이 `.md` 로 바꿀 수 있나.
이후 내용도 `.md` 로 남기고 싶다.

**먼저 확인한 것**

- `plan_log/` 에는 `.txt` 가 하나도 없다. 실제 대상은 `task_log/*.txt` 7개뿐이었다
- **훅은 확장자를 안 본다.** `task_log_check.py` 의 PostToolUse 는 경로가 `task_log/` 로 시작하는지만
  보고, `is_recordable()` 은 `.py` 가 아니면 False, `auto_test_check.test_target_for()` 도 `.py` 가
  아니면 None. 즉 이름만 바꿔도 동작은 안 깨진다 — 위험은 훅이 아니라 **본문의 뜻이 렌더링에서
  깨지는 것**이었다
- 인코딩은 7개 전부 UTF-8 no-BOM, 줄끝은 `phase1.txt` 만 CRLF

**선택지**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| 확장자만 `git mv` | 바이트 완벽 보존 | 렌더링이 깨져 `.md` 로 바꾼 값이 없다 | 기존 기록은 공백으로 열을 맞춘 블록이 많다(대조표·시나리오 기대값·지표) |
| 최소 마크다운화 | 정렬을 지키면서 표·링크가 산다 | 규칙을 정하고 무손실을 따로 검증해야 한다 | 규칙을 4개로 좁히면 기계적으로 적용 가능하다 |
| 전면 재작성 | 제일 읽기 좋다 | 과거 기록이 현재 요약으로 바뀐다 | 이 저장소 기록의 값어치는 2절·4절(버린 안·되돌린 시도)에 있다 |

**고른 것과 이유**

최소 마크다운화. 규칙 4개(제목 `#` / 절 `##` / 공통 들여쓰기 제거 / 정렬 블록은 표 아니면 펜스)만
적용하고 문장은 안 건드린다. 사용자가 정렬 블록 처리를 **"진짜 마크다운 표"** 로 골라, 열 이름이
있는 블록은 `|` 표로 재구성하고 없는 블록만 펜스에 남기는 것으로 갈랐다.

기각한 둘은 위 "안 하기로 한 것" 에 그대로 남겼다.

**검증**

정규화 후 문자 스트림 대조(펜스·표 구분행·줄머리 마크업·구분자·공백 제거) — 7개 전부 일치.
의도한 추가는 splitter 기록의 "위 표 순서." 1곳뿐이고 스크립트가 그것을 이름으로 출력한다.

**남은 질문**

위 "미결" 두 줄.

## 2회차 — 2026-08-28 · 「세 INDEX 의 줄끝을 통일할까」 — 통일할 것이 없었다

**물은 것**

작업 중에 `task_log/INDEX.md`·`verify_log/INDEX.md` 가 LF 에서 CRLF 로 뒤집혀 편집 스크립트가
죽었다(`plan_log/INDEX.md` 만 LF 로 남았다). 사용자가 *"통일해야 하는지 알려줘"* 로 물었다.

**선택지**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| **아무것도 안 한다 (고름)** | 비용 0 | 작업 트리가 계속 갈려 보인다 | **HEAD 가 이미 전부 LF** 라 저장소에는 불일치가 0이다. 읽는 코드도 0건(훅의 `INDEX.md` 히트 둘은 안내 문구다) |
| 손으로 통일 | 지금 눈에 맞는다 | **안 남는다** | 다음 `write_text()`·checkout 이 다시 뒤집는다. 오늘 맞춘 것이 내일 갈린다 |
| `.gitattributes` 로 못 박기 | **지속된다** | 저장소 전체·모든 세션의 작업 트리를 바꾼다 | 대가가 «스크립트가 가정하면 깨진다» 하나뿐이라 감지 두 줄로 공짜로 막힌다 |

**고른 것과 이유**

아무것도 안 한다. **판정을 가른 것은 작업 트리가 아니라 HEAD 였다** — `git show HEAD:<path>` 로
찍어 보니 세 INDEX 도 CLAUDE.md 도 코드도 **CRLF 0 · 전부 LF** 다. `core.autocrlf=true` 가
커밋에서 정규화하기 때문이고, 그래서 작업 트리 값은 **그 파일을 마지막으로 쓴 도구의 자국**일
뿐 남에게 가지 않는다.

**증거 하나가 그것을 못 박는다** — 줄끝을 뒤집은 그 커밋(`ee5b046`)의 stat 이 두 파일 모두
`1 +` 다. 한 줄 추가이지 **줄끝 변경이 아니다.** 즉 뒤집힘은 커밋된 적이 없다.

**그래서 진짜 문제는 줄끝이 아니라 「가정」이었다.** 오늘 스크립트가 두 번 죽은 것은 파일이
갈려서가 아니라 줄끝을 상수로 박아서다 — 한 번은 CRLF 를 가정해 `StopIteration`, 한 번은
`assert NL == "
"` 이 죽었다. **두 번째는 내가 첫 번째를 겪고 넣은 가드였다**(그때의 관측을
규칙으로 승격했는데 몇 시간 만에 낡았다). 고칠 것은 파일이 아니라 그 습관이었다.

**한 가지는 실제로 위험하다** — **한 파일 안에 섞인 줄끝**이다. 그때는 감지도 틀리므로
스크립트로 만지면 안 된다. 지금 셋 다 안 섞였고, 검사 한 줄로 앞으로도 막는다.

**남은 질문**

감지를 넣고도 줄끝으로 또 깨지는 일이 생기는지. 생기면 그때 손잡이는 수동 통일이 아니라
`.gitattributes` 다 — 위 «안 하기로 한 것» 에 다시 볼 조건으로 적어 뒀다.
