# code-tracker 설계

상태: 구현됨 (1회차, 미커밋)
관련 기록: (구현 회고는 아직 없다)

## 확정된 것

지금까지 확정된 결정만 모은다. **여기만 읽으면 현재 설계를 안다.**

- **사람에게 설명하는 산출물을 만드는 스킬이다** — 근거: 저장소의 코드 관련 스킬 둘이
  이 축을 안 갖는다. `rag-code-review` 는 *위반을 지적*하고 독자가 저장소를 안다고 전제하며,
  `knowledge/` 는 *계약*을 담고 사람이 손으로 갱신한다. 「이 코드가 무슨 일을 하나」를
  저장소 밖 독자에게 답하는 자리가 비어 있었다
- **이 스킬의 핵심은 설명이 아니라 출처다** — 근거: 2026-09-03 세션 실측. 「코드만 읽고
  기능 목록」 요청에 낸 첫 목록에서 **여섯 항목이 코드가 아니라 `CLAUDE.md` 지식에서 왔고**,
  사용자가 짚어 코드로 확인하기 전까지 어느 문장이 관측이고 어느 문장이 전언인지 갈리지
  않았다(확인 결과 여섯 다 실재). 같은 세션에서 코드를 직접 훑으니 **문서에 없던 기능 15개**가
  더 나왔다. 그래서 모든 주장에 파일·심볼을 달고, 못 단 문장은 「추정」으로 표시한다
- **이름은 `code-tracker`** — 근거: 기존 스킬 8개가 전부 kebab-case. 사용자가 처음 말한
  `code_tracker` 는 snake_case 라 혼자만 다르다
- **범위는 경로/모듈 인자, 없으면 `git diff`** — 근거: diff 는 git 이 범위를 공짜로 주지만
  기존 코드는 누군가 범위를 줘야 한다. 2026-09-03 세션에서 그 「무엇을 설명할지 가르는 일」이
  실제로 작업의 절반이었다
- **한 파일에 두 층**(위=표준 용어 · 아래=내부 어휘 `<details>`) — 근거: 두 벌로 나누면
  같은 사실이 두 파일에 생겨 한쪽만 다시 돌렸을 때 어긋난다. 이 저장소가 salt·인용 검사·
  문서 목록에서 반복해 기각해 온 「두 번째 진실」과 같은 모양이다
- **`output/code-tracker/` 로 나가고 커밋하지 않는다** — 근거: `.gitignore` 의 `/preview.html`
  선례가 사유까지 적어 두었다 — *"템플릿을 고치면 곧바로 낡아 어느 시점의 화면인지 알 수 없게
  된다."* 코드 설명은 정확히 같은 모양이다. `output/` 은 이미 gitignore 라 새로 추가할 것이 없다
- **코드를 먼저 읽고 위키로 보태되, 어긋난 자리를 산출물 5절에 적는다** — 근거:
  `rag-code-review` 가 이미 쓰는 우선순위(실제 코드 > reference > 추측)와 같다. 위키를 먼저
  읽으면 그 문장이 코드를 읽은 결과처럼 산문에 섞인다
- **HTML 기본, `--md` 로 Markdown. 둘을 동시에 내지 않는다** — 근거: 「저장소 밖 독자」
  결정이 가른다. HTML 파일 하나를 보내면 바로 열리고 두 층 접기·다이어그램이 의존성 없이 돈다
- **다이어그램은 mermaid, 실선은 코드에서 확인한 호출만** — 근거: 다이어그램은 글보다 강하게
  각인되므로 틀리면 글보다 더 나쁘다. 확인 못 한 관계는 점선이거나 안 그린다
- **절 구성은 물음 순서**(무엇을 하나 → 어떻게 도나 → 왜 이렇게 됐나 → 조심할 것 →
  문서와 어긋난 자리) — 근거: 두 층 결정과 그대로 맞물린다. 밖 독자는 앞 둘에서 멈추고
  동료는 끝까지 읽는다
- **5절은 어긋난 게 없어도 "없음"을 적는다** — 근거: 절을 지우면 *대조를 안 했다* 와
  *대조했는데 어긋난 게 없다* 가 안 갈린다. `query_log` 의 「키를 늘 쓴다」와 같은 잣대다
- **줄번호를 안 쓴다** — 근거: `CLAUDE.md` 가 *"한 줄만 밀려도 조용히 거짓이 되고 아무도
  안 알려준다"* 로 이미 그은 선이다. 파일과 심볼로 가리킨다
- **상한을 넘기면 크기가 아니라 의미로 갈라 파일을 나눈다** — 근거: `knowledge/` 가
  20,000자를 넘을 때 폴더로 승격하는 것과 같은 잣대
- **머리말 수치도 세어서 쓴다**(2회차) — 근거: **두 회차 연속으로 틀렸다.** 1회차
  `retrieval` 이 「근거 21개」(실측 18) · 2회차 `backend/app` 이 「근거 24개」(실측 28)였고,
  **둘 다 본문 근거는 멀쩡한데 머리말만 틀렸다** — 규율이 문장에만 걸려 있고 수치에는 안
  걸려 있었다. 세는 JS 한 줄을 SKILL.md 에 박았고 `dangling`(목적지 없는 각주) 검사가 함께
  간다

## 미결

다음 논의의 시작점.

- **범위가 넓을 때 「의미로 가르는」 기준** — 정하려면: `rag_pipeline/` 전체처럼 실제로
  넘치는 범위를 한 번 돌려 본다. 1회차는 `rag_pipeline/retrieval/`(파일 12개)로만 돌려
  한 파일에 들어갔으므로 **이 규칙이 아직 한 번도 발화하지 않았다**
- **diff 모드의 절 구성** — 정하려면: 실제 PR 하나에 돌려 본다. 물음 순서의 3·4절(왜·조심할 것)이
  변경분에서는 재료가 얕을 수 있는데, 1회차는 경로 모드로만 검증했다
- **산출물이 얼마나 자주 낡는가** — 정하려면: 같은 범위를 코드 변경 뒤에 다시 돌려 무엇이
  달라지는지 본다. gitignore 라 낡음의 대가는 작지만, **다시 돌리는 비용을 아직 안 쟀다**
- **`--md` 의 두 층이 HTML 만큼 읽히나** — 정하려면: 사람이 둘을 나란히 읽어 본다.
  1회차는 `<details>` 로 냈고 GitHub 에서는 접히지만 **에디터에서는 통째로 펼쳐진다**
- **5절에서 「어긋남」과 「안 다룸」을 가를지**(2회차) — 정하려면: 「안 다룸」이 몇 번 더
  나오는지 본다. 2회차에서 처음 나와 표본이 1이라 규칙을 못 세우고, 지금은 「추정」 블록으로
  성질이 다르다는 것만 표시한다. **가르면 5절이 두 목록이 되어 「없음」을 두 번 적어야 하는데**
  그 대가가 값어치를 넘는지 아직 모른다

## 안 하기로 한 것

- **훅 연동**(Stop/PostToolUse 로 자동 실행) — 이유: 산출물이 gitignore 라 자동으로 돌 이유가
  약하고, 이 저장소가 *"차단 게이트를 셋으로 늘리면 `SKIP_*=1` 이 습관이 된다"* 를 반복해서
  근거로 쓴다(`문서-최신성.md` 1회차의 CLAUDE.md 전용 훅 기각과 같은 자리) /
  다시 볼 조건: 사람이 스킬 부르기를 자주 잊는 것이 관측되면
- **두 벌 분리**(`_외부.html` · `_내부.md`) — 이유: 같은 사실이 두 파일에 생긴다.
  한쪽만 다시 돌리면 어긋나는데 에러가 안 난다 / 다시 볼 조건: 한 파일 두 층이 실제로
  너무 길어져 밖 독자가 못 읽는 것이 관측되면
- **미리 정한 「흐름」 목록**(`적재 경로`·`질의 경로` 같은 고정 이름) — 이유: 산출물이
  안정적이지만 **새 모듈이 생기면 목록을 손으로 고쳐야 하고 안 고치면 조용히 빠진다.**
  `openwork` 의 `SECTIONLESS_BY_DESIGN`·`auto_test_check` 의 매핑이 같은 실패 모드를 갖는다
- **HTML/MD 동시 산출** — 이유: 위 「두 벌 분리」와 같은 모양이다
- **`.claude/wiki/` 아래에 산출물을 커밋** — 이유: 낡은 설명이 저장소에 사는 것이 이 저장소가
  제일 경계하는 상황이다. 덤으로 `knowledge/` 는 20,000자 상한과 `test_docs.py` 검사 대상이라
  생성물이 그 검사를 흔든다
- **줄번호 표기** — 이유: 위 「확정된 것」 참고
- **`rag-code-review` 에 모드로 얹기** — 이유: 한 스킬이 반대되는 두 계약(지적 vs 설명)을
  갖게 된다. `answer_question()` 과 `answer_question_with_retries()` 를 한 함수의 스위치로
  안 접은 것과 같은 잣대다

## 1회차 — 2026-09-04 · 사람 협업용 코드 리뷰를 문서로 뽑는 스킬

**물은 것**

사용자 요청: *"code_tracker 라는 스킬을 만들고 싶어. 기능 내용은 사람들이 협업할 때 하는
코드 리뷰(코딩 에이전트가 하는 코딩 리뷰가 아님)를 해주는 스킬이야. 코드 흐름, 설명을
html이나 md파일로 뽑아주는"*

`plan-interview` 로 4라운드를 돌았다. 라운드마다 사용자가 고른 것만 확정했다.

**선택지 — 라운드별**

| 라운드 | 갈림길 | 고른 것 | 버린 것과 이유 |
|---|---|---|---|
| 1 | 리뷰 대상 | (사용자가 되물음) 기존 코드도 포함 | — |
| 1 | 독자 | (사용자가 되물음) 동료 + 밖 사람 둘 다 | — |
| 2 | 범위 지정 | 경로/모듈 이름 | 미리 정한 흐름 목록(새 모듈이 조용히 빠짐) · 인자 없으면 전체 목차 |
| 2 | 두 독자 | 한 파일 두 층 | 두 벌 분리(두 번째 진실) · 실행 인자로 하나만(두 독자가 같은 문서를 못 가리킴) |
| 2 | 보관 | gitignore(`output/`) | 저장소 커밋(낡은 설명이 산다) · 골라서 손으로 커밋(옮긴 것은 여전히 낡음) |
| 3 | 읽는 범위 | 코드 우선 + 어긋나면 표시 | 오직 코드만(기각 근거를 못 실음) · 코드+문서 무차별(출처가 안 갈림) |
| 3 | 형식 | HTML 기본 + `--md` | MD 기본(밖 독자에게 렌더러가 필요) · 둘 다 항상(두 벌과 같은 모양) |
| 3 | 다이어그램 | mermaid, 확인한 것만 | 글과 표로만(갈래 많은 흐름을 못 따라감) · 요청할 때만(옵션은 안 쓰임) |
| 4 | 절 구성 | 물음 순서 | 코드 순서(「왜」가 흩어짐) · 리뷰 순서(기존 코드에는 「변경」 칸이 빔) |
| 4 | 근거 표기 | 문장마다 파일·심볼 | 절 단위 목록(문장이 관측인지 안 갈림) · 안 달기(이번 세션의 문제가 그대로) |
| 4 | 길이 | 의미로 갈라 나눔 | 한 파일 유지(조용히 얕아짐) · 상한 없음(모델이 끝까지 못 감) |

**고른 것과 이유**

핵심은 **「이 스킬의 값어치는 설명이 아니라 출처다」** 로 정리됐다. 설명은 그럴듯하게 쓰기
쉽고, 어려운 것은 읽는 사람이 어느 문장을 믿을 수 있는지 아는 것이다. 이 판단의 근거는
추측이 아니라 **바로 앞 세션에서 모델이 실제로 밟은 실패**다(위 「확정된 것」 2번).

그 결론이 나머지 축 여럿을 끌고 갔다 — 근거 표기(문장마다), 읽는 범위(코드 우선 + 어긋남
표시), 다이어그램(확인한 것만 실선), 「추정」 블록이 전부 같은 뿌리에서 나왔다.

**구현과 검증** (같은 날 이어서)

- 만든 것: `.claude/skills/code-tracker/SKILL.md`(150줄 — 기존 8개의 97~241줄 범위 안) ·
  `.claude/skills/code-tracker/template.html`
- `pytest tests/test_docs.py` 12 passed — 새 SKILL.md 의 인용 경로가 전부 실재
- `pytest` 전체 **1981 passed · 8 skipped · 7 deselected** (92.55초)
- 실사용 1회: `rag_pipeline/retrieval/`(파일 12개 + config + 위키 1개 = 14개 읽음, 근거 18개)
- 브라우저 실측: mermaid 렌더 O · 안쪽 층 기본 접힘 O · 근거 토글 O(CSS만, JS 없음) ·
  가로 스크롤 없음(1000px·375px 양쪽)
- 근거 표본 6개를 `grep` 으로 대조 — 전부 실재
- `--md` 경로는 **다른 작은 범위**(`tokenize.py`)로 확인했다. 같은 문서를 두 형식으로 내면
  위에서 기각한 「두 벌」이 된다
- `git status` 에 `output/` 이 안 나온다 — gitignore 정상

**계획과 어긋난 것**

없다. 다만 **첫 산출물에서 스킬 자신의 규칙을 어긴 자리가 하나 나왔다** — 머리말에 「근거
21개」라고 썼는데 DOM 실측은 18개였다. 세어 보지 않고 쓴 수이고, 이 스킬이 막으려는 바로 그
종류다. 브라우저 검증이 잡아 고쳤다. **산출물의 메타 수치도 관측이어야 한다**는 것이 이
회차에서 는 것이고, SKILL.md 에는 아직 그 문장이 없다.

**남은 질문**

위 「미결」 넷. 그중 앞의 둘(넓은 범위 · diff 모드)은 **1회차가 원리적으로 못 밟은 경로**라
다음 실사용에서 자동으로 걸린다.

## 2회차 — 2026-09-05 · 두 번째 실사용에서 같은 실수가 재현돼 규칙을 하나 더 박았다

**물은 것**

사용자가 `backend/app` 으로 스킬을 돌려 달라고 했다. 실사용 2회차이고, 1회차가 못 밟은
경로를 밟는지 보는 자리이기도 했다.

**관측**

- 읽은 파일 12개 · 근거 28개 · **위키와 어긋난 자리 2건**
- 근거 표본 9개를 `grep` 으로 대조 — 9/9 실재. 끊긴 각주 0
- 렌더 정상(mermaid · 두 층 접힘 · 가로 스크롤 없음)
- **1회차의 미결 둘은 이번에도 안 걸렸다** — `backend/app` 이 2,576줄인데 한 파일에
  들어갔고(「넓은 범위」 규칙 미발화), diff 모드는 경로 인자를 받아 안 밟았다

**5절이 잡은 것 — 1회차와 같은 모양 하나, 새 모양 하나**

| 건 | 무엇 | 1회차와 같은가 |

| ① | `backend.md` 1절이 *"`documents.py` 가 하는 일은 **넷뿐이다**"* 라는데 엔드포인트는 6개이고 **색인**이 그 열거에 없다 | **같다** — 1회차의 `retriever.md` 「주입과 갈래」도 셋을 열거하는데 실제는 다섯이었다 |

**고친 것**

`SKILL.md` 에 「머리말 수치도 주장이다 — 세지 않고 쓰지 않는다」를 더했다(176줄).

**왜 1회차에 안 넣었나.** 1회차에도 같은 실수를 했고 회고에 *"SKILL.md 에는 아직 그 문장이
없다"* 로 적어 뒀는데, 그때는 **표본이 하나라 우연과 못 갈랐다.** 두 번째가 나오면서
*"규율이 문장에만 걸려 있고 수치에는 안 걸려 있다"* 가 관측이 됐다 — 두 회차 다 **본문 근거는
멀쩡한데 머리말만 틀렸다**는 것이 그 근거다.

**규칙이 아니라 세는 방법을 박았다.** 「정확히 써라」는 1회차에도 지키려 했고 안 지켜졌다.
그래서 산출물을 열어 재는 JS 한 줄을 넣고, **`dangling`(목적지 없는 각주) 검사를 같이** 걸었다
— 수를 맞추는 것보다 그쪽이 먼저다. 「세기 전에는 머리말을 비워 둔다」도 함께 적었다.
