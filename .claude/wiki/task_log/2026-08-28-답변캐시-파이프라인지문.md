# 답변 캐시를 켤 수 있는 상태로 만든다 — 파이프라인 지문과 컬렉션 차원 검사

- 작업일: 2026-08-28
- 검증 방법: ruff · 전체 pytest · **실제 qdrant 엔진**으로 지문 왕복(임시 경로) ·
  실제 `.env` 로 지문 실측 · **서버 E2E**(`ANSWER_CACHE_MODE=exact`, 조건 두 개).
  **유료 질의 2건**(재작성·Cohere 리랭킹·생성 각 2회). `-m integration` 미실행

사용자가 *"유사 질문에 과거 답변이 나오는 설계 하지 않았었나"* 로 이 기능을 다시 꺼냈다.
있었다 — `plan_log/시맨틱-캐시.md` 6회차까지, 구현은 `rag_pipeline/answer_cache/`. 기억에서
어긋난 것은 이름 하나(`user_query` → `qa_cache`)뿐이었고, 그 기억이 걸린 자리는 따로 있었다:
질의 로그 `data/queries.jsonl` 의 `key` 가 `cache_point_id_for()` 로 만들어진다.

면담 두 라운드로 좁힌 것은 **켜기 전 미결부터 닫는다**였다. **캐시는 여전히 꺼둔다.**

  payload 에 `pipeline` 칸 · `lookup()`/`put()` 이 `fingerprint` 를 받는다 ·

- `rag_pipeline/answer_cache/__init__.py`

  `uses_bm25()` 를 빼내 공개했다. 지문의 첫 칸이 이 판정이라 두 벌이면 안 된다.
- `rag_pipeline/query.py`
  `answer_question()` 이 지문을 **한 번** 만들어 `lookup()`·`put()` 에 같은 값을 넘긴다.

## 2. 설계 결정

### payload 에 지문을 싣고 조회 때 대조한다 — 기동 시 `clear()` 를 버렸다

캐시가 낡는 축이 넷인데 셋만 막혀 있었다.

| 무엇이 바뀌면 낡나 | 무엇이 막나 |
|---|---|
| 임베딩 모델·차원 | 컬렉션 이름 (`collection_name_for(..., prefix=)`) |
| 문서 삭제·수정 | `_sources_still_valid()` |
| 새 문서 색인 | `clear()` |
| **검색·생성 설정** | **아무것도 안 막았다** |

히트하면 `retrieve()` 를 아예 안 부르는 것이 이 기능의 절약 전부인데, 그것은 곧
**리랭킹도 재작성도 건너뛴다**는 뜻이다. 지금 `.env` 는 둘 다 켜져 있다.

버린 안은 **기동 시 지문이 달라졌으면 `clear()`** 다. 지문을 어딘가 저장해야 하는데
qdrant 컬렉션에 메타 자리가 없어 sentinel point 같은 새 상태 축이 생긴다 — **1회차가
«색인 세대 번호» 를 기각한 바로 그 이유**를 되풀이하게 된다. 게다가 개발 중 잦은 재기동이
캐시를 계속 비워 기능이 사실상 안 돈다.

### 「출력을 가르는 것만」이라는 잣대를 「기본은 싣고 뺄 것만 명시」로 뒤집었다

잣대 자체는 그대로다(CLAUDE.md 의 salt 규칙). 뒤집은 것은 **적용 방향**이고, 근거는
**틀리는 방향의 비대칭**이다 — 빠뜨리면 **낡은 답을 조용히 서빙**하고, 넘치면 **미스가 한 번
더 날 뿐**이다. 그래서 손으로 고르는 대신 각 설정 객체를 `model_dump()` 로 통째로 훑는다.
설정 필드가 새로 생겨도 저절로 든다 — **손으로 세면 그때 빠뜨린다.**

빼는 것은 셋이고, **셋째는 지문을 실제로 찍어보고 나서야 나왔다**(4절).

### `rewrite_mode` 를 싣는다 — `rewrite.py` 의 salt 와 반대인데 잣대는 같다

`retrieval/rewrite.py` 의 캐시 salt 는 `rewrite_mode` 를 **안 싣는다.** 재작성 *호출* 은
`(질의, 1차 pool)` 만 보고 mode 는 그 **뒤에서** 갈리므로 그 호출의 출력을 안 가른다.
반면 이 지문이 가리는 것은 *검색 결과와 답 본문* 이고 `fuse`/`replace` 는 그것을 실제로
가른다. 실측으로도 그렇다 — CLAUDE.md 에 적힌 대로 `fuse` 가 LLM 60건에서 RRF 를 여덟 칸
이기는 반면 `replace` 는 `hit@1`·`hit@20` 에서 진다. **같은 잣대가 반대 답을 낸 자리라
«통일하자» 로 뭉개지기 쉬워** 양쪽에 테스트를 두고 서로를 가리키게 했다.

### 지문 불일치는 항목을 안 지운다 — `_sources_still_valid()` 와 대우를 갈랐다

근거 대조는 안 맞으면 `_drop()` 을 부른다. 지문은 안 부른다. **근거가 사라진 것은 확정
사망이지만 설정 변경은 되돌리면 다시 유효해지는 조건부 사망**이라, 같은 대우를 하면 손잡이를
왔다 갔다 할 때마다 캐시를 통째로 버린다. `exact` 갈래는 `put()` 이 같은 point id 를
덮어써 저절로 정리되고, `semantic` 에 남는 항목은 상한·퇴거(미결)의 몫이다.

실제 qdrant 로 확인했다 — 지문을 되돌리니 **같은 항목이 다시 히트**한다.

### 옛 형식에 마이그레이션을 안 만든다

`pipeline` 키가 없으면 `payload.get("pipeline")` 이 `None` 이라 어느 지문과도 다르다 —
**공짜로 미스가 된다.** `_sources_still_valid()` 의 *"짝이 안 맞으면 믿지 않는 쪽으로
떨어뜨린다"* 와 같은 대우이고, 운영 `.qdrant` 에 `qa_cache_*` 컬렉션이 **아예 없어**
실제 대상도 0건이다.

### BM25 판정을 `uses_bm25()` 한 벌로 모았다

지문의 첫 칸이 «BM25 갈래가 돌았나» 인데, 그 판정(`bm25 is not None and len(bm25) > 0`)이
`retrieve()` 와 `_branches_for()` 에 **이미 두 벌**이었다. 세 벌로 늘리는 대신 하나로 모았다 —
한쪽만 고쳐지면 **지문이 조용히 어긋나 낡은 답이 히트하는데 에러가 안 난다.**

### `use_bm25`·`reranker_on`·`rewriter_on` 을 설정에서 파생하지 않는다

셋의 진실은 설정이 아니라 **실제로 넘어온 객체**다. `rerank_model` 이 차 있어도 부르는 쪽이
객체를 안 넘기면 그 단계는 안 돈다 — `evaluation/run_eval.py` 가 실제로 그렇게 부른다.
설정만 보고 지문을 만들면 두 실행이 같은 지문을 달고 **서로의 답을 히트한다.**
그래서 `answer_question()` 이 지문을 만든다 — 거기가 유일하게 «설정 + 객체 + 유효 `top_k`»
셋을 다 아는 자리다.

### 차원 검사는 예외를 안 던진다

6회차가 정해 둔 모양 그대로다. `_ensure_collection()` 이 `bool` 을 돌려주고 `put()` 이 그
자리에서 접는다. `QdrantStore.ensure_collection()` 은 같은 자리에서 `IndexingError` 로 크게
우는데 **여기서는 못 던진다** — 캐시 때문에 질의가 죽으면 최적화가 신뢰성을 깎은 것이 된다.
안 보면 upsert 실패를 `except` 가 삼켜 *"저장하지 못했습니다"* 라는 **원인 없는 경고 하나**로
끝나고, 캐시가 조용히 아무것도 안 쌓는다.

## 4. 실패 분석

### 보장된 것을 재고 증거로 적었다 — `points=1`

서버 E2E 에서 `points` 가 조건 둘을 거치고도 1인 것을 보고 *「`_drop()` 을 안 부른다」의
근거가 실물이 됐다* 고 적었다. **틀렸다.** `put()` 은 `id=cache_point_id_for(answer.query)`
로 저장해 **id 가 질의 문자열 하나로만** 파생되고(지문은 payload 에만 있다) qdrant `upsert`
는 같은 id 면 덮어쓴다 — 같은 질문을 두 번 저장해서 **2가 될 경우의 수가 없었다.**
실패할 수 없는 관측이라 증거가 아니다.

**더 나쁜 것은 그것이 위험한 쪽에 침묵한다는 점이다.** `_drop()` 결정의 위험은 `exact` 가
아니라 `semantic` 에 있다 — 저쪽은 `lookup()` 이 **제일 가까운** point 를 찾아 남의 질의
point 를 물 수 있고, 그러면 `put()` 은 다른 id 에 써 **불일치 항목이 그대로 남는다.**
그런데 `semantic` 은 임계값이 없어 안 켜지므로 **이번 E2E 로는 원리적으로 못 쟀다.**

즉 보장된 쪽을 확인하고 불확실한 쪽에 침묵하는 수치를 증거처럼 적은 것이고, 이것은
이 저장소가 이미 두 번 적어 둔 그 모양이다 — *죽은 Evaluator 가 만점을 받는다* ·
*Cohere 한도 초과가 품질 저하로 읽힌다.* **셋 다 「무엇을 재고 있나」를 안 물은 것이다.**

**그 결정 자체는 실제로 검증됐다 — 다만 다른 자리가 했다.** `verify_log` 2절의 실제
qdrant 왕복(`FP_A` 저장 → `FP_B` 미스 → `FP_A` **다시 히트**)이 그것이고, 지웠으면
셋째 줄이 미스였다. **그래서 문장을 지우지 않고 격하만 했다** — 왜 증거처럼 보였는지가
남을 값어치다.

막은 방법: 없다. **자동으로 못 막는 종류다** — 코드가 아니라 *무엇을 재고 있나* 의 문제라,
테스트로 잠글 대상이 없다. 남길 수 있는 것은 이 문단과 CLAUDE.md 의 한 줄뿐이다.

### 「모든 필드를 싣는다」가 절대 경로를 payload 에 박았다 — 단위 테스트가 못 잡았다

「기본은 싣고 뺄 것만 명시」로 짜고 뺄 것을 둘(`*_api_key`·`generation_top_k`)로 잡았다.
테스트 69개가 전부 통과했다. **그런데 실제 `.env` 로 지문을 찍어보니 이런 것이 들어 있었다.**

```
rerank(rerank_cache_dir=C:\agentic-rag-proj\.cache\rerank,rerank_cache_enabled=True,...)
```

두 가지가 틀렸다. `*_cache_enabled` 는 리랭커·재작성기의 *호출 캐시* 설정이라 파이프라인이
무엇인지를 안 바꾼다(같은 점수를 디스크에서 읽어오느냐 다시 부르느냐일 뿐이다). 더 큰 것은
`*_cache_dir` 이 **절대 경로**라는 것이다 — 실으면 payload 에 머신의 파일 배치가 박히고
**같은 설정이 머신마다 다른 지문을 낸다.** 즉 «넘쳐도 미스 한 번» 이라는 이 모듈의 비대칭
논증이 **여기서만 성립하지 않는다. 늘 미스다.**

**단위 테스트로는 원리적으로 못 잡혔다** — 테스트는 `.env` 를 못 타게 설정을 꽂아 넣는데,
그게 바로 *`.env` 가 무엇을 흘려보내는지* 를 안 보게 만든다. 가른 것은 **실제 설정으로 한 번
찍어본 것** 하나다. 지문이 600자에서 443자가 됐다.

막은 방법: `_SKIP_SUFFIXES` 에 이름 규칙으로 넣고, 테스트 둘을 박았다 —
`test_fingerprint_ignores_call_cache_settings` 와 `test_fingerprint_carries_no_absolute_path`.
뒤엣것이 요점이다. **필드 이름이 아니라 «절대 경로가 값으로 새는가» 를 재므로**, 앞으로
경로를 담은 설정이 새로 생겨도 잡힌다.

### 차원 검사 한 줄이 기존 테스트 19개를 한꺼번에 깼다

`_ensure_collection()` 에 `client.get_collection()` 호출을 넣었더니 가짜 클라이언트에 그
메서드가 없어 `AttributeError` 가 났고, `put()` 의 `except` 가 그것을 삼켜 **전부 `False`**
가 됐다. 실패 메시지는 `assert False is True` 라 원인을 안 가리킨다.

되돌린 것은 아니고 — 가짜에 `get_collection()` 을 더하는 것이 맞는 답이었다. 다만 **새
호출이 계약에 는 것이 이렇게 드러난다**는 것이 남길 값어치다. 가짜의 모양은
`QdrantStore.ensure_collection()` 이 읽는 중첩 그대로(`config.params.vectors.size`) 만들었다 —
평평하게 만들면 실제 클라이언트가 바뀌었을 때 이 가짜가 그것을 안 알려준다.

### 치환 스크립트가 두 자리를 놓쳤다 — assert 가 잡았다

테스트 31곳에 `fingerprint=_FP` 를 넣는 정규식을 `(?=[,)])` 로 썼는데 **29곳만 걸렸다.**
줄바꿈이 뒤따르는 여러 줄 호출 둘이 빠진 것이다. 미리 센 값으로 `assert n == 31` 을 걸어둬서
**쓰기 전에** 죽었다 — 안 걸었으면 두 테스트가 조용히 옛 시그니처로 남았을 것이다.
(`preserve-line-endings` · `heredoc` 함정과 같은 계열이고, 여기서는 개수 단언이 답이었다.)

### heredoc 이 또 물었다

편집 스크립트를 `bash <<'PY'` 로 넣다가 `unexpected EOF while looking for matching`
로 죽었다. 파일로 써서 읽는 방식으로 바꿨다. 이 저장소의 파일이 **전부 CRLF** 라 `sed -i`
계열도 쓰기 어렵고, 결국 «스크래치패드에 파일로 쓰고 python 이 `newline=''` 로 읽어 붙인다»가
이 저장소에서 되는 방법이다. 각 스크립트가 **순수 LF 가 0인지 단언**하게 했다.
