# CPU 발열 손잡이를 셋으로 나눠 열었다 — 임베딩은 GPU 로, 나머지는 상한으로

- 작업일: 2026-08-26
- 검증 방법: 스레드 스윕 6점 · 실제 청크 414개 CPU↔GPU 대조 · E2E 평가 2회(캐시 갈라 재실행) ·
  ruff · pytest. **외부 API 호출 없음** — 전부 로컬 모델이라 vision 0 · llamaparse 0 · 임베딩 API 0

## 1. 무엇을 바꿨나

- `rag_pipeline/config.py`
  `RuntimeConfig` 신설(`torch_num_threads`)과 `ContentRoutingConfig.ocr_max_workers` 추가.
  그리고 `embedding_device` 주석의 *"아직 실측이 아니다"* 를 실측값으로 닫았다.
- `rag_pipeline/runtime.py` (새 파일)
  `apply_torch_threads()`. 값이 프로세스 전역이라 어느 설정 클래스에도 못 매달아 홀로 산다.
- `rag_pipeline/ingestion/embedding/local_st.py` · `rag_pipeline/retrieval/reranker/local_ce.py`
  **기존 모킹 이음새 둘**(`_make_model` · `_load_model`)의 모델 생성 직전에 상한을 먹인다.
  새 이음새를 안 만든 것이 요점이다 — 테스트가 이 둘을 통째로 갈아끼우므로 기본 pytest 는
  여전히 torch 를 안 올린다.
- `rag_pipeline/ingestion/loader/content/router.py`
  `_MAX_OCR_WORKERS` 상수를 걷어내고 `_ocr_workers(count, config)` 가 설정을 읽는다.
- `evaluation/config.py`
  `EVAL_EMBEDDINGS["kure-v1-gpu"]` 추가. **평가는 `.env` 를 안 보므로 이것 없이는 GPU 로 못 간다.**
- `.claude/hooks/auto_test_check.py` · `tests/hooks/test_auto_test_check.py`
  `rag_pipeline/runtime.py` 매핑 추가와 그것을 잠그는 검사(4절 참고).
- `.env.example` · `.env` · `CLAUDE.md`
  설정 셋을 밖으로 열고, 셋이 서로 안 겹친다는 것을 함정 절에 올렸다.

## 2. 설계 결정

### 스레드 설정을 **하나만** 만들었다 — `EMBEDDING_THREADS`/`RERANK_THREADS` 로 안 갈랐다

사용자가 *"임베더랑 리랭커가 쓰는 스레드 수"* 를 물었으므로 축이 둘인 것처럼 보였다.
**아니다.** 실측으로 `at::get_num_threads()` 8 · `omp_get_max_threads()` 8 이고 둘이
**같은 OpenMP 풀**을 쓴다. 갈라 두면 `EMBEDDING_THREADS=4` 와 `RERANK_THREADS=8` 을
동시에 만족시킬 수 없어 **나중에 부른 쪽이 이기고, 설정한 값과 다른 수로 도는 상태가
에러 없이 생긴다.** 이 저장소가 `extra="ignore"` 때문에 겪는 *"덮어썼다고 믿는 값이 실은
안 먹는"* 함정과 같은 모양이라, 이름이 거짓말을 하게 두지 않았다.

그래서 `RuntimeConfig` 라는 클래스를 하나 더 만들었다. `EmbeddingConfig` 에 얹는 쪽이
파일 하나 덜 만드는 길이었지만, 그러면 리랭커가 남의 설정을 읽어야 하고 **소유권이
거짓**이 된다.

### 기본값을 안 낮췄다 — 발열이 문제인데도

`torch_num_threads=None`(=안 건드림) · `ocr_max_workers=8`(=지금과 동일)이다.
발열을 호소한 사용자에게 기본값을 낮춰 주는 것이 친절해 보이지만, **`verify_log/` 의
모든 벽시계와 `regression/baseline.json` 이 8스레드에서 잰 값**이라 기본을 바꾸면 과거
수치가 **조용히 비교 불가**가 된다. `embedding_device` 가 `cuda if available` 자동 감지를
일부러 안 하는 것과 같은 잣대다. 대신 `.env` 에 사용자 머신용으로 `EMBEDDING_DEVICE=cuda`
를 넣어 실제 발열은 그쪽으로 해결했다.

### `set_num_interop_threads()` 를 안 부른다

이 함수는 **병렬 작업이 한 번이라도 시작된 뒤** 부르면 `RuntimeError` 인데 호출부가 그
시점을 알 방법이 없다. 그리고 발열을 만드는 것은 intra-op 다 — 실측으로 임베딩이
CPU-초 1,856.7 을 태우는데 포화 코어가 7.85 로 intra-op 8스레드와 정확히 맞는다.
그래서 `set_num_threads()` 하나만 부르고, **못 잡는 것이 무엇인지**를 docstring 에 적었다.
안 적으면 다음 사람이 "빠뜨렸다"고 읽고 넣는다.

### 캐시 salt 에 `embedding_device` 를 **안 넣는다** — 예약돼 있던 측정으로 정했다

`config.py` 가 *"차이가 float 오차 수준일 것으로 보기 때문인데 **아직 실측이 아니다**
(이 저장소에 CUDA 머신이 없었다). 처음 GPU 를 쓸 때 CPU 벡터와의 코사인 차이를 재기로
했다"* 로 절차까지 예약해 뒀다. 이번에 CUDA 머신이 생겨 쟀다 — 실제 청크 414개에서
**`1−cos` 최대 1.354e-09 · 성분 최대 절대차 5.728e-06** 이다.

그래서 안 넣는다. 넣었으면 `.cache/embedding` 이 전량 미스가 되고 `.qdrant` 컬렉션이
고아가 되는 대가만 치렀다. **컬렉션 이름도 모델에서 파생하므로 GPU 로 옮겨도 재색인이 없다.**

**`rerank_cache_salt_for()` 는 반대로 device 를 싣는데, 그 비대칭이 실수가 아니다** —
저쪽은 *순위가 같다*만 확인했고 *점수가 같다*는 안 봤다(`2026-08-26-리랭커-GPU축.md` 7절).
**같다는 것을 확인한 것과 다를 수 없다는 것은 다르다.**

### 평가 프로필을 갈아끼지 않고 **더했다**

`EVAL_EMBEDDINGS["kure-v1"]` 의 `cpu` 를 `cuda` 로 바꾸는 쪽이 한 글자였다. 안 했다 —
**이름이 곧 실험의 정체**라, 갈아끼면 이미 나온 수치가 어느 장치로 재졌는지를 파일이 못
말한다. `EVAL_RERANKERS` 가 `local` 옆에 `local-gpu` 를 더한 선례를 그대로 따랐고,
동시에 작업 중이던 세션도 같은 근거를 들었다.

`embedding_provider` 를 프로필에 **명시로 박았다.** 안 박으면 코드 기본값을 타는데,
그 기본값이 2026-08-25 에 뒤집히며 `baseline` 프로필이 조용히 *로컬
text-embedding-3-small*(그런 HF 리포는 없다)을 뜻하게 된 전례가 바로 앞 커밋(`99af232`)이다.

### OCR 워커를 **이제** 설정으로 열었다

`router.py` 의 옛 주석이 *"설정(.env)으로 열지 않았다. 이 저장소는 합법값이 실제로 갈리는
두 번째 경로가 생긴 뒤에 설정을 연다"* 로 못 박고 있었다. 그 경로가 생겼다 — **발열**이다.
Tesseract 는 `pytesseract` 가 띄우는 **별도 서브프로세스**라 torch 의 ATen 풀과 무관하고
GPU 로도 못 간다. 즉 `ingest()` 237.5초 중 213.9초를 차지하는 이 부하를 낮출 손잡이가
이것 하나뿐이다. 근거를 지우지 않고 **갱신**해 뒀다 — 왜 닫혀 있었고 무엇이 열었는지가
둘 다 남아야 다음 사람이 판단할 수 있다.

## 4. 실패 분석

### E2E 검증을 통과로 적을 뻔했다 — 아무것도 안 돌았는데

`--embedding kure-v1-gpu` 로 돌린 첫 실행(`g1-all-gpu`)이 지표 49개 전부 동일로 나와
*"GPU 로 옮겨도 결과가 같다"* 로 적기 직전이었다. `usage` 를 보고 갈렸다 —
**`calls: 0` · `reranked: 0` · `rerank_cache_hits: 60`**. 임베딩도 리랭킹도 실제로는 한
번도 안 돌았고 전부 캐시에서 나온 값이었다.

원인은 이 작업이 내린 결정 그 자체다. `cache_salt_for()` 에 device 가 없으므로 **GPU 실행이
CPU 가 만든 벡터를 그대로 읽는다.** 즉 *"GPU 가 같은 결과를 낸다"* 와 *"GPU 가 안 돌았다"* 가
**에러 없이 수치로만** 같아 보인다. 더 나쁜 것은 대조군으로 쓰려던 `e4`·`e5` 도 `calls: 0`
이었다는 것이다 — 이 코퍼스에서 임베딩이 실제로 다시 계산된 적이 최근에 없었다.

`EMBEDDING_CACHE_DIR`·`RERANK_CACHE_DIR` 를 스크래치패드로 돌려 다시 쟀고
(`g2-gpu-freshcache`, `calls: 60` · `reranked: 3000` · `cache_hits: 0`), 그때서야 전건
동일이 뜻을 갖게 됐다. **앞 회차가 리랭크 salt 를 두고 `cache_hits = 0` 을 실증으로 삼은
것과 같은 검사인데, 임베딩 쪽은 salt 에 device 가 없어 훨씬 잘 숨는다.**

### 합성 입력만 봤으면 "완전히 같다"로 적었다

코사인 차이를 먼저 합성 텍스트 200개로 쟀더니 `1−cos` 가 **정확히 0.000e+00** 이었다.
실제 청크 414개로 되재니 **1.354e-09** 로 0이 아니다. 결론(float32 오차 수준)은 같지만,
합성만 믿었으면 *"장치가 벡터를 안 바꾼다"* 라는 더 강한 문장을 적었을 것이다.
합성 텍스트는 한 문장을 반복해 만든 것이라 어휘 다양성이 없어 **자기 확인**이 됐다.

### `runtime.py` 가 자동 테스트 매핑에서 조용히 빠져 있었다

새 파일을 만들고 `tests/test_runtime.py` 까지 붙였는데, `auto_test_check.py` 의
`test_target_for("rag_pipeline/runtime.py")` 가 **`None`** 을 돌려줬다 — 그 파일을 고쳐도
자동 테스트가 안 돈다는 뜻이다. 그런데 `tests/hooks` 는 **전부 통과했다.** 커버리지 검사가
`rag_pipeline/ingestion/` 아래 **디렉터리만** 훑기 때문이다. 즉 CLAUDE.md 가 경고하는
*"그 단계만 자동 테스트가 안 도는데 아무 에러도 안 난다"* 가 최상위 모듈에서는 **검사
자체를 우회한다.** 매핑을 넣고, `test_source_maps_to_area` 에 `query.py`·`runtime.py` 두
줄을 못 박아 다음 최상위 모듈이 같은 길로 안 가게 했다.

### 발열을 못 잰다고 결론 내렸는데, 사용자가 로그를 갖고 있었다

WMI 온도가 권한 거부이고 HWiNFO 공유메모리가 꺼져 있어 **"CPU 온도는 못 잰다, 포화 코어를
대리지표로 쓴다"** 로 닫았다. 사용자가 스윕 중 받아 둔 CSV 를 내놓자 그대로 채워졌다 —
게다가 포화 코어보다 **더 나은 답**이 나왔다(전력·온도·`J/청크`). **못 잰다고 적기 전에
사용자에게 물었어야 했다.** 특히 HWiNFO64 가 **떠 있는 것을 이미 확인해 놓고도** 로깅이
꺼져 있다는 이유로 사용자를 건너뛰었다.

그리고 채우면서 결론 하나가 **뒤집혔다.** 초판은 스레드 축을 *"발열 대비 성능의 무릎은 2"* 로
적었는데, 전력을 보니 **스레드를 줄이는 것 자체가 총 발열을 늘린다**(`J/청크` 2.2배).
포화 코어는 *순간* 부하만 재고 **시간을 곱하지 않아서** 그 역전을 못 본다.

### `nvidia-smi -pl` 을 소음 대책으로 권고했는데 이 GPU 가 지원하지 않는다

`nvidia-smi -q -d POWER` 가 `Current 74.14W / Default 50.00W / Min 5 / Max 85` 를 보여주길래
*"기본보다 24W 올라가 있으니 `-pl 50` 으로 낮추면 된다"* 로 적었다. 사용자가 실행을
요청해서 돌려 보니 일반 권한에서 **`Insufficient Permissions`** 가 났고, 거기서 *"권한만
있으면 된다"* 로 한 번 더 잘못 짚었다. 승격해서 다시 돌리니 진짜 사유가 나왔다 —
**`Changing power management limit is not supported for GPU`.** 노트북 GPU 라 전력 예산을
Dynamic Boost·펌웨어가 쥐고 있다.

**권한 오류가 미지원을 가린 것이 핵심이다.** `-pl` 이 값의 범위를 보여준다고 해서 쓸 수
있는 것이 아니었고, `Min/Max Power Limit` 은 **하드웨어 능력이지 조정 가능 여부가 아니다.**
같은 축에서 `-pm`(지속 모드)도 WDDM 에서 미지원이다.

되는 것은 **클럭 상한 `-lgc`** 였고, 축이 전력이 아니라 클럭이라 *"몇 MHz 가 50W 인가"* 를
새로 재야 했다. 네 점(무제한/1800/1500/1200)을 재서 **1500** 으로 정했다 —
최대 42.2W 로 목표 50W 아래이고, 온도가 거기서 바닥을 치며(1200 으로 더 내려도 안 내려간다),
`J/청크` 효율 무릎도 같은 자리다.

**여기서 CPU 축과 부호가 반대인 사실이 하나 나왔다** — GPU 는 클럭을 낮추면 `J/청크` 가
5.74→4.11 로 **총 에너지도 준다.** 전압이 같이 내려가고 사용률이 96~99% 로 유지돼 노는
구간이 없기 때문이고, CPU 스레드 축은 코어를 놀리면서도 패키지 전력을 계속 물어 반대였다.
**"낮춘다"가 두 축에서 다른 뜻이다.**

### 지표별로 상위 표본을 따로 뽑아 "동시에 얼마였나"를 틀릴 뻔했다

CSV 를 처음 집계할 때 CPU 전력·CPU 온도·GPU 전력의 상위 30표본을 **각각** 뽑아 한 줄에
적었다. 세 값이 **다른 순간**의 것이라 *"cuda 는 CPU 10.7W 이면서 GPU 74.8W"* 같은 문장이
성립하지 않는다. 지점마다 **합 전력이 최대인 연속 60초** 창을 하나 고르고 모든 지표를 그
창에서 읽도록 고쳤다. 값이 실제로 움직였다 — cuda 의 CPU 부하값이 22.6W → 10.7W 였다.

### 파일을 LF 로 바꿔 놓을 뻔했다

첫 `config.py` 편집을 파이썬으로 하면서 `newline="\n"` 으로 써서 CRLF 파일을 통째로 LF 로
바꿨다. `git diff --stat` 이 29줄 추가로만 보여 못 알아챌 뻔했는데(`core.autocrlf=true` 가
정규화한다), **working tree 는 파일마다 줄끝이 다르다** — `config.py` 는 LF, `router.py` 는
CRLF 다. 이후 편집은 전부 **기존 줄끝을 읽어 보존**하도록 바꿨다. 동시에 세션이 일곱 개
도는 저장소에서 전 줄이 바뀐 diff 는 남의 작업을 덮기 쉽다.

## 7. 남은 것

- **소음 자체는 여전히 못 답했다.** 사용자가 준 HWiNFO 로그에 **팬 RPM 컬럼이 없다**
  (339개 중 0 — 노트북 EC 를 못 읽는 것으로 보인다). 전력·온도까지가 한계라
  *"cuda 가 CPU 를 식히는 대신 GPU 팬을 돌리는데 그게 더 시끄러운가"* 는 **사용자 귀가
  답할 문제**로 남는다.
- **GPU 클럭 상한 1500 을 걸어 뒀는데 재부팅하면 풀린다.** `-pm`(지속 모드)이 WDDM 에서
  미지원이라 드라이버 수준으로 못 굳히고, **저장소 설정으로도 못 만든다** — 앱이 GPU 클럭을
  바꾸려면 관리자 권한이 필요하고 적재 파이프라인이 하드웨어 상태를 건드리는 것은 경계
  위반이다. `.env` 에 넣으면 아무도 안 읽는 죽은 설정이 된다. 남는 방법은 **작업
  스케줄러**(부팅 시 관리자로 `nvidia-smi -lgc 210,1500`) 하나이고 **아직 안 만들었다** —
  GPU 를 쓰는 **모든** 작업이 느려지는 설정이라 사용자 결정이 필요하다.
- **클럭 상한이 리랭킹·생성에 미치는 영향을 안 쟀다.** 임베딩 부하로만 네 점을 냈다.
- **소음을 dB 로는 못 쟀다.** 팬 RPM 컬럼이 로그에 없다.
- **6스레드가 8스레드보다 뜨겁고 느린 이유를 안 갈랐다**(93.0 vs 89.3°C · 0.77 vs 0.81
  청크/초). 표본 1회다.
- **VRAM 여유가 얇다.** 두 모델 상주 4.23GB 인데 E2E 중 `nvidia-smi` 가 **7,819 / 8,151 MiB**
  까지 갔다. `embedding_batch_size` 를 키우거나 `rerank_candidates` 를 늘리면 OOM 가능성이
  있고, 그때 CPU 로 내리는 경로가 `TORCH_NUM_THREADS` 다. **OOM 시 자동 폴백은 없다.**
- **`EVAL_SETTINGS` 가 `torch_num_threads` 를 안 박았다.** 스레드 수가 BLAS 리덕션 순서를
  바꿔 벡터를 미세하게 흔들 수 있는데 **안 쟀다.** CPU↔GPU 차이(1.354e-09)보다 작을 것으로
  보이지만 실측이 아니다. 재고 나서 박을지 정한다.
- **`OCR_MAX_WORKERS` 값별 발열을 안 쟀다.** 벽시계는 `2026-08-24-ocr-병렬화.md` 에 있으나
  그 회차는 CPU-초를 안 쟀다.
- **사용자 머신의 `.env` 만 `EMBEDDING_DEVICE=cuda` 다.** `.env.example` 기본은 `cpu` 로
  뒀다 — GPU 없는 머신에서 받아 쓰면 그 줄이 곧 실패이기 때문이다.
- **커밋하지 않았다.** 사용자가 시킬 때 한다. 동시에 세션이 여럿이라 **임시 인덱스로 내
  파일만 스테이징**해야 한다.
