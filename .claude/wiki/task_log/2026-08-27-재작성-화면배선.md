# 재작성을 화면에 이었다 — `.env` 두 줄이 죽은 줄에서 살아났다

- 작업일: 2026-08-27
- 검증 방법: ruff · 전체 pytest · 실제 `.env` 로 설정 사슬 확인 · 실사용 질의 1회.
  **외부 API 재작성 호출 0회**(`.cache/rewrite` 78 → 78). 실사용 질의가 생성·리랭킹은
  태웠지만 재작성은 안 돌았고, 그 이유가 이 기록의 4절이다

## 1. 무엇을 바꿨나

- `rag_pipeline/query.py`
  `answer_question()` 이 `rewriter` 를 받아 `retrieve()` 에 **넘겨주기만 한다**.
- `backend/app/api/routes/query.py`
  질의마다 `get_rewriter(config.rewrite)` 를 불러 넘긴다. Evaluator 와 같은 자리.
- `tests/api/test_query_route.py`
  `_client()` 픽스처에 `_rewrite` 핀 + 배선 테스트 3개.
- `tests/test_query.py`
  넘겨주기·스위치·원 질의 보존·캐시 히트 테스트 4개.
- `.env` · `CLAUDE.md` · `.claude/skills/rag-code-review/references/next-stages.md`
  배선으로 **거짓이 된 문장들**을 고쳤다 (5절).

## 2. 설계 결정

### 재작성기는 **질의마다** 만든다 — 「축이 하나 더 있다」던 것이 착시였다

24회차가 B-0 을 열며 *"정할 것은 싱글턴인가 질의마다인가 하나이고, Evaluator 와 달리
재작성기에는 **캐시 객체가 딸려 있어 축이 하나 더 있다**"* 라고 적었다. 그것을 실제로 열어
보니 **축이 아니었다.**

`ResultCache.__init__` 은 **경로 하나와 불리언 하나를 대입할 뿐**이다 — 디렉터리도 안 만들고
파일도 안 읽는다. 상태를 안 들고 매 호출에 디스크를 보므로, **질의마다 만든 인스턴스가 같은
캐시 파일을 읽는다.** 싱글턴이어야 쌀 이유가 없다.

그래서 Evaluator 의 근거가 그대로 적용된다 — 올릴 가중치가 없고(클라이언트는 `_call_api`
안에서 만든다), 싱글턴으로 두면 `warnings`·`usage` 가 **인스턴스에 누적**돼 서버 수명 내내
쌓인다. 기각: 싱글턴(`app.state.rewriter` + `_rewrite_ready` 표시).

**미결을 열 때 「축이 있다」고 적어 둔 것이 값을 했다** — 열어 보고 없앨 수 있었다.
없었으면 모양만 보고 리랭커 쪽(싱글턴)을 따라갔을 자리다.

### `answer_question()` 은 **넘겨주기만** 한다 — 여기서 다시 쓰면 평가가 못 잰다

배선을 넣을 때 제일 자연스러운 유혹은 `answer_question()` 안에서 질의를 다시 써서
`retrieve()` 에 넘기는 것이다. 그러면 `retrieve()` 를 안 건드려도 되고 코드가 짧다.

**그러면 `evaluation/run_eval.py` 가 `retrieve()` 를 직접 부르므로 평가가 그 경로를 안 밟아
재작성을 영원히 못 잰다**(7회차 기각 항목). 7회차가 코드도 없던 시절에 못 박아 둔 제약이고,
배선하는 회차가 정확히 그것을 밟을 뻔한 자리다.

그래서 **`retrieve()` 에 가는 질의가 원 질의 그대로임을 계약으로 박았다**
(`test_query_reaches_retrieve_unchanged`). 기각: `answer_question()` 안에서 재작성.

### 라우트에서 `run_in_threadpool` 로 안 감싼다

`reranker`·`bm25`·`embedder` 는 감싼다 — 적재가 초 단위라 이벤트 루프에서 하면 서버 전체가
멈춘다. 재작성기는 **만드는 데 적재가 없어 감쌀 것이 없다.** Evaluator 와 같다.
(실제 LLM 호출은 `answer_question` 안에서 일어나고 그 전체가 이미 threadpool 이다.)

## 4. 실패 분석

### 실사용 질의에서 재작성이 안 돌았고, 하마터면 배선을 의심할 뻔했다

배선을 끝내고 실제 질의를 하나 보냈다. 200 · 9,369자 · 6.5초로 **정상 응답**이 왔고 질문
왕복 문구도 맞았다. 그런데 **`.cache/rewrite` 가 78 → 78 로 안 늘었다.**

그 신호만 읽으면 결론은 *"배선이 틀렸다"* 다. 실제 원인은 달랐다.

```
uvicorn 프로세스 CreationDate : 2026-08-27 13:42:59   (--reload 켜짐)
rag_pipeline/query.py         : 20:54:00
backend/.../routes/query.py   : 20:55:29
.env                          : 20:40:11
확인 시각                      : 21:03:30
```

**`--reload` 가 켜져 있는데 프로세스가 한 번도 재시작되지 않았다.** 그 응답은 배선 이전
코드가 낸 것이고, 24회차의 `.env` 두 줄도 그 프로세스에서는 애초에 안 읽혔다.

**가른 것은 프로세스 생성 시각과 파일 수정 시각의 대조 하나다.** 이것은 CLAUDE.md 가
워밍업에서 이미 값을 치른 자리와 같은 종류다 — *"VRAM 숫자만 보고 두 번 잘못 짚었다"*.
**신호 하나가 기대와 다를 때 먼저 의심할 것은 코드가 아니라 그 신호가 무엇을 재는가다.**

되돌린 것은 없다. 대신 검증 절차를 고쳤다 — `verify_log` 6절이 **실사용 확인 전에 프로세스
생성 시각부터 본다**를 명령으로 적어 뒀다.

**미해결**: `--reload` 가 왜 안 물었는지는 안 봤다. 재현 조건을 안 잡았고, 이 작업의 범위도
아니다. 7절에 남긴다.

### `.env` 핀을 배선보다 먼저 넣었다 — 이번엔 안 밟았다

라우트가 질의마다 `get_rewriter()` 를 부르므로, `tests/api` 의 `_client()` 픽스처가
`_rewrite` 를 안 박으면 **개발자 `.env` 의 `REWRITE_MODEL` 이 픽스처에 실린다.**
그리고 이 저장소는 24회차에 그 줄을 **실제로 채웠다** — 즉 이번에는 함정이 무장돼 있었다.

`_evaluator` 핀이 있는 것을 보고 **라우트를 고치기 전에** 핀을 먼저 넣었다.
CLAUDE.md 가 적어 둔 *"켜진 채 태어나는 부수 효과는 「이따 픽스처 넣지」가 성립할 시간이
없다"* 그대로이고, 이번에는 순서 덕에 안 샜다.

## 7. 남은 것

- **서버 재시작이 필요하다.** 지금 떠 있는 프로세스(13:42 기동)는 배선도 `.env` 도 안 물었다.
  재시작 뒤 질의 하나에 `.cache/rewrite` 가 1 늘면 끝난다
- **재작성을 켠 화면의 지연을 안 쟀다.** 질의당 LLM 1회가 는다. 위 6.5초는 **재작성이 빠진
  값이라 기준선으로 쓰면 안 된다**
- **`--reload` 가 왜 안 물었나** — 재현 조건을 안 잡았다
- **`query_log` 에 재작성 흔적이 없다** — 판정이 `verdict` 칸을 얻은 것과 달리, 재작성은
  돌았는지조차 로그에 안 남는다. 운영에서 *모델이 뭐라고 다시 썼나* 를 되짚을 길이
  `.cache/rewrite` 파일뿐이다. 필요해지면 그때 축을 연다(지금은 근거가 없다)
- **화면에 배지가 없다** — `cached_from`·`verdict` 는 배지가 있는데 재작성은 없다.
  일부러 안 했다: 사용자가 *무엇을 물었나* 와 *무엇으로 검색했나* 가 갈리는 것을 보여줄지는
  결정이 필요하고, 그 결정의 근거가 아직 없다
- **재작성 + 리랭커 조합의 품질** — 23회차가 연 축 그대로. 배선과 무관하게 미측정이다
