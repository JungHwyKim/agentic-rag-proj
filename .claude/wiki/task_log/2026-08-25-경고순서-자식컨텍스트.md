## 2. 설계 결정

### 요소에 쓴 해법을 경고에 그대로 옮겼다 — 순서를 자리에 싣는다

어제 병렬화하면서 요소 순서는 지켰는데 `ctx.warnings` 순서는 완료 순서가 됐다. **둘이 갈린
이유가 이번 설계의 전부다** — 요소는 `order` 를 들고 다녀 정렬로 문서 순서를 복원할 수
있지만, **경고는 문자열이라 자기 자리를 모른다.** 공유 목록에 append 하는 순간 순서 정보가
완료 시각에 실리고, 그 뒤로는 복원할 근거 자체가 없다.

그래서 워커가 **자식 `LoadContext`** 에 쓰고, 문서 순서로 도는 조립 루프가 `absorb()` 로
합친다. 요소가 index 별 칸에 담겼다 문서 순서로 조립되는 것과 같은 모양이다.

**버린 안 — 끝에서 정렬한다(알파벳순 등).** 결정론적이긴 한데 뜻이 달라진다.
`regression/baseline.json` 의 `warnings 대조 규칙` 이 *"정확한 리스트 비교(순서 포함).
정규화하지 않는다"* 로 못 박아 둔 이유가 **경고가 쪽 번호를 담기 때문**이다 —
*"쪽 번호를 지우는 정규화를 넣으면 쪽 계산이 밀린 회귀가 조용히 통과한다."* 순서를 내용으로
정하면 같은 종류의 신호를 버린다.

**버린 안 — `contextvars`/스레드 로컬로 자리를 심는다.** `warn()` 이 "나는 지금 몇 번 리전에
있나"를 읽게 하는 방식이다. 되긴 하는데 **순서 정보가 호출 스택에 숨는다** — 자식 방식은
`ImageOutcome` 에 자식이 눈에 보이게 실려서, 조립 루프를 읽으면 순서가 어디서 정해지는지가
바로 보인다.

### 경고 순서만으로는 이 작업을 정당화 못 한다 — 가드가 진짜 이유다

소비자를 전부 확인했는데 **오늘 순서 때문에 깨지는 것이 하나도 없었다.**
`regression/measure.py` 는 `loader.detect_regions()` 만 부르고 `route_all()` 을 안 타고,
`evaluation/run_eval.py` 는 표시에 `len()` 만 쓰고, 테스트 46곳은 전부 `any(... in w)` 나
개수다. 그래서 이 작업의 값어치는 `absorb()` 의 가드 쪽에 있다.

`absorb()` 가 자식의 `vision_calls` · `llamaparse_calls` · `mark_symbols` 가 비었는지
검사하고 아니면 던진다. **어제까지 "유료 핸들러를 병렬 구간에 넣으면 안 된다"는 경계가
주석과 테스트에만 있었다** — 되돌리는 사람이 안 읽으면 상한이 새고 과금이 늘어나는데
**키 없는 기본 pytest 는 그걸 못 잡는다.** 이제 실행 시점 검사가 됐다.

**`RagPipelineError` 를 안 쓴 것도 결정이다.** `backend/app/main.py` 의
`_STATUS_BY_EXCEPTION` 은 `list[tuple[type[RagPipelineError], int]]` 이고 그 표의 예외는
전부 사용자에게 보일 한국어 `user_message` 를 가진 **런타임 조건**이다. 이건 코드를 잘못
고쳐야 도달하는 자리라 성질이 다르다. 평범한 `RuntimeError` 로 던지고 매핑표에 넣지 않았다.

선례가 있다 — embedding 이 `len(out) == len(in)` 을 못 지키면 **예외를 던지기로** 하며
`contracts.md` 2절을 일부러 안 따랐다. 이유가 같다: **조용히 틀리는 것보다 시끄럽게 죽는
편이 낫다.**

### 테스트를 먼저 쓰고 깨지는 것을 확인했다

`test_warning_order_follows_document_order` 를 먼저 넣고 돌리니
`At index 0 diff: '경고 07' != '경고 00'` 으로 깨졌다. **완료 순서로 쌓인다는 직접 증거**다.
같이 넣은 교차 테스트는 `['이미지 2', '이미지 0', '텍스트 1', '텍스트 3']` 을 냈다 —
병렬 경고가 직렬 경고보다 **통째로 앞에 몰린다**는 것까지 드러났고, 이건 예상 못 했던 축이다.

이 순서를 지킨 덕에 알게 된 것이 하나 더 있다. 어제 쓴
`test_parallel_matches_serial` 의 `parallel_ctx.warnings == serial_ctx.warnings` 는
**두 빈 리스트를 비교하고 있어서 아무것도 안 지켰다.**

## 4. 실패 분석

### 어제 쓴 테스트가 빈 리스트끼리 비교하고 있었다

`test_parallel_matches_serial` 에 `assert parallel_ctx.warnings == serial_ctx.warnings` 를
넣어 두고 "경고까지 동일한지 본다"고 생각했는데, 그 테스트의 가짜 OCR 은 경고를 안 낸다.
**빈 리스트 == 빈 리스트를 검사하고 있었다.** 통과하는데 아무것도 보장하지 않는다.

이 저장소가 splitter 때 겪은 것과 같은 종류다 —
`test_split_table_pieces_keep_header` 초판이 `rows[0] == chunk.metadata["rows"][0]` 으로
자기 자신을 비교했다. **비교하는 두 값이 실제로 무엇인지 한 번은 눈으로 봐야 한다.**

이번에는 "고치기 전에 돌려서 깨지는지 본다"가 그것을 잡아줬다. 새 테스트를 옛 코드에 먼저
돌리지 않았다면 같은 실수를 한 번 더 했을 것이다.

### 어제 문서 셋에 적은 것이 오늘 거짓이 됐다

어제 `CLAUDE.md` · `references/loader.md` 에 **"경고 순서는 더 이상 결정론적이지 않다"** 를
근거와 함께 적었다. 그때는 참이었고 잘 적은 것이지만, 하루 만에 뒤집혔다.

되돌리면서 문장을 지우지 않고 **"2026-08-24 에 좁아졌다가 2026-08-25 에 되돌아왔다"** 로
경위를 남겼다. 지웠으면 다음 사람이 "왜 자식 컨텍스트 같은 걸 만들었나"를 알 수 없다.

**남은 위험**: 하루짜리 사실을 문서에 적는 비용이 이번엔 컸다. 다만 어제 시점에서 그것은
정확한 기록이었고, 안 적었으면 오늘 이 질문 자체가 안 나왔다. 규칙을 바꿀 일은 아니라고 본다.

### 실파일이 이 변경을 검증하지 못한다는 것을 늦게 알았다

47쪽 스캔 PDF 로 확인하려 했는데, 그 문서의 경고 47개는 전부 `pdf.py` 의
`detect_regions()` 가 내는 것이라 **직렬 구간 소산이다.** 병렬화 전에도 후에도 순서가 안
흔들린다. 즉 "쪽 번호 오름차순 True" 는 이번 변경과 무관하게 원래 참이었다.

**실파일이 우연히 안 갖고 있는 입력**이라 가상이 만들어야 하는 자리였다. 검증 기록의
가상/실제 구분이 정확히 이것을 위한 것이었는데, 실파일을 먼저 돌려보고 나서야 알았다.
