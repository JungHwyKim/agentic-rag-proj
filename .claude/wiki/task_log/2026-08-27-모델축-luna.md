# 판정 모델을 축으로 열고, luna 안에서 v1·v3 를 재서 프롬프트 이득이 모델을 안 탄다는 것을 확인한다

- 작업일: 2026-08-27
- 검증 방법: `ruff` · 전체 `pytest`(1219 passed) · 사람 세트 43건 혼동행렬 4장.
  **외부 API 과금 있음 — `gpt-5.6-luna` 172호출**(1건 탐침 1 + v3 85 + v1 86), 사용자 승인.
  대조군(mini) 재확인과 표 재생성은 **0호출**(캐시 적중)

## 1. 무엇을 바꿨나

- `rag_pipeline/config.py`
  `evaluator_temperature` 를 `float | None` 으로. **`None` 이 "그 인자를 안 보낸다"** 는 뜻이고,
  gpt-5 계열이 `temperature=0.0` 을 400 으로 거부하기 때문이다. 기본값은 `0.0` 그대로다
- `rag_pipeline/generation/evaluate.py`
  `max_tokens=` → `max_completion_tokens=` (분기 없음), `temperature` 는 `None` 이 아닐 때만 싣는다
- `evaluation/config.py`
  `EVAL_EVALUATORS`(`mini`·`luna`) + `evaluator_profile()` + `eval_config(evaluator=...)`.
  `EVAL_SETTINGS["evaluator"]` 는 기본 프로필을 **가리키기만** 한다
- `evaluation/verdicts.py`
  `--evaluator` 인자. `meta` 에 `evaluator_profile`·`prompt_version`, 출력 파일 이름에 그 둘
- `tests/evaluation/test_eval_config.py` · `tests/generation/test_evaluate.py`
  프로필 축 가드 7건과 호출 인자 계약 4건
- `.env.example` · `CLAUDE.md`
  파라미터 제약과 "빈 값이 아니라 주석 처리" 를 적는다

## 2. 설계 결정

### `temperature` 를 안 보내는 것을 `None` 으로 표현한다 — `1.0` 을 보내지 않는다

luna 는 기본값(1)만 받으므로 `temperature=1.0` 을 보내도 결과는 같다. 그런데 그렇게 하면
**`0.0` 이 재현을 위해 고른 값이었다는 사실이 코드에서 지워진다** — 필드가 `float` 인 채로
남아, 나중에 읽는 사람은 두 모델이 같은 조건에서 재진 것으로 본다. `None` 은 *그 축을 포기했다* 는
것을 타입으로 말한다. 버린 안: `evaluator_temperature=1.0` 을 luna 프로필에 박기.

### 토큰 상한은 모델별로 안 가른다 — 탐침 1호출이 그 분기를 없앴다

`gpt-4.1-mini` 도 `max_completion_tokens` 를 받는다(2026-08-27 탐침). 그래서 `_call_api()` 에
모델 이름을 보는 `if` 가 하나도 없다. 갈랐다면 새 모델을 더할 때마다 그 표를 손봐야 하고,
빠뜨리면 **에러가 아니라 전건 `failed`** 로 나타난다.

### 프로필을 갈아끼지 않고 더한다 — `mini` 를 남긴다

지금까지의 판정 수치(v1 28/31 · v2 28/32 · v3 30/32)가 전부 `gpt-4.1-mini` · temperature 0
으로 나왔다. `EVAL_SETTINGS["evaluator"]` 를 luna 로 갈아끼웠으면 그 세 표가 **어느 모델로
재졌는지를 저장소 파일이 못 말하게** 된다. `local` 옆에 `local-gpu` 를, `kure-v1` 옆에
`kure-v1-gpu` 를 더한 것과 같은 판단이다.

### 프로필 dict 의 기본값이 **꺼짐이 아니다** — 리랭커와 반대다

`EVAL_RERANKERS` 는 기본이 `off` 인데 여기는 `mini` 다. 가르는 것은 **안 돌았을 때 무슨 일이
나는가**다. 리랭커가 안 돌면 지표가 그냥 리랭커 없는 수치이고, 판정이 안 돌면 **전건 `failed`
인데 혼동행렬은 멀쩡해 보인다.** 그래서 이쪽은 *반드시 돌아야* 하는 자리다.

### 모델 간 절대 비교를 기각하고 **luna 안에서의 v1 vs v3** 로 갔다

luna 는 temperature 를 못 고정하므로 mini 수치와 나란히 놓으면 차이에 **모델과 샘플링이
함께** 들어간다. 세 판의 차이가 전부 한두 건 규모였으므로 그 혼합으로는 우열을 못 말한다.
버린 안 둘 — *v3 한 판만 luna 로*(모델 때문인지 온도 때문인지 못 가른다) · *mini 를
temperature 1 로 다시 재서 맞추기*(86호출을 더 쓰고도 mini 쪽 기준선이 흔들린다).

### 프롬프트 판은 축으로 안 만들고 손으로 되돌렸다 (사용자 결정)

`EVALUATOR_PROMPTS` dict 를 만들어 `--prompt v1|v3` 로 고르는 안을 냈고, 사용자가 손으로
되돌리는 쪽을 골랐다. mini 의 세 판이 실제로 밟은 길이고 제품 코드가 옛 프롬프트를 안 든다.
**대가는 실제로 물었다** — 4절.

## 4. 실패 분석

### v1 실행이 v3 표를 덮었다 — 축을 하나만 넣었기 때문이다

계획 단계에서 *"라벨이 같으면 luna 실행이 mini 표를 덮는다"* 를 발견해 출력 파일 이름에
**판정 프로필**을 넣었다(`{label}-verdicts-{evaluator}.json`). 그런데 이 회차가 실제로 가른
축은 프로필이 아니라 **프롬프트 판**이었다 — `--evaluator luna` 로 v3 를 재고, `prompts.py` 를
v1 로 되돌려 같은 명령을 돌리자 **두 실행이 같은 파일 이름을 갖고** 뒤엣것이 앞엣것을 덮었다.
에러는 없었다.

**같은 함정을 한 축 옆에서 다시 밟은 것이다.** 지난 세션이 `h-ce-gpu-verdicts-preflip.json` 을
손으로 남긴 것이 정확히 이 사고를 손으로 막은 흔적인데, 그것을 보고도 프로필만 넣었다.
가른 것은 지식이 아니라 **"무엇이 이 실행의 정체인가"를 끝까지 세지 않은 것**이다 —
캐시 salt 는 `모델 + 프롬프트 버전` 둘로 갈리는데 파일 이름은 하나로만 갈랐다.
**salt 가 갈리는 축과 산출물 이름이 갈리는 축은 같아야 한다.**

되살리는 데 비용은 안 들었다(캐시 172건 전량 적중, 두 판 재생성 0호출). 잃을 뻔한 것은
**표 자체가 아니라 그 표가 어느 프롬프트의 것인지**였다.

막은 방법: `EVALUATOR_PROMPT_VERSION` 을 `meta` 와 파일 이름에 함께 싣는다 →
`h-ce-gpu-verdicts-luna-v3.json`. 이름이 어느 판인지 못 말하던 중간 파일은 지웠다
(내용이 `-luna-v1.json` 과 같은 것을 확인한 뒤).

### 핸드오프의 세트 수가 낡아 있었다

「다음 승인 단위」의 확인표가 `정답 20 · 부정 23` 인데 실제는 **정답 21 · 부정 22** 다
(`56fb382` 가 `hbas-06` 을 되돌린 뒤). 같은 파일 안에서 이미 *"「다음 승인 단위」의 30/43 은
낡은 수다"* 라고 12회차가 적어 뒀는데 확인표 쪽은 안 고쳐져 있었다. 0단계에서 먼저 찍어
확인했다. **핸드오프는 가설이다** 가 또 맞았다.

### `.env.example` 을 그대로 복사하면 죽는 줄이 이미 하나 있었다

`EVALUATOR_TEMPERATURE=` 를 빈 값으로 두면 `float | None` 이 `''` 를 파싱하다
ValidationError 로 죽는다는 것을 확인하다가, **같은 함정이 `ANSWER_CACHE_THRESHOLD=` 에 이미
있는 것**을 발견했다. `git show HEAD:.env.example` 로 재현했다 — 그 파일을 그대로 `.env` 로
복사하면 `AnswerCacheConfig()` 가 죽는다. 지금 `.env` 에 그 줄이 없어 안 물렸을 뿐이다.
둘 다 주석 처리로 고쳤고(`# EMBEDDING_DIMENSIONS=` 가 선례), 고친 뒤 `.env.example` 전체를
`.env` 로 복사해 두 설정 객체가 뜨는 것을 확인했다.

### 잘못 짚을 뻔한 것 — pytest 중 `Loading weights`

전체 pytest 한 판에서 `Loading weights: 0/393` 이 찍혀 *"기본 테스트가 가중치를 적재한다"*
로 볼 뻔했다. 폴더별로 훑어도(`tests/*/`) 0회였고, 이후 전체 실행 **두 판 모두 0회**라
재현되지 않았다. 동시에 도는 다른 프로세스의 출력이 섞인 것으로 보이고, 내가 고친 파일 중
가중치를 올릴 수 있는 것은 없다. **원인을 못 닫았으므로 단정하지 않는다** — 다시 보이면
그때가 실제 신호다.

## 5. 회귀 테스트

| 4절/2절의 항목 | 막은 테스트 |
|---|---|
| `temperature=None` 이면 인자가 안 실린다 | `tests/generation/test_evaluate.py::test_none_temperature_is_omitted_entirely` |
| 기본값(0.0)은 그대로 실린다 = mini 경로 불변 | 같은 파일 `::test_default_temperature_is_still_sent` |
| `max_tokens` 로는 안 나간다 | 같은 파일 `::test_token_budget_uses_the_new_parameter_name` |
| 온도가 캐시 salt 에 안 들어간다(258건 보호) | 같은 파일 `::test_temperature_is_not_in_the_salt` |
| 새 프로필의 오타가 조용히 무시되는 것 | `test_eval_config.py::test_every_evaluator_profile_key_is_a_real_field` (전 프로필) |
| gpt-5 프로필이 온도를 안 박아 전건 400 이 되는 것 | 같은 파일 `::test_every_evaluator_profile_pins_its_temperature` |
| 없는 이름이 조용히 기본값으로 떨어지는 것 | 같은 파일 `::test_unknown_evaluator_profile_stops` |
| `.env` 가 프로필의 `None` 을 덮는 것 | 같은 파일 `::test_env_cannot_move_a_named_evaluator_profile` |
| 축을 넣고도 기본 실행이 안 바뀌는 것 | 같은 파일 `::test_evaluator_default_is_the_same_as_naming_it` |

**못 막은 것: 출력 파일 이름의 축 누락.** 4절의 그 사고는 테스트가 아니라 **구조**로 막았다
(salt 를 만드는 상수를 파일 이름이 그대로 쓴다). 축이 또 늘면 같은 실수가 가능하다 — 다만
그때는 salt 도 함께 늘어야 하므로 두 곳이 같이 눈에 띈다.

## 7. 남은 것

- **두 모델의 우열은 안 났고, 이 회차가 답할 물음도 아니었다.** luna 가 총합에서 앞서지만
  운영점이 다르다 — K=10 에서 luna 는 부정 26/26 · 긍정 8/17, mini 는 부정 19/26 · 긍정 13/17
- **luna 수치는 재현이 안 된다.** 온도를 못 고정해, 캐시를 지우면 다른 표가 나올 수 있다
- **긍정 쪽이 왜 안 오르나** — 두 모델 다 v3 에서 *충분* 칸이 제자리이거나 −1 이다.
  「그다음 후보」의 *경계 순위 정답의 빈도* 가 비용 0 으로 이 자리를 잰다
- **`reasoning_effort`** 는 여전히 미정. 이번에 예산이 남아(4,399/512 상한 밖) 급하지 않다
- **`.env` 의 `EVALUATOR_MODEL` 은 여전히 비어 있다** — 화면을 켜는 것은 별개 축이다
- 커밋하지 않았다
