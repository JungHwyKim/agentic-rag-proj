# 답변 캐시 `exact` 를 켜고, 질의 로그에 `source` 칸을 더했다

- 검증일: 2026-08-28
- 대상: [task_log/2026-08-28-답변캐시-exact.md](../task_log/2026-08-28-답변캐시-exact.md) ·
  `plan_log/시맨틱-캐시.md` 8회차
- 비용: **유료 호출 1질의분**(사용자 승인된 계획의 검증 절차) — 실사용 왕복 1회차에서
  재작성(`gpt-4.1-mini`) 1 · 리랭킹(Cohere `rerank-v3.5`) 1 · 판정(`gpt-4.1-mini`) 1.
  **2·3회차는 캐시 히트라 셋 다 0회다** — 그것이 이 기능이 아끼는 것의 실물이다.
  `-m integration` 은 안 돌렸다.

## 1. 확인하려 한 것

**임계값이 맞는가가 아니다** — `exact` 갈래에는 정할 임계값이 없다. 이번에 잰 것은 셋이다.

1. `.env` 한 줄로 캐시가 실제로 켜지고, 같은 질문이 캐시에서 나오는가 (실서버)
2. 새 `source` 칸이 갈래를 실제로 가르는가 — **그리고 이 검증 자신이 실사용으로 안 세어지는가**
3. `exact` 로 켠 것이 기존 테스트의 뜻을 바꾸지 않는가

## 2. 가상 데이터

무엇을 고립시켰나: **헤더 하나만** 바꿨다. 질의·답변·경로는 전부 같고 `X-Query-Source` 만
없음 / 정상값 / 오타값 / 공백 / 200자로 갈랐다. 다섯째(오타)가 이 설계의 핵심이라 함께 뒀다 —
화이트리스트를 두면 그 줄이 `user` 로 접혀 **오타 하나가 측정 트래픽을 실사용으로 세게** 한다.

```python
# tests/api/test_query_log.py — 라우트를 통째로 지나가고 파일 한 줄을 읽는다
mocker.patch(
    "backend.app.api.routes.query.answer_question",
    return_value=Answer(query="q", text="답", sources=[]),
)
_client().post("/api/v1/query", data={"query": "q"}, headers={"X-Query-Source": "probe"})
assert _lines(query_log_path)[0]["source"] == "probe"
```

| 입력(헤더) | 기대 | 실측 | 판정 |
|---|---|---|---|
| 없음 | `source == "user"` | `"user"` | 의도한 변화 |
| `probe` | 그대로 실린다 | `"probe"` | 의도한 변화 |
| `prboe`(오타) | **접지 않고 그대로** | `"prboe"` | 의도한 변화 |
| `"   "`(공백만) | `"user"` | `"user"` | 의도한 변화 |
| `"p"×200` | 32자로 잘림 | `"p"×32` | 의도한 변화 |
| 한 줄의 키 집합 | 아홉 → **열**(`source` 추가) | 열 | 의도한 변화 |

## 3. 실제 데이터

실파일 픽스처가 아니라 **운영 색인과 실서버**가 입력이다. 신원은 컬렉션으로 적는다.

| 컬렉션 | points | dim |
|---|---:|---:|
| `documents_nlpai-lab_KURE-v1_default` | 721 | 1024 |
| `documents_text-embedding-3-small_default`(그림자) | 721 | 1536 |
| `qa_cache_nlpai-lab_KURE-v1_default` | **2** | 1024 |

### 3-1. 실사용 왕복 — 같은 질문 3회

질의는 `학교기록물 보존기간은 무엇을 기준으로 정하나요?` 이고 3회차만 **띄어쓰기를 둘로**
늘렸다. 셋 다 `X-Query-Source: e2e` 를 붙여 **실사용 분모에서 뺐다.**

| 회차 | 질의 | 기대 | 실측(벽시계 / 로그 `elapsed_ms`) | `cached` | 판정 |
|---|---|---|---|---|---|
| 1 | 원문 | 미스 | 11.218초 / 11,190ms | `false` | 의도한 변화 |
| 2 | 원문 | 히트 | **0.015초 / 5ms** | `true` | 의도한 변화 |
| 3 | 공백 2칸 | **같은 key 라 히트** | 0.013초 / 5ms | `true` | 의도한 변화 |

- **11,190ms → 5ms.** 이것이 `exact` 가 아끼는 것의 전부이고, 아끼는 것에 검색·재작성·
  리랭킹·판정·생성이 통째로 들어 있다
- **셋의 `key` 가 같다** — `cache_point_id_for()` 의 NFC + 공백 정규화가 실서버에서 돈다
- **히트 회차는 `verdict=null` · `rewrite_mode=null`** 이다. 판정도 재작성도 안 돌았다는
  뜻이고, *"캐시가 히트하면 재작성도 안 돈다"* 를 화면 경로에서 처음 확인했다
- 화면 문구는 `방금 물어보신 "…" 의 답변입니다` + `유사 질문` 이고, **3회차에서도 원 질문
  (공백 1칸)** 을 보여준다 — 배지가 가리키는 것이 *캐시에 실린 질문* 이라는 계약대로다
- **왕복 문구가 셋 다 보낸 문자열과 글자까지 같다**(`data-echo` 대조). cp949 오염 없음 —
  셸을 안 거치고 `urllib` 로 보냈다

### 3-2. 로그에 실제로 남은 줄

```
2026-08-28T10:50:56 source=e2e  cached=False 11190ms verdict=sufficient rw=fuse
2026-08-28T10:51:07 source=e2e  cached=True      5ms verdict=None       rw=None
2026-08-28T10:51:07 source=e2e  cached=True      5ms verdict=None       rw=None
```

| 항목 | 기준선 | 이번 | 판정 |
|---|---|---|---|
| `data/queries.jsonl` 줄 수 | 53 | 56 | 의도한 변화 |
| `source == "user"` 인 줄 | (칸 없음) | **0** | 의도한 변화 — 옛 53줄은 키가 없어 빠지고, 새 3줄은 `e2e` 다 |
| `qa_cache` points | 1 (7회차 E2E 잔류분) | **2** | 의도한 변화 — 3요청이 point 를 **하나만** 늘렸다(히트는 `put()` 을 안 한다) |

**`source=user` 가 0인 것이 이번 검증의 부수적 성과다** — 판정 규칙의 분모(실사용 50줄)에
내 검증 트래픽이 한 줄도 안 들어갔다. 새 칸의 첫 사용자가 그 칸을 만든 세션 자신이다.

## 5. 판정

| 항목 | 판정 |
|---|---|
| `.env` 한 줄로 캐시가 켜진다 | **의도한 변화** — `IngestConfig().answer_cache` 가 `mode=exact · threshold=None` |
| 같은 질문이 캐시에서 나온다 | **의도한 변화** — 11,190ms → 5ms · 배지 · 같은 `key` |
| `source` 가 갈래를 가른다 | **의도한 변화** — 가상 5입력 + 실서버 3줄 |
| `tests/answer_cache` 2건 실패 | **회귀가 아니라 드러난 결함** — 아래 |
| `qa_cache` 증가 속도 | **확인 필요** — 표본이 3요청뿐이다. 상한·퇴거는 여전히 미결이고, 재려면 실사용이 쌓여야 한다 |

**실패 2건이 이번 판에서 제일 값나가는 관측이다.** `test_get_answer_cache_returns_none_without_threshold`
와 `test_semantic_without_threshold_stays_off` 가 `AnswerCacheConfig(answer_cache_threshold=None)`
만 꽂고 **모드를 안 박았다.** 그래서 `.env` 에 `ANSWER_CACHE_MODE=exact` 를 적는 순간
`get_answer_cache()` 가 캐시를 돌려주며 빨개졌다 — **그때까지 통과하던 근거는 코드가 아니라
`.env` 의 침묵**이었고, 뒤엣것의 주석은 스스로 *"`.env` 를 안 건드리면 지금까지와 글자 그대로
같다"* 고 적고 있었다. 6회차가 이 함정을 미리 적어 뒀는데(`offline_config` 쪽) 정작
**캐시 자신의 테스트**가 안 박혀 있었다. 둘 다 `answer_cache_mode="semantic"` 을 함께 박아
고쳤다 — 이름이 `semantic` 이라고 말하는 테스트가 실제로 semantic 을 재게 된 것이다.

## 7. 재지 못한 것

- **적중률과 반복률** — 판정 규칙의 분모가 `source == "user"` 50줄인데 지금 **0줄**이다
  (옛 53줄은 칸이 없어 빠진다). 규칙은 `evaluation/README.md` 8절에 있고, 재는 시점은
  실사용이 쌓인 뒤다. **이번에 일부러 안 채웠다** — 검증 트래픽으로 분모를 만들면 그 수가
  곧 자기 자신을 잰 수가 된다
- **헤더 없는 실서버 요청**(`source="user"` 경로) — 실서버로는 안 쟀다. 보내는 순간 그것이
  실사용 한 줄이 되어 위 분모를 오염시킨다. 가상 쪽 첫 행이 그 자리를 대신한다
- **`semantic` 갈래** — 임계값이 없어 켤 수가 없다. 4·5회차가 닫은 자리 그대로다
- **캐시 상한·퇴거** — 표본이 없다. `exact` 는 `put()` 이 같은 id 를 덮어써 «서로 다른 질문
  수»만큼만 늘지만, **uuid 꼬리를 붙이는 측정 트래픽에는 그 성질이 안 먹는다**
- **워밍업 정상 여부** — `app.state.warmup_errors` 를 안 읽었다. 이번 판의 축이 아니다
