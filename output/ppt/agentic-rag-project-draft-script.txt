[SLIDE 03]
제목: 문서가 달라질수록 검색 근거가 쉽게 무너진다
대본:
이 프로젝트가 출발한 문제는 문서 포맷이 달라질수록 검색의 근거도 쉽게 무너진다는 점입니다. PDF와 HWPX, DOCX는 같은 내용을 담고 있어도 표, 제목, 이미지, 페이지 경계를 표현하는 방식이 서로 다릅니다. 이 차이를 제대로 처리하지 못하면 구조가 손실되고, 검색 결과가 문맥을 잃게 됩니다. 반대로 모든 문서와 이미지를 유료 Vision이나 외부 파서에 보내면 비용이 급격히 늘어납니다. 또한 구현이 끝났다는 사실과 실제 품질이 검증됐다는 사실을 구분하지 않으면 운영 단계에서 문제를 발견하기 어렵습니다. 따라서 핵심 질문은 다양한 문서를 하나의 스키마로 바꾸면서도 구조, 비용, 품질을 동시에 통제할 수 있는가입니다.
[/SLIDE]

[SLIDE 06]
제목: 여덟 포맷을 세 진입점으로 단순화했다
대본:
지원하는 입력은 PDF, HWPX, DOCX, PPTX, XLSX, 이미지, 텍스트, CSV와 마크다운입니다. 포맷은 다양하지만 외부에서 사용하는 진입점은 세 개로 단순화했습니다. ingest는 파일 하나를 통일된 ParsedDocument로 변환합니다. index_document는 그 결과에 청킹, 임베딩, 색인을 연결해 검색 가능한 벡터를 만듭니다. answer_question은 검색부터 판정과 생성까지 이어서 최종 Answer를 반환합니다. 이 구분 덕분에 파싱만 필요한 소비자와 색인까지 필요한 서비스가 같은 코드를 재사용하면서도 서로의 응답 계약을 침범하지 않습니다. 화면에서는 문서 업로드, 삭제, 재색인과 Hybrid Retrieval, Reranker, 출처 표시, Evaluator 기능을 이 세 진입점 위에 연결했습니다.
[/SLIDE]

제목: 파싱보다 손실 통제에 집중했다
대본:
적재 파이프라인은 포맷 판별, 문서 로더, 콘텐츠 라우팅, 정제, 청킹, 임베딩, 색인 순서로 진행됩니다. 여기서 가장 중요한 설계 원칙은 파싱 성공 여부보다 정보 손실을 통제하는 것입니다. 먼저 파일 확장자를 그대로 믿지 않고 매직바이트와 내부 구조를 확인해 실제 포맷을 판별합니다. 각 단계는 ParsedDocument나 Chunk처럼 명확한 타입 계약을 사용하기 때문에 필요하면 구현체를 교체할 수 있습니다. 외부 처리에 실패한 경우에도 경고와 비용 카운터를 메타데이터에 남겨 문제가 조용히 사라지지 않도록 했습니다. 전체 원칙은 무료 로컬 처리를 우선하고, 문서 구조상 꼭 필요한 경우에만 유료 API로 승급하는 것입니다.

[SLIDE 08]
제목: 2단계 라우팅과 폴백이 외부 API 실패를 흡수한다
대본:
라우팅은 두 단계로 이루어집니다. 먼저 실제 파일 형식에 맞는 문서 로더를 선택하고, 로더가 문서 안에서 텍스트, 표, 이미지 같은 영역을 찾습니다. 그다음 콘텐츠 라우터가 각 영역을 어떤 방식으로 텍스트화할지 결정합니다. 이때 문서 로더는 어디에 무엇이 있는지만 알고, OCR이나 Vision 같은 처리 방법은 콘텐츠 핸들러만 알도록 경계를 분리했습니다. 표 처리에서 LlamaParse나 Vision이 실패하면 네이티브 표 추출로 내려가고, 이미지 Vision이 실패하면 앞서 얻은 OCR 결과를 재사용합니다. 호출 상한을 넘는 경우에도 경고를 남기고 로컬 경로를 계속 사용합니다. 외부 API 핸들러가 예외 대신 빈 결과를 반환하는 규약이 이 폴백 사슬을 유지하는 핵심입니다.
[/SLIDE]

[SLIDE 09]
제목: 검색 후보를 넓히고 신뢰를 높인다
대본:
질문 처리에서는 먼저 같은 질문에 대한 캐시가 있는지 확인합니다. 캐시에 없으면 필요에 따라 질의를 재작성하고, 의미 기반 Dense 검색과 키워드 기반 BM25 검색을 함께 수행합니다. 두 결과는 RRF 방식으로 합쳐 서로 다른 검색 방식의 장점을 살립니다. 이후 Cohere 리랭커가 후보의 순서를 다시 조정하고 최종 Top-K 근거를 선택합니다. 선택된 근거는 Evaluator가 충분, 불충분, 실패 중 하나로 판정하지만, 이 판정이 답변 내용을 직접 바꾸지는 않습니다. 현재는 판정 결과를 Answer의 verdict로 함께 전달해 검색 평가와 생성 품질 평가가 섞이지 않게 했습니다. 질의 재작성은 화면 연결까지 끝났고, 서버 재시작 후 운영 경로에서 효과와 지연을 한 번 더 실측하는 단계가 남아 있습니다.
[/SLIDE]

대본:
모델은 하나의 종합 점수가 아니라 역할별 품질과 운영 비용을 기준으로 선택했습니다. 임베딩은 OpenAI small과 KURE-v1을 비교했고, 60개 질의에서 Dense hit@10이 0.4833에서 0.8500으로 높아진 KURE-v1을 운영 기본값으로 선택했습니다. 리랭커는 로컬 모델, OpenAI, Cohere를 비교한 뒤 nDCG 개선과 0.568초의 지연, GPU 경합 제거를 근거로 Cohere v3.5를 선택했습니다. 충분성 판정은 gpt-4.1-mini를 기준선으로 유지하고, Luna는 temperature 0을 지원하지 않아 동일 조건의 절대 비교는 보류했습니다. 문서 해석은 Tesseract를 우선 사용하고 복잡한 경우에만 Vision이나 LlamaParse로 승급합니다. 질의 재작성은 fuse와 replace 두 모드를 유지하면서 실제 운영 지표를 보고 선택할 예정입니다.
[/SLIDE]

이 프로젝트의 하네스는 설계 논의부터 코드 변경, 검증, 회귀 확인까지 한 흐름으로 연결합니다. 아직 정하지 않은 설계는 먼저 plan_log에 기록하고, 구현 후에는 선택한 방식과 버린 방식, 그 이유를 task_log에 남깁니다. 테스트와 실측에서 나온 숫자는 verify_log로 분리해 나중에 같은 조건으로 다시 확인할 수 있게 합니다. 파일이 변경되면 해당 영역 테스트를 우선 실행하고, 작업을 마칠 때 전체 회귀 테스트로 다른 기능이 깨지지 않았는지 확인합니다. 실제 비용이 발생하는 integration 테스트는 자동으로 실행하지 않고 사용자 승인이 있을 때만 허용합니다. 간단히 말하면 지식은 문서에, 실행 규칙은 훅에, 품질의 기준선은 테스트에 남기는 워크플로우입니다.
