# backend — 라우트의 몫과 화면의 함정

`backend/` 을 읽거나 고칠 때만 컨텍스트에 들어온다. 뿌리 `CLAUDE.md` 에서 2026-08-31 에
내려왔다.

**`.claude/skills/rag-code-review/references/backend.md` 와 자[尺]가 다르다.** 저쪽은 «리뷰가
잡을 위반»이고 이쪽은 «쓰는 동안 밟으면 조용히 틀리는 것»이다. 절 구성이 비슷해 보이지만
합치면 리뷰 기준이 설계 문서가 된다.

**여기 없는 것 둘을 미리 밝힌다** — `embedder` 주입과 질의 로그 `source` 는 backend 에서
밟기 쉬운데도 **뿌리에 남겼다.** 둘 다 밟아도 **에러가 안 나서**(업로드가 65초 걸릴 뿐 ·
지표가 조용히 오염될 뿐) 넓은 자리에 둬야 한다는 판정이다. 반대로 qdrant 배타 잠금은
`RuntimeError` 로 즉사하고 `rag_pipeline/ingestion/indexing/base.py` docstring 과 테스트가
받쳐, 여기로 내려도 회수된다.

**원문을 한 글자도 안 고치고 옮겼다.** 실측 수치와 «버린 안»이 이 문장들의 값어치라,
다듬으면 그것이 사라진다.

**여기 있는 항목을 뿌리 `CLAUDE.md` 에 다시 적으면 `tests/test_docs.py` 가 막는다**(같은
항목 제목이 두 `CLAUDE.md` 에 있으면 실패). 한 사실은 한 파일에만 산다.
### backend ↔ rag_pipeline 분리

- `backend/app/api/routes/documents.py` 는 업로드 수신 / 확장자 화이트리스트 1차 검증 / UUID 임시저장 / 정리 / **원본 보관·서빙·삭제·재색인**만 한다. 파싱은 `ingest()`, 색인은 `index_document()` 가 한다. **원본이 `Settings.originals_dir` 에 남는 것은 backend 만의 일이다** — 저장 이름은 예약 문자를 치환하고 `sha256(document_id)` 앞 6자를 **항상** 붙인 것이라 `document_id` 만으로 계산된다(매핑 파일이 없는 이유이고, 부딪힐 때만 붙이면 그 계산이 깨져 두 번째 진실이 생긴다). 치환만 하면 `보고서:1.pdf` 와 `보고서_1.pdf` 가 같은 파일이 되어 **한쪽의 원문 보기가 남의 파일을 에러 없이 보여준다**. **저장은 색인이 성공한 뒤**이고 파싱 전용 `upload` 는 저장하지 않는다 — 목록에 없는 파일이 쌓이면 화면과 어긋난다. **삭제는 색인과 원본을 함께 지운다.** **업로드와 색인이 두 엔드포인트인 이유**: `upload` 의 반환이 곧 공개 API 스키마(`ParsedDocument`)라 거기에 색인을 얹으면 파싱만 원하던 소비자의 응답이 바뀐다. 화면의 업로드 버튼은 색인 쪽을 부른다. **색인 쪽은 HTML 조각이 아니라 204 + `HX-Trigger` 를 돌려준다** — 문서 목록 조각은 `routes/query.py` 의 `GET /documents` 가 이미 만들고, 여기서 다시 렌더하면 같은 목록의 두 번째 진실이 생긴다. 색인 뒤 `app.state.bm25` 는 되돌리고(저장소를 전량 훑은 **스냅샷**이라 낡는다) **답변 캐시는 객체를 두고 `clear()` 로 내용만 비운다** — 스냅샷이 아니라 갈아끼울 이유가 없고(경고만 잃는다), 낡은 항목은 조회 시점에 근거 청크를 되짚어 스스로 걸러낸다. 그런데도 비우는 것이 따로 필요한 이유는 그 대조가 **새 문서가 들어온 경우를 원리적으로 못 잡아서**다(사라진 것이 없어 옛 답의 근거는 멀쩡하다). **재색인도 같은 축이라 비운다** — 파서를 고쳐 청크가 *늘어난* 경우는 옛 답의 근거가 멀쩡해 대조가 못 잡는다. 그래서 셋의 대우가 다르다: 색인·재색인은 비우고 **삭제는 안 비운다**(거기는 근거 청크가 실제로 사라져 스스로 걸러진다). **재색인이 `index_document()` 에 넘기는 `original_name` 은 디스크 이름이 아니라 문서 키다** — `안내서__a3f9c2.pdf` 를 넘기면 `document_id` 가 새로 생겨 delete 가 옛 청크를 못 찾고 문서가 두 벌이 되는데 **에러가 안 난다**
- 화면은 서버 렌더다(Jinja2 + 벤더링한 htmx, Node 툴체인 없음). `routes/pages.py` 가 화면을, `routes/query.py` 가 HTMX 가 부를 **HTML 조각**을 돌려준다 — JSON 을 주고 브라우저에서 다시 조립하면 템플릿이 두 벌이 된다. **그래서 이 저장소에는 프런트엔드 디렉터리가 없다** — 빈 `frontend/` 가 이 결정 이후로 안 쓰인 채 남아 있다가 2026-08-31 에 지워졌다. 다시 만들려는 생각이 들면 그것이 곧 위 결정을 뒤집는 것이다
- 로더는 동기·CPU 바운드라 `run_in_threadpool` 로 넘긴다
- `backend/app/main.py` 의 `_STATUS_BY_EXCEPTION` 이 `RagPipelineError` 를 HTTP 상태코드로 매핑하고 `user_message`(한국어)를 그대로 응답에 내보낸다. 새 예외를 만들면 이 매핑에 추가해야 500이 안 난다. **화면에서 온 요청(`HX-Request` 헤더)에는 같은 상태코드로 HTML 조각을 준다** — htmx 가 4xx/5xx 를 swap 안 하는 것을 200 으로 낮춰 피하면 그 계약이 화면 경로만 우회하는데, 그것이 SSE 를 기각한 자리와 같다. 뒤집는 것은 `chat.html` 의 `htmx:beforeSwap` 한 줄이다. **업로드가 제일 자주 낼 415·413 은 이 매핑을 안 탄다** — `routes/documents.py` 가 던지는 `HTTPException` 이라 `StarletteHTTPException` 핸들러가 따로 같은 규칙을 태운다. 그쪽을 빼먹으면 나머지가 전부 통과하는 채로 **확장자 오류만 화면에서 조용하다**
- **질의 라우트가 판정(Evaluator)만 질의마다 새로 만든다** — `embedder`·`bm25`·`reranker` 는 `app.state` 싱글턴인데 여기만 아니고, 가르는 것은 **가중치**다(저 셋은 KURE 2.27GB · cross-encoder 적재 · 저장소 전량 훑기이고 `OpenAIEvaluator` 에는 그런 것이 없다). 모양만 따라 싱글턴으로 두면 `warnings`·`usage` 가 **인스턴스에 누적**돼, `EVALUATOR_MODEL` 은 찼는데 키가 없는 조합에서 질의마다 경고 한 줄이 서버 수명 내내 쌓인다(읽는 사람도 없고 에러도 안 난다). 화면은 **불충분·실패일 때만** 배지를 그리고 *충분* 은 줄 자체를 안 그린다 — `cached_from` 배지와 같은 규칙이다. **모델 사유는 `title` 에만 담는다**(길이가 모델 마음대로라 배지에 펼치면 레이아웃이 무너진다). `query_log` 에는 `verdict` 한 칸이 늘었고 **판정을 안 돌렸어도 키는 있다**(`null`) — 빼면 *꺼져 있었다* 와 *옛 형식이라 칸이 없다* 가 집계에서 안 갈린다. `reasoning` 은 안 싣는다(상한도 정리도 없는 파일이다). **2026-08-27 에 칸이 둘 더 늘었다** — `rewritten`(재작성 질의 **전문**)과 `rewrite_mode` 이고, 같은 «키를 늘 쓴다» 규칙 아래 있다. 화면도 같은 규칙이라 **재작성이 실제로 걸렸을 때만** 흐린 한 줄을 그린다(꺼짐·폴백·캐시 히트는 셋 다 `Answer.rewrite is None` 이고 화면이 할 일이 같아서 안 가른다). **로그 쪽이 `reasoning` 과 반대인 것은 모순이 아니다** — 저쪽은 읽는 도구가 이미 있고(`verdicts.py --wrong`) 이쪽은 **여기가 유일한 기록**이다(`.cache/rewrite` 는 내용 해시가 키라 원 질의를 아예 안 담아 *무엇이 무엇으로 바뀌었나* 를 못 되짚는다). 길이도 산문 대 한 문장(`rewrite_max_tokens` 256)이다. **화면 문구가 `rewrite_mode` 에서 갈리는 것이 흔적을 한 덩어리로 둔 이유다** — `fuse` 는 원 질의 갈래도 함께 돌았으므로 *"…로 바꿔 검색했습니다"* 가 거짓이고 `replace` 는 *"…도 함께"* 가 거짓이라, 질의만 싣고 mode 를 빼면 템플릿이 문구를 고를 근거가 없다. **2026-08-28 에 칸이 하나 더 늘었는데 이것만 축이 다르다** — `source` 다. 앞의 셋이 *답이 어떻게 나왔나* 라면 이것은 ***그 줄이 분모에 들어가나*** 를 가른다. 실측(53줄)으로 갈래가 넷인데 셋이 오염이고 **방향이 양방향**이라 — uuid 꼬리 프로브 28줄·cp949 깨짐 4줄은 서로 다른 문자열이라 반복률을 아래로, 같은 질의를 되풀이한 서버 E2E 4줄은 위로 민다 — **합계 하나로는 못 읽고 한 갈래만 빼면 더 틀린다**(실사용은 **17줄뿐**이었다). 구멍이 계층에 있다는 것이 이 칸의 이유다: `run_eval` 은 이 로그가 backend 에 있다는 것이 막고 `tests/api` 는 autouse 픽스처가 막는데, **사람이 HTTP 로 넣는 측정 트래픽만 실사용과 같은 문으로 들어와 아무것도 안 막는다.** 그래서 요청이 `X-Query-Source` 헤더로 스스로 밝히고 안 밝히면 `user` 다 — 미들웨어를 기각한 이유(`Answer` 를 못 봐 분자가 사라진다)의 거울상이라 라우트가 읽는다. **합법값을 화이트리스트로 안 좁힌다** — 모르는 값을 `user` 로 접으면 오타 하나가 측정 트래픽을 **실사용으로 세게** 만드는데 그것이 이 칸이 막으려던 바로 그 일이다(값이 무엇이든 *실사용이 아니다* 는 확실하다). 길이만 32자로 자른다(헤더는 외부 입력이다). **`append_query_log(source=)` 에 기본값을 안 뒀다** — 새 호출부가 빠뜨리면 조용히 실사용으로 세는 대신 `TypeError` 로 터진다. **기본값이 `user` 인 것은 안전한 쪽이 아니라 정직한 쪽이다** — 헤더를 안 붙인 측정은 다시 실사용으로 세어지고, 이 칸은 그 사고를 *막는* 것이 아니라 갈래를 **데이터에 남기는** 것이다. **2026-08-29 에 칸이 셋 더 늘었다** — `retries`·`stop_reason`(재시도 루프)과 `generation_model` 이다. 앞 둘은 같은 «키를 늘 쓴다» 규칙이고, 화면도 같은 규칙이라 **재시도가 실제로 돌았을 때만**(`count > 0`) 흐린 한 줄을 그린다. **다만 `answered` 를 그 줄에서 빼면 안 된다** — `count > 0` 이면서 `answered` 인 회차가 바로 *다시 찾아 근거를 채운* 성공 사례라, 빼면 실패한 재시도만 화면에 남아 루프가 손해만 보는 것처럼 읽힌다(계획이 여기서 틀렸고 구현이 고쳤다). **셋째는 축이 또 다르고 `citation` 과 반대쪽이다** — 인용을 로그에 안 싣는 이유가 *"언제든 다시 계산된다"* 인데, **모델 이름은 모델을 바꾼 뒤에 되짚을 방법이 없다**(화면 질의의 기록은 이 파일 하나뿐이라 `rewritten` 과 같은 자리다). `source=` 와 같이 **기본값을 안 뒀다**
- 설정도 둘로 나뉜다: `backend/app/core/config.py`(웹) vs `rag_pipeline/config.py`(파싱). 둘 다 `PROJECT_ROOT/.env` 를 읽는다


## 알고 있어야 할 함정

- **Windows 에서 uvicorn 을 두 번 띄우면 둘 다 같은 포트에 붙고, 질의가 어느 쪽으로 갈지 갈린다**: 실측(2026-08-27) — 13:42 기동본과 21:14 기동본이 **동시에 127.0.0.1:8000 에 바인딩**돼 있었다. Windows 는 `SO_REUSEADDR` 로 중복 바인딩을 허용해 **두 번째가 에러 없이 뜬다**(그래서 «포트가 이미 쓰인다»는 신호가 아예 안 온다). 결과는 새 코드를 띄웠는데 **낡은 프로세스가 답하는** 상태이고, 그것이 «배선이 안 먹는다»로 보인다 — 재작성을 켠 채 질의를 넣었는데 `.cache/rewrite` 가 78 그대로였고, 낡은 쪽은 `rewrite.py` 가 **존재하지도 않던** 시점의 코드였다. **가르는 신호는 둘이다** — `Get-NetTCPConnection -LocalPort 8000` 의 소유 PID 가 **부를 때마다 다르게 나오는 것**(둘이 같은 소켓 주소를 물고 있다는 뜻)과, `Get-CimInstance Win32_Process` 로 본 uvicorn **자식의 생성 시각이 마지막 편집 시각보다 앞선 것**(`--reload` 가 걸렸으면 자식이 새로 태어나므로, 안 태어났다는 것은 그 프로세스가 낡은 코드라는 뜻이다). **RSS 로는 못 가른다** — Windows 가 유휴 프로세스의 워킹셋을 트리밍해 KURE 를 올린 프로세스도 205MB 로 보인다(이걸로 *모델을 안 올렸으니 질의를 안 받았다* 고 읽어 한 번 헛짚었다). 처방은 트리 전체를 죽이고 하나만 띄우는 것이다 — `taskkill //F //T //PID <최상위>`(Git Bash 는 슬래시를 둘로 쓴다. 하나면 경로로 바뀐다). **앞 회차가 남긴 *"실사용 확인 전에 프로세스 생성 시각부터 본다"* 의 나머지 절반이고**, 이번에 는 것은 **프로세스가 하나라는 보장이 없다**는 것이다. 근거는 `.claude/wiki/task_log/2026-08-27-재작성-흔적.md` 4절
- **htmx 의 기본값 둘이 «공짜로 되는 것처럼 보이는데 조용히 틀린다»**: 실측(2026-08-28, 벤더링한 htmx 2.0.4 소스 대조) — ① **`hx-indicator` 를 안 주면 `htmx-request` 클래스가 «요청을 낸 엘리먼트 자신»에 붙는다**(`Zt` 의 `if(t==null){t=[e]}`). 그래서 표시를 폼의 **형제**에 두고 `.htmx-request .pending` 으로 켜려 하면 **한 번도 안 뜨는데 에러가 없다** — 질의 화면의 「답변을 만드는 중…」이 2회차부터 그 상태로 살아 있었고, 그것을 잠갔다고 믿은 테스트는 **그 문자열이 응답에 있는지만** 쟀다. ② **같은 엘리먼트의 두 번째 요청은 기본이 `queue last` 다**(`g==null → g="last"`). 입력 예약이 공짜로 되는 것처럼 보이지만 그 큐가 담는 것은 값이 아니라 *«폼을 다시 읽어라»* 인 클로저라, 폼을 비우는 순서와 엉키면 **빈 질문이 나간다.** 끄는 것은 `hx-sync="this:drop"` 이고(`this` 는 소스에 `if(I==="this")` 로 실재한다) 예약은 값으로 직접 든다. ③ **폼 값을 언제 비우느냐가 요청 성립을 가른다** — htmx 는 [폼 값 수집 → `configRequest` → **검증** → `beforeRequest` → 전송] 순인데, 인라인 스크립트의 `submit` 리스너는 htmx 것보다 **먼저** 등록된다(`htmx.min.js` 가 `defer` 라 나중에 process 한다). 거기서 입력칸을 비우면 htmx 가 **빈 값을 읽고** `required` 검증에 걸려 `htmx:validation:halted` 로 **요청이 아예 안 나가는데**, 낙관적으로 그린 「생성 중」만 화면에 남고 **에러가 없다** — 2026-08-28 에 실제로 그렇게 만들었고 «답변을 안 준다» 로 돌아왔다. 그리기도 비우기도 `htmx:beforeRequest` 에서 한다(그 순간 요청이 확정이라 경합이 원리적으로 없고, 검증에 걸린 요청에는 말풍선을 아예 안 그린다). ④ **`htmx:afterRequest` 안에서 같은 폼을 다시 보내면 그 요청이 조용히 떨어진다** — htmx 는 그 이벤트를 **먼저** 쏘고 그 다음에 in-flight 잠금을 푼다(`m = function(){u.xhr=null; ...}` 가 `onload` 끝에서 불린다). 그래서 핸들러 안에서 곧바로 `requestSubmit()` 하면 아직 «도는 중» 이라 `hx-sync="this:drop"` 이 떨구고, **에러 없이 «예약은 되는데 자동 발사만 안 되는» 모양**이 된다. `setTimeout(…, 0)` 으로 콜스택 밖에서 보낸다. **①~④ 는 전부 같은 모양이다 — htmx 의 이벤트가 htmx 자신의 상태 정리보다 먼저 온다**
