## 확정된 것

- **PDF 표 기본 핸들러는 `pymupdf`** — 근거: 실측으로 무과금 경로가 유효한 마크다운 표에
  `rows` 까지 갖고 있었고, 유료 경로는 HTML 파편(표청크 62개 중 여는 태그 없는 조각 16개,
  마크다운 표 0개)을 냈다. LlamaParse 코드는 살려두고 설정값만 바꾼다.
  **2026-08-19 반영됨** — `config.py` 기본값 · `.env.example` · `.env`.
  회고: [task_log/2026-08-19-표핸들러-기본값.md](../task_log/2026-08-19-표핸들러-기본값.md)

  근거는 splitter 가 표를 행 단위로만 쪼갠다는 것. 실측 어긋난 행 373 → 0

  `table_pdf_handler="hybrid"` 가 된다. **다만 3회차에서 켤 이유가 없어져 닫았다** — 아래 참고
- **PDF 표 리전 되붙이기 — 로더에서, 조건 셋을 모두 만족할 때만** (2회차 확정, 2026-08-19 구현됨).

## 안 하기로 한 것

- **`output_tables_as_markdown=True` 로 LlamaParse 출력을 마크다운 고정** — 이유: 그 옵션의
  설명이 "마크다운 표는 병합 셀 같은 복잡한 구조를 표현하지 못한다"이고, 문제의 표에
  `colspan="4"` 가 실재한다. **HWPX 에서 방금 고친 열 밀림을 PDF 에서 새로 만드는 셈**이고
  승급의 목적("복잡한 표를 더 잘 보려고")과 정면으로 충돌한다 /
  다시 볼 조건: 병합 셀이 없는 코퍼스를 주로 다루게 되면
- **빈 칸 비율을 복잡도 신호로 쓰기** — 이유: 실측이 역방향이다. 분절이 0쌍인 AI가이드 PDF
  의 중앙값이 50% 로 시행령(25%)보다 높고, 실제로 깨진 p4 표는 상위 6위 안에도 없다 /
  다시 볼 조건: 없음(대리값이 잘못 골라진 사례로 남긴다)
- **"열 개수가 행마다 다름"을 PDF 승급 신호로 쓰기** — 이유: pymupdf 가 병합 칸을 빈
  문자열로 채워 **PDF 경로에서는 절대 발화하지 않는다**(실측 어긋난 행 0). 이 신호가
  살아있는 곳은 HWPX 인데 HWPX 표는 blob 이 없어 LlamaParse 로 가지 않는다

## 1회차 — 2026-08-18 · 실파일 청킹에서 드러난 표 문제 셋

**물은 것**

실파일 6개를 무과금·유료 두 경로로 청킹해 본 결과 표에서 문제가 셋 나왔다. 무엇을 어떤
순서로 고칠 것인가.

1. PDF 가 한 표를 여러 리전으로 쪼갠다 — 시행령 4쪽 표 하나가 5리전. 열 이름이 첫 조각에만
   남고 나머지는 데이터 행을 헤더 자리에 놓는다
2. LlamaParse 가 마크다운이 아니라 HTML 을 준다
3. 중첩 표를 담은 상자가 1칸 블롭이 된다

**측정 — 지금 잴 수 있었던 것과 못 잰 것**

| 항목 | 잴 수 있나 | 결과 |
|---|---|---|
| 리전 분절의 규모 | 잰다(무과금) | PDF 2개·리전 29개 중 **인접 병합후보 4쌍, 전부 시행령 4쪽** |
| 분절 판별자 | 잰다 | x 범위 소수점까지 동일, 세로 간격 6.8~6.9 로 일정, 열 수 4로 동일 |
| 조각 vs 상한분할 구분 | 잰다 | **같은 bbox = splitter 조각 / 다른 bbox = 별개 리전** |
| LlamaParse 출력 모양 | 쟀다(유료, 승인) | HTML. 표청크 24→62, 여는 태그 없는 조각 16/33, 마크다운 표 0 |
| 마크다운 옵션의 실제 결과 | **못 잰다** | 유료 호출이 더 필요하다. 옵션 존재만 무료로 확인 |
| 어느 표현이 검색에 유리한가 | **못 잰다** | 정답 질의 세트가 없다 |

**사용자 제안 — 승급(pymupdf 기본 + 복잡한 표만 LlamaParse)**

제안된 신호 여섯을 pymupdf 결과에서 실제로 뽑을 수 있는지 대조했다.

| 신호 | 뽑을 수 있나 |
|---|---|
| 열 개수가 행마다 다름 | **죽은 신호** — pymupdf 가 빈 문자열로 채워 PDF 에서 절대 발화 안 함 |
| 병합 셀이 심함 | **역방향** — 대리값(빈칸 비율)이 멀쩡한 표를 집고 깨진 표를 놓친다 |
| 헤더가 여러 단계 | 잴 수단 없음 |
| 셀이 다른 열로 밀림 | 검출할 수 있으면 고칠 수 있다 — 순환 |
| 표 경계가 안 잡힘 | **유일하게 살아있음** — bbox 인접 |
| 표 안에 또 다른 구조 | PDF 에서 알 수 없음(HWPX 는 `hp:tbl` 중첩으로 안다) |

**고른 것과 이유**

- 기본값을 `pymupdf` 로 한다. 실측이 근거다
- 승급 구조는 **방향이 맞다** — `image_handler="hybrid"` 와 같은 모양이고, 이 저장소가 유료
  Vision 을 아끼려고 이미 쓰는 패턴이다. 다만 **지금 켜지 않는다**

켜지 않는 이유 둘이 이번 회차의 결론이다.

1. **쓸 수 있는 트리거가 리전 인접 하나인데, 그것은 리전 병합과 같은 판별자다.** 표본이
   깨진 표 1개뿐이라 임계값을 정할 수 없어 병합을 미뤘고, 같은 이유가 승급에도 걸린다
2. **승급은 분절을 고칠 수 없다.** `table_llamaparse.handle()` 은 **리전 하나의 blob** 을
   보내므로 LlamaParse 는 애초에 조각 하나만 본다. 조각을 잘 파싱해줘도 열 이름은 여전히
   다른 조각에 있다. 실측이 이를 뒷받침한다 — 유료 패스에서 p4 표가 합쳐지기는커녕
   5조각에서 **10조각**이 됐다

따라서 **리전 병합(1번)이 승급의 선행 조건**이고, 승급을 켜려면 **HTML→`rows` 복원**도
함께 있어야 한다. 셋의 순서는 `리전 병합 → HTML rows 복원 → 승급 트리거` 다.

**남은 질문**

- PDF 를 얼마나 더 모아야 간격 임계값을 정할 수 있나. 지금은 깨진 표 1개다
- HTML→`rows` 복원을 한다면 `colspan`/`rowSpan` 을 HWPX 와 같은 규칙(세로 되풀이 / 가로
  빈 칸)으로 맞출 것인가. 맞추면 두 포맷의 표가 같은 모양이 된다
- 승급을 켜면 비용 상한이 필요하다. Vision 은 `max_vision_calls_per_doc` 가 있는데 표에는
  대응물이 없다

## 2회차 — 2026-08-19 · PDF 를 더 모아 되붙이기 임계값을 정했다

**물은 것**

1회차에서 리전 병합을 미룬 이유는 조각난 표 표본이 **1개**(시행령 4쪽)뿐이라 간격 임계값을
정할 근거가 없어서였다. 사용자가 PDF 3개를 더 모아 왔다(학교기록물 PDF · 2026 중등 기초학력
계획 PDF/HWPX · 아동정책 안내서 PDF). 이제 정할 수 있나.

**측정**

PDF 5개 · 표 리전 103개 · 같은 쪽 인접쌍 36개. x 범위가 ±2pt 안에서 일치하는 쌍의 간격:

```
 6.8  6.8  6.8  6.8      시행령 4쪽 — 한 표가 5조각
18.8  18.8  21.6         학교기록물 PDF 31쪽
26.0  26.1               2026 중등 16쪽
33.6  36.4  36.8  39.2   2026 중등 26·31쪽
```

내용을 열어 각 그룹의 정체를 확인했다.

| 그룹 | 열 수 | 정체 | 붙여야 하나 |
|---|---|---|---|
| 시행령 p4 | 4→4 | 첫 조각이 헤더 행 `단계\|실행항목\|세부내용 및 방법\|담당` | **그렇다** |
| 학교기록물 p31 | 2→2 | 한 행씩 잡힌 절차 흐름. 헤더가 없다 | 아니다 |
| 2026중등 p16 | 2→2 | `• 기초학력 진단` 등 각각 별개 상자 | 아니다 |
| 2026중등 p31 | 6→3→2→3 | 서로 다른 표 | 아니다 |

**선택지**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| 간격 12 + x ±2 + 열 수 동일 | 6.8 과 18.8 사이 2.8배 틈의 가운데. 오검출 0 | 학교기록물 31쪽은 못 붙인다 | 임계값이 표본 하나가 아니라 **분포의 틈**에서 나온다 |
| 간격만으로 판정 | 규칙이 단순 | 2026중등 31쪽을 잘못 붙인다 | 열 수 조건이 실제로 일하는 사례가 있다 |
| "앞 조각이 헤더만 있는 1행" 조건 추가 | 시행령을 정확히 집는다 | 근거가 다시 표본 하나에 묶인다 | 1회차에서 미룬 이유가 그대로 돌아온다 |

**고른 것과 이유**

첫째 안. **임계값을 관측값(6.8)이 아니라 두 무리 사이의 틈에서 골랐다** — 6.8 을 보고 "12
미만" 을 정한 것이 아니라, 6.8 무리와 18.8 무리가 갈린다는 사실에서 정했다. 이 저장소가 반복
머리말에서 겪은 "오염된 자[尺]로 임계값을 정하는" 실수를 피하는 방식이다.

되붙이기를 **로더**에 둔 것도 이번에 확정했다. 승급으로는 못 고친다 — `handle()` 이 리전
하나의 blob 만 보내므로 외부 API 는 조각 하나밖에 못 본다(실측: 유료 경로에서 같은 표가
10조각). splitter 도 못 고친다 — 좌표를 안 받고, 조각의 첫 행을 헤더로 되풀이하는 것은
리전이 온전하다는 전제에서 옳은 동작이다.

**곁가지로 정한 것**

- 중복 픽스처(`「2025년 학교기록물 관리 지침」 (1).hwpx`, 기존 파일과 바이트 동일)를 지웠다.
  이름이 부분 문자열로 겹쳐 `_find()` 가 둘을 잡았다 — CLAUDE.md 가 경고한 함정이 실제로
  발생했고 `pytest.fail` 이 사고를 막았다
- `test_extracts_body_without_warnings` 가 **문단** 글자수를 세던 것을 전체 요소로 바꿨다.
  2026중등은 본문의 82%가 표에 있어 문단만 세면 파싱 실패로 오인된다

**남은 질문**

- 되붙인 뒤에도 남는 "복잡함"의 신호가 무엇인가. 승급 트리거는 그것이 있어야 정해진다
- 헤더 없이 조각난 표(학교기록물 31쪽)를 붙일 것인가
- 학교기록물은 PDF 판 이미지가 81개로 HWPX 판 20개의 4배다. 원인 미확인

## 3회차 — 2026-08-19 · PDF 병합 셀을 무료로 고치자 승급의 이유가 사라졌다

**물은 것**

2회차 끝에서 승급은 이런 상태였다 — 선행 조건(리전 병합)은 풀렸는데 **트리거로 쓸 신호가
사라졌다**(bbox 인접이 유일했고 그것을 병합이 소비했다). 남은 전제는 HTML→`rows` 복원.

그래서 순서를 뒤집어 물었다. **승급이 노리던 "복잡한 표" 결함 중 실제로 남은 것이 무엇인가.**

| 원래 문제 | 상태 |
|---|---|
| HWPX 병합 셀로 열 밀림 | 고침(2026-08-18, 어긋난 행 373→0) |
| PDF 리전 분절 | 고침(2회차, 오검출 0) |
| PDF 병합 셀 값 손실 | **남음** — 빈 문자열이라 정렬은 맞고 값만 없다 |

셋째 하나만 남았고, **그것을 무료로 고칠 수 있다면 승급도 HTML 복원도 필요 없어진다.**

**전제 확인 — "PDF 는 병합 정보가 없다"가 틀렸다**

이틀 동안 깔려 있던 전제였다. 실제로는 PyMuPDF 가 병합에 덮인 자리를
`row.cells[j] is None` 으로 내놓고 `extract()` 는 같은 자리에 빈 문자열을 준다. 겹쳐 보면
**"병합에 덮인 자리"와 "그냥 빈 칸"이 갈린다.** 되풀이가 가능하다.

**측정 — 세로와 가로를 가를 수 있나**

PDF 5개 · 표 칸 3,503개.

```
None 칸 897 (25.6%)
  ├ 첫 행이라 세로 불가        108
  ├ 위에 앵커 있음             661
  │   └ 그중 왼쪽 칸이 이 열까지 뻗음  226 (34.2%)
  └ 위 없고 왼쪽만 있음        116
```

**선택지**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| 가로 먼저 판정, 아니면 세로 채움 | 226칸 오염을 막는다 | 판정이 두 단계 | 34.2% 는 무시할 수 없는 비율이다 |
| 위에 앵커가 있으면 세로 | 규칙이 한 줄 | **226칸에 엉뚱한 값** | 실측이 기각했다 |
| 그대로 두고 승급으로 해결 | 코드 안 늘어남 | 과금 + LlamaParse 는 HTML 을 준다 | 무료로 되는 일에 돈을 쓴다 |

**고른 것과 이유**

첫째 안. 규칙은 HWPX 와 같게 맞췄다(세로 되풀이 / 가로 빈 칸) — 근거도 같다. splitter 가 표를
행 단위로만 쪼개므로 아래로 이어진 행은 다른 청크로 갈 수 있지만 옆으로 이어진 칸은 늘 같은
행에 남는다. 두 포맷의 표가 같은 모양이 되는 것도 덤이다.

**승급을 닫는다**

노리던 결함 셋이 전부 무료 경로에서 해결됐다. 트리거로 쓸 신호도 없고 LlamaParse 는 여전히
HTML 을 준다. **다시 볼 조건은 "무료 경로가 못 고치는 표 결함이 실측으로 새로 나오면" 이다.**

기각이 아니라 **닫음**으로 적는 이유는 승급 구조 자체는 여전히 옳기 때문이다
(`image_handler="hybrid"` 와 같은 모양). 필요해지면 그때 여는 것이 맞다.

**남은 질문**

- 비워 둔 450칸이 진짜 가로 병합인가. 사람이 문서를 열어 세지 않았다
- HWPX 판과 PDF 판의 같은 표가 이제 정말 같은 모양인가. 규칙만 맞췄고 결과를 대조하지 않았다
