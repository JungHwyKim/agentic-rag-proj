# splitter 설계

상태: 구현됨 (2026-08-17, 커밋 전)
관련 기록: [task_log/2026-08-17-splitter-청킹단계.md](../task_log/2026-08-17-splitter-청킹단계.md)

## 계획과 실제가 어긋난 곳

1회차에서 못 본 것 하나가 구현 중에 드러났다. **제목 머리를 청크 본문에 붙이기로 해놓고
상한과의 상호작용을 안 따졌다.** 머리를 분할 뒤에 붙이니 1200 상한에 최대 1258자 청크가
생겼다(PDF 3 / 시행령 7 / 학교기록물 9). 예산에서 머리 길이를 미리 빼는 것으로 고쳤고,
회고 4-(가) 에 있다.

나머지는 계획대로다. 특히 **승격을 `load()` 에 둔 판단이 실제로 값을 했다** — 회귀 기준선의
documents 6건이 전부 그대로였다.

## 확정된 것

### 책임 경계

- **로더**가 heading 을 포함한 구조 표시를 만든다. splitter 는 `ElementType.TITLE` 만 보고
  포맷을 모른다 — `CLAUDE.md` 의 "로더는 어디에 무엇이 있는가만 답한다"와 같은 규율이다
- **cleaner** 는 텍스트 정제만 한다. 지금과 같다
- **splitter** 는 병합·분할·청크 metadata 만 한다. Vision/OCR 을 새로 부르지 않는다 —
  로더가 이미 `IMAGE_TEXT` 텍스트 요소로 내놓기 때문에 splitter 입장에서 "이미지" 분기는 없다.
  남는 특수 케이스 하나는 Vision 이 `data_table` 을 준 요소에 `metadata["rows"]` 가 붙는다는 것

### splitter 의 주 작업은 자르기가 아니라 병합이다

실측(아래 1회차)에서 세 문서 전부 **1200자 넘는 텍스트 요소가 0개**이고 중앙값이 15~40자다.
지시서 초안의 "구조로 나누고 크면 자른다"는 이 코퍼스에서 뒤집힌다. 요소 수백 개를 heading
경계까지 **붙이는 것**이 주 작업이고, 자르기는 표에서만 실제로 발화한다.

그래서 **병합 경계인 heading 이 splitter 의 선행 조건**이고, PDF·HWPX 가 그걸 안 내놓으므로
**로더 확장이 splitter 앞에 별도 작업으로 붙는다.**

### heading 승격 규칙 (로더 몫)

- 신호는 **문단/블록 전체가 본문 글자 크기보다 큰가**. 본문 크기는 **문서별 최빈값**으로 구한다.
  절대 임계값을 쓰지 않는다 — 실측상 본문이 HWPX 949 / 1500 / 1200, PDF 9.5 로 문서마다 다르다
- **배율 임계값도 쓰지 않는다.** 부등호 하나로 판정한다. 시행령 안내서는 제목 1600 / 본문 1500 로
  차이가 6.7% 뿐이라, 1.2배 같은 임계값을 두면 제목 19개가 통째로 사라진다
- **문단 안에 크기가 섞이면 승격하지 않는다.** 큰 글씨가 제목이 아니라 강조인 경우가 여기서
  걸러진다(사람 이름·인용 강조). 실측상 혼재 문단의 실제 내용은 ※인용, 표지 장식, 목차 줄이었다
- **번호·기호 머리(□ · 1. · 제N조)를 승격 트리거로 쓰지 않는다.** 마커는 `heading_level`
  힌트로만 쓴다
- `heading_level` 은 본문보다 큰 크기들의 순위로 준다. docx 가 이미 쓰는
  `metadata["heading_level"]` 칸을 그대로 쓴다
- **문서 전체를 본 뒤에 판정해야 하므로 로더에 2패스가 생긴다** — 최빈값을 알아야 첫 요소도
  판정할 수 있다. 리전을 모은 뒤 승격하는 형태가 된다

### 크기·오버랩

- oversized 분할 규칙은 넣되 **오버랩은 그 구간에만** 적용한다. 구조 경계로 자른 뒤 오버랩을
  얹으면 의미 단위를 다시 흐린다
- **표 청크에는 오버랩을 주지 않는다.** 행이 중복 색인된다
- 큰 표는 헤더 행을 반복하며 행 그룹으로 나눈다. 표 요소는 `text`(마크다운)와
  `metadata["rows"]`(원본 2차원 배열)를 둘 다 갖고 있어 이 분할이 실제로 가능하다

### 계약

- 출력은 `schemas/chunk.py` 의 `Chunk`, 진입점은 `split(document, config) -> list[Chunk]`
- **`ingest()` 안에서 `split()` 을 부르지 않는다.** 아래 "합성 지점" 절
- **`page` 를 분할 경계나 비율의 분모로 쓰지 않는다.** 같은 문서를 PDF 28쪽 / HWPX 97쪽으로
  센다(이번 세션 재확인). `cleaner/headers.py` 가 이미 같은 함정에서 등장 횟수 비율을 버리고
  걸친 폭으로 갈아탔다. HWPX 가 쪽 걸친 표에 싣는 `page_end` 도 청크로 함께 옮긴다
- **`order` 연속성을 가정하지 않는다.** cleaner 가 머리말을 지운 자리와 핸들러가 요소를 0개
  만든 자리에 빈틈이 있다. `chunk_index` 는 새로 매기는 별개 값이다

### 합성 지점 — `pipeline.py` 를 이번에 손대지 않는다

- `backend/app/api/routes/documents.py:upload_document()` 가 `response_model=ParsedDocument` 로
  선언하고 `ingest()` 결과를 그대로 반환한다. **`ingest()` 의 반환 타입이 곧 공개 HTTP 응답
  스키마다.** 청크를 내보내는 것은 splitter 결정이 아니라 API 결정이다
- 청크를 만들고 버리는 호출은 "순차 합성"이 아니다 — 각 단계 출력이 다음 단계 입력이 되는 것이
  합성인데 소비자(embedding)가 없다. 게다가 업로드마다 요소 285~721개를 다시 훑는 비용이
  `run_in_threadpool` 안에서 응답 지연에 그대로 얹힌다
- `pipeline.py` 의 예약 주석은 `split → embed → index` 를 **한 덩어리로** 적어놨다. 원래 의도도
  "split 만 먼저 끼운다"가 아니었다

`split()` 은 `rag_pipeline/ingestion/splitter/__init__.py` 의 공개 함수로만 존재하고
`tests/ingestion/splitter/` 가 `ingest()` 결과를 넣어 직접 부른다.

**이건 `CLAUDE.md` "새 파이프라인 단계 추가" 4번(예약 주석을 실제 호출로 바꾼다)을 일부러
건너뛰는 것이다.** 누락이 아니라 결정이다. 같은 절차의 나머지는 지키되 한 곳이 더 어긋난다 —
설정 3곳 중 `config.py` 와 `.env.example` 만 해당하고 `offline_config` 에는 끌 것이 없다.
splitter 는 외부 API 를 안 쓴다. `auto_test_check.py` 매핑 추가는 `ingest()` 에 안 붙어도 필요하다.

## 미결

- **청크 크기 상한 임시값** — heading 섹션을 그대로 청크로 쓰면 실측상 평균 214자(PDF) /
  342자(HWPX) / 782자(시행령)가 나온다. 지시서 초안의 1200자를 채우려면 **섹션 경계를 넘어
  합쳐야 하고**, 그건 같은 지시서의 "서로 다른 Section 을 한 Chunk 로 합치지 않는다"와 정면
  충돌한다. 지금 안은 "상한만 두고 하한은 두지 않는다"(= 섹션이 곧 청크, 본문 없는 heading 만
  다음 섹션에 붙임). 200자 청크가 검색에 충분한지는 **못 잰다** — 정하려면 `평가-세트.md`
- **크기 단위(문자 vs 토큰)** — 정하려면 임베딩 모델을 골라야 한다. 한국어는 모델마다 문자/토큰
  비율이 크게 다르다. 문자로 굳히면 모델 교체 때 전부 다시 잰다
- **표지·간지 장식 오탐** — 실측상 "DNA" · "플러스" · "2019" · "2025. 1." ·
  "- OECD 권고안의 적용 -" 이 균일하게 큰 문단으로 남아 제목으로 승격된다. 지금 규칙을 만들지
  않는다 — "첫 쪽 제외" 같은 규칙은 표지가 여러 쪽인 문서에서 깨진다. 정하려면: 표지 판별을
  어느 단계가 할지부터
- **`ingest()` 에 언제 끼우고 그때 무엇을 반환하나** — 정하려면 embedding·indexing 이 있어야
  한다. 후보는 `IngestResult(document, chunks)` 반환과 엔드포인트 분리(파싱 결과와 색인 결과를
  나눔) 둘인데, 지금 고르면 소비자가 없는 상태에서 공개 API 스키마를 정하는 셈이 된다
- **`document_id`** — 저장소에 없다. backend 는 업로드마다 `uuid4()` 임시 파일명만 만들고 버린다.
  deterministic chunk ID 의 전제인데, 파일 내용 해시(`loader/content/base.py` 의
  `content_hash()`)를 쓰면 "재업로드 = 중복"이라는 **indexing 정책**을 먼저 정하는 셈이 된다
- **excel/csv 를 못 쟀다** — CSV 는 파일 전체가 표 하나, Excel 은 시트당 표 하나에
  `max_excel_rows=5000`. 행 그룹 분할이 제일 크게 걸리는 곳인데 `tests/fixtures/` 에 없다
- **AI가이드 HWPX 의 표가 0개** — 같은 문서 PDF 판은 표 10개다. `_is_layout_box` 강등이
  유력하나 확인하지 않았다. splitter 가 아니라 로더 쪽 관측으로 남긴다

## 안 하기로 한 것

- **Parent-Child / Child Retriever / Parent Document Store** — 이유: 지금 청크 크기가 적절한지
  자체를 못 재는데 그 보정 장치를 먼저 만들 근거가 없다 / 다시 볼 조건: 평가에서 "청크가 작아
  문맥이 부족" 또는 "커서 정확도가 떨어짐"이 확인될 때
- **Semantic Chunking · LLM 기반 경계 판단** — 이유: 비용이 요소 수에 비례해 붙는다(문서당
  요소 285~721개) / 다시 볼 조건: 구조 기반이 실패하는 문서 유형이 확인될 때
- **번호·기호 머리 단독으로 heading 승격** — 이유: 실측상 큰 글씨와 마커가 겹치는 문단이
  AI가이드 PDF 0/74, HWPX 0/54 다. 마커만 보면 PDF 75개·HWPX 80개·시행령 158개를 제목으로
  오인한다 / 다시 볼 조건: 글자 크기 정보가 없는 포맷이 들어올 때
- **텍스트 요소에 전역 오버랩** — 이유: 구조 경계로 자른 뒤 오버랩은 의미 단위를 다시 흐린다.
  oversized 구간에만 준다
- **`ingest()` 안에서 청크를 만들고 버리기** — 이유: 위 "합성 지점" / 다시 볼 조건:
  embedding 또는 indexing 이 생겨 청크를 소비할 곳이 생길 때
- **`ingest(split=True)` 같은 플래그로 반환 타입 가르기** — 이유: 반환 타입이 인자에 따라
  달라지면 `response_model` 을 선언할 수 없고 호출부가 분기를 떠안는다
- **splitter 지시서에 Retrieval 구조(Dense/Sparse/Hybrid/Reranker)를 못 박는 것** — 이유:
  그 코드가 한 줄도 없어서 "변경하지 않았다" 체크박스가 항상 통과한다. 검사로서 값어치가 0이다.
  retriever 논의로 옮긴다

## 1회차 — 2026-08-17 · 지시서 초안 검토와 실측

**물은 것**

사용자가 chunking 지시서 초안을 가져와 "필요한 부분·불필요한 부분·수정할 부분"을 요청했다.
초안의 뼈대는 `Structure-first → Type-aware → Size fallback` 이었다.

**드러난 것 — 초안의 전제가 이 저장소에서 성립하지 않는다**

초안은 "문서 구조에서 추출된 heading/section 정보를 활용하라"를 3·4절의 축으로 삼는데,
heading 을 실제로 내놓는 로더는 docx(`_element_type_of()` → `TITLE` + `heading_level`),
markdown(`#`), pptx(제목 placeholder) 셋뿐이다. **PDF 와 HWPX 는 전부 `PARAGRAPH` 고정**이고,
`tests/fixtures/` 는 HWPX 4 + PDF 1 + HWP 1 이라 **heading 이 나오는 포맷이 하나도 없다.**

초안대로면 실제 문서에서 항상 fallback 으로 떨어져 구조 기반 청킹이 이름만 남는다.

곁가지: `hwpx.py` 가 `layout_table` 을 실으며 *"cleaner 가 제목으로 승격할지 판단한다"* 고
주석에 적어놨는데 cleaner 는 그 값을 안 쓴다. 승격 자리가 비어 있었다.

**실측 (1) — splitter 의 실제 입력**

`tests/fixtures/` 를 `ingest()` 로 통과시켜 쟀다. LlamaParse·Vision·OCR·캐시 전부 꺼서 과금 없음.

| 문서 | 요소 | 쪽 | 비표 텍스트 자수 중앙/최대 | 1200자↑ | 표 |
|---|---|---|---|---|---|
| AI가이드 PDF | 509 | 28 | 23 / 123 | **0개** | 10개, 최대 818자 |
| AI가이드 HWPX | 721 | 97 | 15 / 167 | **0개** | 0개 |
| 시행령 HWPX | 285 | 26 | 40 / 554 | **0개** | 9개, 최대 3,243자 / 67행 |

PDF 원본 블록은 707개 중 349개(49%)가 20자 미만이고 최대가 123자다.

**이 표가 초안을 뒤집었다.** 텍스트에서 oversized 분할은 한 번도 발화하지 않는다. 초안 5절의
예시("20,000자 Section")는 이 코퍼스에 존재하지 않는다. 반대로 **표는 3개가 1200자를 넘는다** —
oversized 분할이 실제로 필요한 곳은 표뿐이다.

그래서 초안 8절 원칙 6("작은 Section 을 인접과 합치지 않는다")과 16절 검증 항목("Chunk 가
지나치게 작은 경우가 없는가")이 **서로 모순**이라는 것도 드러났다. 합치지 않으면 청크의 절반이
20자짜리가 된다.

**실측 (2) — heading 신호**

사용자가 "큰 글씨는 제목일 수도 있지만 사람 이름 같은 건 단순 강조"라고 지적해, 승격 신호
후보 셋을 각각 쟀다.

| 문서 | 본문 크기 | 문단 전체가 큼 | 문단 내 혼재 | 번호·기호 머리 | 큰글씨∩마커 |
|---|---|---|---|---|---|
| AI가이드 PDF | 9.5 | 74 / 707블록 | 4 | 75 | **0** |
| AI가이드 HWPX | 949 | 54 / 746문단 | 24 | 80 | **0** |
| 시행령 HWPX | 1500 | 19 / 257문단 | 3 | 158 | 19 |
| 학교기록물 HWPX | 1200 | 53 / 431문단 | 1 | 103 | 37 |

먼저 스타일 기반을 봤으나 AI가이드 HWPX 의 `header.xml` 에는 스타일이 `Normal` **하나뿐**이라
그 길이 막혔다. 크기 정보(`charPr height`)는 240~2617 로 살아 있었다.

**선택지**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| 로더가 뽑는다 | 경계상 맞다. splitter 가 포맷을 모른다 | splitter 앞에 로더 작업이 붙는다 | "어디에 무엇이 있는가"는 로더 몫이라는 기존 규율 그대로 |
| splitter 가 텍스트로 추론 | 로더를 안 건드린다 | 포맷 지식이 splitter 로 샌다 | 로더/핸들러 경계를 무너뜨린 것과 같은 종류의 침범 |
| heading 없이 간다 | 지금 당장 만든다 | structure-first 가 사실상 폐기 | 요소 중앙값 15~40자라 병합 경계가 없으면 붙일 곳을 못 정한다 |

**고른 것과 이유**

**로더가 뽑는다**(사용자 선택). 나머지 둘을 기각한 이유는 위 표 그대로다. 특히 셋째 안은
실측 (1) 때문에 못 쓴다 — 병합이 주 작업인데 경계가 없으면 문서 전체가 한 청크가 된다.

승격 규칙은 실측 (2) 가 정했고, 사용자의 우려와 **반대 방향**으로 결론이 났다.

- 큰 글씨는 쓴다. 단 **문단/블록 전체가 균일하게 클 때만**. 혼재 문단은 강조로 보고 버린다 —
  실측상 혼재의 실제 내용이 ※인용, 표지 장식, 목차 줄이었다. 사용자가 걱정한 오탐이 여기서 걸린다
- **번호·기호 머리를 승격 트리거로 쓰는 안을 기각**했다. 직관과 달리 큰 글씨와 마커가 겹치는
  문단이 AI가이드에서 PDF 0/74, HWPX 0/54 다. 마커 단독이면 시행령에서 158개를 제목으로 오인한다
- 본문 크기는 문서별 최빈값으로 구하고 **부등호 하나로 판정**한다. 배율 임계값을 두면
  시행령(제목 1600 / 본문 1500, 6.7% 차)의 제목 19개가 통째로 사라진다.
  `cleaner/headers.py` 가 분모를 의심해 얻은 교훈과 같은 자리다

출력 타입은 `Chunk` 신설 + `split()` 별도 노출로 정했다(사용자 선택). 이어서 사용자가
"청크를 버릴 거면 `ingest()` 에 필수 단계로 넣는 게 맞나"를 짚었고, 계약을 확인해
**`pipeline.py` 를 이번에 손대지 않기로** 했다(위 "합성 지점").

크기는 splitter 를 먼저 만들고 임시값으로 두기로 했다(사용자 선택) — `평가-세트.md` 의 1번
미결("세트가 먼저냐 splitter 가 먼저냐")에 대한 답이 이쪽으로 났다. 청크가 있어야 "정답 청크"를
정의할 수 있어 순환도 이쪽에서 끊긴다.

**초안에서 덜어낸 것**

Retrieval 구조 선언(0·13·17절)과 18절의 관련 체크박스, 중복 다이어그램(7절·17절),
Image 절의 절반(로더가 이미 `IMAGE_TEXT` 로 내놓는다), 16절의 "검색 가능한 텍스트가
되었는가"(못 잰다). 초안 2절이 "Loader 가 가능한 한 많은 구조 정보를 추출한다"를 지나가는
문장으로 끼워 넣었는데, 그건 실제로 필요한 변경이라 별도 결정으로 올렸다.
