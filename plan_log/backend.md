# backend 설계

상태: 논의 중 (1~8회차)
관련 기록: task_log/... (구현 후 채운다)

`frontend.md` 와 짝이다 — 저쪽 1회차의 확정 10줄 중 **프론트 고유는 2줄뿐**(HTMX 스택 ·
히스토리 자리만 두기)이고 나머지는 backend 또는 생성 결정이다. 그것을 이 파일로 옮기는 것이
2회차이고, **1회차인 지금은 가리키기만 한다**(미결 첫 줄에 조건이 있다).

## 표면 지도

**이 파일의 유일한 원본 콘텐츠다.** 나머지 절은 전부 다른 곳을 가리킨다 — 같은 문장이 두
곳에 살면 한쪽만 고쳐진다(`문서-최신성.md` 6회차). 2026-08-23 워킹 트리 기준.

| 메서드 · 경로 | 하는 일 | 이 결정이 사는 곳 |
|---|---|---|
| `POST /api/v1/documents/upload` | 업로드 수신 · 확장자 1차 검증 · UUID 임시저장 · 정리. 파싱은 `ingest()`. **색인은 안 한다** | `CLAUDE.md` "backend ↔ rag_pipeline 분리" |
| `GET /api/v1/health` | 상태 확인 | — |
| `POST /api/v1/query` | 질문 → `answer_question()` → **HTML 조각**(`_answer.html`) | `routes/query.py` docstring · `frontend.md` 1회차 |
| `GET /api/v1/documents` | 사이드바 문서 목록 조각. `QdrantStore.list_documents()` 를 `getattr` 로 집어 없으면 목록만 빈다 | `frontend.md` 1회차 (Protocol 안 넓힘) |
| `GET /` | 채팅 화면 전체(`chat.html`). **`api_prefix` 를 안 붙인다** — 사람이 여는 주소다 | `routes/pages.py` docstring |
| `/static` (mount) | 벤더링한 htmx 등 정적 파일 | `CLAUDE.md` "backend ↔ rag_pipeline 분리" |

앱 수준으로 함께 봐야 하는 넷.

- **`store` 싱글턴은 `lifespan` 이 든다. 다만 열기를 startup 에서 시도하지 않는다** —
  `QdrantStore` 가 처음 쓸 때 클라이언트를 만들도록 늦춰져 있고, 그 게으름을 깨면 색인이
  없는 상태에서 서버가 아예 안 뜬다. 근거는 `main.py:lifespan` 주석
- **`embedder` 는 첫 질의에 만든다** — `get_embedder()` 가 키 없으면 그 자리에서 예외라
  startup 에서 만들면 키 없는 개발 환경에서 화면조차 못 본다. `query.py:_embedder()`
- **`_STATUS_BY_EXCEPTION` 은 7종을 매핑한다.** `EmbeddingError`·`IndexingError`·
  `GenerationError` 셋이 `/query` 가 생기며 **처음 살아났다**(그전에는 닿는 HTTP 경로가
  없었다). `main.py`
- **설정은 `backend/app/core/config.py:Settings`** — 파싱 설정과 갈라져 있다


## 확정된 것

- **backend 설계의 거처는 이 파일이다** — 근거: 그전까지 backend 결정이 `CLAUDE.md` ·
  `frontend.md` · `indexing.md` · `splitter.md` · `검색-생성.md` 다섯 곳에 흩어져 있어,
  *"색인 엔드포인트를 어디서 정했나"* 를 알려면 세 파일을 뒤져야 했다
- **`frontend.md` 의 backend·생성 항목은 여기로 옮겼다 (2회차에 실행)** — 1회차는 시점이
  나빠 가리키기만 했다. 옮긴 것은 맨 위 세 절뿐이고 **1회차 본문은 그쪽에 그대로 뒀다**.
  25개 중 18개가 왔고 5개는 화면 결정이라 남았으며 2개는 중복이라 지웠다
- **생성 관련 결정의 최종 거처도 이 파일이다** — gpt-4.1-mini 실호출 · 환각은 프롬프트로만 ·
  점수 임계값 기각 · 인용 코드검증 기각 · `GenerationError` 재시도. 근거: 지금 그 결정들이
  `/query` 한 엔드포인트 안에서만 산다. 단계 파일로 떼어내기에는 다섯 줄뿐이다 /
  다시 볼 조건: 생성 고유 결정이 늘면 `plan_log/생성.md` 로 분가한다
- **인증·레이트리밋은 안 한다** — 아래 "안 하기로 한 것"
- **`index_document()` 의 store 소유권은 "연 쪽이 닫는다"** — 인자로 받으면 안 닫고(호출자
  소유), 안 받으면 열고 반드시 닫는다. **방향을 거꾸로 잡으면 한쪽이 반드시 죽는다**:
  주입받은 것을 닫으면 backend 가 다음 요청에서 죽고, 자기가 연 것을 안 닫으면
  `evaluation/run_eval.py` 가 색인 루프 **직후** 자기 `get_store()` 를 열다가 잠금으로 죽는다.
  `store=` 를 안 넘겼을 때 `config.indexing.qdrant_path` 가 계속 존중되는 것도 같은 계약이다
  — 평가가 실행마다 경로를 가르는데 기본 경로로 떨어지면 기준선이 **수치로만** 오염된다
- **업로드와 색인은 두 엔드포인트다** — `upload` 의 반환이 곧 공개 API 스키마라 거기에 색인을
  얹으면 파싱만 원하던 소비자의 응답이 바뀐다. 색인 쪽은 HTML 조각이 아니라
  **204 + `HX-Trigger`** 를 돌려준다: 목록 조각은 `GET /documents` 가 이미 만들고 여기서 다시
  렌더하면 같은 목록의 두 번째 진실이 생긴다
- **색인 뒤 BM25 는 되돌리고 답변 캐시는 `clear()` 로 비운다** — 둘의 대우가 다르다.
  BM25 는 저장소를 전량 훑은 **스냅샷**이라 객체를 버리지만(`None`), 답변 캐시는 `store`
  참조만 들고 질의마다 새로 읽으므로 **객체는 그대로 두고 내용만 비운다**(갈아끼우면
  `warnings` 만 잃는다). 낡은 항목은 조회 시점에 근거 청크를 되짚어 스스로 걸러진다.
  **그런데도 비우는 것이 따로 필요한 이유**는 그 대조가 *새 문서가 들어온 경우*를 원리적으로
  못 잡아서다 — 사라진 것이 없어 옛 답의 근거는 여전히 멀쩡하다.
  **이 항목은 2026-08-24 에 닫혔다**(열린 채로 넘긴 뒤 캐시 쪽 세션이 정했다).
  근거와 기각한 대안은 `plan_log/시맨틱-캐시.md` 에 있다
- **업로드의 이중 검증(확장자 화이트리스트 + 매직바이트)은 어긋나지 않는다** — 근거: 실측.
  화이트리스트 22종 중 표본을 합성할 수 있는 **18종을 `detect_format()` 에 왕복시켜 어긋남
  0**, 로더가 아는 13개 포맷이 전부 화이트리스트에 있다. 레거시 4종(`.doc`·`.ppt`·`.xls`·
  `.hwp`)은 **감지가 `olefile` 로 스트림 이름을 읽는데 그 라이브러리가 읽기 전용이라 표본을
  못 만들어** 재지 못했다. 화이트리스트가 더 엄한 것은 설계다 — 레거시 4종을 일부러 들여
  `UnsupportedLegacyLoader` 가 변환 안내를 주게 한다
- **화면 오류는 상태코드를 유지한 채 서버가 HTML 로 준다** — `HX-Request` 헤더가 있으면
  `_error.html` 조각, 없으면 지금 그대로 JSON 이다. `_STATUS_BY_EXCEPTION` 의 상태코드와
  `user_message` 는 **한 자도 안 바뀐다**. htmx 가 4xx/5xx 에 swap 을 안 하는 것은
  `htmx:beforeSwap` 한 줄로 뒤집는다. **오류를 200 으로 돌려주는 안은 기각** — 그것이
  `frontend.md` 1회차가 스트리밍을 기각한 바로 그 자리다(아래 "안 하기로 한 것")
- **415·413 도 같은 규칙을 탄다** — 이 둘은 `RagPipelineError` 가 아니라 `HTTPException`
  이라(`_reject_unsupported_extension()` · `_save_upload()` 가 던진다) FastAPI 기본 핸들러로
  간다. `StarletteHTTPException` 핸들러를 신설해 같은 헤더 규칙을 태우고, `HX-Request` 가
  없으면 기본 핸들러에 위임한다. **`RagPipelineError` 쪽만 고치면 업로드가 제일 자주 낼
  오류가 여전히 안 보인다**
- **오류 자리는 각자다** — 업로드는 사이드바 `#upload-error`, 질의는 `#messages` 말풍선.
  질의 쪽은 composer 가 이미 `#messages`·`beforeend` 라 **배선 변경 0** 이다.
  ~~성공 204 는 본문이 비어 있어 그 자리를 저절로 비운다~~ → **6회차에서 거짓으로 판명.**
  htmx 는 204 를 "빈 값으로 덮으라"가 아니라 **"할 일 없음"으로 읽고 swap 을 건너뛴다**
  (`htmx.min.js` 의 `responseHandling` 에 `{code:"204", swap:false}`). 실패한 뒤 정상 파일로
  재시도해 성공해도 빨간 줄이 남았다. **지우는 것은 `hx-on::after-request` 의 한 줄**이고,
  204 자체는 4회차 계약대로 그대로 둔다
- **원본은 `original_files/` 에 남고, 이름은 계산된다** — 저장 이름은 원본 파일명의 Windows
  예약 문자를 치환하고 **`sha256(document_id)` 앞 6자를 항상 붙인 것**이다. 항상 붙이므로
  `document_id` 만 있으면 계산돼 **매핑 파일이 필요 없고**(두 번째 진실이 안 생긴다),
  치환 뒤 `보고서:1.pdf` 와 `보고서_1.pdf` 가 같은 이름이 되는 충돌도 원천봉쇄된다.
  **저장은 색인이 성공한 뒤**다 — 실패한 원본이 남으면 목록에 없는 파일이 쌓인다.
  **`POST /documents/upload`(파싱 전용)는 저장하지 않는다**
- **원문 서빙은 두 자리에서 열린다** — 사이드바 문서 이름과 답변의 출처 태그다. 뒤엣것은
  **PDF 일 때만 `#page=N`** 을 붙인다(HWPX 쪽 수가 부풀어 있다는 함정이 그대로 걸리고, HWPX 는
  브라우저가 못 연다). 브라우저가 렌더하는 형식만 `inline` 이고 나머지는 `attachment` 이며
  `X-Content-Type-Options: nosniff` 를 붙인다 — **`.svg`·`.html` 이 화이트리스트에 없어**
  같은 오리진 스크립트 경로는 이미 닫혀 있다
- **삭제는 색인과 원본을 함께 지운다** — 보이는 것과 실제가 어긋나지 않게 하는 쪽을 골랐다.
  응답은 색인과 같은 **204 + `HX-Trigger`** 이고, **BM25 는 되돌리고 답변 캐시는 안 건드린다**.
  삭제에서는 캐시 쪽 근거가 더 강하다 — 조회 시점에 근거 청크를 되짚으므로 **청크가 사라지면
  자동으로 걸러진다**
- **색인 진행 표시는 두 구간이고 잴 수 있는 것이 다르다** — 업로드(브라우저→서버)는
  `htmx:xhr:progress` 의 `loaded/total` 이 **실제 수치**라 퍼센트를 쓰고, 색인(파싱·임베딩·
  저장)은 `index_document()` 안에서 한 번에 돌아 **밖으로 나오는 신호가 없어** 무한
  애니메이션 + 경과 시간이다. **퍼센트를 지어내지 않는다** — 이 저장소가 임계값을 지어내지
  않는 것과 같은 잣대다. 여기서만 `.pending` 규약을 벗어난다(문구 한 줄에는 퍼센트를 실을
  자리가 없다). 답변 말풍선 쪽은 그대로 `.pending` 이다
- **업로드 폼은 성공·실패 무관하게 리셋한다** — composer 가 `successful` 일 때만 하는 것과
  **의도한 비대칭**이다. 파일 input 은 안 비우면 `change` 가 안 떠서 같은 파일 재시도도
  성공 뒤 재색인도 막히고, 질문 글자는 실패 때 남아야 한다. 같은 파일 두 줄이 반대로 도는
  것이라 주석과 테스트로 잠근다


아래 여덟은 `frontend.md` 1회차가 정한 것을 2회차에 옮겨온 것이다.

- **`/query` 는 dense 검색 + LLM 답변 1회** — hybrid·reranker·rewriter 루프·semantic cache
  전부 제외. 근거: `retrieval/` 에 `.py` 가 0개이고 저것들은 `검색-생성.md` 가 Phase 4~5 와
  제일 마지막 단계로 예약해 둔 것이다. 화면이 그 설계를 먼저 굳히면 안 된다
- **`store` 는 uvicorn startup 싱글턴** — 근거: qdrant 로컬 파일 모드가 저장 디렉터리에
  배타 잠금을 건다. `검색-생성.md` 가 *"질의 엔드포인트가 store 를 언제 잡고 언제 놓는지"* 로
  열어둔 미결이 여기서 닫힌다
- **문서 목록은 `QdrantStore` 에만 scroll 을 더해 얻는다. `VectorStore` Protocol 은 안 넓힌다**
  — 근거: `검색-생성.md` 확정(*"새 추상화를 안 만든다 / 두 번째 구현체가 실재할 때"*)과 같은
  잣대. backend 가 구체 타입을 한 군데서 알게 되는 것이 대가다
- **답변 생성은 gpt-4.1-mini 실호출** — `rag_pipeline/generation/` 에 첫 코드가 생긴다.
  모킹 이음새는 모듈 레벨 `_make_client()`(`image_vision`·`table_vision` 과 같은 형태),
  실패는 예외(`GenerationError`) — embedding·indexing 과 같은 이유로 내려갈 폴백 층이 없다
- **환각은 프롬프트로만 막는다. 점수 임계값을 지어내지 않는다** — 근거: Dot 점수 분포를
  아직 안 쟀다. 이 저장소의 임계값은 분포의 틈에서 나오는데 그 틈이 어디인지 모른다.
  대신 `RetrievedChunk.dense_score` 가 이미 실려 나가므로 **분포는 저절로 모인다**
- **스트리밍은 안 한다** — 근거: SSE 는 첫 바이트에 이미 200 을 보낸 뒤라
  `main.py:_STATUS_BY_EXCEPTION` 이 **못 잡는다**(색인 없음 503 · 임베딩 실패 503 이 전부
  사라진다). 그 매핑은 이 저장소가 명시적으로 지키는 계약이다
- **배선은 `rag_pipeline` 에 세 번째 진입점** — `retrieve()`(검색) + `answer_question()`(조립).
  **`store` 와 `embedder` 를 인자로 받는다** — `index_document()` 처럼 스스로 열면 싱글턴과
  충돌한다. `evaluation/run_eval.py` 의 임시 배선도 `retrieve()` 를 부르게 바꿔 배선이
  실제로 한 곳이 되게 한다
- **`Answer.sources` 의 원소는 `RetrievedChunk`** — 근거: `schemas/retrieval.py` 에 이미 있고
  `text`·`metadata`(`page`·`page_end`·`heading_path`·`source_name`)·`dense_score: float|None`
  까지 갖췄다. 새 dict 를 만들면 같은 것의 세 번째 진실이 된다

8회차(재색인 API)에서 더해진 것.

- **재색인은 새 결합이 아니라 입구다** — `index_document()` 가 이미
  `delete_by_document_id(파일명)` → `upsert()` 로 돌고 7회차가 원본을 디스크에 남겼다.
  없던 것은 둘을 잇는 라우트 하나뿐이다. 7회차가 삭제 API 의 미룸을 푼 논리와 같다
- **`POST /documents/{document_id}/reindex` — 문서 하나 · 동기** — 근거: 전량은 문서 10건에
  분 단위라 타임아웃이고, 백그라운드로 돌리면 작업 레지스트리·수명·동시성이 딸려 오며
  **오류가 응답이 아니라 폴링으로 오게 돼 5회차 오류 표시 배선이 바뀐다**. 그 덩어리는
  「진짜 단계별 색인 진행률」 미결과 같은 것이다
- **`index_document(original_name=key)` — 디스크 이름이 아니라 문서 키를 넘긴다** — 디스크
  이름은 `안내서__a3f9c2.pdf` 라 그대로 넘기면 `document_id` 가 **새로 생겨** `delete` 가 옛
  청크를 못 찾고 문서가 두 벌이 된다. 이 라우트에서 제일 조용하게 틀릴 수 있는 자리다
- **`store=` 주입은 여기서도 필수** — 색인 라우트와 같은 이유다(안 넘기면 같은 uvicorn 안에서
  자기 자신과 배타 잠금으로 부딪힌다)
- **`_keep_original()` 을 안 부른다** — 파일이 이미 제자리라 `shutil.move` 가 자기 자신을
  덮는다. 임시 파일이 없어 `finally: unlink` 도 없다
- **답변 캐시는 비운다(`clear()`)** — **삭제 라우트와 갈리는 자리다.** 근거 대조는 *"딛고 선
  청크가 사라지거나 바뀌었다"* 를 id + 텍스트 해시로 잡지만, 파서를 고쳐 **청크가 늘어난**
  경우는 옛 답의 근거가 멀쩡해 **원리적으로 못 잡는다** — 색인 라우트가 비우는 이유(새 문서
  유입)와 같은 축이다
- **그림자 색인도 함께 다시 한다** — 근거: 색인 라우트가 둘을 함께 채우고 삭제 라우트가 둘을
  함께 지운다. 한쪽만 다시 하면 두 컬렉션이 서로 다른 청크를 들어 `overlap.py` 가 경고하는
  상태가 되는데 **그 어긋남은 화면에 안 보인다**(배지는 *있다/없다* 만 본다). 대가는 그림자가
  켜져 있을 때의 OpenAI 재과금이다
- **원본이 없는 문서는 목록에 실어 버튼을 감춘다** — `_mark_shadow_gaps()` 옆에 같은 모양으로
  `original_missing` 을 단다. 404 안내는 눌러야 알 수 있고 6회차에 사용자가 물고 온 것이
  그 종류다
- **URL 의 `{document_id}` 는 불투명 문자열** — 7회차 원본 서빙과 같다. 나중에 명시적 id 로
  옮겨도 공개 URL 이 안 깨진다. 파일명 키를 유지하면서 뒷길을 열어두는 값이 이것뿐이다

## 안 하기로 한 것

- **CORS 미들웨어** — 이유: 화면을 이 앱이 직접 서빙하므로 브라우저가 교차 출처 요청을
  아예 안 낸다. 오리진만 비우는 것이 아니라 **미들웨어째 걷어냈다** — 합법값이 하나뿐인
  설정은 죽은 설정이고, 값이 없는 미들웨어는 죽은 코드다(`embedding.provider`·`distance`·
  `qdrant_url` 을 안 만든 잣대와 같다) / **다시 볼 조건**: 별도 오리진에서 도는 프런트나
  이 API 의 외부 소비자가 실재할 때
- **인증·레이트리밋** — 이유: 밖에 노출될 전제가 아직 없다. qdrant 가 로컬 파일 모드라
  디렉터리 배타 잠금으로 한 프로세스만 쓰고, 프론트를 같은 uvicorn 이 서빙하며,
  `.env` 의 키를 로컬에서 읽는다. **감수 사항이 7회차에 커졌다**: 노출되는 순간 유료 LLM 을
  부르는 `/query` 에 더해 **올린 원본 파일까지 통째로 열린다**(`GET /documents/{id}/original`).
  경로 탈출은 막았지만 그것과 인증은 다른 축이다 / **다시 볼 조건**: 이 앱이 `127.0.0.1` 밖으로
  나가거나 사용자가 둘 이상이 될 때
- **원본 디스크 상한·자동 정리** — 이유: 기본값을 지금 지어내야 한다. 이 저장소가 근거 없는
  값으로 두 번 덴 자리다(이미지 표시 크기 50pt 탐침값 · 쪽 경계 헤더 반복 휴리스틱). 그리고
  자동 삭제는 **사용자가 모르는 사이 원문만 사라지는 상태**(색인은 남아 목록엔 보인다)를
  만든다. 대신 사이드바에 **총 용량을 보여주고** 삭제 버튼을 손에 쥐어 준다 /
  **다시 볼 조건**: 실제로 디스크가 걸릴 때
- **원본을 해시 이름으로만 저장** — 이유: 폴더를 손으로 열었을 때 16진수뿐이라 무슨 파일인지
  알 수 없다. 접미사만 해시로 두면 사람이 읽는 것과 충돌 회피를 둘 다 얻는다
- **부딪힐 때만 해시 접미사** — 이유: 평소엔 이름이 깨끗하지만 **이름이 `document_id` 만으로
  계산되지 않게 되어**, "이 문서의 원본이 어느 파일인가"를 알려면 디스크를 뒤지거나 매핑을
  들여야 한다 — 두 번째 진실이다
- **삭제를 *색인 해제* 와 *완전 삭제* 두 버튼으로 가르기** — 이유: 문서 상태가 셋(색인됨 /
  원본만 / 없음)이 되어 사이드바 한 줄이 감당을 못 한다 / **다시 볼 조건**: 재색인 API 가
  생겨 *"원본만 있는 상태"* 가 실제로 쓸모를 가질 때
- **원본을 재색인용으로만 보관(되돌려주는 라우트 없이)** — 이유: 제일 싸지만 **소비자가
  없다**. 3회차가 CORS 를 미들웨어째 걷어낸 잣대와 같다 — 쓰는 곳 없는 기능은 죽은 코드다
- **`frontend.md` 항목을 이 파일로 *복사*** — 이유: 같은 문장이 두 곳에 살면 한쪽만
  고쳐진다. `문서-최신성.md` 6회차가 "삼중으로 적힌 계약"을 걷어낸 것과 같은 형태다.
  2회차에 하는 것은 복사가 아니라 **이동**이다
- **`frontend.md` 를 `backend.md` 로 개명** — 이유: 확정된 1회차의 제목이 바뀐다. 그리고
  프론트 고유 결정 2줄(HTMX 스택 · 히스토리 자리만 두기)은 그쪽에 남아야 한다
- **`frontend.md` 1회차 본문(라운드 표 · 대조에서 갈린 셋)을 옮기기** — 이유: 그 세션에서
  실제로 일어난 일의 기록이라 옮기면 거짓이 된다. **2회차에도 안 옮긴다.** 옮기는 것은
  맨 위 세 절뿐이다
- **문서 삭제 API 를 문서 레지스트리보다 먼저 만들기** — 이유: 위 미결. 지우는 대상이
  파일명인 채로 굳는다
- **`DECISIONS.md` 같은 넷째 기록 폴더** — 이유: `frontend.md` 1회차가 이미 기각했다.
  이 저장소의 ADR 자리는 `plan_log/<기능>.md` 다. **저쪽 항목은 2회차에 옮기지 않고 지웠다**
  — 같은 기각이 두 곳에 살면 한쪽만 고쳐진다
- **오류를 200 으로 돌려주기** — 이유: htmx 가 그냥 swap 해서 JS 도 확장도 필요 없지만,
  `_STATUS_BY_EXCEPTION` 계약을 **화면 경로만 우회**하게 된다. `frontend.md` 1회차가
  스트리밍을 기각한 이유(*"SSE 는 첫 바이트에 200 을 보낸 뒤라 그 매핑이 못 잡는다"*)와
  같은 자리다 — 같은 실수를 다른 문으로 다시 하는 것이다 / **다시 볼 조건**: 없음
- **htmx `response-targets` 확장 벤더링** — 이유: `hx-target-4xx`/`hx-target-5xx` 로 자리를
  요소마다 선언할 수 있어 JS 가 0줄이지만, 얻는 것이 `htmx:beforeSwap` 한 줄과 같은데
  벤더 파일이 하나 늘고 htmx 2.x 와 버전을 맞춰 둬야 한다 / **다시 볼 조건**: 오류 자리가
  요소마다 갈라져 전역 리스너 하나로 감당이 안 될 때
- **라우트별 try/except 로 HTML 을 돌려주기** — 이유: 415 를 던지는
  `_reject_unsupported_extension()` 이 `try` **이전**이라 거기까지 감싸야 하고, 상태코드를
  알려면 `main.py` 사설 `_status_for()` 를 끌어써 **매핑의 두 번째 진실**이 생긴다.
  새 화면 라우트가 생기면 빠뜨려도 아무 에러가 안 난다
- **415·413 을 `RagPipelineError`(`UnsupportedFormatError`·`FileTooLargeError`)로 바꾸기** —
  이유: 핸들러 하나로 모이는 것은 맞지만 backend 의 **1차 검증이 rag_pipeline 예외를 던지게**
  되어, 3회차가 실측으로 닫은 *"확장자 화이트리스트가 backend 에 있는 것"* 경계가 흐려진다.
  기존 테스트의 응답 본문도 같이 움직인다
- **공용 오류 배너 하나 / 업로드 오류도 `#messages` 로** — 이유: 사이드바에서 누른 결과가
  본문 위에 뜨고, 질의 실패가 대화 흐름에서 빠져 **어느 질문이 실패했는지**가 안 남는다.
  업로드 폼의 `hx-target` 을 `#messages` 로 두면 성공 204 도 거기로 간다


아래 여섯도 `frontend.md` 에서 옮겨왔다. **"위 “확정된 것”" 을 가리키는 둘은 그 확정 항목도
함께 왔으므로 여기서도 풀린다.**

- **SSE 토큰 스트리밍** — 이유: 위 "확정된 것"(예외 매핑이 죽는다) / 다시 볼 조건:

  스트림 안의 에러 이벤트 규약을 함께 정하면 된다
- **점수 임계값으로 근거 없음을 판정** — 이유: 지금 그 값을 지어내야 한다. 이 저장소가 두 번
  데인 형태다(이미지 표시 크기 50pt 탐침값 · 쪽 경계 헤더 반복 휴리스틱) /
  다시 볼 조건: `dense_score` 가 쌓여 관련·무관 청크의 분포에 틈이 보일 때
- **인용 문장을 코드로 대조해 검증** — 이유: PDF 가 한국어 낱말 사이 공백을 잃어
  문자열 대조가 까다롭다(`evaluation/scoring.py:squash()` 가 있는 이유). 첫 회차에 넣기엔
  부품이 많다 / 다시 볼 조건: 프롬프트만으로 환각이 실제로 안 잡힐 때
- **`Answer.sources` 를 `SearchResult` 로** — 이유: `retrieval.py` docstring 이
  *"dense 만 쓸 때는 SearchResult 로 충분하다"* 고 말하는 것은 **검색 내부의 이야기**이고,
  프론트가 렌더하는 **공개 계약**은 축이 다르다. hybrid 가 붙는 순간 반환 타입이 바뀌어

## 5회차 — 2026-08-24 · 조용한 실패를 닫는다 (업로드·질의 오류 표시)

**물은 것**

사용자가 *"실제 파일 업로드 했는데 어디에 저장돼? 그리고 색인 실패에 대한 내용도
확인해보자"* 로 물었다. 앞엣것은 확인이고, 뒤엣것이 4회차가 새로 연 미결이다.

**확인이 먼저 답을 냈다 — 원본 파일은 아무 데도 안 남는다**

`_save_upload()` 가 `%TEMP%\upload-<uuid32>-<확장자>` 로 쓰고 `finally` 가 지운다. 실측으로
`%TEMP%` 의 `upload-` 잔여물 **0개**라 정리가 실제로 돌고 있다. 남는 것은
`.qdrant/collection/documents_text-embedding-3-small_default/storage.sqlite` 하나뿐이고,
읽기 전용으로 열어 보니 **480 point · 6문서**였다(그중 둘이 이번에 버튼으로 올린 것 —
버튼이 실제로 동작한다는 첫 실증이다. 4회차는 "브라우저에서 안 눌러봤다"로 끝났다).
payload 는 `document_id`(원본 파일명 NFC) · `chunk_id` · `text` · `metadata` 뿐이라
**원본 바이트를 되찾을 길이 없다.** 결함이 아니라 미결 *"문서 목록의 진짜 출처(rDBMS)"* 가
서 있는 자리다.

**미결이 연 문장보다 범위가 넓었다 — 코드에서 셋을 더 찾았다**

| 찾은 것 | 기록에 있었나 |
|---|---|
| 색인 실패가 화면에서 조용하다 | 4회차 미결 — **있었다** |
| `/query` 도 똑같이 조용하다 — composer 의 `hx-on::after-request` 가 `successful` 일 때만 분기한다 | **없었다** |
| 업로드 input 을 안 비워 **같은 파일을 다시 못 올린다** — 실패 재시도도, 성공 뒤 재색인도 | **없었다** |
| 415·413 은 `RagPipelineError` 가 아니라 `HTTPException` 이라 **다른 핸들러**를 탄다 | **없었다** |

**마지막 것이 이번 회차에서 제일 조용한 종류다** — `RagPipelineError` 핸들러만 고치면
테스트는 전부 통과하는데, 업로드가 실제로 제일 자주 낼 오류인 415(확장자)가 **여전히 안
보인다.** 4회차의 `qdrant_path` 항목과 같은 형태다: 에러가 안 나는 채로 목적만 못 이룬다.

**고른 것과 버린 것**

| 갈림길 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 범위 | **업로드 표시 + 질의 표시 + 업로드 리셋** | 업로드만 — `/query` 에 같은 결함이 남고 오류 자리를 두 번 설계하게 된다(4회차가 "목록의 두 번째 진실"을 피한 잣대와 반대) |
| 전달 | **상태코드 유지 + 서버가 HTML + `htmx:beforeSwap` 한 줄** | 오류를 200 으로 · `response-targets` 확장 벤더링 — 위 "안 하기로 한 것" |
| 자리 | **각자 자리**(사이드바 `#upload-error` · `#messages` 말풍선) | 공용 배너 · 둘 다 `#messages` — 위 "안 하기로 한 것" |
| 가르는 축 | **`HX-Request` 헤더** | 라우트별 try/except · 415·413 을 `RagPipelineError` 로 — 위 "안 하기로 한 것" |

**전달 방식이 스트리밍 기각과 같은 자리에서 갈렸다**

오류를 200 으로 돌려주면 htmx 가 그냥 swap 해서 JS 도 확장도 필요 없다. 제일 싸 보인다.
그런데 `frontend.md` 1회차가 스트리밍을 기각한 이유가 정확히 *"SSE 는 첫 바이트에 200 을
보낸 뒤라 `_STATUS_BY_EXCEPTION` 이 못 잡는다"* 였다. **같은 실수를 다른 문으로 다시 하는
것**이다. 그 계약을 지키기로 하면 htmx 가 swap 을 안 하므로 어디선가 한 번 뒤집어야 하고,
그 자리가 `htmx:beforeSwap` 한 줄이다.

**`HX-Request` 를 고른 이유는 415 다**

라우트별 try/except 가 더 좁아 보였다 — `/documents/index` 는 이미 204 + `HX-Trigger` 로
*"htmx 전용"* 임을 인정한 라우트다. 그런데 415 를 던지는 `_reject_unsupported_extension()` 이
`try` **이전**이라 거기까지 감싸야 하고, 상태코드를 알려면 `main.py` 사설 `_status_for()` 를
끌어써 **매핑의 두 번째 진실**이 생긴다. 헤더 축이면 두 핸들러가 같은 규칙 한 줄을 나눠 쓴다.

**공짜로 얻는 성질 하나**

업로드 폼에 `hx-target="#upload-error" hx-swap="innerHTML"` 을 주면 **성공 204 는 본문이
비어 있어 그 자리를 저절로 비운다.** 재시도가 성공했을 때 옛 오류를 지우는 코드를 따로 짤
필요가 없다 — 조각을 안 그리는 응답이 곧 지우는 응답이다.

**reset 비대칭은 의도다**

업로드 폼은 성공·실패 무관하게 `this.reset()`, composer 는 `successful` 일 때만.
**파일 input 은 안 비우면 재시도 자체가 막히고, 질문 글자는 실패 때 남아야 한다.** 같은
파일 안에서 두 줄이 반대로 도는 것이라, 나중에 "일관성"을 이유로 한쪽에 맞추면 조용히
망가진다. 주석과 테스트로 잠근다.

**남은 질문**

위 "미결". `RetrievalError` · `top_k` · 문서 삭제 API · 답변 품질의 자[尺] · 문서 목록의
진짜 출처 · `GenerationError` 재시도는 그대로다. **이번에는 미결이 늘지 않는다** — 새로
찾은 셋을 전부 이번 범위 안에서 닫기 때문이다.

다만 **검증에 구멍이 하나 남는다.** 업로드 실패는 `.exe` 를 올리면 415 가 자연히 나서
과금 없이 브라우저에서 실증되지만(4회차가 못 한 자리다), **질의 실패는 `.env` 에 키가 있어
자연히 안 난다.** 라우트 테스트가 계약을 덮되 화면에서 본 것은 아니다 — 못 잰 것으로
남긴다.

## 6회차 — 2026-08-24 · 사용자가 눌러 보고 둘을 물고 왔다

**물은 것**

5회차를 구현한 뒤 사용자가 실제로 브라우저에서 눌렀다. `.exe` 두 번은 기대대로 빨간 줄이
떴는데 **그 다음 정상 `.hwpx` 를 올려 색인이 성공했는데도 빨간 줄이 안 사라졌다.** 그리고
*"큰 파일을 넣었는데 색인이 되는 건지 프로세스가 멈춘 건지 구별이 안 간다"* 며 진행률 바를
요청했다.

**5회차의 기록 한 줄이 거짓이었다**

5회차에 *"공짜로 얻는 성질"* 이라며 적은 것 — **성공 204 는 본문이 비어 있어 그 자리를
저절로 비운다** — 이 틀렸다. htmx 는 204 를 빈 본문으로 취급하지 않고 **swap 을 통째로
건너뛴다**(`htmx.min.js`: `responseHandling:[{code:"204",swap:false},…]`).

**테스트가 못 잡은 이유가 이번 회차의 교훈이다.** 그것을 잠갔다고 믿은
`test_successful_index_sends_empty_body_that_clears_the_slot` 은 **서버가 204 와 빈 본문을
보낸다**만 확인한다. 이름만 화면 동작을 재는 것처럼 지어져 있었다. 4회차 세션이
`test_index_leaves_the_answer_cache_alone` 을 두고 *"이름과 달리 객체 동일성만 잰다"* 고
경고했던 것과 **정확히 같은 함정에 다음 회차가 빠졌다.**

이름을 `test_successful_index_returns_204_with_no_body` 로 고치고, 화면 쪽은
`test_success_clears_the_error_slot` 이 따로 잠근다. 그리고 **htmx 의 204 동작 자체를**
`test_vendored_htmx_never_swaps_on_204` 로 못 박았다 — 벤더링한 파일을 갈아끼웠을 때 이
전제가 바뀌면 거기서 알린다.

| 갈림길 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 성공 시 오류 지우기 | **`hx-on::after-request` 에서 `successful` 일 때 한 줄** | 204 → 200 으로 낮추기 — 저절로 비워지지만 4회차가 정한 응답 계약을 바꾸고 `test_index_returns_204_with_refresh_trigger` 가 깨진다 / `HX-Trigger: documents-changed` 를 듣게 하기 — 그 이벤트는 "목록이 바뀌었다"는 뜻이라 오류 지우기에 쓰면 우연한 결합이 된다 |

**진행률 — 잴 수 있는 것과 없는 것을 갈랐다**

`index_document()` 는 파싱→청킹→임베딩→저장을 **한 번의 블로킹 호출**로 돈다. backend 는 그
안을 못 본다. 밖에서 추론할 것도 없다 — `upsert` 는 맨 끝에 한 번이라 0%에서 100%로 튄다.

| 구간 | 표시 | 근거 |
|---|---|---|
| 업로드 (브라우저→서버) | **실제 퍼센트** | `htmx:xhr:progress` 의 `loaded`/`total` — 진짜 수치다 |
| 색인 (파싱·임베딩·저장) | 무한 애니메이션 + **경과 시간** | 신호가 없다. **퍼센트를 지어내지 않는다** |

**버린 것 셋.** *가짜 퍼센트*(경과 시간으로 바를 채우기) — 이 저장소가 임계값을 지어내지
않는 것과 같은 잣대이고, 멈춘 색인도 부드럽게 100%까지 간다. *backend 가 단계를 직접
부르기* — `index_document()` 를 복제해 **색인 순서의 두 번째 진실**이 생긴다. *업로드 바만
넣기* — localhost 라 큰 파일도 순식간에 100%가 되고 정작 긴 구간은 그대로 깜깜하다.

**`.pending` 규약을 여기서만 벗어났다** — 4회차가 새 방식을 안 들인 판단은 옳았지만, 그
규약은 문구 한 줄을 켜고 끄는 것이라 **퍼센트를 실을 자리가 없다.** 답변 말풍선 쪽은 그대로다.

**htmx 이벤트 하나가 두 번 흐른다** — htmx 는 `progress`·`loadend` 를 `xhr` 과 `xhr.upload`
**둘 다**에 건다. 그래서 `sending` 플래그로 앞 구간만 퍼센트로 읽는다. `loaded >= total`
로만 판정하면 파일이 아주 작아 `progress` 가 한 번도 안 뜨는 경우를 놓쳐, 첫 `loadend`
에서도 색인 구간으로 넘어가게 했다.

**남은 질문**

위 "미결"에 하나가 늘었다 — **진짜 단계별 색인 진행률**(백그라운드 + 폴링, `rag_pipeline`
공개 API 변경). 사용자가 `rag_pipeline` 을 안 건드리는 선을 그었고, 경과 시간만으로 충분한지
**먼저 써 보고 정하기로 했다.**

## 7회차 — 2026-08-24 · 원본을 보관하고, 목록을 줄일 수단을 준다

**물은 것**

6회차 뒤 사용자가 *"색인된 건 `finally` 로 삭제된다면서 사이드바엔 그대로 있는데 버그냐"* 고
물었다. **버그가 아니다** — 지워지는 것은 `%TEMP%` 의 원본 바이트이고 목록에 뜨는 것은
qdrant payload 라 애초에 다른 물건이다. 그런데 그것을 확인하는 과정에서 **실제 한계 둘**이
드러났고, 사용자가 그 둘을 그대로 요청으로 냈다: `original_files/` 에 원본 보관 · 삭제 API.

**미뤄둔 근거를 다시 재보니 약해져 있었다**

이 파일과 `indexing.md` 둘 다 삭제 API 를 *"먼저 만들면 **무엇을 지우는가**가 파일명인 채로
굳는다"* 로 미뤄뒀다. 재보니:

| 미룬 이유 | 다시 재 본 결과 |
|---|---|
| 삭제 대상이 파일명으로 굳는다 | **이미 굳어 있다** — `index_document()` 가 재색인에서 `delete_by_document_id(파일명)` 을 이미 부른다. 같은 이름으로 다시 올리면 옛 청크가 **지금도** 지워진다 |
| 문서 레지스트리가 먼저 | 부품은 이미 있다 — `delete_by_document_id()` 가 `VectorStore` **Protocol 에 있다**(`list_documents()` 와 달리 `getattr` 로 봐줄 필요도 없다) |
| 굳는 위험 | **URL 의 `{document_id}` 하나만 남는다.** 처음부터 불투명 문자열로 받으면 나중에 명시적 id 로 옮겨도 안 깨진다 |

**즉 삭제 API 는 새 결합을 만드는 것이 아니라 있는 것을 노출한다.** 미룸을 푼 근거가 이것이다.

**순서는 사용자의 요청과 반대였다**

원본을 저장하면 **삭제가 지울 대상이 둘**이 된다. 그래서 ②(삭제)가 아니라 ①(저장)이 먼저
정해져야 계약이 선다. 면담을 그 순서로 돌렸다.

**고른 것과 버린 것 (2라운드)**

| 갈림길 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| 원본 용도 | **화면에서 원문 열기** | 재색인용 보관만 · 그냥 보관 — 위 "안 하기로 한 것" |
| 삭제 범위 | **색인 + 원본 둘 다** | 색인만 · 버튼 둘로 가르기 — 위 "안 하기로 한 것" |
| 저장 이름 | **안전문자 치환 + 항상 해시 접미사** | 해시만 · 부딪힐 때만 접미사 — 위 "안 하기로 한 것" |
| 열리는 자리 | **사이드바 + 출처 태그** | 한쪽만 — 두 맥락이 다르다("이 문서 뭐였지" vs "이 근거 진짜야?") |
| 디스크 | **안 막고 총 용량만 보여준다** | 상한 설정 — 위 "안 하기로 한 것" |

**충돌 하나를 면담 중에 찾아 되돌렸다**

사용자가 *"원본 이름 + 안전문자 치환"* 을 골랐는데, 그대로 두면 `보고서:1.pdf` 와
`보고서_1.pdf` 가 디스크에서 **같은 이름**이 된다. 색인은 둘을 다른 문서로 아는데 원문은
하나뿐이라 **한쪽의 "원문 보기"가 남의 파일을 조용히 보여준다.** 에러가 안 나므로 알아챌
길이 없다 — 이 저장소가 제일 싫어하는 형태라 라운드를 하나 더 돌아 해시 접미사로 닫았다.

**서빙의 위험은 화이트리스트가 이미 절반을 막고 있었다**

*"사용자가 올린 임의 파일을 그대로 되돌려준다"* 의 고전적 위험은 같은 오리진에서 스크립트가
도는 것인데, `SUPPORTED_EXTENSIONS` 에 **`.svg` 도 `.html` 도 없다.** 남는 것은 경로 탈출과
Content-Type 이고 둘 다 정석으로 막는다. Content-Type 을 확장자로 정하는 것도 근거가 있다 —
3회차가 화이트리스트 22종을 `detect_format()` 에 왕복시켜 **잰 것 18 · 어긋남 0** 으로
이중 검증이 어긋나지 않음을 실측했다.

**공짜로 얻은 것 하나**

`RetrievedChunk.metadata` 에 `page` 가 **이미** 실려 있고 브라우저 PDF 뷰어는 `#page=N` 을
해석한다. 그래서 출처 태그에서 **원문 그 쪽으로 바로** 갈 수 있다. 새로 나를 배관이 없다.
다만 **PDF 한정**이다 — HWPX 쪽 수 부풀림(AI가이드 97쪽 vs 실제 28쪽)이 그대로 걸리는데,
HWPX 는 어차피 브라우저가 못 열어 실질 제약이 아니다.

**남은 질문**

위 "미결". **삭제는 닫혔고 재색인과 `document_id` 명시화가 남았다** — 7회차로 원본이 남게 돼
재색인의 **전제는 생겼고**, 남은 것은 *"무엇을 기준으로 같은 문서라 볼 것인가"* 다. 그리고
**인증 미룸의 감수 사항이 커졌다** — 노출되면 유료 `/query` 에 더해 올린 원본까지 열린다.

## 8회차 — 2026-08-26 · 재색인 입구를 내고, 버전 축을 갈라 미룬다

**물은 것**

사용자가 진행률 보고를 받은 뒤 *"evaluator 지금 구현중인데 병행하기 좋은 단계 있을까?
기능 겹치지 않아서 같은 파일 동시 작업이 제일 적을것같은"* 을 물었다. 그래서 이 회차의 첫
판단은 설계가 아니라 **파일 교집합**이었다.

**병행 대상을 파일로 골랐다**

다른 세션(`implement-evaluator-phase4`)의 계획 파일을 읽어 그쪽이 물 파일을 확정했다 —
`rag_pipeline/{config,query}.py` · `tests/conftest.py` · `schemas/answer.py` ·
`generation/evaluate.py` · `.env.example` · `evaluation/{verdicts,config}.py` ·
`tests/{generation,evaluation}/**` · `tests/test_query.py`. 그리고 그 계획서가
*"backend 는 이번에 안 건드린다"* 로 못 박고 있었다. **backend 트랙의 교집합이 0** 이라
여기가 답이었다.

**병행 금지로 가른 것이 더 값어치가 있다** — 특히 splitter 의 PDF 제목 유실 고치기는
**파일이 하나도 안 겹치는데** 청킹이 바뀌면 Evaluator 가 지금 만들려는 분모(`h-ce-gpu`)가
통째로 갈린다. 파일 충돌이 아니라 자[尺] 충돌이라 **diff 에 안 보인다.** `hybrid.py` 개명은
import 로, 긍정 20건 도장은 `reviewed_hash` 로 각각 그쪽을 깬다.

**선택지 — `document_id` 를 이번에 명시화하나**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| **재색인만 · 파일명 유지** | 새 결합 없이 입구만 낸다 | 동명 충돌이 감수 사항으로 남는다 | `index_document()` 가 이미 파일명으로 delete→upsert 를 한다. 7회차가 삭제에서 쓴 논리와 같다 |
| 내용 해시로 덮어쓰기 감지 | 조용히 덮이는 것만 없앤다 | payload 스키마가 바뀌어 **전량 재색인이 사실상 전제**가 된다 | 같은 라운드에서 고른 *"문서 하나·동기"* 와 정면으로 부딪힌다 |
| 명시적 id + 레지스트리 | 가장 정확 | rDBMS + 기존 색인·원본 이름·공개 URL 마이그레이션 | `indexing.md` 가 *"레지스트리가 실제로 들어올 때"* 로 미뤄둔 자리다 |

**사용자가 되짚은 것과 그 답**

*"버전관리를 고려하면 2번이고 유효함까지 고려하면 3번이지?"* — **절반만 맞다.**
2번은 버전 *감지* 이지 관리가 아니다(어느 쪽이 새 판인지 모르고 되돌릴 수도 없다).
3번은 담을 *자리* 를 만드는 것이지 유효성 자체가 아니다. 그리고 **둘 다 같은 병목에
걸린다** — 판이 여럿이거나 유효/폐지가 섞이면 검색이 그것을 걸러야 하는데
`search(filters=)` 가 *일부러* 없다. 그것을 만들면 `retrieval/` 을 건드려 **이 트랙을 고른
이유(병행 안전)가 사라진다.** 그래서 별도 트랙으로 갈라 미결에 세웠다.
