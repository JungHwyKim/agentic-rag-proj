# 하네스 확장 설계

상태: 확정 (1회차)
관련 기록: task_log/... (구현 후 채운다)

## 확정된 것

지금까지 확정된 결정만 모은다. **여기만 읽으면 현재 설계를 안다.**

- **에이전트는 담당 영역에 코드가 있을 때만 두껍게 쓴다** — `ingestion-specialist` 는
  두껍게(loader·cleaner 가 실재한다), `retrieval-specialist`·`rag-evaluator` 는 얇게 쓰고
  `plan-log` 로 라우팅한다. 근거: 이 저장소가 세 곳에서 같은 말을 못박아 뒀다 —
  `references/next-stages.md`("추측으로 만든 체크리스트로 리뷰하면 없는 규칙을 근거로 멀쩡한
  설계를 지적하게 된다"), `plan-log` 2단계, `code_reviewer_plan.md` §0
- **에이전트는 판정 기준을 복제하지 않고 `rag-code-review/references/` 를 읽는다** —
  `code-reviewer` 가 이미 쓰는 위임 구조다. 규칙이 두 벌로 갈라지면 한쪽이 조용히 낡는다
  (실측: 2회차에서 `references/cleaner.md` 가 실제로 그렇게 낡았다 — `문서-최신성.md` 2회차)
- **자동 테스트 훅은 PostToolUse 에 단다** — 취향이 아니라 강제다. `tests/hooks/
  test_hook_wiring.py:test_pretooluse_covers_both_shells` 가 PreToolUse 의 **모든** matcher 에
  `re.fullmatch(matcher, "Bash")` 와 `"PowerShell"` 을 요구하므로, `matcher: "Write|Edit"` 를
  PreToolUse 에 추가하면 그 테스트가 깨지고 → `pre_commit_check` 가 커밋을 막는다
- **테스트 범위를 두 층으로 가른다** — PostToolUse 는 변경 경로에 대응하는 **영역별** 테스트만,
  Stop 은 **전체 1회**. 근거: 기본 스위트가 210개인데 합성 문서 생성(docx/pptx/xlsx/pdf/hwpx)과
  OCR 이 섞여 있어 매 편집마다 전체를 돌리기엔 무겁다. 실제 소요는 구현 후 실측해 `task_log` 에
  남긴다 — **지금은 "무겁다"까지만 아는 상태이고 초 단위 수치는 재지 않았다**
- **매핑 누락을 테스트로 강제한다** — 새 단계 디렉터리가 생겼는데 매핑 표에 안 넣으면 그 단계는
  자동 테스트가 한 번도 안 도는데 아무 에러도 안 난다. 근거: `paid_test_check.py` 가 남긴 교훈이
  정확히 이것이다 — `-m integration` 금지가 CLAUDE.md·스킬 3개·에이전트까지 5곳에 적혀 있었지만
  *"전부 모델을 향한 설득"* 이었고, 그래서 훅으로 못박았다. 산문은 보조로만 둔다
- **훅 스크립트 하나가 두 이벤트를 처리한다** — `plan_log_check.py` 가 이미 3이벤트를
  `payload["hook_event_name"]` 로 분기하는 선례다. 파일이 늘면 배선 테스트 표면도 함께 는다
- **Skill 은 반복이 입증된 절차에만 만든다** — `document-ingestion` 은
  `task_log/routing-diff-시행령개정안.txt` 가 그 절차를 손으로 한 기록이라 근거가 있다.
  `regression-test` 는 기준선 artifact 를 이번에 신설한다

## 미결

다음 논의의 시작점.

- **영역별 테스트 하나가 얼마나 걸리나** — 정하려면: 구현 후 각 매핑 대상을 실제로 돌려 잰다.
  수십 초가 걸리는 대상이 있으면 그 항목을 더 잘게 쪼갠다. 지금은 전체 210개가 무겁다는 것만
  알고 영역별 수치는 없다
- **Stop 훅 3개가 실제로 성가신가** — 정하려면: 한 세션에서 몇 번 막히는지 체감한다.
  `문서-최신성.md` 1회차가 "세 번째 훅은 한 세션의 종료를 세 번 막을 수 있고 얻는 것보다
  성가심이 크다"며 CLAUDE.md 전용 훅을 기각한 전례가 있다. 이번 훅은 *테스트가 실제로 실패할
  때만* 막으므로 평상시 0회일 것으로 보지만, 그건 예상이지 실측이 아니다
- **`regression/baseline.json` 이 fixtures 없는 환경에서 쓸모가 있나** — 정하려면: `tests/fixtures/`
  가 gitignore 라 다른 클론에는 없다. baseline 은 커밋되는데 대조할 입력이 없는 상태가 된다.
  실제로 그 상황을 만나면 정한다

## 안 하기로 한 것

- **`retrieval-specialist`·`rag-evaluator` 를 지금 상세히 쓰기** — 이유: `rag_pipeline/ingestion/`
  아래 `retriever/`·`reranker/` 디렉터리가 없고 `pipeline.py` 예약 주석에도 없다(`split`/`embed`/
  `index` 뿐). 적재 경로 밖이라 **진입점 자체가 미설계**다. 청크 전략·하이브리드 가중치·리랭커
  선택을 지금 쓰면 대부분 폐기되고, 폐기된 안이 모범 사례로 남는 병(`문서-최신성.md` 3회차)을
  또 앓는다 / 다시 볼 조건: 해당 디렉터리에 코드가 생기고 `plan_log/` 에 설계가 확정되면
- **`retrieval-evaluation`·`rag-evaluation` 스킬** — 이유: 평가 대상 자체가 없다. retriever 도
  질의 세트도 골든 답변도 지표 계산 코드도 `eval` 마커도 없다. `plan_log/평가-세트.md` 가
  **"확정된 것: 없다"** 로 열려 있고 순서 문제(세트가 먼저냐 splitter 가 먼저냐)조차 안 정해졌다
  / 다시 볼 조건: `평가-세트.md` 의 미결 첫 항목이 정해지고 질의 세트가 실재하면
- **`debug-rag` 스킬** — 이유: `rag-code-review`(계약 위반을 본다)와 일반 디버깅 사이 경계가
  모호하다. 스킬은 반복되는 절차에만 만든다는 기준을 통과 못 한다 / 다시 볼 조건: 같은 디버깅
  절차를 손으로 두 번 이상 반복한 기록이 `task_log/` 에 쌓이면
- **PreToolUse 에 자동 테스트 훅 달기** — 이유: `test_pretooluse_covers_both_shells` 가 깨지고
  커밋이 막힌다 / 다시 볼 조건: 없음. 테스트가 옳다 — matcher 가 한쪽 셸만 덮으면 도구를 바꾸는
  것만으로 검사가 통째로 우회된다
- **매 편집마다 전체 pytest** — 이유: 210개에 합성 문서 생성과 OCR 이 섞여 있고, 한 작업에서
  파일을 여러 번 고치면 같은 테스트를 반복해서 돌린다 / 다시 볼 조건: 영역별 실측이 전체와
  별 차이 없게 나오면 (그때는 가르는 것 자체가 무의미하다)
- **Integration 테스트 자동 실행** — 이유: `paid_test_check.py` 를 우회해야 하고, LlamaParse/
  OpenAI 에 **사용자 승인 없이 과금**된다. 기존 훅 둘(`paid_test_check`·`pre_commit_check`)이
  일관되게 안 돌리는 방침을 지킨다 / 다시 볼 조건: 없음
- **매핑 누락을 CLAUDE.md 산문으로만 막기** — 이유: 위 "확정된 것" 의 `paid_test_check` 교훈.
  5곳에 적어도 설득일 뿐이었다 / 다시 볼 조건: 없음
- **훅 스크립트를 이벤트마다 하나씩** — 이유: `plan_log_check.py` 선례. 파일이 늘면
  `test_every_hook_script_is_wired`·`test_hook_module_imports` 가 검사할 표면도 함께 는다
  / 다시 볼 조건: 한 스크립트의 이벤트 분기가 읽기 어려워지면

## 1회차 — 2026-08-16 · 하네스에 "만드는 쪽"과 "자동 검증"이 없다

**물은 것**

기존 `.claude/` 구조와 기능은 유지하면서, RAG 개발을 지원하는 Subagent / Skill / Hook 을
충돌 없이 추가하고 싶다. 제안된 것은 Subagent 3종(`ingestion-specialist`·
`retrieval-specialist`·`rag-evaluator`), Skill 5종(`document-ingestion`·`retrieval-evaluation`·
`rag-evaluation`·`regression-test`·`debug-rag`), Hook 4종(단위 테스트·integration 테스트·
종료 전 검증·regression).

**먼저 읽은 것**

지어내기 전에 지금 무엇이 있고 무엇이 없는지부터 조사했다.

| 영역 | 상태 |
|---|---|
| `rag_pipeline/ingestion/` 아래 실제 디렉터리 | **`loader/`·`cleaner/` 둘뿐** |
| `pipeline.py` 예약 주석 | `split`/`embed`/`index` — **retriever·evaluation 은 여기에도 없다** |
| `plan_log/` | `문서-최신성.md`(확정) · `평가-세트.md`(**확정된 것 없음**) |
| 평가 자산 | 질의 세트·골든 답변·지표 코드·`eval` 마커 **전부 없음** |
| `.claude/` | 에이전트 1 · 스킬 3 · 훅 5 · `tests/hooks/` 가 배선을 테스트로 못박음 |

**하네스가 스스로 강제하는 제약이 설계를 상당히 결정했다**

`tests/hooks/test_hook_wiring.py` 는 기본 `pytest -q` 에 포함되고, `pre_commit_check` 가
커밋 시 그걸 돌린다. **즉 이 테스트를 깨는 설계는 커밋 자체가 불가능하다.**

| 테스트 | 설계에 미친 영향 |
|---|---|
| `test_pretooluse_covers_both_shells` | 자동 테스트 훅을 **PreToolUse 에 못 단다** → PostToolUse |
| `test_every_hook_script_is_wired` | 새 훅은 반드시 settings.json 배선 |
| `test_wired_scripts_exist` | command 경로를 슬래시 `.claude/hooks/<이름>.py` 로 |
| `test_hook_module_imports` | `if __name__ == "__main__":` 가드 필수 |

`task_log_check.py` docstring 이 경고하는 것도 그대로 받는다 — Stop 훅에서 종료코드 2 는
대화를 이어가므로 `claim_session()` 세션당 1회 장치가 없으면 **영원히 안 끝난다.**

**세션 중에 제약 하나를 직접 겪었다**

이 세션의 Stop 훅이 "소스를 고쳤는데 task_log 가 없다"며 막았는데, 잡힌 변경은 **이전 세션이
남긴 미커밋 cleaner 작업**이었다. 훅은 워킹트리 diff 만 보므로 누가 고쳤는지 구분하지 못한다.
새 테스트 훅도 같은 성질을 갖는다 — 이건 결함이라기보다 *"판단이 서지 않으면 막지 않는다"*
는 기존 관통 규약과 맞바꾼 것이고, 이번 설계도 같은 쪽을 택했다(매핑에 없으면 조용히 통과).

**선택지 — 미구현 영역을 어느 깊이로 쓸까**

| 안 | 장점 | 단점 | 이 프로젝트에서의 근거 |
|---|---|---|---|
| A. 얇게 — 확실한 계약만 쓰고 `plan-log` 로 라우팅 | 지금 참인 것만 남는다. 코드가 생기면 살을 붙인다 | 당장 해주는 일이 적다 | `next-stages.md` 가 이미 이 방식이다. cleaner 가 실제로 그 경로를 밟아 `references/cleaner.md` 로 승격됐다 |
| B. 전체 설계 — 지금 상세히 | 즉시 쓸 수 있어 보인다 | 코드를 짤 때 대부분 틀린 것으로 드러난다 | `문서-최신성.md` 3회차가 정확히 이 병을 진단했다 — `plan-log` 가 폐기된 안(임계값 20%)을 모범 사례로 가르치고 있었다 |
| C. 지금은 안 만든다 | 틀릴 일이 없다 | 나중에 만들 조건과 레시피가 아무 데도 안 남아 다시 처음부터 조사한다 | — |

**고른 것과 이유**

**A.** 이 저장소가 세 곳에서 같은 말을 못박아 뒀고(`next-stages.md`·`plan-log`·
`code_reviewer_plan.md` §0), cleaner 승격이 그 경로가 실제로 작동한다는 증거다.

기각:
- **B** — `문서-최신성.md` 3회차가 이미 대가를 치른 병이다. 폐기된 안이 모범 사례로 남는다
- **C** — 조건과 레시피를 남기면 다시 조사할 필요가 없다. C 의 유일한 장점은 A 도 갖는다

**Skill 5종 중 2종만 고른 이유**

사용자 원칙("Skill 은 반복되는 절차에만")을 그대로 적용했다.

- `document-ingestion` — **채택.** `task_log/routing-diff-시행령개정안.txt` 가 이 절차를 손으로
  한 기록이다. 반복 절차임이 입증돼 있다
- `regression-test` — **채택.** 기준선 artifact 는 이번에 신설한다
- `retrieval-evaluation`·`rag-evaluation` — **보류.** `평가-세트.md` 가 "확정된 것: 없다" 로
  열려 있다. 평가할 대상이 없는데 평가 스킬을 만들면 빈 껍데기다
- `debug-rag` — **기각.** 반복이 입증되지 않았고 `rag-code-review` 와 경계가 모호하다

보류·기각한 셋은 **승격 조건을 위 "안 하기로 한 것" 에 적어뒀다.** 조건이 차면 그때 만든다 —
사용자가 직접 쓸 일은 없다.

**사용자에게 물은 것**

기술로 답이 안 나오고 우선순위로 갈리는 넷을 물었다. 답은 전부 위 확정 사항에 반영했다 —
미구현 영역은 얇게 / 테스트는 영역별 + 종료 시 전체 / Skill 은 2종만 / integration 자동 실행
금지 유지.

논의 도중 사용자가 **"새 ingestion 단계가 추가될 때 테스트 매핑도 함께 추가한다"** 를 규칙으로
넣자고 제안했다. 방향은 맞지만 산문으로만 넣으면 `paid_test_check` 가 이미 겪은 실패
(*"5곳에 적어도 전부 설득일 뿐"*)를 반복하므로, **테스트로 강제**하는 쪽으로 바꿔 받았다.
형태는 기존 배선 테스트의 짝을 그대로 본뜬다.

| 기존 (`test_hook_wiring.py`) | 신설 |
|---|---|
| `test_every_hook_script_is_wired` | `test_every_stage_is_mapped` |
| `test_wired_scripts_exist` | `test_mapped_targets_exist` |
| `LIBRARY_MODULES` | `UNMAPPED_BY_DESIGN` |

`UNMAPPED_BY_DESIGN` 에는 `config.py`·`schemas/**`·`exceptions.py` 가 들어간다 — 전 영역에
영향을 주므로 부분 실행이 무의미하고 Stop 게이트가 전체로 잡는 게 맞다.

**남은 질문**

위 "미결" 전부. 특히 영역별 테스트 소요 실측이 첫 번째다 — 그 수치가 나와야 매핑을 더 잘게
쪼갤지 정할 수 있다.
