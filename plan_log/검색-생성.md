# 검색·생성 설계

상태: 논의 중 (2회차)
관련 기록: task_log/... (구현 후 채운다)

`평가-세트.md` 와 짝이다 — 이 단계의 모든 수치 결정이 저쪽 세트 위에서만 정해진다.

## 확정된 것

- **Dense 는 기존 qdrant 를 그대로 쓴다** — 근거: `QdrantStore.search()` 가 이미 있고 컬렉션
  정체성(모델·차원)·Dot 거리·NFC 문서 키가 전부 실측 근거를 달고 서 있다(`indexing.md`).
  ChromaDB 로 갈아타면 그 근거를 처음부터 다시 세워야 한다
- **retriever 는 `VectorStore` Protocol 만 받는다** — 근거: `next-stages.md` 가 이미 계약으로
  적어둔 것이고, 사용자가 "언제든 다른 저장소를 쓸 수 있게" 를 요구했다. **새 추상화를 안
  만든다** — `base.py` 의 Protocol 에 `search()` 가 이미 있다. `provider` 설정은 두 번째
  구현체가 실재할 때 더한다(`embedding.provider` 를 안 만든 것과 같은 잣대)
- **BM25 는 저장소 밖 별도 인덱스** — 근거: qdrant sparse 벡터로 얹으면 Protocol 과 컬렉션
  스키마를 고쳐야 하고 방금 정한 저장소 중립이 깨진다(Chroma 에는 sparse 가 없다)
- **dense·BM25 병합은 RRF** — 근거: Dot 점수와 BM25 점수는 단위가 달라 그대로 못 섞는다.
  RRF 는 순위만 써서 정규화가 필요 없다
- **Reranker 는 로컬 우선 + `Reranker` Protocol + `get_reranker()`** — 근거: "기본 pytest 는
  키 없이 전부 통과" 를 지키는 것이 로컬뿐이다. 상용은 비교 실험 때 두 번째 구현체로 온다
- **평가 세트를 Phase 0 으로 올린다. 정답은 LLM 초안 + 사람 검수** — 근거: 사용자가 가져온
  스펙의 Phase 2·4·10 DoD 셋이 전부 라벨링 QA셋을 요구하는데 세트가 없다. 상세는 `평가-세트.md` 2회차
- **Vision·LlamaParse 를 tool 목록에서 뺀다** — 근거: 아래 "안 하기로 한 것"
- **`RetrievedChunk` 는 `SearchResult` 에 경로별 점수를 얹은 것이고 `metadata` 를 버리지 않는다**
  — 근거: `metadata` 에 `page`·`heading_path`·`page_end` 가 들어 있어 **출처 인용의 유일한
  근거**다. 스펙의 `content`/`source` 두 필드만 남기면 Context Builder·Generator 가 인용을 못 만든다.
  이름도 `text` 로 맞춘다(저장소 전체가 쓰는 이름)
- **점수 필드는 `float | None`** — 근거: 한쪽 경로에만 걸린 청크가 실재한다. required float 로
  두고 `0.0` 을 채우면 **"점수가 0"과 "후보가 아님"이 안 갈린다.** PDF 표에서 `extract()` 만
  보면 병합 셀과 빈 칸이 안 갈리던 것과 같은 종류다
- **진행은 단계별 + 단계마다 사용자 승인** — 사용자 요청. 첫 승인 단위는 Phase 0 하나다

2회차(Phase 2 나머지 절반, hybrid)에서 더해진 것.

- **BM25 인덱스는 질의 시점에 store 를 전량 읽어 짓는다** — `VectorStore` Protocol 에
  `iter_chunks()` 를 더한다. 색인 시점에 별도 파일로 두면 삭제·재색인을 두 곳에 해야 하고
  한쪽만 갱신되면 **조용히 낡는다.** `list_documents()` 를 일부러 Protocol 에 안 올린 판단과
  갈리는 이유는 **소비자**다 — backend 는 구체 타입을 알아도 되지만 retriever 는
  *"`VectorStore` Protocol 만 받는다"* 가 1회차 확정이다
- **BM25 인덱스를 `store`·`embedder` 와 같이 인자로 받는다** —
  `retrieve(query, *, store, embedder, top_k, bm25=None, config=None)`.
  `query.py` 가 이미 *"수명을 부르는 쪽이 정한다"* 로 서 있어 같은 대우를 한다.
  **`use_bm25` 설정은 안 만든다** — 인덱스를 안 넘기는 것이 곧 끄는 스위치라 죽은 설정이 된다
- **경고는 `Bm25Index.warnings` 에 쌓는다** — 반환 계약(`-> list[RetrievedChunk]`)을 안 바꾼다.
  호출부가 인덱스를 들고 있으니 밖에서 읽히고, 이것은 `dense.py` 가 embedder 를 인자로 받는
  이유(*"여기서 만들면 그 값을 밖에서 못 본다"*)와 같은 자리다
- **한국어 토크나이저는 한글 bigram + 영문·숫자 낱말** — `시행령은` 과 `시행령` 이
  `시행`·`행령` 을 공유해 조사 문제에 **구조적으로** 강하고, 가르는 것이 문자 종류라는
  **이분법**이라 분포의 틈을 고를 필요가 없다. 쪽 경계를 *한글을 가진 블록이 0개인가* 로
  고른 것과 같은 모양이다. 새 의존성이 없다
- **BM25 구현은 `rank_bm25`(BM25Okapi)** — 직접 짜서 IDF·길이 정규화가 틀리면 그 오차가
  *"hybrid 가 효과 없다"* 로 읽혀 **판정 자체를 오염시킨다.** 토큰 수를 근사하지 않고
  `tiktoken` 을 넣은 것과 같은 판단이다. `k1`·`b` 는 라이브러리 기본값이고 설정으로 안 연다
- **병합은 RRF. 두 경로에서 `candidate_k=50` 씩 뽑고 `rrf_k=60`** — 앞은 **임시값**이고
  `schemas/retrieval.py` docstring 이 이미 쓴 수라 새 수를 지어내지 않았다. 뒤는 RRF 원 논문
  값이다. **두 경로를 같은 수로** 뽑는 이유: 한쪽만 길면 RRF 가 긴 쪽에 유리해져 기울기가
  숫자가 아니라 구조에서 나오고 원인 추적이 어렵다. 합류 열쇠는 저장소가 주는 point id
- **BM25 가 못 돌면 dense-only 로 내려가고 경고를 남긴다** — 로더의 *빈 결과 + warn* 규약이
  성립하는 조건은 **내려갈 층이 있는가**이고 여기는 있다(dense 가 독립적으로 돌고 기준선도
  그것이다). embedding·indexing 이 예외인 이유는 그 층이 없어서였다. **dense 를 먼저 부른다** —
  BM25 를 먼저 하면 "컬렉션이 없다"가 경고로 삼켜져 색인 전 상태가 *"BM25 만 실패했네"* 로 보인다
- **`RetrievalConfig` 는 `IngestConfig.retrieval` lazy 프로퍼티** — `GenerationConfig` 가 이미
  그 모양이고 `answer_question()` 이 `cfg.generation.generation_top_k` 를 읽고 있다.
  `top_k` 는 여기 안 넣는다(셋째 출처를 만들면 어느 것이 이겼는지 호출부마다 달라진다)
- **hybrid 이득은 무조건이 아니다 — 질의 낱말이 정답과 겹칠 때만 난다.**
  겹침(`|질의∩정답|/|질의|`) 3분위로 가르면 이득이 **±0.000 / +0.300 / +0.250** 이고,
  겹침 0 구간은 순위 `↑6 ↓5` 로 **방향 자체가 없다**(중립이 아니라 잡음이다 — 정답과 안
  겹쳐도 다른 낱말이 겹치는 청크가 후보로 들어와 맞는 결과를 밀어낸다). 겹치는 40건은
  `↑24 ↓0` 으로 나빠진 것이 없다. **자기 말로만 묻는 사용자에게 hybrid 는 dense 와 같고,
  그 구간은 BM25 로 못 고친다.** 두 포맷 다 못 잡던 6건과 평평했던 후보 폭 표면이 전부
  이것으로 설명된다(`verify_log/2026-08-24-어휘겹침.md`, 이쪽에서 독립 재현)
- **겹침 0 구간에서 나빠지는 기전은 "BM25 후보의 침입" 이 아니라 "RRF 의 동등 투표권" 이다.**
  밀어낸 후보 35개 중 BM25 에만 걸린 것은 1개뿐이고, 나머지는 dense 후보에도 이미 있었다.
  정답이 BM25 에서 dense 보다 낮고(`ai-04` dense #9 vs BM25 #25) RRF 가 두 순위를 반씩
  섞어 뒤집힌다. **RRF 는 점수를 버려 BM25 가 얼마나 확신하는지를 못 본다** — 단위가 달라
  못 섞는다는 이유로 고른 성질의 대가가 여기서 드러난다. `candidate_k` 로는 못 고친다
  (추월자가 대부분 상위권이다). **이번에 안 고친다** — 재판정 조건: 겹침 0 구간이 실제
  사용자 질의에서 얼마나 흔한지를 먼저 재야 한다
- **Phase 2 첫 측정 완료 — hybrid 가 dense 를 전 지표에서 이겼다.** `hit@10` 0.4833 →
  **0.6667** · `MRR` 0.2530 → **0.3875** · `nDCG@10` 0.3145 → **0.4609**. 모든 k 축(@1~@20)과
  **모든 그룹**이 같은 방향이고, 질의별로 이김 30 · 짐 5 · 그대로 25 다. dense 재현은
  60/60 무변화라 기준선이 안 움직였다. 실제 청구 $0.00(캐시).
  전문은 `verify_log/2026-08-23-hybrid-측정.md`
- **세트를 갈아 끼울 수 있다** — `run_eval --qa-set <path>`. 기본은 `qa_set.jsonl` 이고,
  다른 세트를 줄 때는 **기준선 대조를 건너뛴다**(`query_id` 가 안 겹쳐 전 항목이 "없음→N"으로
  나오는데 그것은 회귀가 아니라 애초에 다른 질문들이다). 사람 질의 세트가 첫 소비자다
- **평가는 `--hybrid` 플래그 하나** — `evaluation/baseline.json` 이 dense 로 굳어 있어
  `--save-baseline` 없이 돌리면 기존 `compare_to_baseline()` 의 **질의별 승·패·무가 곧
  hybrid vs dense** 다. 1회차가 정한 *수치 하나로 승패를 안 본다* 가 장치로 이미 서 있다
- **`EVAL_SETTINGS` 에 `retrieval` 을 더한다** — 빠지면 같은 명령이 머신마다 다른 수치를 내고
  그 모듈이 존재하는 이유가 무너진다

## 미결

- **LangGraph 를 정말 쓸지** — 정하려면: Checkpoint A 를 돌려보고 while 루프로 부족한지 본다.
  체크포인팅·스트리밍·병렬 분기가 필요해지면 값을 하지만, 지금 흐름은 while 로 표현된다.
  `AgentState` 를 pydantic 으로 굳혀두고 나중에 LangGraph 로 가면 reducer·`Annotated` 때문에
  다시 쓰게 되므로, 쓸 거면 Phase 7 **전에** 정해야 한다
- **agent 코드의 거처** — `retrieval/` · `generation/` · 새 `agent/` 중 어디. 정하려면:
  Router 가 무엇에 의존하는지가 Phase 8 에서 드러난다
- **질의당 LLM 호출 상한과 카운터** — 정하려면: Phase 4~5 에서 Evaluator·Rewriter 가 실제로
  몇 번 도는지 본다. 적재의 `max_vision_calls_per_doc` 에 대응하는 자리인데 **축이 다르다** —
  적재는 문서당 1회로 끝나고 질의는 반복된다
- **Evaluator·Rewriter 의 실패 계약** — 정하려면: 폴백 층이 있는지 본다. 로더 쪽은 빈 결과 +
  `warn()`(내려갈 층이 있어서), embedding·indexing 은 예외(없어서)다. Evaluator 가 실패했을 때
  "충분"으로 떨어뜨리면 나쁜 context 로 답을 만들고, "불충분"으로 떨어뜨리면 재시도를 태운다.
  **둘 다 조용히 나빠서** 세 번째 답이 필요할 수 있다
- ~~**질의 엔드포인트가 `store` 를 언제 잡고 언제 놓는지**~~ — **닫혔다**(2회차). backend 가
  `lifespan` 에서 하나 열어 앱 수명 내내 들고, 스크립트는 `with` 로 쓴다. `query.py` docstring
  이 *"여기서 열지 않는 것이 곧 계약"* 으로 못 박았다
- ~~**`RetrievalError` 를 새로 만들지**~~ — **안 만든다**(2회차). BM25 실패가 예외가 아니라
  폴백이고, dense 가 던지는 `IndexingError` 는 이미 503 으로 매핑돼 있다
- **`candidate_k`·`rrf_k` 의 근거 있는 값** — **첫 측정은 끝났지만 값은 여전히 임시다.**
  50·60 **한 점**만 쟀고 다른 값과 안 견줬다. 정하려면: 몇 점을 더 재서 곡선을 본다
- **hybrid 의 +18%p 중 얼마가 LLM 어휘 편향인가** — **절반은 갈렸다.** 사용자가 문서를 안 보고
  쓴 질의 48건(정답 있는 21건, `evaluation/qa_set_human.jsonl`)에서 **이득이 그대로 남는다**
  (`hit@10` +0.2381 · LLM 세트 +0.1833). **질의 어투를 통째로 바꿔도 안 사라진다.**
  남은 절반: **정답 span 을 모델이 질의 낱말로 검색해 골랐다** — 정답 쪽이 질의 어휘로
  기울었을 수 있다. 정하려면: 사람이 질의와 정답을 **모두** 지정한다.
  **사용자 전수 검수 뒤 다시 쟀고 결론이 그대로다** — 정답 자리를 4건 옮기고(AI 가이드가
  전부 목차 줄이었다) span 12건을 온전한 문장으로 늘린 수정본에서 이득 `hit@10` +0.2000.
  세트를 그만큼 흔들었는데 방향이 안 바뀐 것이 이 결론의 근거다.
  또 표본 20건이라 질의 1개가 5%p 여서 두 세트의 이득 차이 자체는 못 가른다
  (`verify_log/2026-08-23-사람질의-편향.md`)
- **진 질의 5건 중 넷이 AI 가이드 그룹** — 우연인지 그 문서의 성질인지 미확인
- **bigram 이 형태소 분석기보다 나은가** — 정하려면: 비교 6번. 세트가 있어 잴 수는 있지만
  Phase 2 범위를 키우지 않으려고 한 변수씩 간다
- **backend 가 색인하게 될 때 BM25 를 어떻게 무효화하나** — 지금은 문제가 아니다(backend 가
  `index_document()` 를 안 불러 서버가 사는 동안 컬렉션이 안 바뀐다). 정하려면:
  `plan_log/backend.md` 의 qdrant 잠금 미결이 닫힐 때 함께
- **`top_k` 기본값과 relevance threshold** — 지금 5는 임시값이다. **baseline 이 생겼다**
  (`hit@10` 0.483 · `MRR` 0.253 · `verify_log/2026-08-22-검색평가-세트.md`). 맞힌 것의 순위가
  대부분 앞쪽이라 **`top_k` 를 키우는 것보다 후보 자체를 늘리는 쪽**(hybrid)이 먼저다
- **`DESIGN.md`·`IMPLEMENTATION_SPEC.md` 의 거처** — 지금 설계 논의가 `rag_pipeline/retrieval/`
  와 `plan_log/` 두 곳에 산다. 정하려면: 두 문서를 정정한 뒤 겹치는 부분이 얼마나 남는지 본다

## 다음 승인 단위

Phase 1(계약)과 Phase 2 의 dense 절반은 **이미 구현돼 있다** — `schemas/retrieval.py` ·
`retrieval/dense.py` · 그 위의 `generation/` · `query.py` · backend 채팅 화면.
지금 승인 단위는 **Phase 2 의 나머지 절반**(BM25 + RRF)이고, 첫 판정은 **비교 1번**
(dense vs hybrid)이다. 기준선은 `evaluation/baseline.json` 이 들고 있다.

그다음은 **Phase 3**(리랭커). 순서 지표(`nDCG@5`·`precision@3`)로 재야 하고
`recall@후보수` 로 재면 차이가 정의상 0 이다.

## 안 하기로 한 것

- **ChromaDB** — 이유: qdrant 로 이미 색인하고 그 선택에 실측 근거가 여럿 달려 있다. 갈아타면
  indexing 단계가 고아가 되거나 같은 청크가 두 저장소에 남아 진실이 둘이 된다 /
  다시 볼 조건: qdrant 로컬 파일 모드의 배타 잠금이 실제 운영에서 막힐 때. 그때도 먼저 보는
  것은 qdrant 서버 모드다
- **Vision·LlamaParse 를 질의 시점 tool 로 두는 것** — 이유: **넣을 입력이 없다.** `blob` 은
  splitter→records→chunk 경로에 한 번도 안 나오고(확인함), 바이트는 로더 경계에서 죽는다.
  질의 시점에 남는 것은 청크 텍스트뿐이다. DESIGN 6장이 "LlamaParse 의 소속"을 미결로 열어둔
  것이 이걸로 닫힌다 — **적재 시점 전처리**다. 덧붙여 LlamaParse 는 표를 HTML 로 돌려줘
  기본값이 꺼져 있다(`표-경로.md` 1회차) / 다시 볼 조건: 청크 payload 에 blob 참조를 싣고
  "이 청크의 원본 이미지를 다시 본다"가 실제 요구로 나오면. 그때도 tool 이 아니라 **재적재
  트리거**에 가깝다
- **`RetrievedChunk` 에 `content`·`source` 만 두는 것** — 이유: 위 "확정된 것"
- **Phase 1 에서 `AgentState` 까지 한꺼번에 정의하는 것** — 이유: 소비자가 Phase 7 에 있고,
  LangGraph 를 쓸지가 미결이라 지금 굳히면 state 모양을 두 번 쓰게 된다. 스펙의 Pre-Lock A 가
  "필드 설계만 Phase 1 에 확정"한 취지는 살리되 **코드로 굳히는 것은 미룬다** /
  다시 볼 조건: LangGraph 여부가 정해지면
- **`search(filters=...)`** — `indexing.md` 1회차에서 이미 닫힌 것을 되풀이하지 않는다.
  쓸 축이 `document_id` 뿐이고 `page` 는 HWPX 쪽 수 함정 때문에 못 쓴다

2회차에서 떨어진 것.

- **`HybridRetriever` 클래스 + `get_retriever()` 팩토리** — 이유: **이번 계획의 첫 판이 그것이었고
  트리와 대조하다 뒤집혔다.** 그 사이 저장소가 `store`·`embedder` 를 인자로 받는 함수 쪽으로
  갔고, 클래스를 세우면 `answer_question()`·`run_eval`·`routes/query.py` 가 **두 가지 호출
  규약**을 동시에 알게 된다 / 다시 볼 조건: 검색 쪽이 상태를 여럿 들게 되면
- **색인 시점에 BM25 를 별도 파일로 저장** — 이유: `index_document()` 가 두 번째 sink 를 갖고
  삭제·재색인을 두 곳에 해야 한다. 한쪽만 갱신되면 조용히 낡는다 / 다시 볼 조건: 코퍼스가
  질의 시점 빌드가 부담될 만큼 커지면
- **모듈 레벨 인덱스 캐시(컬렉션 이름 키)** — 이유: 숨은 전역 상태라 테스트가 서로의 상태를
  물려받는다. `offline_config` 가 `tmp_path` 로 저장 위치를 가르는 이유와 정면으로 부딪힌다
- **별도 최상위 `RetrievalConfig`** — 이유: 처음엔 *`IngestConfig` 는 이름 그대로 적재 설정*
  이라고 봤는데, 그 사이 `GenerationConfig` 가 lazy 프로퍼티로 들어가 **생성도 적재 객체 안에
  산다.** 검색만 밖에 두면 이유 없는 비대칭이 된다
- **`use_bm25` 설정** — 이유: 인덱스를 안 넘기는 것이 곧 끄는 스위치다. 합법값이 하나뿐인
  죽은 설정이 된다(`embedding.provider` 를 안 만든 것과 같은 잣대)
- **`RetrievalResult(chunks, warnings)` 타입 신설** — 이유: Phase 3~5 의 계약이 전부 따라
  바뀐다. 스펙이 Phase 1 을 맨 앞에 둔 취지가 이 계약 고정이었다
- **공백 분리 + 조사 절단 규칙** — 이유: **조사 목록을 우리가 지어내야 한다.** 임계값을 분포의
  틈에서만 고르던 태도와 어긋나고, 틀려도 아무도 안 알려준다
- **전부 bigram / 낱말 + 한글 bigram 둘 다** — 이유: 앞은 긴 영단어가 잡음 bigram 을 만들고,
  뒤는 토큰이 두 배가 되며 **길이 정규화가 섞여** BM25 의 문서 길이 보정이 뭘 재는지 불분명해진다
- **BM25 를 직접 구현** — 이유: IDF·길이 정규화 오차가 *"hybrid 가 효과 없다"* 로 읽힌다 /
  다시 볼 조건: `rank_bm25` 가 못 쓰게 되면
- **`top_k * 배수` 로 후보 폭** — 이유: 비교할 때 두 변수가 함께 움직인다
- **BM25 만 전량 채점하고 dense 만 상한** — 이유: 두 경로의 순위 길이가 달라져 RRF 가 긴 쪽에
  유리해진다. 기울기가 숫자가 아니라 구조에서 나와 원인 추적이 어렵다
- **`--retriever dense|hybrid` 로 갈래별 기준선** — 이유: `baseline.json` 이 둘로 늘고
  **갈래 간 비교가 오히려 어려워진다**(서로 다른 파일을 손으로 대조해야 한다). 기존
  `compare_to_baseline()` 이 dense 기준선에 대고 재는 것이 곧 원하는 비교다

## 1회차 — 2026-08-22 · 사용자 설계서 검토와 Phase 0 확정

**물은 것**

사용자가 `rag_pipeline/retrieval/` 에 `DESIGN.md`·`IMPLEMENTATION_SPEC.md` 를 두고
"읽어보고 설계 방향 제안해줘" 를 요청했다. 11-phase 구성에 Pre-Lock A/B/C 를 붙인 핸드오프용
스펙이다.

**드러난 것 — 뼈대는 옳고 어긋난 곳이 여섯이다**

뼈대 셋은 이 저장소가 실제로 밟은 길과 같은 모양이라 그대로 둔다 — retrieval loop 을 agent
레이어 **앞에** 독립적으로 세우는 것, LangGraph 를 **마지막에** 묶는 것, Checkpoint A 로 retry
cap 을 그래프 전에 따로 검증하는 것.

어긋난 여섯:

1. **Dense 를 ChromaDB 로 전제** — qdrant 로 이미 색인한다
2. **Phase 2·4·10 의 DoD 셋이 라벨링 QA셋을 요구** — `평가-세트.md` 는 1회차이고 확정된 것이
   없다. 그대로 두면 세 DoD 가 전부 미충족으로 남는다
3. **Vision·LlamaParse 를 질의 시점 tool 로 전제** — 넣을 입력이 없다(위 "안 하기로 한 것")
4. **`RetrievedChunk` 가 `metadata` 를 버린다** — Phase 9·10 이 출처 인용을 못 만든다
5. **질의 시점 비용 규약이 없다** — 질문 하나에 Router + Evaluator×3 + Rewriter×3 + Generator
   ≈ 최대 10회 LLM 호출인데 상한도 카운터도 없다. 적재는 문서당 1회라 상한·캐시가 다 있는데
   **반복되는 쪽에 없다**
6. **하네스 다섯이 빠졌다** — `RetrievalConfig` · `.env.example` · `offline_config` ·
   `auto_test_check.py` 매핑 · `_STATUS_BY_EXCEPTION`. `indexing.md` 1회차에서 같은 다섯이
   빠졌던 자리다

곁가지로 위치 어긋남 둘: `schema.py` 를 `retrieval/` 안에 두는 것(기존은 `schemas/` 한 곳),
`content` 필드명(저장소 전체가 `text`).

**고른 것과 이유**

전부 사용자가 골랐다. 위 "확정된 것" 이 결과다. 특기할 둘:

- **저장소 교체 가능성을 요구했지만 새 추상화는 안 만들었다.** 요구를 받아 적기 전에 계약을
  확인했더니 `VectorStore` Protocol 에 `search()` 가 이미 있었다 — retriever 가 구상 타입을
  안 잡기만 하면 요구가 충족된다. `provider` 설정을 지금 만들면 합법값이 하나뿐인 죽은 설정이
  되므로 미룬다. **비교 실험을 하는 순간 두 번째 구현체가 생기니 그때 설정이 저절로 살아난다**
- **Reranker 도 같은 모양으로 처리했다** — "로컬로 돌리되 추후 상용도" 라는 요구를
  `Reranker` Protocol + 팩토리로 받고 설정은 미뤘다. `get_embedder()` 가 밟은 길 그대로다

**기각한 것**은 위 "안 하기로 한 것" 에 이유와 함께 있다.

**곁다리로 얻은 것 — 비교 실험 설계**

사용자가 "hybrid vs dense / reranker 유무 / reranker 로컬 vs 상용" 비교를 요청해 여섯 축을
세웠다. 여기서 함정 하나를 먼저 박았다 — **리랭커를 `recall@후보수` 로 재면 차이가 정의상
0 이다.** 순서만 바꾸고 집합을 안 바꾸기 때문이다. 순서 지표(`nDCG@5`·`precision@3`·
`recall@5`)로 재야 한다. 이걸 모르고 재면 "리랭커가 효과 없다"는 잘못된 결론이 나온다.

축 여섯 중 하나는 **이미 열려 있던 미결을 닫는다** — 같은 문서의 HWPX 판 45청크 vs PDF 판
104청크 중 어느 쪽이 검색에 유리한지(CLAUDE.md 가 "아직 못 잰다"고 적어둔 자리).
`tests/fixtures/` 에 두 포맷 짝이 4쌍 있어 잴 수 있다.

판정 방법도 함께 정했다 — 수치 하나로 승패를 안 본다. 질의 50개면 `recall@10` 5%p 차이가
질의 2.5개라 잡음과 안 갈린다. **질의별 승/패/무 표**를 같이 내고 진 질의를 직접 읽는다
(표 청크가 지는 것과 본문 청크가 지는 것은 고칠 곳이 다르다). 임계값 12pt 를 관측값이 아니라
분포의 틈에서 고른 것과 같은 태도다.

**남은 질문**

위 "미결" 전부. 다음 회차는 Phase 0 수치가 나온 뒤에 연다 — LangGraph 여부와 질의당 호출
상한은 실제로 몇 번 도는지를 보고 정하는 것이 근거 있다.

## 2회차 — 2026-08-23 · Phase 2 의 나머지 절반(BM25 + RRF)

**물은 것**

사용자가 *"phase1~2 로 넘어가자"* 라고 했다. `IMPLEMENTATION_SPEC.md` 의 Phase 1(계약)과
Phase 2(hybrid retriever)를 실제로 짜자는 뜻이다.

**계획이 한 번 통째로 무효가 됐다 — 그것이 이 회차의 첫 산출이다**

면담 세 라운드를 다 돌고 계획서까지 쓴 뒤에 사용자가 *"변화있는지 확인해줘"* 라고 물었고,
`git log` 를 보니 **그 사이 세션들이 dense 검색 → 생성 → `query.py` 진입점 → backend 채팅
화면까지 이미 세워 놓았다.** 계획이 전제한 것 다섯이 사실이 아니었다.

| 계획이 전제한 것 | 실제 트리 |
|---|---|
| Phase 2 가 통째로 비어 있다 | `retrieval/dense.py:retrieve()` 가 있고 그 위에 세 겹이 얹혔다 |
| `Retriever` Protocol + `get_retriever()` 팩토리 | **클래스가 없다.** 함수이고 `store`·`embedder` 를 인자로 받는다 |
| store 수명이 미결 | **닫혔다.** backend `lifespan` 이 하나 열어 들고 있다 |
| `RetrievalConfig` 를 별도 최상위로 | `GenerationConfig` 가 `IngestConfig` lazy 프로퍼티로 들어와 있다 |
| `run_eval --dense` 를 `--retriever` 로 바꾼다 | `--k` 다축 채점 + `baseline.json` + 승·패·무 대조가 이미 있다 |

**무효가 된 결정 셋이 전부 "인스턴스가 있다"는 같은 전제에 기대 있었다** — 경고를 어디 싣나 ·
BM25 인덱스가 어디 사나 · 설정을 어디 두나. 세 라운드 중 라운드 1의 Q3, 라운드 2의 Q3,
라운드 3의 Q1 이 통째로 다시 열렸다.

**교훈은 "핸드오프는 가설이다"** — 같은 저장소에 세션이 여럿 붙는 동안 `plan_log` 의 미결은
**닫혀 있는데도 열린 것처럼 보인다.** `plan_log/검색-생성.md` 는 1회차에 멈춰 있었는데
실제 구현은 `backend.md`·`frontend.md` 로 갈라져 자랐다. **회차 파일만 읽고 계획하면 안 된다 —
트리를 함께 본다.**

**선택지 — 면담 3라운드 + 재라운드 1**

라운드 1.

| 물음 | 안 | 이 프로젝트에서의 근거 |
|---|---|---|
| BM25 를 누가 채우나 | 질의 시점 store 전량 열거 / 색인 시점 별도 파일 / 평가 러너 안에서만 | 1회차가 *"저장소 밖 별도 인덱스"* 만 정하고 **채우는 주체를 안 정했다.** 둘째는 삭제·재색인이 두 곳이 된다 |

| bigram 경계 | 한글만 bigram / 전부 bigram / 둘 다 | 코퍼스가 공문서라 `AI`·조항 번호가 섞인다 |
| 평가 러너 | 둘 다 Retriever 경유 / `--hybrid` 만 추가 | 비교가 한 코드 경로 안에서 일어나야 한다 |

재라운드(트리 대조 뒤).

| 물음 | 안 | 이 프로젝트에서의 근거 |
|---|---|---|
| 인덱스 자리(인스턴스가 없다) | 인자로 받는다 / `HybridRetriever` 클래스 / 모듈 캐시 | `query.py` 가 이미 *"수명을 부르는 쪽이 정한다"* 로 서 있다 |
| 설정 자리 | `IngestConfig.retrieval` lazy / 별도 최상위 / 인자로만 | **그 사이 `GenerationConfig` 가 lazy 로 들어갔다** — 생성이 적재 객체 안에 사는데 검색만 밖에 두면 비대칭이다 |
| 비교 방법 | `--hybrid` + 기존 기준선 대조 / 갈래별 기준선 | `compare_to_baseline()` 이 이미 승·패·무를 낸다. 기준선이 dense 라 **그것이 곧 원하는 비교**다 |

**고른 것과 이유**

전부 사용자가 골랐고 위 "확정된 것" 이 결과다. 특기할 셋.

- **재라운드에서 사용자가 스스로 앞선 답을 뒤집었다.** 설정 자리를 라운드 1에서 *별도 최상위*
  로 골랐는데, `GenerationConfig` 가 lazy 프로퍼티로 들어와 있다는 사실을 보고 `IngestConfig`
  안으로 옮겼다. **근거가 바뀌어서지 마음이 바뀐 것이 아니다** — 계획이 근거로 삼은 트리가
  틀렸던 것이고, 같은 잣대(비대칭을 안 만든다)가 반대 답을 냈다
- **`use_bm25` 설정이 저절로 죽었다.** 라운드 1~3 에서는 설정 항목으로 셌는데, 재라운드에서
  인덱스를 인자로 받기로 하자 **안 넘기는 것이 곧 끄는 스위치**가 되어 합법값이 하나뿐인
  설정이 됐다. 앞 결정이 뒤 설정을 지운 것이라 `embedding.provider` 와 같은 자리다
- **`iter_chunks()` 를 Protocol 에 올리는 것이 `list_documents()` 판단과 안 부딪힌다.**
  저쪽은 *"두 번째 구현체가 실재할 때 올린다"* 며 일부러 안 올렸는데, 가르는 것은 **소비자**다 —
  backend 는 구체 타입을 알아도 되지만 retriever 는 *"`VectorStore` Protocol 만 받는다"* 가
  1회차 확정이라 Protocol 에 없으면 계약을 어긴다

**곁다리로 얻은 것 둘**

- **`SearchResult` 를 열거에 못 쓴다는 것을 읽다 발견했다.** `score` 가 required float 이라
  열거 결과에 `0.0` 을 채우게 되는데, 그것은 이 저장소가 두 번 경고한 *"0.0 과 없음이 안
  갈린다"* 를 되풀이하는 것이다(`float | None` 결정 · PDF `extract()` 함정). `score` 를 뺀
  `StoredChunk` 를 두고 `SearchResult` 가 상속한다
- **`_STATUS_BY_EXCEPTION` 이 이미 준비돼 있었다.** `IndexingError` 가 503 으로 등록돼 있어
  (indexing 1회차가 *"끼우는 순간 살아나는데 그때 빠져 있으면 500"* 이라며 미리 넣었다)
  1회차가 지적한 *하네스 다섯* 중 둘이 저절로 닫혔다 — 이것과 `auto_test_check` 매핑이다

**남은 질문**

위 "미결" 전부. 이번 회차가 닫은 것은 store 수명과 `RetrievalError` 둘이고,
새로 연 것은 `candidate_k`·`rrf_k` 재판정 · 토크나이저 비교 · backend 색인 시 BM25 무효화 셋이다.
