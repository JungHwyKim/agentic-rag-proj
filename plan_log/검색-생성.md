# 검색·생성 설계

상태: 논의 중 (1회차)
관련 기록: task_log/... (구현 후 채운다)

`평가-세트.md` 와 짝이다 — 이 단계의 모든 수치 결정이 저쪽 세트 위에서만 정해진다.

## 확정된 것

- **Dense 는 기존 qdrant 를 그대로 쓴다** — 근거: `QdrantStore.search()` 가 이미 있고 컬렉션
  정체성(모델·차원)·Dot 거리·NFC 문서 키가 전부 실측 근거를 달고 서 있다(`indexing.md`).
  ChromaDB 로 갈아타면 그 근거를 처음부터 다시 세워야 한다
- **retriever 는 `VectorStore` Protocol 만 받는다** — 근거: `next-stages.md` 가 이미 계약으로
  적어둔 것이고, 사용자가 "언제든 다른 저장소를 쓸 수 있게" 를 요구했다. **새 추상화를 안
  만든다** — `base.py` 의 Protocol 에 `search()` 가 이미 있다. `provider` 설정은 두 번째
  구현체가 실재할 때 더한다(`embedding.provider` 를 안 만든 것과 같은 잣대)
- **BM25 는 저장소 밖 별도 인덱스** — 근거: qdrant sparse 벡터로 얹으면 Protocol 과 컬렉션
  스키마를 고쳐야 하고 방금 정한 저장소 중립이 깨진다(Chroma 에는 sparse 가 없다)
- **dense·BM25 병합은 RRF** — 근거: Dot 점수와 BM25 점수는 단위가 달라 그대로 못 섞는다.
  RRF 는 순위만 써서 정규화가 필요 없다
- **Reranker 는 로컬 우선 + `Reranker` Protocol + `get_reranker()`** — 근거: "기본 pytest 는
  키 없이 전부 통과" 를 지키는 것이 로컬뿐이다. 상용은 비교 실험 때 두 번째 구현체로 온다
- **평가 세트를 Phase 0 으로 올린다. 정답은 LLM 초안 + 사람 검수** — 근거: 사용자가 가져온
  스펙의 Phase 2·4·10 DoD 셋이 전부 라벨링 QA셋을 요구하는데 세트가 없다. 상세는 `평가-세트.md` 2회차
- **Vision·LlamaParse 를 tool 목록에서 뺀다** — 근거: 아래 "안 하기로 한 것"
- **`RetrievedChunk` 는 `SearchResult` 에 경로별 점수를 얹은 것이고 `metadata` 를 버리지 않는다**
  — 근거: `metadata` 에 `page`·`heading_path`·`page_end` 가 들어 있어 **출처 인용의 유일한
  근거**다. 스펙의 `content`/`source` 두 필드만 남기면 Context Builder·Generator 가 인용을 못 만든다.
  이름도 `text` 로 맞춘다(저장소 전체가 쓰는 이름)
- **점수 필드는 `float | None`** — 근거: 한쪽 경로에만 걸린 청크가 실재한다. required float 로
  두고 `0.0` 을 채우면 **"점수가 0"과 "후보가 아님"이 안 갈린다.** PDF 표에서 `extract()` 만
  보면 병합 셀과 빈 칸이 안 갈리던 것과 같은 종류다
- **진행은 단계별 + 단계마다 사용자 승인** — 사용자 요청. 첫 승인 단위는 Phase 0 하나다

## 미결

- **LangGraph 를 정말 쓸지** — 정하려면: Checkpoint A 를 돌려보고 while 루프로 부족한지 본다.
  체크포인팅·스트리밍·병렬 분기가 필요해지면 값을 하지만, 지금 흐름은 while 로 표현된다.
  `AgentState` 를 pydantic 으로 굳혀두고 나중에 LangGraph 로 가면 reducer·`Annotated` 때문에
  다시 쓰게 되므로, 쓸 거면 Phase 7 **전에** 정해야 한다
- **agent 코드의 거처** — `retrieval/` · `generation/` · 새 `agent/` 중 어디. 정하려면:
  Router 가 무엇에 의존하는지가 Phase 8 에서 드러난다
- **질의당 LLM 호출 상한과 카운터** — 정하려면: Phase 4~5 에서 Evaluator·Rewriter 가 실제로
  몇 번 도는지 본다. 적재의 `max_vision_calls_per_doc` 에 대응하는 자리인데 **축이 다르다** —
  적재는 문서당 1회로 끝나고 질의는 반복된다
- **Evaluator·Rewriter 의 실패 계약** — 정하려면: 폴백 층이 있는지 본다. 로더 쪽은 빈 결과 +
  `warn()`(내려갈 층이 있어서), embedding·indexing 은 예외(없어서)다. Evaluator 가 실패했을 때
  "충분"으로 떨어뜨리면 나쁜 context 로 답을 만들고, "불충분"으로 떨어뜨리면 재시도를 태운다.
  **둘 다 조용히 나빠서** 세 번째 답이 필요할 수 있다
- **`RetrievalError` 를 새로 만들지** — 정하려면: 위 실패 계약이 먼저다. 만들면
  `_STATUS_BY_EXCEPTION` 등록이 따라온다
- **질의 엔드포인트가 `store` 를 언제 잡고 언제 놓는지** — `next-stages.md` 가 "설계 결정이고
  정해진 바가 없다"고 열어둔 자리다. qdrant 로컬 파일 모드가 배타 잠금을 걸어 **요청마다 열고
  안 닫으면 두 번째 질의가 죽는다.** 정하려면: backend 질의 엔드포인트를 실제로 만들 때
- **`top_k` 기본값과 relevance threshold** — 지금 5는 임시값이다. **baseline 이 생겼다**
  (`hit@10` 0.483 · `MRR` 0.253 · `verify_log/2026-08-22-검색평가-세트.md`). 맞힌 것의 순위가
  대부분 앞쪽이라 **`top_k` 를 키우는 것보다 후보 자체를 늘리는 쪽**(hybrid)이 먼저다
- **`DESIGN.md`·`IMPLEMENTATION_SPEC.md` 의 거처** — 지금 설계 논의가 `rag_pipeline/retrieval/`
  와 `plan_log/` 두 곳에 산다. 정하려면: 두 문서를 정정한 뒤 겹치는 부분이 얼마나 남는지 본다

## 다음 승인 단위

`rag_pipeline/retrieval/IMPLEMENTATION_SPEC.md` 의 phase 순서를 따른다 — **Phase 1**
(`schemas/retrieval.py` 는 이미 있으므로 나머지 타입) → **Phase 2**(hybrid retriever).
Phase 2 의 첫 판정은 **비교 1번**(dense vs hybrid)이고, baseline `hit@10` 0.483 이 그 기준선이다.

## 안 하기로 한 것

- **ChromaDB** — 이유: qdrant 로 이미 색인하고 그 선택에 실측 근거가 여럿 달려 있다. 갈아타면
  indexing 단계가 고아가 되거나 같은 청크가 두 저장소에 남아 진실이 둘이 된다 /
  다시 볼 조건: qdrant 로컬 파일 모드의 배타 잠금이 실제 운영에서 막힐 때. 그때도 먼저 보는
  것은 qdrant 서버 모드다
- **Vision·LlamaParse 를 질의 시점 tool 로 두는 것** — 이유: **넣을 입력이 없다.** `blob` 은
  splitter→records→chunk 경로에 한 번도 안 나오고(확인함), 바이트는 로더 경계에서 죽는다.
  질의 시점에 남는 것은 청크 텍스트뿐이다. DESIGN 6장이 "LlamaParse 의 소속"을 미결로 열어둔
  것이 이걸로 닫힌다 — **적재 시점 전처리**다. 덧붙여 LlamaParse 는 표를 HTML 로 돌려줘
  기본값이 꺼져 있다(`표-경로.md` 1회차) / 다시 볼 조건: 청크 payload 에 blob 참조를 싣고
  "이 청크의 원본 이미지를 다시 본다"가 실제 요구로 나오면. 그때도 tool 이 아니라 **재적재
  트리거**에 가깝다
- **`RetrievedChunk` 에 `content`·`source` 만 두는 것** — 이유: 위 "확정된 것"
- **Phase 1 에서 `AgentState` 까지 한꺼번에 정의하는 것** — 이유: 소비자가 Phase 7 에 있고,
  LangGraph 를 쓸지가 미결이라 지금 굳히면 state 모양을 두 번 쓰게 된다. 스펙의 Pre-Lock A 가
  "필드 설계만 Phase 1 에 확정"한 취지는 살리되 **코드로 굳히는 것은 미룬다** /
  다시 볼 조건: LangGraph 여부가 정해지면
- **`search(filters=...)`** — `indexing.md` 1회차에서 이미 닫힌 것을 되풀이하지 않는다.
  쓸 축이 `document_id` 뿐이고 `page` 는 HWPX 쪽 수 함정 때문에 못 쓴다

## 1회차 — 2026-08-22 · 사용자 설계서 검토와 Phase 0 확정

**물은 것**

사용자가 `rag_pipeline/retrieval/` 에 `DESIGN.md`·`IMPLEMENTATION_SPEC.md` 를 두고
"읽어보고 설계 방향 제안해줘" 를 요청했다. 11-phase 구성에 Pre-Lock A/B/C 를 붙인 핸드오프용
스펙이다.

**드러난 것 — 뼈대는 옳고 어긋난 곳이 여섯이다**

뼈대 셋은 이 저장소가 실제로 밟은 길과 같은 모양이라 그대로 둔다 — retrieval loop 을 agent
레이어 **앞에** 독립적으로 세우는 것, LangGraph 를 **마지막에** 묶는 것, Checkpoint A 로 retry
cap 을 그래프 전에 따로 검증하는 것.

어긋난 여섯:

1. **Dense 를 ChromaDB 로 전제** — qdrant 로 이미 색인한다
2. **Phase 2·4·10 의 DoD 셋이 라벨링 QA셋을 요구** — `평가-세트.md` 는 1회차이고 확정된 것이
   없다. 그대로 두면 세 DoD 가 전부 미충족으로 남는다
3. **Vision·LlamaParse 를 질의 시점 tool 로 전제** — 넣을 입력이 없다(위 "안 하기로 한 것")
4. **`RetrievedChunk` 가 `metadata` 를 버린다** — Phase 9·10 이 출처 인용을 못 만든다
5. **질의 시점 비용 규약이 없다** — 질문 하나에 Router + Evaluator×3 + Rewriter×3 + Generator
   ≈ 최대 10회 LLM 호출인데 상한도 카운터도 없다. 적재는 문서당 1회라 상한·캐시가 다 있는데
   **반복되는 쪽에 없다**
6. **하네스 다섯이 빠졌다** — `RetrievalConfig` · `.env.example` · `offline_config` ·
   `auto_test_check.py` 매핑 · `_STATUS_BY_EXCEPTION`. `indexing.md` 1회차에서 같은 다섯이
   빠졌던 자리다

곁가지로 위치 어긋남 둘: `schema.py` 를 `retrieval/` 안에 두는 것(기존은 `schemas/` 한 곳),
`content` 필드명(저장소 전체가 `text`).

**선택지 — 면담 3라운드**

**고른 것과 이유**

전부 사용자가 골랐다. 위 "확정된 것" 이 결과다. 특기할 둘:

- **저장소 교체 가능성을 요구했지만 새 추상화는 안 만들었다.** 요구를 받아 적기 전에 계약을
  확인했더니 `VectorStore` Protocol 에 `search()` 가 이미 있었다 — retriever 가 구상 타입을
  안 잡기만 하면 요구가 충족된다. `provider` 설정을 지금 만들면 합법값이 하나뿐인 죽은 설정이
  되므로 미룬다. **비교 실험을 하는 순간 두 번째 구현체가 생기니 그때 설정이 저절로 살아난다**
- **Reranker 도 같은 모양으로 처리했다** — "로컬로 돌리되 추후 상용도" 라는 요구를
  `Reranker` Protocol + 팩토리로 받고 설정은 미뤘다. `get_embedder()` 가 밟은 길 그대로다

**기각한 것**은 위 "안 하기로 한 것" 에 이유와 함께 있다.

**곁다리로 얻은 것 — 비교 실험 설계**

사용자가 "hybrid vs dense / reranker 유무 / reranker 로컬 vs 상용" 비교를 요청해 여섯 축을
세웠다. 여기서 함정 하나를 먼저 박았다 — **리랭커를 `recall@후보수` 로 재면 차이가 정의상
0 이다.** 순서만 바꾸고 집합을 안 바꾸기 때문이다. 순서 지표(`nDCG@5`·`precision@3`·
`recall@5`)로 재야 한다. 이걸 모르고 재면 "리랭커가 효과 없다"는 잘못된 결론이 나온다.

축 여섯 중 하나는 **이미 열려 있던 미결을 닫는다** — 같은 문서의 HWPX 판 45청크 vs PDF 판
104청크 중 어느 쪽이 검색에 유리한지(CLAUDE.md 가 "아직 못 잰다"고 적어둔 자리).
`tests/fixtures/` 에 두 포맷 짝이 4쌍 있어 잴 수 있다.

판정 방법도 함께 정했다 — 수치 하나로 승패를 안 본다. 질의 50개면 `recall@10` 5%p 차이가
질의 2.5개라 잡음과 안 갈린다. **질의별 승/패/무 표**를 같이 내고 진 질의를 직접 읽는다
(표 청크가 지는 것과 본문 청크가 지는 것은 고칠 곳이 다르다). 임계값 12pt 를 관측값이 아니라
분포의 틈에서 고른 것과 같은 태도다.
