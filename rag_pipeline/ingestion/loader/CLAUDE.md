# loader — 경계와 함정

이 폴더와 그 아래(`document/`·`content/`)를 읽거나 고칠 때만 컨텍스트에 들어온다.

뿌리 `CLAUDE.md` 에서 2026-08-31 에 내려왔다. 그때 뿌리가 147,014자였고 그중 51%가 함정 절
하나였는데, **그 절 56항목 중 23개가 이 폴더 것**이었다. 뿌리는 이제 «어느 폴더에 무엇이
있나»만 갖는다 — **요약도 안 남긴다.** 요약을 두면 그것이 낡는 두 번째 진실이 된다.

**원문을 한 글자도 안 고치고 옮겼다.** 실측 수치와 «버린 안»이 이 문장들의 값어치라,
다듬으면 그것이 사라진다.

**`.claude/skills/rag-code-review/references/loader.md` 와 자[尺]가 다르다.** 저쪽은 «리뷰가
잡을 위반»이고 이쪽은 «쓰는 동안 밟으면 조용히 틀리는 것»이다. 둘이 어긋나면 그때
합칠지 다시 본다 — 지금 합치면 리뷰 기준이 설계 문서가 되거나 그 반대가 된다.

**여기 있는 항목을 뿌리 `CLAUDE.md` 에 다시 적으면 `tests/test_docs.py` 가 막는다**(같은
함정 제목이 두 `CLAUDE.md` 에 있으면 실패). 한 사실은 한 파일에만 산다.

## 로더의 2단계 라우팅

로더 **안에서** 라우팅이 두 번 일어난다(파이프라인 단계 수와는 무관한 이야기다).

```
detect_format()            매직바이트로 실제 포맷 판별 (확장자 불신)
  ↓                        loader/detect.py — zip/ole는 내부 구조까지 봐야 갈린다
get_loader()               1차 라우팅: FileFormat → 문서 로더
  ↓                        loader/registry.py 의 _FACTORIES 분기표
BaseDocumentLoader.load()  템플릿 메서드 (loader/document/base.py)
  ├ detect_regions()       ← 포맷별 로더가 구현하는 유일한 추상 메서드
  ├ route_all()            2차 라우팅: ContentType → 콘텐츠 핸들러
  └ DocumentMetadata 조립  LoadContext의 비용 카운터·경고를 옮겨 담는다
```

## 지켜야 할 경계

- **문서 로더**(`loader/document/*`)는 "어디에 무엇이 있는가"만 `ContentRegion` 목록으로 답한다. OCR/Vision/LlamaParse를 직접 부르지 않는다.
- **콘텐츠 핸들러**(`loader/content/*`)만 "어떻게 텍스트로 만드는가"를 안다. 표를 LlamaParse로 볼지, 이미지를 Vision으로 볼지는 `loader/content/router.py` 와 설정으로만 바뀐다.
- 모든 출력은 `ParsedDocument(metadata, elements)` 로 수렴한다 (`schemas/document.py`).

이 경계를 지키지 않고 로더 안에서 OCR을 부르기 시작하면 설계가 무너진다.

## 폴백 사슬 — 외부 API 실패가 적재를 멈추면 안 된다

- **표**: `table_llamaparse` (blob이 있고 `table_pdf_handler="llamaparse"` 일 때) → 실패·키없음이면 `table_native` 로 내려간다. **기본값은 `pymupdf` 라 이 경로가 꺼져 있다** — LlamaParse 가 표를 마크다운이 아니라 HTML 로 돌려줘 `rows` 를 못 얻고, 그러면 splitter 가 헤더 반복을 못 하고 태그 한가운데를 자른다(실측: 시행령 PDF 표청크 24→62, 그중 16개가 여는 태그 없는 조각). 근거와 되살릴 조건은 `.claude/wiki/plan_log/표-경로.md`
- **표 승급**: `table_pdf_handler="hybrid"` 면 **빈 칸에 벡터 드로잉이 있는 표만** `table_vision` 으로 올라가고, 실패하면 `table_native` 다. **표를 다시 읽는 것이 아니라 빈 칸만 채운다** — 갈아끼우면 병합 셀·되붙이기·쪽 경계·갈린 셀 결과를 버리게 된다. 격자를 프롬프트에 함께 실어 같은 크기를 요구하고 **모양이 다르면 통째로 버린다**. **같은 벡터 경로의 표시는 문서 안에서 한 번만 묻는다** — Vision 이 더해주는 것은 "그게 무슨 기호인가" 하나뿐이고 자리는 기하가 안다. 실측으로 AI가이드 PDF 의 표시 74칸이 경로 서명 1종이라 표 6개가 호출 1회다. **문서당 1회가 아니라 서명당 1회인 것이 요점이다** — 앞엣것은 재본 적 없는 가정이고, 서명 축은 서명이 둘이면 두 번 물고 한 리전 안에 여러 모양이 섞였으면 늘 부른다. **기호를 실제로 얻었을 때만 기억한다**(실패한 서명을 기억하면 남은 표가 전부 죽는다). 기본값은 `pymupdf` 라 꺼져 있다
- **이미지**: `classify()` → SKIP(로고·아이콘 크기 필터) / OCR / Vision → Vision 실패 시 classify가 이미 돌린 OCR 결과를 재사용한다

외부 API 핸들러는 **예외를 던지지 않고 빈 리스트를 반환**하는 게 규약이다. 이 규약을 깨면 라우터의 폴백이 동작하지 않는다.


## 알고 있어야 할 함정

- **LlamaParse SDK**: `llama-parse` 와 `llama-cloud-services` 는 둘 다 deprecated다. `llama-cloud>=1.0` 의 `Client.parsing.parse()` 를 쓴다. **응답의 `markdown` 은 문자열이 아니다** — `pages` 를 담은 pydantic 모델이고 성공한 페이지에만 `markdown: str` 이, 실패한 페이지에는 `error` 가 들어온다. 문자열로 알고 `.strip()` 을 부르다 `AttributeError` 로 적재 전체가 멈춘 적이 있다(2026-08-18, 유료 표 경로 첫 실행). **가짜 응답을 문자열로 만들면 테스트가 이 오해를 그대로 검증한다** — 그래서 `test_router.py` 의 가짜는 실제 `pages` 모양이다
- **Vision 에 보낼 이미지 포맷은 `blob_kind` 가 아니라 바이트에서 읽는다**: 로더들이 이미지 리전의 `blob_kind` 에 `"png"` 를 하드코딩하는데 `blob` 은 문서에 박힌 **원본 바이트**다(PDF 는 `extract_image()` 결과, HWPX 는 zip 의 BinData 그대로). `image_vision` 이 그것을 `data:image/png` 로 붙여 보내다가 **jpx·bmp 가 전부 `BadRequestError` 로 거절**당했다 — 실측으로 AI가이드 PDF(jpx 4/4) · 시행령 HWPX · 가로쪽(bmp 12/12)이 `vision_calls=0` 이었고, 유일하게 전부 성공한 AI가이드 HWPX 는 jpeg 28/28 이었다(5/5 일치). 그래서 `_normalize_for_vision()` 이 `PIL.Image.format` 으로 판정한다. **지원 포맷(png·jpeg·gif·webp)은 재인코딩하지 않는다** — 전부 PNG 로 구우면 JPEG 사진이 3배로 부풀어(3.8MB→11.1MB) base64 가 20MB 상한의 74%까지 간다. 못 받는 것만 구우면 25%다. 확장자도 못 믿는다: 학교기록물 HWPX 의 `.jpg` 7개 중 4개가 실제로는 MPO 다
- **전면 스캔 PDF 는 Tesseract 가 적재 시간의 90%다 — 그래서 `route_all()` 이 무료 OCR 만 병렬로 돈다**: 실측(2026-08-24, 47쪽·13MB·추출 가능 텍스트 **0자**·이미지 47/47 OCR)으로 `ingest()` 237.5초 중 213.9초가 Tesseract 이고 쪽당 4.55초다(`image_to_data` 2.30 + `image_to_string` 2.25). `pytesseract` 는 subprocess 라 대기 중 GIL 을 놓아 스레드가 듣는다 — 워커 8에서 **51.8초**(요소 수·본문 자수·회귀 기준선 documents 10건 전부 동일). **유료 Vision·LlamaParse 는 일부러 직렬로 남겼다** — 상한 검사가 `if ctx.vision_calls >= 상한` 과 증가로 **갈라져** 있고 `mark_symbols` 메모도 조회와 기록이 갈라져 있어, 병렬로 올리면 상한을 넘겨 과금되고 '서명당 1회'가 여러 번이 되는데 **키 없는 기본 pytest 가 그걸 못 잡는다**. 같은 이유로 **워커는 공유 `ctx` 가 아니라 자식 `LoadContext` 에 쓰고 조립 구간이 문서 순서로 `absorb()` 한다** — 경고는 문자열이라 자기 자리를 몰라 `e.order` 재정렬로 못 되돌리기 때문이고(요소와 갈리는 지점이다), **그 `absorb()` 가 자식의 유료 카운터가 비었는지 검사해 경계를 구조로 지킨다**(어기면 조용히 과금되는 대신 `RuntimeError` 로 터진다). **`classify()` 가 `LoadContext` 를 인자로 안 받는 것이 이 병렬화의 전제다**(판정이 비용의 절반인 108.0초라 병렬 구간 안에 있어야 하고, 그럴 수 있는 근거가 그것 하나다). **여는 것·판정·무료 OCR 이 한 워커 안에서 끝나는 것도 되돌리면 안 된다** — 판정 결과를 모아 두면 `preprocess()` 가 `load()` 를 강제해 디코드된 픽셀 약 1.2GB 가 동시에 산다(2500x3535 RGB × 47, 계산값). 워커 8은 **한계값이 아니라 무릎**이다 — 16이 42.3초로 18% 더 빠르지만 같은 uvicorn 이 질의도 받는다(직전 대비 -102.1/-62.1/-23.8/**-9.5**초). **병렬로 안 되는 바닥이 23.6초 남아 20~30초대에는 못 간다**(PyMuPDF 쪽 루프·300dpi 래스터·cleaner, 아직 안 쪼갬) **2026-08-26 에 워커 수가 `OCR_MAX_WORKERS` 설정이 됐다**(기본 8로 동작 불변) — 그전 근거였던 *"합법값이 갈리는 두 번째 경로가 생긴 뒤에 연다"* 에서 그 경로가 **발열**로 생겼다. Tesseract 는 서브프로세스라 `TORCH_NUM_THREADS` 도 GPU 도 안 먹어, 적재 쪽 CPU 부하 손잡이가 이것 하나뿐이다
- **OCR 한국어**: `ocr_psm=6` 을 쓴다(기본 3은 한글 한 줄을 세로로 오인식). `preserve_interword_spaces=1` 이 없으면 "주식회사"가 "주 식 회 사"로 쪼개져 임베딩·검색이 망가진다. 다만 `image_to_data` 는 이 옵션을 무시하므로 **신뢰도는 `image_to_data`, 최종 텍스트는 `image_to_string`** 으로 용도를 분리해 뒀다 — 합치지 말 것
- **이미지 전처리**: 600px 미만일 때만 확대한다. 이미 큰 이미지를 늘리면 보간 흐림 때문에 인식률이 떨어진다(실측: 원본 7토큰 → 미세 업스케일 후 0토큰)
- **HWPX 쪽 번호**: `hp:tbl` 의 `hp:sz height` 를 믿으면 안 된다. 쪽을 넘기는 표는 이 값이 **시작 쪽에 남은 공간으로 잘려서** 저장돼 있다(실측: 43행 표가 선언 34206 / 실제 98326). 실제 높이는 `hp:cellSz height` 를 `hp:cellSpan rowSpan` 으로 나눠 복원해야 나온다. vertpos만 보고 쪽을 세면 쪽 넘긴 표 뒤로 쪽 번호가 전부 밀린다
- **HWPX 레이아웃 표**: 한글은 제목·인용을 그릴 때 표를 쓴다. 내용 든 칸이 2개 이하이고 9칸 이하인 표는 `_is_layout_box` 가 본문 문단으로 강등한다(`metadata["layout_table"]` 로 표시). 그림이 든 상자는 캡션-그림 관계가 끊기므로 표로 남기고, **표가 든 상자도 남긴다** — 강등하면 안쪽 표가 문단으로 뭉개진다. 세는 것은 `_table_rows()` 의 격자가 아니라 **실제 `tc` 목록**이다. 격자는 병합 칸을 여러 칸으로 펴므로 그걸 세면 9칸·2칸의 뜻이 달라진다(실측: 그렇게 뒀더니 시행령 안내서 표가 9→13개)
- **HWPX 병합 셀**: 병합에 덮인 자리는 `hp:tc` 가 **아예 안 나온다.** `hp:cellAddr` 를 안 보고 `tc` 를 순서대로 담으면 그만큼 값이 왼쪽으로 밀려, `지침확인`(실행항목)이 `단계` 열에 들어간 채 색인된다 — 실측으로 시행령 안내서 HWPX 표 173행 중 127행, 세 문서 합쳐 373행이 그 상태였다. `_table_rows()` 가 `cellAddr`·`cellSpan` 으로 격자를 채워 편다. **세로 연장은 값을 되풀이하고 가로 연장은 빈 칸으로 둔다** — splitter 가 표를 행 단위로만 쪼개서, 아래로 이어진 행은 다른 청크로 갈 수 있지만 옆으로 이어진 칸은 늘 같은 행에 남기 때문이다. PDF 경로도 같은 규칙을 쓴다(아래)
- **PDF 병합 셀**: PyMuPDF 는 병합에 덮인 자리를 `row.cells[j] is None` 으로 내놓고 `extract()` 는 같은 자리에 빈 문자열을 준다. **두 소스를 겹쳐 봐야 "병합에 덮인 자리"와 "그냥 빈 칸"이 갈린다** — `extract()` 만 보면 구분이 안 되고, "PDF 는 병합 정보가 없다"고 잘못 결론 내기 쉽다(실제로 그 전제로 유료 승급을 검토한 적이 있다). `pdf.py:_fill_merged_cells()` 가 채운다. **판정은 기하다** — 격자 칸의 중심점을 실제로 덮는 셀 사각형을 찾아, 그 셀의 **왼쪽 열이면서 위에 있을 때만** 세로 연장으로 보고 채운다. "같은 열 위에 값이 있으면 채운다" 식으로 하면 **위 칸이 실제로 여기까지 내려오지 않는 자리까지 채운다**(실측: 그 규칙이 897칸 중 13칸을 잘못 채웠다). 격자 경계는 **모든 칸 모서리의 합집합**에서 얻어야 한다 — 그 행의 칸들만 보면 여러 격자 행에 걸친 칸 때문에 행 범위가 부풀어 중심점이 엉뚱한 행으로 간다
- **`row.cells[j] is None` 은 한 가지 뜻이 아니다**: 격자 칸 중심을 덮는 셀이 **있으면** 병합에 덮인 자리이고, **없으면** `find_tables()` 가 셀 사각형을 아예 안 낸 **격자 구멍**이다. 실측(PDF 4개)으로 앞이 514자리 · 뒤가 3자리인데 **표시가 있는 곳은 뒤쪽뿐**이고(0 vs 1), 표 안에서 사라지던 행 라벨(AI가이드 17쪽 `책임성`)도 뒤쪽이었다. 한 덩어리로 세면 "얻는 것이 거의 없다"로 끝난다. `pdf.py:_grid_holes()` 가 가른다. **병합 자리는 일부러 안 건드린다** — 거기는 "가로 연장은 빈 칸으로 둔다"가 비워둔 곳이라 옆 칸 값이 이미 덮고 있다. 구멍 글자를 되살릴 때 **표 전체가 빈 열은 뺀다**: 안 빼면 표 바깥 여백을 열로 삼킨 자리의 쪽 번호가 표에 들어간다(실측 2건 중 1건). 잣대는 splitter 의 "표 전체에서 비어 있는 열은 버린다"와 같은 것이고, 채우면 그 열이 더 이상 빈 열이 아니게 돼 splitter 가 살려두는 것이 곧 그 가드의 이유다. **구멍 채우기는 표가 살아남을지 판정한 뒤에 한다** — 앞에 두면 구멍 글자만으로 빈 표가 되살아나 리전 수가 움직인다
- **표 빈 칸의 드로잉은 대부분 배경 음영이다**: 체크 표시가 벡터 드로잉이라 `extract()` 로 못 얻는 표가 있는데(AI가이드 12~17쪽), *빈 칸에 드로잉이 있는가* 로 잡으면 **오검출 233**이다 — 엑셀 서식이 칸마다 배경색을 깔기 때문이다(실측: 2026중등 22쪽 한 표). 가르는 것은 **셀 대비 면적비**다(`pdf.py:_MARK_AREA_RATIO`) — 음영은 1.00, 표시는 0.08~0.10 이고 **그 사이에 값이 없다.** 임계값이 아니라 의미의 경계라 분포의 틈을 고를 필요가 없다. 종횡비·채움색으로 가르려 하면 문서마다 다시 정해야 한다
- **PDF 는 한 표를 여러 리전으로 쪼갠다**: `find_tables()` 가 시행령 4쪽의 표 하나를 5개로 나눠 내놓았다. splitter 는 각 조각의 첫 행을 헤더로 되풀이하므로 실제 열 이름이 첫 조각에만 남는다. `pdf.py:_merge_split_tables()` 가 **세로 간격 12pt 미만 · 좌우 끝 ±2pt 일치 · 열 수 동일**을 모두 만족할 때만 되붙인다. 임계값 12 는 관측값이 아니라 **분포의 틈**에서 나왔다 — 실측(PDF 5개·리전 103개·인접쌍 36개)으로 조각난 표는 간격 6.8, 별개 표·상자는 전부 18.8 이상이라 2.8배 틈이 있다. **이 되붙이기를 외부 API 로 대신할 수 없다** — 핸들러가 리전 하나의 blob 만 보내 LlamaParse 는 조각 하나밖에 못 본다. 같은 표를 **HWPX 판은 처음부터 하나로 잡아** `part 0/2·1/2` 로 쪼개며 양쪽에 같은 헤더를 넣는다 — 되붙이기가 맞추려는 기준이 이쪽이다
- **쪽 경계는 다른 축으로 판정한다**: 같은 쪽에서 쓴 *세로 간격 12pt* 는 쪽이 바뀌면 축 자체가 사라진다. `pdf.py:_merge_across_pages()` 가 **좌우 끝 ±2pt · 열 수 동일 · 두 리전 사이에 한글을 가진 텍스트 블록이 0개**로 판정한다. **헤더 반복으로 판정하면 안 된다** — 그럴듯해 보이지만 실측으로 **오검출 4 · 미검출 3** 이다(쪽을 가로지르는 인접 표 쌍 11개, 정답은 HWPX 행 수). AI가이드 12~17쪽이 `원칙 1`~`원칙 5` 각각의 별개 표인데 헤더를 글자까지 되풀이해서다. 한글 유무를 쓰는 이유는 참 4건 사이에 있던 것이 전부 쪽 번호 하나(6자·한글 0자)여서이고, **기하 띠(쪽 높이 상·하위 %)는 틈이 1.0%p 뿐이라 기각**했다(머리말 최하단 5.7% vs 본문 최상단 6.7%). 감수 사항: 한글 머리말이 매 쪽 반복되는 문서는 못 잇는다. 이어 붙인 뒤 `_fill_merged_cells()` 를 다시 못 돌리므로(쪽별 셀 기하가 없다) 세로 병합 앵커는 **빈 칸이 이어지는 구간까지만** 되풀이한다
- **쪽 경계가 셀 하나를 가로지르면 글자가 갈린다**: 시행령 PDF 24~25쪽의 `업무정보\n(4)` 한 셀(4행 세로 병합)이 24쪽 1행 `업무정보` + 25쪽 3행 `(4)` 로 갈렸다. `pdf.py:_join_split_cells()` 가 잇되 **판정은 기하다** — 앞 조각이 1행이고 뒤 조각이 다행 앵커일 때만. **`rows` 의 값 반복으로 판정하면 안 된다**: `구분` 열의 `선택`/`선택`·`필수`/`필수` 가 병합처럼 보여 실측 오검출 2건이다(기하 판정은 0건). `extract()` 만으로는 병합과 빈 칸이 안 갈린다는 것과 같은 이야기다. 이으면 **두 조각이 덮던 행 전부**에 넣고, 구분자는 `\n` 이다(같은 표의 안 갈린 형제 셀이 그 모양이라 마크다운에 `업무정보 (3)` 으로 렌더된다). 판정에 쓰는 셀 행 수는 되붙이기 시점에 표 객체가 없어 `metadata` 사설 키로 실어 나르는데, **첫 격자 행을 둘 담아야 한다** — 반복 헤더를 버리면 두 번째가 첫 데이터 행이다. **쪽 경계가 행 자체를 가르는 경우는 아직 못 잡는다**(학교기록물 23~24쪽, 표본 1건)
- **쪽을 넘긴 요소의 끝 쪽은 `metadata["page_end"]` 다**: HWPX 로더가 싣고 splitter 가 `Chunk.page_end` 로 나르고 indexing 이 payload 에 넣는 **이미 있는 규약**이다. 다른 이름(`page_span` 등)으로 새 키를 만들면 그 포맷만 이 흐름에서 **에러 없이 조용히** 빠진다 — 실제로 PDF 쪽 넘김 표에서 그럴 뻔했다
- **한컴 변환본은 본문을 통째로 도형으로 만들 수 있다**: 신뢰가능 AI 가이드의 변환본(`_fixed.hwpx`)은 `hp:tbl` 이 **0개**이고 `hp:drawText` 가 376→**860** 개, 섹션이 14→**1** 개다. `_is_layout_box` 가 표를 강등한 것이 아니라 **표가 문서에 없다** — 강등이면 `metadata["layout_table"]` 이 남는데 그것도 0이라 둘이 갈린다. **본문 대조로는 이 붕괴가 안 보인다**: 요소 텍스트 기준 PDF 커버리지가 오히려 96.8%→**100%** 로 올라가고(PDF 쪽 미검출 10개는 전부 마크다운 표 요소인데 그 셀 내용은 문단으로 100% 살아 있다) 자수도 18,489→19,192 로 는다. 실파일을 받았을 때 **표 리전 수와 쪽 수를 함께 봐야** 한다 — `tests/ingestion/loader/document/test_hwpx_real.py` 가 이 셋(표 0 · 쪽 1 · 머리말 잔류 55)을 일부러 잠가 두었다
- **HWPX 가로 쪽**: 한컴은 가로 쪽에서도 `hp:pagePr` 의 `width`/`height` 에 물리 용지(세로) 치수를 그대로 넣고 방향은 `landscape` 속성으로만 표시한다. **이름과 반대로 `NARROWLY` 가 가로, `WIDELY` 가 세로다**(실측: 시행령 개정안 안내서 가로쪽 판 — 두 섹션 모두 width=59528 height=84188 인데 WIDELY 섹션의 최상위 문단 vertpos 가 69898 까지 올라가 71435=height-여백 에 육박한다. 가로였다면 46775 를 넘을 수 없다). 그래서 가로 섹션의 본문 높이는 `width` 에서 얻는다. 안 가르면 53% 과대평가해 쪽 넘긴 표를 한 쪽으로 세고 이후 쪽 번호가 밀린다
- **HWPX 쪽 수를 분모로 쓰지 말 것** (미해결): 로더가 세는 HWPX 쪽 수가 문서에 따라 크게 부풀어 있다. 실측 — 신뢰가능 AI 가이드는 PDF 판이 28쪽(파일 구조에서 직접 확인)인데 HWPX 판을 97쪽으로 센다. 본문 분량은 20,895자 vs 21,843자로 거의 같다. 쪽당 요소 수 중앙값이 PDF 19 / HWPX 5 이고 요소가 1개뿐인 쪽이 21개다. 섹션은 14개뿐이라 `start_section()` 만으로는 설명이 안 되고 `vertpos` 감소 휴리스틱의 과다 발화로 보인다. 시행령 문서는 사람이 확인한 26쪽과 맞으므로 일률적으로 깨진 것은 아니다. **깨지는 문서가 어느 쪽인지는 실측으로 좁혀졌다** — 정답 질의 세트를 만들며 두 판의 쪽을 대조하니 시행령·중등 기초학력은 HWPX 와 PDF 쪽이 **정확히 같고**, 학교기록물은 **+1 로 일정하며**(표지 한 장), 신뢰가능 AI 가이드만 −1~−56 으로 벌어진다. 즉 부풀림은 문서별이고 그 문서 안에서는 일정하지 않다 — **보정 상수로 못 고친다.** **쪽 수로 비율을 계산하는 판정(머리말 등)을 만들 때 이 값을 분모로 쓰면 문서마다 결과가 뒤집힌다** — `cleaner/headers.py` 가 등장 횟수 비율 대신 걸친 폭을 쓰는 이유다. **반대쪽 끝도 있다** — 같은 문서를 한컴에서 다시 저장한 변환본(`_fixed.hwpx`)은 `vertpos` 888개가 **전부 0** 이라 쪽이 **1로 붕괴**한다. 부풀림(97)과 붕괴(1)는 같은 축의 두 끝이고, 붕괴 쪽에서는 파생 피해가 더 크다 — 걸칠 쪽이 하나뿐이라 `cleaner/headers.py` 의 머리말 제거가 25건→**0건**이 되어 반복 머리말 55개가 본문에 그대로 실린다
- **HWPX 제목은 스타일로 못 찾는다**: 한컴이 서식을 문단 스타일이 아니라 `charPr` 로 직접 박는 문서가 흔하다. 실측으로 신뢰가능 AI 가이드 HWPX 의 `Contents/header.xml` 에는 스타일이 `Normal` **하나뿐**이었다(글자 높이는 240~2617 로 살아 있다). 그래서 `headings.py` 가 글자 크기를 쓴다. 판정 규칙 셋(문서별 최빈값 / 배율 아닌 부등호 / `min` 이지 `max` 가 아님)은 그 파일 docstring에 근거와 함께 있다 — **되돌리면 강조가 제목이 되거나 제목이 통째로 사라진다**
- **PDF 는 한국어 낱말 사이 공백을 잃는다**: 같은 문장이 HWPX 는 `데이터세트는 물리적 이관시 그 특성이 변할 수 있어`, PDF 는 `데이터세트는물리적이관시그특성이 변할수있어` 로 나온다 — 없어야 할 자리에 공백이 있고 있어야 할 자리에 없다. **두 포맷의 텍스트를 대조하는 코드는 공백을 지우고 비교해야 한다**(`evaluation/scoring.py:squash()`). 안 그러면 PDF 판이 내용이 같은데도 안 맞는 것으로 나와, 포맷 비교가 검색이 아니라 추출 품질을 재게 된다. 규모는 아직 안 쟀다
- `.hwp`/`.doc`/`.ppt` 는 감지는 되지만 파싱하지 않는다. `UnsupportedLegacyLoader` 가 변환 안내와 함께 415로 거부한다. 정확한 안내를 주려면 업로드 자체는 받아야 하므로 `SUPPORTED_EXTENSIONS` 에는 포함돼 있다
- Tesseract는 외부 설치가 필요하다(5.5.0 + 한국어 traineddata). PATH에 없으면 `.env` 의 `TESSERACT_CMD` 로 지정한다
- zip bomb 방어는 `loader/detect.py:MAX_UNCOMPRESSED_BYTES`(500MB) 에 있다
