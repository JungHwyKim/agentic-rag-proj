검색·생성 스키마 설계서

적재 파이프라인이 이미 굳혀 놓은 계약 위에 검색·생성이 어떻게 얹히는지를 그림으로 남긴다. 설계 근거와 기각한 안은 plan_log/검색-생성.md, 평가 세트는 plan_log/평가-세트.md 에 있다.

1. 스키마 — 적재가 끝나는 곳에서 검색이 시작한다

검색은 ParsedDocument 에서 출발하지 않는다. 사슬은 splitter 에서 이미 한 번 끊겼고, 저장소가 SearchResult 를 내놓으므로 검색은 거기서 출발한다. 

classDiagram
    direction LR

    class ParsedDocument {
      +DocumentMetadata metadata
      +Element[] elements
    }
    class Chunk {
      +str chunk_id
      +str document_key
      +str text
      +int page
      +int page_end
      +str[] heading_path
      +dict metadata
    }
    class VectorRecord {
      +str id
      +float[] vector
      +str text
      +str document_id
      +str chunk_id
      +dict metadata
    }
    class SearchResult {
      +str id
      +float score
      +str text
      +str document_id
      +str chunk_id
      +dict metadata
    }
    class RetrievedChunk {
      +str chunk_id
      +str document_id
      +str text
      +dict metadata
      +float dense_score
      +float bm25_score
      +float fused_score
      +float rerank_score
      +ranking_score()
    }

    ParsedDocument --> Chunk : split()
    Chunk --> VectorRecord : to_records + embed
    VectorRecord --> SearchResult : store.search()
    SearchResult --> RetrievedChunk : from_search_result()

새로 생기는 경계는 SearchResult → RetrievedChunk 하나다. 새 타입을 만드는 이유는 경로별 점수를 실어 나를 곳이 필요해서이고, 경로가 dense 하나뿐이면 이 타입은 필요 없다.

metadata 를 버리면 안 된다. page · page_end · heading_path · source_name 이 전부 거기 들어 있고, 출처 인용의 유일한 근거다. 이것을 떨어뜨리면 Context Builder 와 Generator 가 “무슨 문서 몇 쪽”을 붙일 수 없다.
점수는 float | None 이다. dense 상위 50개와 BM25 상위 50개는 대부분 안 겹쳐서 한쪽 경로에만 걸린 청크가 실재한다. 필수 float 로 두고 빠진 자리에 0.0 을 채우면 “점수가 0”과 “후보가 아니었음”이 안 갈린다 — PyMuPDF 의 extract() 만 보면 병합 셀과 빈 칸이 안 갈리던 것과 같은 손실이다.

이름을 text 로 맞추는 이유

Element.text · Chunk.text · SearchResult.text 가 전부 text 다. 여기만 content 로 두면 단계를 넘을 때마다 이름을 바꿔 붙이게 되고, 그 지점이 자리 밀림을 숨긴다.

2. 질의 시점 흐름

flowchart TD
    Q["사용자 질의"] --> R{"Router"}

    R -->|retrieve| DE["질의 임베딩 embed_query()"]
    R -->|web_search| WS["Web Search"]

    DE --> DS["Dense 검색 VectorStore.search()"]
    Q --> BM["BM25 검색 (저장소 밖 lexical 인덱스)"]

    DS --> FU["RRF 병합 — 순위만 쓴다"]
    BM --> FU
    FU --> RR["Reranker (Protocol + 로컬 구현체)"]
    WS --> EV
    RR --> EV{"Relevance Evaluator"}

    EV -->|충분| CB["Context Builder"]
    EV -->|불충분| RW["Query Rewriter"]
    RW -->|재시도 최대 3회| R
    EV -->|재시도 소진| CB

    CB --> GE["Generator"]
    GE --> A["답변 + 출처"]

Dense 와 BM25 는 서로 다른 입력을 받는다 — dense 는 질의 벡터, BM25 는 질의 문자열이다. 병합이 RRF 인 이유는 Dot 점수(대략 −1~1)와 BM25 점수(상한 없음)의 단위가 달라 그대로 더하면 BM25 가 항상 이기기 때문이다. RRF 는 순위만 써서 정규화가 필요 없다.

질의 임베딩은 색인과 같은 EmbeddingConfig 를 써야 한다. 컬렉션 이름이 {collection}_{model}_{dim} 이라, 모델이 다르면 collection_name_for() 가 다른 이름을 만들어 검색이 컬렉션이 없습니다 로 죽는다.

3. 왜 Vision·LlamaParse 가 질의 시점 tool 이 될 수 없나

가져온 설계서는 Agent 가 고를 수 있는 tool 로 Retriever · Web Search · Vision · LlamaParse 넷을 두었다. 뒤의 둘은 넣을 입력이 없다.

      L --> B["ContentRegion.blob (원본 이미지 바이트)"]

    E --> C["Chunk.text + metadata"]
    C --> VR["VectorRecord payload"]

    subgraph QRY["질의 시점 — 텍스트만 남는다"]
      VR --> SR["SearchResult.text"]

    end

    B -. "blob 은 Chunk 로 안 넘어간다" .-> X(("여기서 죽는다"))

확인했다 — blob 은 splitter → records → chunk 경로에 한 번도 안 나온다. 질의 시점에 남는 것은 청크 텍스트뿐이라, 두 tool 에 건넬 바이트가 없다.

Tool판정근거
Retriever메인 트랙Phase 2~5, Phase 6 에서 wrapping
Web Search유지질의 문자열만 있으면 된다
Vision제외바이트가 로더 경계에서 죽는다. 이미지 해석은 이미 적재 때 끝났다
LlamaParse제외같은 이유. 게다가 표를 HTML 로 돌려줘 기본값이 꺼져 있다

이것으로 원 설계서 6장의 “LlamaParse 의 소속” 미결이 닫힌다 — 적재 시점 전처리다. 다시 열릴 조건은 청크 payload 에 blob 참조를 싣고 “이 청크의 원본 이미지를 다시 본다”가 실제 요구로 나올 때이고, 그때도 tool 이 아니라 재적재 트리거에 가깝다.

4. 평가 세트 — 정답을 chunk_id 로 매기지 않는다

flowchart TD
    QA["qa_set.jsonl — query + gold_spans"] --> N1["squash() — NFC · 소문자 · 공백 제거"]
    RES["검색 결과 상위 k 의 청크 텍스트"] --> N2["squash()"]
    N1 --> M{"부분문자열 포함?"}
    N2 --> M
    M -->|yes| HIT["hit · recall · MRR · nDCG"]
    M -->|no| MISS["진 질의 목록 — 사람이 직접 읽는다"]

채점과 세트 검증이 같은 squash() 를 쓴다. 두 곳에서 따로 정규화하면 한쪽을 고쳤을 때 조용히 갈린다. 공백을 지우는 이유는 PDF 경로가 한국어 낱말 사이 공백을 잃기 때문이다 — 살려서 대조하면 PDF 판이 정답을 못 맞힌 게 아니라 띄어쓰기 때문에 0점이 되고, 포맷 비교가 검색이 아니라 추출 품질을 재게 된다.

안문제
chunk_id 목록 청킹을 고치면 세트가 통째로 무효다. 그런데 청크 상한 재판정이 이 세트의 목적 중 하나라 자기 자신을 못 잰다. 게다가 같은 문서의 HWPX 판과 PDF 판은 chunk_id 가 애초에 달라, 양쪽에 따로 정답을 매기면 두 포맷이 아니라 두 세트를 비교하게 된다
쪽 번호 못 쓴다. 같은 문서를 PDF 28쪽 / HWPX 97쪽으로 세는 미해결 함정이 있다
gold_spans (채택) 청킹·포맷이 바뀌어도 산다. recall 의 분모가 청크가 아니라 span 이라 청킹에 안 흔들린다
리랭커를 recall@후보수 로 재면 차이가 정의상 0 이다. 후보 집합을 안 바꾸고 순서만 바꾸기 때문이다. 이것으로 재고 “리랭커가 효과 없다”고 결론 내리는 것이 이 평가에서 제일 하기 쉬운 실수라, 지표를 비교 축마다 갈라 둔다 — 집합이 바뀌는 비교는 hit@10·recall@10·MRR, 순서만 바뀌는 비교는 nDCG@5·precision@3 이다.

5. 지켜야 할 경계

  • retriever 는 VectorStore Protocol 만 안다. QdrantStore 나 qdrant_client 를 직접 import 하지 않는다 — 저장소를 갈아끼울 수 있게 하는 것이 이 한 줄이고, 새 추상화는 필요 없다
  • BM25 는 저장소 밖에 둔다. qdrant sparse 벡터로 얹으면 Protocol 과 컬렉션 스키마를 고쳐야 하고 저장소 중립이 깨진다
  • Reranker 는 Protocol + 팩토리, 로컬 구현체 먼저. reranker_provider 설정은 상용 구현체가 실재할 때 더한다 — 구현체가 하나면 합법값이 하나뿐인 죽은 설정이다
  • 새 예외는 _STATUS_BY_EXCEPTION 에 등록한다. 빠뜨리면 500 이다
  • 기본 pytest 는 키 없이 전부 통과해야 한다. 외부 호출을 하는 단계는 offline_config 에 끄는 설정을 넣는다
