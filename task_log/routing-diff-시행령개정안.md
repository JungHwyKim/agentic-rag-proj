2. 원인 A — 쪽을 넘기는 표 때문에 쪽 번호가 밀린다 (버그)

hwpx.py 의 _PageTracker 는 최상위 문단의 vertpos(쪽 안 세로 위치)가 작아지는
지점을 쪽 경계로 본다. 표가 쪽을 넘겨도 vertpos 가 줄어드는 사건은 표 다음
문단에서 딱 한 번뿐이라, 표가 먹은 쪽 수를 셀 수 없다.

쪽 기하 (Contents/section0.xml 의 hp:pagePr):
  용지 높이 84188, 여백 top 4251 / bottom 2834 / header 2834 / footer 2834
  → 본문에 쓸 수 있는 높이 71435

hp:tbl 의 hp:sz height 는 믿으면 안 된다. 쪽을 넘기는 표는 이 값이
"시작 쪽에 남은 공간"으로 잘려서 저장돼 있다. 실제 높이는 hp:tc 의
cellSz height 를 cellSpan rowSpan 으로 나눠 행별로 복원해야 나온다.

표 26개를 전부 이 방식으로 재면 쪽을 넘기는 표는 정확히 2개다.

  코드 p13  43행 x 5열   시작 vertpos 35612  남은 공간 35823
            선언 높이 34206 (남은 공간에 맞춰 잘린 값)
            실제 높이 98326  →  2쪽 차지   +1쪽

  코드 p23  67행 x 6열   시작 vertpos 11642  남은 공간 59793
            선언 높이 58939 (역시 잘린 값)
            실제 높이 102135 →  2쪽 차지   +1쪽

  나머지 24개는 전부 한 쪽에 들어간다.
  (19행 x 4열 표도 실제 높이 58159 < 남은 공간 63037 이라 안 넘긴다)

  코드 추정 24쪽 + 놓친 2쪽 = 실제 26쪽

보정식:  실제쪽 = 코드쪽            (코드쪽 <= 13)
         실제쪽 = 코드쪽 + 1        (14 <= 코드쪽 <= 23)
         실제쪽 = 코드쪽 + 2        (코드쪽 = 24)

이미지는 이 보정만으로 완전히 일치한다.

  코드 10 -> 10    코드 16 -> 17    코드 17 -> 18    코드 18 -> 19
  코드 19 -> 20    코드 20 -> 21    코드 21 -> 22    코드 22 -> 23
  = [10,17,18,19,20,21,22,23]  →  사용자 확인 목록과 정확히 동일

이미지 12개 전부 BMP, 최소 589x562. 라우터의 크기 필터(min 100x100)에 걸리는
건 하나도 없다. 즉 12개 모두 OCR/Vision 경로로 간다.

5. 조치 — 둘 다 수정 완료 (2026-08-14)

  A. 쪽 번호  [rag_pipeline/ingestion/loader/document/hwpx.py]

     _table_height() 추가. hp:sz height 가 잘린 값이므로 cellSz height 를
     cellSpan rowSpan 으로 나눠 실제 높이를 복원하고 둘 중 큰 값을 쓴다.
     _PageTracker.consume_table() 이 남은 공간과 비교해 넘긴 쪽 수를 더한다.
     _usable_body_height() 가 hp:pagePr 에서 본문 높이를 읽는다.
     기하 정보가 없는 문서는 예전처럼 동작한다(넘긴 쪽 0으로 취급).

     쪽에 걸친 표는 metadata["page_end"] 에 끝 쪽을 남긴다. 시작 쪽만으로
     출처를 달면 표 뒷부분이 엉뚱한 쪽을 가리키기 때문이다.

     결과: page_count 24 -> 26

     [작업 중 한 번 잘못 짚었다가 되돌린 것]
     처음에는 표 높이로 '표가 끝난 위치'를 계산해 다음 문단과 비교하도록
     짰다. 이 문서에서는 잘 맞았는데 학교기록물 지침에서 없는 쪽 경계를
     2개 만들어냈다. 원인은 떠 있는 표(hp:pos treatAsChar="0")다 —
     뒤따르는 문단의 vertpos 에 표 높이가 반영되지 않는 문서가 있다.
     (해당 표: 22행 4열, 16046~44126 을 차지하는데 뒤 문단이 17966.
      그 뒤로 23726 25646 29486 ... 59640 까지 한 쪽으로 쭉 이어진다)
     그래서 한 쪽에 들어가는 표는 vertpos 를 건드리지 않고, 실제로 쪽을
     넘긴 표에서만 쪽을 더하도록 좁혔다. 회귀 테스트로 박아뒀다
     (test_fitting_table_does_not_break_page).

  B. 레이아웃 표  [같은 파일 _is_layout_box()]

     내용이 든 칸이 2개 이하이면서 전체 9칸 이하인 표를 TEXT 로 강등하고
     metadata["layout_table"]=True 를 남긴다(cleaner 가 제목 승격 판단).
     그림이 든 상자는 캡션-그림 관계가 끊기므로 표로 남긴다.

     기준을 '전체 칸 수'가 아니라 '내용이 든 칸 수'로 잡은 근거:
     이 문서의 표 27개를 재보니 실데이터 표는 내용 칸이 최소 9개,
     껍데기 상자는 최대 2개로 그 사이가 완전히 비어 있었다.
     덕분에 3x3 인용 상자(가운데 칸만 채움)까지 같은 규칙으로 걸린다.

     결과: 표 26 -> 9 (강등 17), 인용 상자 4개 포함
