# 실패를 화면에 띄웠다 — 상태코드는 지킨 채 `HX-Request` 로 갈래를 냈다

- 작업일: 2026-08-24
- 검증 방법: 라우트 계약 10종 + 화면 배선 4종 합성 테스트 · 실서버 관측 · 저장소 읽기 전용 관측 · ruff · pytest 전체. **외부 API 호출 없음** (예외는 `side_effect` 주입, 415·413 은 파일이 로더에 닿기 전에 거절된다)

  `.error` · `#messages .error` · `#upload-error:empty`. 토큰 둘(`--danger`·`--danger-bg`)만

## 2. 설계 결정

### 상태코드를 200 으로 낮추지 않았다 — 스트리밍을 기각한 바로 그 자리다

htmx 는 4xx/5xx 를 기본적으로 swap 하지 않는다. 제일 싼 해법은 **오류를 200 으로 돌려주는
것**이고 그러면 JS 도 확장도 필요 없다.

버렸다. `frontend.md` 1회차가 SSE 스트리밍을 기각한 이유가 *"첫 바이트에 이미 200 을 보낸
뒤라 `_STATUS_BY_EXCEPTION` 이 못 잡는다"* 였다. **같은 실수를 다른 문으로 다시 하는
것**이고, 이번엔 하필 그 매핑을 지키자고 시작한 작업이다. 대신 `htmx:beforeSwap` 한 줄로
뒤집는다 — 계약은 서버에 남고 화면이 한 번 양보한다.

`response-targets` 확장 벤더링도 버렸다. 얻는 것이 그 한 줄과 같은데 벤더 파일이 늘고
htmx 2.x 와 버전을 맞춰 둬야 한다.

### 가르는 축이 `HX-Request` 인 결정적 이유는 415 다

라우트별 `try/except` 가 더 좁아 보였다 — `/documents/index` 는 이미 204 + `HX-Trigger` 로
*"htmx 전용"* 임을 인정한 라우트다. 그런데 **415 를 던지는
`_reject_unsupported_extension()` 이 `try` 이전**이라 거기까지 감싸야 하고, 상태코드를
알려면 `main.py` 사설 `_status_for()` 를 끌어써 **매핑의 두 번째 진실**이 생긴다.
헤더 축이면 두 핸들러가 같은 규칙 한 줄을 나눠 쓰고, 새 화면 라우트가 생겨도 저절로 맞는다.

415·413 을 `RagPipelineError` 로 바꾸는 안도 버렸다. 핸들러 하나로 모이긴 하지만 backend 의
**1차 검증이 rag_pipeline 예외를 던지게** 되어, 3회차가 *"잰 것 18 · 어긋남 0"* 으로 닫은
*"확장자 화이트리스트가 backend 에 있는 것"* 경계가 흐려진다.

### 오류 자리는 각자다

업로드는 사이드바 `#upload-error`, 질의는 `#messages` 말풍선이다. 질의 쪽은 composer 가
이미 `#messages`·`beforeend` 라 배선 변경이 0이다.

> **아래 한 문단은 틀렸고 사용자가 눌러서 잡았다. 8절에 고친 내용이 있다.**
>
> ~~업로드 폼에 `hx-target="#upload-error" hx-swap="innerHTML"` 을 주니 **성공 204 는 본문이
> 비어 있어 그 자리를 저절로 비운다.** 재시도가 성공했을 때 옛 오류를 지우는 코드를 따로 짤
> 필요가 없다 — 조각을 안 그리는 응답이 곧 지우는 응답이다.~~

공용 배너와 *둘 다 `#messages`* 는 버렸다. 사이드바에서 누른 결과가 본문 위에 뜨고,
질의 실패가 대화 흐름에서 빠져 **어느 질문이 실패했는지**가 안 남는다.

### `_error.html` 에 `variant` 인자를 두지 않았다

자리마다 모양이 다르니 조각을 둘로 하거나 인자로 가르는 것이 자연스러워 보인다. 그런데
**인자로 가르면 예외 핸들러가 어느 라우트인지 알아야 하고, 그러면 헤더 하나로 가른 이유가
사라진다.** 조각은 한 벌로 두고 `#messages .error` 가 말풍선 치수를 덧입힌다.

### reset 비대칭은 의도다

업로드 폼은 조건 없이 `this.reset()`, composer 는 `event.detail.successful` 일 때만.
**file input 은 안 비우면 같은 파일을 다시 골라도 `change` 가 안 떠서 재시도도 재색인도
막히고, 질문 글자는 실패 때 남아야 한다.** 같은 파일 안에서 두 줄이 반대로 도는 것이라
*"일관성"* 을 이유로 한쪽에 맞추면 조용히 망가진다 — 그래서 테스트가 **둘을 한 자리에서**
단언한다.

### `isError` 는 안 건드렸다

`shouldSwap = true` 옆에 `isError = false` 를 같이 쓰는 예가 흔하다. 켜면 `htmx:responseError`
가 안 떠 **콘솔 진단이 사라진다.** 그리는 것과 실패로 남기는 것은 다른 축이라 앞엣것만 켰다.

## 4. 실패 분석

### 실서버에 걸었더니 JSON 이 왔다 — 코드가 아니라 프로세스가 옛것이었다

`.exe` + `HX-Request` 를 띄워 둔 서버에 보냈더니 415 는 맞는데 `application/json` 이었다.
같은 요청이 `TestClient` 에서는 HTML 로 통과하고 있었다.

**원인은 `--reload` 가 `main.py` 변경에 한 번도 반응하지 않은 것**이다(워커 PID 33260 의
생성 시각이 서버 기동 시각 그대로). 그런데 `GET /` 로 받은 화면에는 `#upload-error` ·
`error-swap` · `hx-target` 이 **전부 최신으로 실려 나왔다** — Jinja2 가 템플릿을 mtime 으로
매 요청 새로 읽기 때문이다.

**"화면은 새것, 파이썬은 옛것"** 이라는 조합이 여기서 위험하다. 배선 6종이 다 보이는 것을
근거로 *"실서버에서 확인했다"* 고 적었으면 **거짓이 기록에 박혔을 것**이다. 4회차가
*"렌더된 HTML 문자열로만 확인했다"* 를 정직하게 남긴 것과 같은 자리인데, 이번엔 실서버까지
갔는데도 같은 함정이 한 겹 더 있었다.

**막은 방법**: 404 를 `HX-Request` 로 한 번 더 찔러 봤다(`{"detail":"Not Found"}` → 옛 코드
확정). **템플릿이 아니라 파이썬만 지나는 경로를 따로 찌른 것**이 갈랐다.

서버를 내렸다 새로 띄우니 같은 404 가 `<p class="error" role="alert">Not Found</p>` 로 왔다.
**그 404 가 결국 두 몫을 했다** — 옛 코드를 밝힌 탐침이자, 라우트를 아예 안 지나는 경로라
`StarletteHTTPException` 핸들러가 실제로 산다는 증거다(라우트별 try/except 였으면 못 잡는다).

### 막다른 길 — `test_pages.py` 의 import 패턴을 안 보고 썼다

새 테스트 둘에서 `TEMPLATES_DIR` 를 모듈 상단 import 로 있다고 가정했다가 `NameError` 로
깨졌다. 그 파일은 템플릿 원문을 보는 테스트마다 **함수 안에서** import 하는 패턴이었다.
파일 끝만 읽고 앞을 안 본 탓이다 — 다른 세션 소유 파일에 붙일 때는 형식을 먼저 본다.

### 안 밟은 함정 하나

413 테스트가 `get_settings` 를 갈아끼우는데, 이 저장소의 `get_settings()` 는 `lru_cache` 가
없어 매번 새로 만든다. **붙는 순간 이 테스트가 옆 테스트를 깬다**는 뜻이라
`test_settings_are_not_cached_between_tests` 로 그 전제를 잠갔다.

## 8. 후속 — 사용자가 눌러 보고 둘을 물고 왔다 (같은 날)

### 8-1. 2절의 "지우개" 가 거짓이었다

`.exe` 두 번은 기대대로 빨간 줄이 떴는데, **정상 `.hwpx` 를 올려 색인이 성공했는데도 빨간
줄이 안 사라졌다.**

원인: **htmx 는 204 에 swap 을 아예 안 한다.** 빈 본문으로 덮는 것이 아니라 *"할 일 없음"*
으로 읽고 건너뛴다 — `htmx.min.js` 에 `responseHandling:[{code:"204",swap:false},…]` 가 박혀
있다. `{code:"[45]..",swap:false,error:true}` 도 같은 표에 있고, 그쪽은 `beforeSwap` 으로
뒤집었으면서 **204 는 뒤집을 생각을 안 했다.**

**테스트가 왜 못 잡았나 — 이것이 이번 후속의 핵심이다.**
`test_successful_index_sends_empty_body_that_clears_the_slot` 은 서버가 204 와 빈 본문을
보낸다만 확인한다. **이름만 화면 동작을 재는 것처럼 지어져 있었다.** 4회차 세션이
`test_index_leaves_the_answer_cache_alone` 을 두고 *"이름과 달리 객체 동일성만 잰다"* 고
경고했는데, 그 경고를 받아 적고도 **다음 회차에서 같은 함정에 빠졌다.** 경고를 아는 것과
자기 테스트에 적용하는 것이 다르다.

고친 방법: 이름을 `..._returns_204_with_no_body` 로 바꾸고, 화면 쪽은
`test_success_clears_the_error_slot` 이 따로 잠근다. **htmx 의 204 동작 자체도**
`test_vendored_htmx_never_swaps_on_204` 로 못 박았다 — 벤더 파일을 갈아끼웠을 때 전제가
바뀌면 거기서 알린다.

기각: **204 → 200 으로 낮추기**(저절로 비워지지만 4회차 응답 계약이 바뀌고
`test_index_returns_204_with_refresh_trigger` 가 깨진다) · **`HX-Trigger: documents-changed`
를 듣게 하기**(그 이벤트는 "목록이 바뀌었다"는 뜻이라 오류 지우기에 쓰면 우연한 결합이다).

### 8-2. 색인 진행 바 — 잴 수 있는 것과 없는 것을 갈랐다

*"큰 파일을 넣었는데 되는 건지 멈춘 건지 구별이 안 간다"* 는 요청이었다.

`index_document()` 는 파싱→청킹→임베딩→저장을 **한 번의 블로킹 호출**로 돈다. backend 는 그
안을 못 보고, 밖에서 추론할 것도 없다 — `upsert` 는 맨 끝에 한 번이라 0%에서 100%로 튄다.

| 구간 | 표시 | 근거 |
|---|---|---|
| 업로드 | **실제 퍼센트** | `htmx:xhr:progress` 의 `loaded`/`total` |
| 색인 | 무한 애니메이션 + **경과 시간** | 신호가 없다. 퍼센트를 지어내지 않는다 |

**버린 것 셋.** *가짜 퍼센트*(시간으로 바를 채우기) — 이 저장소가 임계값을 지어내지 않는
것과 같은 잣대이고, **멈춘 색인도 부드럽게 100%까지 간다.** *backend 가 단계를 직접 부르기*
— `index_document()` 를 복제해 색인 순서의 두 번째 진실이 생긴다. *업로드 바만 넣기* —
localhost 라 큰 파일도 순식간에 100%가 되고 정작 긴 구간이 그대로 깜깜하다.

**`.pending` 규약을 여기서만 벗어났다.** 4회차가 새 방식을 안 들인 판단은 옳았지만 그 규약은
문구 한 줄을 켜고 끄는 것이라 퍼센트를 실을 자리가 없다. 답변 말풍선(`#pending`)은 그대로다.

**htmx 이벤트가 두 번 흐른다** — `progress`·`loadend` 를 `xhr` 과 `xhr.upload` **둘 다**에
걸기 때문이다. `sending` 플래그로 앞 구간만 퍼센트로 읽는다. `loaded >= total` 로만
판정하면 파일이 아주 작아 `progress` 가 한 번도 안 뜨는 경우를 놓쳐, 첫 `loadend` 에서도
색인 구간으로 넘어가게 했다.
