# 기록 훅이 도구를 안 가리게 했다 — Bash 로 쓴 기록이 안 보이던 구멍

- 작업일: 2026-08-19
- 검증 방법: 훅 테스트 90개(신규 9건 포함) + ruff. **비용 0.**
  전문은 [verify_log/2026-08-19-기록훅-도구비의존.md](../verify_log/2026-08-19-기록훅-도구비의존.md)
- 설계 논의: [plan_log/하네스-확장.md](../plan_log/하네스-확장.md) 4회차

## 1. 무엇을 바꿨나

- `.claude/hooks/_hookutil.py` — 세션 시작 마커(`claude_session_started`)와
  `mark_session_start()` · `session_started_at()` · `wrote_under(prefix, session_id)` 신설
- `.claude/hooks/plan_log_check.py` · `task_log_check.py` — Stop 판정을
  `_recorded_this_session()` 로 묶고 **마커 OR mtime** 두 경로로 본다. 기준 시각은
  `SKIP_*` 검사보다 **먼저** 찍는다
- `tests/hooks/test_record_hooks.py` 신설 (9건)

`settings.json` 은 안 건드렸다. matcher 를 넓히지 않고 고쳤다는 것이 이 작업의 요점이다.

## 2. 설계 결정

### 발견 — 일을 다 하고도 막혔다

같은 세션에서 Vision 포맷 수정을 끝내고 `plan_log/이미지-경로.md` 3회차 · `verify_log` ·
`task_log` · INDEX 3곳을 남기고 **커밋까지 한 뒤** Stop 훅이 "설계 논의를 했는데 plan_log/ 에
기록이 없습니다"로 막았다.

원인은 판정 방식이다. 두 기록 훅은 "이번 세션에 기록했는가"를 PostToolUse 의
`tool_input.file_path` 로만 봤는데 **그 필드는 Write/Edit 에만 있다.** 그 세션은 auto mode
지침에 따라 기록을 전부 Bash(python heredoc)로 썼고, 그래서 마커가 한 번도 안 생겼다.

### 오탐의 값을 어떻게 봤나

"짜증나지만 안전한 쪽"이 아니다. **일을 하고도 막히는 게이트는 `SKIP_*=1` 을 습관으로
만들어 검사 자체를 죽인다.** 이 저장소는 그 위험을 이미 명시적으로 계산한 적이 있다 —
`plan_log/검증-기록.md` 1회차가 "차단 게이트를 셋으로 늘리면 `SKIP_*=1` 이 습관이 되므로"
새 훅을 기각했다. 같은 저울이 여기에도 걸린다. 그래서 무력화의 한 형태로 다뤘다.

방향은 다행히 **오탐(false block)** 쪽뿐이다. 두 훅의 *트리거* 는 멀쩡하다 —
`plan_log_check` 의 ACTIVE 마커는 Skill 호출에서 오고, `task_log_check` 는 `git status` 로
소스 변경을 본다. 둘 다 Bash 와 무관하다. 깨진 것은 *만족 조건* 뿐이다.

### 고른 것 — 도구가 아니라 파일을 본다

`wrote_under()` 가 세션 시작 시각 이후에 mtime 이 갱신된 파일이 그 폴더에 있는지 본다.
누가 무슨 도구로 썼는지 묻지 않는다.

**이 선택은 이 장치 전체의 전제에서 곧바로 나온다.** `_hookutil` docstring 이 이미
"모델에게 시키는 일은 지켜질 때도 있고 아닐 때도 있지만, 훅은 하네스가 돌린다"고 적어 뒀다.
그러니 "기록은 Write/Edit 로 쓰라"는 지시로 고치는 것은 **훅이 존재하는 이유를 스스로
부정하는 해법**이다.

마커는 없애지 않고 **주 경로로 남겼다.** 있으면 파일시스템을 훑을 필요가 없고,
mtime 은 보조다.

### 2026-08-17 의 교훈을 되살리지 않았는지 확인했다

제일 걱정한 것은 이것이다. 2회차에서 **git status 판정을 버린 이유**가 "세션을 구분하지
못해 지난 세션의 미커밋 기록이 이번 세션을 통과시킨다"였는데(발견 시점 `plan_log/` 미커밋
3건으로 실제 무력화), 파일을 다시 보기 시작하면 그 구멍이 되살아나는 것 아닌가.

되살아나지 않는다. **분모가 다르다** — git 은 "커밋됐는가"를 묻고 mtime 은 "이 세션에
쓰였는가"를 묻는다. 지난 세션이 남긴 미커밋 파일은 mtime 이 세션 시작보다 옛것이라 그대로
걸린다. 커밋은 작업트리 mtime 을 안 건드리므로 방금 커밋한 기록도 정상적으로 잡힌다.
이 두 방향을 테스트로 못 박았다.

### 기각한 안

| 안 | 왜 버렸나 |
|---|---|
| matcher 에 `Bash\|PowerShell` 을 더해 명령줄에서 경로 파싱 | **고치려던 실패가 그대로 남는다** — `sed -i "$f"` 처럼 리터럴 경로가 없으면 못 잡는다. 반대로 `grep plan_log/` 같은 읽기를 기록으로 오인한다. 임의의 셸 명령을 파싱하는 것은 추측이다 |
| `git status` 판정으로 되돌리기 | 그것이 2026-08-17 에 발견된 세션 미구분 버그 그 자체다 |
| "기록은 Write/Edit 로 써라"를 문서에 적기 | 훅이 존재하는 전제를 부정한다(위 참조). CLAUDE.md 는 "지켜질 때도 있고 아닐 때도 있다" |
| 기준 시각으로 ACTIVE 마커 mtime 쓰기 | `plan_log` 는 되지만 `task_log` 에는 대응 마커가 없다. 그리고 스킬을 늦게 부른 세션에서 기록이 마커보다 먼저 쓰일 수 있다 |

### 기준 시각을 못 믿는 경우를 따로 뒀다

`mark_session_start()` 가 **이번 호출이 처음 만든 것이면 True** 를 준다. 그러면 모든 파일이
그보다 옛것이라 mtime 판정이 무조건 False 가 되므로, 부르는 쪽이 `trust_mtime=False` 로
종전(마커만) 동작을 탄다. **이 경로가 실제로 발화하는 것을 이번에 봤다** — 새 코드가 처음
돌아간 Stop 이 정확히 그 상태였고, 그래서 이 작업의 기록이 없다며 (옳게) 막혔다.

## 4. 실패 분석

되돌린 시도는 없다. 다만 **처음 떠오른 해법이 기각된 안 1번(matcher 넓히기)이었다.**
"Bash 도 matcher 에 넣으면 되지" 가 제일 자연스러운데, 넣어도 `tool_input` 에 `file_path` 가
없어 아무것도 안 잡힌다는 것을 payload 구조를 보고서야 알았다. 명령 문자열을 파싱하는
쪽으로 이어가려다, **그러면 고치려는 실패(못 잡음)와 새 실패(오인)를 동시에 갖게 된다**는
점에서 접었다.

`auto_test_check.py` 도 같은 뿌리를 갖지만 **이번에 안 고쳤다.** 그쪽 Stop 은
`changed_paths()`(git)로 판정해 소스 변경을 놓치지 않는다 — 잃는 것은 PostToolUse 의 빠른
되먹임뿐이고 전체 실행이 Stop 에서 받아낸다. 성격이 "오탐으로 검사를 죽인다"가 아니라
"피드백이 늦다"라 저울이 다르다.
