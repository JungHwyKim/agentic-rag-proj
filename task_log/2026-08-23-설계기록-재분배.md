# frontend.md 가 이고 있던 backend 결정 18개를 backend.md 로 옮기고 포인터를 재조준했다

- 작업일: 2026-08-23
- 검증 방법: 항목 대조(기준 커밋 원본 vs 지금) · `git grep` 포인터 · 중복 겹침 이사 전후 대조 · ruff · pytest 전체. **외부 API 호출 없음** — 코드 로직을 안 바꿨다

  맨 위 세 절만 축약했다(25 → 5). `---` 아래 1회차 본문은 안 건드렸다. 겸사겸사 낡아 있던
  머리 두 줄(`구현 대기` · `관련 기록:` 플레이스홀더)을 고쳤다.
- `plan_log/INDEX.md`
  두 행의 상태 칸과 요약.
- 포인터 10곳 — `rag_pipeline/{config,exceptions}.py` ·
  `rag_pipeline/generation/{__init__,prompts}.py` · `backend/app/main.py` ·

  전부 주석·문서 안의 문서 경로 한 줄이다. **제품 코드의 로직은 한 줄도 안 바꿨다.**

## 2. 설계 결정

### 옮기는 것은 맨 위 세 절뿐이고 회차 본문은 안 옮긴다

`frontend.md` 1회차 본문(라운드 표·대조에서 갈린 셋)은 **그 세션에서 실제로 일어난 일의
기록**이라 옮기면 거짓이 된다. 반대로 맨 위 세 절은 `문서-최신성.md` 가
*"지금까지 확정된 결정만 모은다. 여기만 읽으면 현재 설계를 안다"* 로 정한 **갱신되는 요약**이라
재분배해도 아무것도 안 잃는다.

**이 구분을 모델이 라운드 2에서 틀리게 설명했다** — "옮겨온다"의 대가로 *"이미 확정된 회차를
사후 편집하게 된다"* 를 달았는데, 옮길 대상이 회차 본문이 아니었다. 사용자가
*"옮겨 적을 수는 없어?"* 로 되물어 잡혔다.

### 복사가 아니라 이동이다

기각한 것: **복사**(양쪽에 남기기). 이유는 이 저장소가 반복해 데인 형태여서다 —
같은 문장이 두 곳에 살면 한쪽만 고쳐진다(`문서-최신성.md` 6회차가 "삼중으로 적힌 계약"을
걷어낸 것과 같다). **실측으로도 이동이 옳았다**: `CLAUDE.md` 와의 30자 겹침이 이사 전
`frontend.md` 3건 → 이사 후 `backend.md` **2건**으로 줄었다. 복사였다면 최소 3건이 유지되고
`frontend.md` 쪽에도 그대로 남아 총량이 두 배가 된다.

### 25개를 세어보고 "다 없애느냐"에 답했다

사용자 질문이 *"backend.md에 옮기면 리스트 다 없애는거야?"* 였다. 세어보니 **남는 5개가 전부
화면 자체의 결정**(HTMX 스택 · 히스토리 자리만 · React 기각 · Streamlit 기각 · Phase 2 착수
기각)이고 나머지 18개는 제목과 내용이 어긋나 있었다. **분류가 곧 답이었다** — `frontend.md`
라는 제목이 실제로 덮는 범위가 25개 중 5개였다.

### 중복 2개는 옮기지 않고 지웠다

- `top_k` 기본값 — `indexing.md` · `검색-생성.md` 가 이미 같은 미결을 이고 있다.
  옮겼으면 같은 질문의 **네 번째 자리**가 생긴다
- `DECISIONS.md` 기각 — `backend.md` 1회차가 이미 `DECISIONS.md 같은 넷째 기록 폴더` 로 썼다

**지운 사실과 이유를 양쪽에 적었다.** 안 적으면 다음 사람이 "이사 중 흘렸나" 를 의심한다.

### 옮긴 18개 중 하나는 새 줄이 아니라 기존 미결로 합쳤다

`frontend.md` 의 *"업로드 버튼을 진짜로 붙일 때 store 를 어떻게 나누나"* 와 `backend.md`
1회차의 *"색인 엔드포인트"* 가 **같은 질문**이었다. 두 파일이 다른 이름으로 같은 것을 열어두고
있었던 것이고, 이사가 그걸 드러냈다. 합치면서 `CLAUDE.md` 와 겹치던 산문은 다시 안 옮겼다 —
위 중복 3 → 2 가 정확히 이 자리다.

### 포인터 12곳 중 10곳만 고쳤다

기각한 것: **전부 고치기**, 그리고 **`frontend.md` 에 `→ backend.md` 스텁 남기기**.

`task_log/2026-08-23-프론트엔드-1회차.md`(2곳)와 `verify_log/…`(1곳)는 **지난 세션의 회고**다.
회고는 그 시점에 무엇을 보고 썼는지가 값어치라 고치면 기록이 사후 편집된다.
스텁 안은 *가리키는 것이 또 가리키는* 2단 포인터를 만드는데, 이 저장소가 지금까지 한 번도
안 만든 형태다.

## 4. 실패 분석

**계획의 전제가 두 번 틀렸고 둘 다 워킹 트리를 다시 봐서 잡혔다.**

1. **"다른 세션이 끝났다"가 틀렸다.** `task_log`·`verify_log`·세 `INDEX.md` 가 쓰인 것을
   보고 세션 종료 의례로 읽었는데, 그 세션은 **다음 작업**까지 가서 `evaluation/inspect.py` ·
   `backend/preview.py` 를 새로 만들고 있었다. 결정적 증거는 `.pytest_cache` 가 **17초 전**에
   갱신된 것이었다. 그 전제 위에 세운 "커밋 A = 프론트 구현"이 성립하지 않았다 — 트리에 두
   작업이 섞였고 세 `INDEX.md` 는 양쪽 변경이 한 파일에 들어 있어 **가를 수가 없었다**
2. **"`frontend.md` 가 바뀌었을 것"도 틀렸다.** 사용자가 변경을 짚어 다시 읽었는데 mtime
   11:44 · 1회차 본문까지 동일이었다. 바뀐 것은 **주변**이었고, **그 확인 과정이 1번을 찾게 했다**

결국 사용자가 직접 커밋해 둘 다 풀렸다. 1회차가 걸어둔 조건 (a)(커밋)와 (b)(세션 종료)가
같은 동작으로 함께 닫혔다.

**그리고 검증 도중에도 한 번 더 움직였다** — HEAD 가 `f6c67f7` → `04e3f4d` 로 바뀌었다
(그쪽이 `query.py` 의 죽은 재수출을 지웠다. 마침 그 파일은 내가 포인터를 고친 파일이기도
했는데 겹친 줄이 달라 충돌은 없었다). **코드가 바뀌었으므로 그 전에 돌린 pytest 를 버리고
다시 돌렸다.** 수치는 같았지만 같은지 확인한 것과 같을 것이라 믿은 것은 다르다.

**막다른 길 하나** — 처음에는 "옮기면 매핑이 끊기나"를 감으로 답할 뻔했다. 사용자가
*"데이터 손실이 일어난다든가 없어?"* 로 물어 실제로 `grep` 을 돌린 것이 **진짜 블로커
(포인터 12곳 · git 미추적)를 찾게 했다.** 감으로 답했으면 커밋 전에 잘라내 되돌릴 곳이
없어졌을 것이다.
