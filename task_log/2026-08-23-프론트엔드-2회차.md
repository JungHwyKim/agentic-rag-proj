## 2. 설계 결정

### "CSS 가 없다"는 버그가 아니라 보는 경로였다 — 판정 근거는 Jinja 주석이다

사용자가 *"예시화면이랑 너무 다르고 CSS 도 없이 텍스트만 있다"* 고 제보했다. 처음엔 내 CSS 가
부실한 것으로만 읽었는데, 두 번째 스크린샷에 `{# 채팅 화면 전체… #}` 가 **글자로 찍혀** 있었다.

**Jinja 주석은 서버가 렌더할 때 사라진다.** 그것이 화면에 보인다는 것은 그 화면에 렌더가 한
번도 안 일어났다는 뜻이고, 곧 `file://` 로 템플릿을 직접 열었다는 뜻이다. `<link
href="/static/app.css">` 가 `file:///static/app.css` 로 풀려 404 이고 htmx 자리도 안 채워진다.

**한 제보 안에 서로 다른 두 문제가 있었고 하나는 고칠 것이 없었다.** 가르지 않았으면 CSS 를
계속 만졌을 것이다 — 사용자 화면에는 그 CSS 가 애초에 로드되지 않는데.

### 소스 태그 가로 배치는 CSS 값이 아니라 마크업 문제였다

`<div class="source">` 가 버튼과 발췌를 쌍으로 감싸는 구조에서는, 발췌가 전체 폭을 쓰려면
래퍼가 `flex: 1 1 100%` 여야 하고 **그러면 버튼도 같이 세로로 쌓인다.** CSS 만 만져서는
못 푼다. 루프를 둘로 나눠 버튼 줄과 발췌 묶음을 분리했다.

**버린 안: 발췌에 id 를 붙이고 토글**. 한 화면에 답변이 여럿 쌓이므로 답변마다 고유 토큰이
필요하고, 그러면 라우트가 토큰을 만들어 넘겨야 한다. `this.closest('.sources')
.querySelectorAll('.excerpt')[N]` 로 범위를 좁히면 같은 효과를 배선 0으로 얻는다.

### 예시 치수를 그대로 쓰지 않았다 — 예시가 실데이터를 대표하지 않는다

화면 구성안은 문서 2개·소스 2개에 파일명이 짧다(`계약서_v2.pdf`). 실제는 문서 5개·소스 5개에
`국가아동권리보장원+권리지원부_제3차+아동정책기본계획+아동용+안내서.pdf` 다.
**태그 줄바꿈·이름 잘림·사이드바 폭은 긴 이름에서만 드러나므로** 예시 값으로 맞추면
확인하려던 것을 정확히 못 본다. 그래서 배치만 예시를 따르고 치수는 실데이터로 잡았다.

파일명은 `22ch` 에서 자르고 원본은 `title` 에 둔다. **쪽 번호는 안 자른다** — 태그의 요점이
`파일 · p.4` 의 뒤쪽이라, 거길 자르면 태그가 존재할 이유가 없다.

### 배너 스타일이 인라인인 것이 이 작업에서 제일 틀리기 쉬운 자리다

`file://` 로 열면 *"이 파일은 서버가 렌더하는 템플릿입니다"* 배너가 뜬다. 그 스타일을
`app.css` 에 두면 **CSS 가 안 왔다는 것을 알리는 배너가 스타일 없이 뜬다** — 자기 자신을
부정하는 배치다. 인라인 `style=` 로 못 박고 `class=` 가 없는지까지 테스트로 잠갔다.

딸린 것: `preview.html` 도 `file://` 로 열리므로 그대로 두면 *"직접 열지 말라"* 가 **정작
직접 열라고 만든 파일에** 뜬다. 생성기가 `id="file-warning"` 으로 지우고, 그 id 의 존재를
테스트가 잠근다(앵커가 빗나가면 조용히 되살아난다).

### 미리보기 산출을 커밋하지 않는다

`preview.html` 은 템플릿을 고치는 순간 낡는다. 저장소에 두면 **어느 시점의 화면인지 아무도
모르게 된다.** 생성기만 커밋하고 산출은 `.gitignore` 다. 거처를 `backend/` 로 둔 것은
렌더 대상이 `backend/app/templates/` 라서이고, `auto_test_check.py` 의 `backend/` → `tests/api`
매핑을 그대로 물려받아 훅 경계를 새로 맞출 필요가 없다.

## 4. 실패 분석

### 미리보기를 아무도 열 수 없는 곳에 두고 "확인해 주세요" 라고 했다

1차로 스크래치패드에 만들었다. 경로가
`AppData\Local\Temp\claude\C--agentic-rag-proj\<세션 uuid>\scratchpad\preview.html` —
**123자**다. 사용자는 그것을 안 열고 다시 `chat.html` 스크린샷을 보내왔고, 나는 그 왕복을
겪고 나서야 경로를 세어 봤다.

**고를 때 본 축이 하나뿐이었다** — *"저장소를 안 더럽힌다"*. **사람이 실제로 열 수 있는가**를
안 봤다. 저장소 루트로 옮겨 같은 세션 안에서 결정을 뒤집었다.

### 같은 진단을 두 번 말하고 세 번째에야 고쳤다

첫 제보에 *"파일을 직접 여신 것 같다"* 고 답했고, 두 번째 제보에도 같은 설명을 반복했다.
**설명이 맞는데 상황이 안 바뀌면 설명이 아니라 배치를 고쳐야 한다.** 배너와 짧은 경로가
그 자리다 — 셋째 왕복에서야 그렇게 했다.

### 셸 heredoc 이 조용히 두 파일을 안 만들었다

`bash` heredoc 으로 테스트 파일 둘을 쓰려다 `unexpected EOF` 로 죽어 **두 파일이 통째로
안 만들어졌다.** `ls` 로 확인하고 `Write` 로 옮겨 썼다. 원인은 못 밝혔다.

### 다른 세션의 중간 상태를 밟았다 (내 실패는 아니지만 기록한다)

검증 중 `tests/retrieval` 이 `ImportError: cannot import name 'retrieve' from
rag_pipeline.retrieval.dense` 로 죽었다. 내 변경이 아니라 `hybrid-search-bm25-rrf` 세션이
`retrieve()` 를 `hybrid.py` 로 옮기던 중이었다. **손대지 않고 피어에게 확인**한 뒤 넘어갔다 —
같은 작업 트리라 고치려 들었으면 그쪽 리팩터를 되돌렸을 것이다.
