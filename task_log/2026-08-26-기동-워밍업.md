# 기동 워밍업 — 첫 질의 19초를 배경으로 옮기되, 기본값은 꺼진 채로 둔다

- 작업일: 2026-08-26
- 검증 방법: 가짜 모델로 계약 9건 + 실제 uvicorn 기동에서 GPU 메모리 관측. **외부 API 호출 없음**(질의를 한 건도 안 보냈다). 전문은 3절

## 1. 무엇을 바꿨나

- `backend/app/core/config.py`
  `warmup_on_startup` 하나를 더했다. **기본값이 꺼짐인 것이 이 작업에서 제일 중요한 한 줄**이다(2절).
- `backend/app/api/routes/query.py`
  `warm_up()` 을 냈고, 모듈 락을 두고, getter 셋의 인자를 `Request` 에서 `FastAPI` 로 바꿨다.
  워밍업에는 요청이 없어서다. 겸해 `_embedder` 를 threadpool 로 넘겼다.
- `backend/app/main.py`
  lifespan 이 데몬 스레드로 `warm_up` 을 띄운다. 설정이 켜졌을 때만.
- `.env.example`
  켜는 줄과 **왜 기본이 꺼짐인지**를 적었다.
- `tests/api/test_warmup.py`
  9건. 2절의 결정 중 되돌리면 조용히 깨지는 것들을 잠갔다.

## 2. 설계 결정

### 설정 축을 넣었다 — 안 넣으려던 것을 뒤집었다

처음 판단은 *"설정을 안 만든다"* 였다. 이 저장소는 죽은 설정을 금지하고
*"안 넘기는 것이 곧 끄는 것"* 을 선호하며, 워밍업은 첫 질의가 어차피 하는 일을 앞당길
뿐이라 새 실패 모드를 만들지 않는다고 봤다.

**틀렸다. `tests/api` 의 일부가 `with TestClient(...)` 로 lifespan 을 진짜로 돌린다** —
`test_query_route.py` 1곳 · `test_shadow_routes.py` 6곳이다. 기본이 켜짐이면
**기본 pytest 가 KURE 가중치 2.27GB 를 내려받고 적재한다.** CLAUDE.md 가 임베딩 provider
핀으로 두 번이나 막아 둔 유출과 같은 종류인데, 여기서는 픽스처가 아니라 **설정 기본값이
유일한 방어**다. `offline_config` 는 이 경로를 안 지난다.

그래서 `RERANK_MODEL` 이 비면 꺼지는 것과 같은 모양으로 뒀다 — **저장소 커밋본은 꺼진 채**,
켜는 것은 모델을 이미 받아 둔 머신의 `.env` 결정.

버린 것: *"테스트 쪽에서 끄게 한다"*. 그러면 새 lifespan 테스트가 생길 때마다 잊고, 잊으면
**아무 에러 없이 2.27GB 가 적재된다.** 방어를 새 테스트의 기억력에 걸지 않는다.

### 배경 스레드다 — 동기 적재를 기각했다

동기로 올리면 첫 질의가 0초가 되는 대신 **기동이 97ms 에서 20초대**가 되고, 모델을 못 받는
환경에서는 서버가 아예 안 떠 화면조차 못 본다. `local_ce.py` 가 *"로딩이 느리거나 실패해도
서버는 떠야 한다"* 를 계약으로 적어 둔 자리다. 배경으로 밀면 그 계약을 지키면서 첫 질의만
덜 문다 — 실측으로 기동 **97ms**, 질의 없이 VRAM **+2.4GB**(3절).

### 락을 넣었다 — 워밍업이 그것을 필요하게 만들었다

전에는 셋을 만드는 쪽이 요청 하나뿐이라 경쟁이 없었다. 이제 배경 스레드가 같은 getter 를
부른다. 락이 없으면 워밍업이 `state.embedder` 를 세팅하기 **전에** 들어온 질의가 자기 것을
또 만들어 **KURE 2.27GB 가 두 벌** 뜬다 — 에러가 안 나고 메모리로만 드러난다.
`_rerank_ready` 는 표시지 락이 아니다.

**그래서 getter 가 `Request` 대신 `FastAPI` 를 받는다.** 워밍업에는 요청이 없는데, 두 경로가
서로 다른 함수를 쓰면 *같은 인스턴스를 공유한다* 는 보장이 사라진다. 버린 것: 워밍업이
`get_embedder()` 를 직접 부르고 결과를 `app.state` 에 꽂는 안 — 그러면 경쟁 구간이 그대로다.

### 임베더도 threadpool 로 넘겼다 (곁다리로 잡은 것)

`_reranker` 는 *"cross-encoder 적재가 초 단위라 이벤트 루프에서 하면 서버 전체가 멈춘다"* 는
이유로 이미 threadpool 에 있었는데, **더 큰 쪽이 밖에 있었다.** 임베더 첫 인코딩이
11.8~14.7초다(`verify_log/2026-08-26-첫질의-대표값.md`). 워밍업이 꺼져 있으면 첫 질의 동안
서버 전체가 그만큼 멈춘다. 같은 이유가 더 크게 적용되는 자리라 같이 넘겼다.

### 리랭커 워밍업 후보는 둘이다

`local_ce.rerank()` 는 `len(candidates) <= 1` 이면 모델을 안 올리고 받은 것을 그대로
돌려준다. **하나만 먹이면 워밍업이 조용히 리랭커를 안 데운다** — 그 실패는 *"첫 질의가
여전히 느리다"* 로만 드러나므로 테스트로 잠갔다.

### BM25 와 저장소는 일부러 뺐다

BM25 구축은 414청크에서 **0.09초**라 회수할 것이 없다. 더 중요하게는 `embed_query()` 도
`rerank()` 도 qdrant 를 안 열어서, **워밍업이 저장소를 한 번도 안 건드린다.** lifespan 이
*"색인이 아직 없으면 서버가 아예 안 뜬다"* 로 남겨 둔 게으름이 그대로 유지된다.
BM25 를 데우면 그 게으름이 깨진다.

### 실패는 삼키되 조용히는 아니다

워밍업 실패가 서버를 죽이면 게으른 적재보다 나빠진다. 그래서 예외를 잡되
`app.state.warmup_errors` 에 남긴다. 버린 것: `pass` 로 완전히 무시 — 이 저장소에서
조용한 실패는 늘 수치로만 드러났고, 그때마다 비쌌다.

## 4. 실패 분석

**시그니처만 바꾸고 호출부를 안 고쳐 `tests/api` 가 무더기로 깨졌다.** getter 를
`Request` → `FastAPI` 로 바꾼 뒤 `ask()` 의 `_embedder(request)` 를 그대로 뒀더니,
`app.state` 가 실제로는 `request.state`(요청 단위 상태)를 가리켜 `KeyError: 'ingest_config'`
가 났다. **타입 힌트가 있는데도 안 잡혔다** — `from __future__ import annotations` 라
런타임 검사가 없고, `Request` 와 `FastAPI` 둘 다 `.state` 를 갖고 있어 속성 접근이 성립하기
때문이다. 뒤늦게 `_reranker` 호출부 하나가 더 남아 있어 같은 실패를 한 번 더 봤다.

교훈은 **시그니처와 호출부는 같은 편집에서 끝낸다**는 것이고, 이 파일을 나중에 갈라 담을
사람에게도 같은 함정이다 — 시그니처를 되돌리면서 호출부만 남기면 정확히 이 실패가 난다.

**내가 쓴 테스트가 `.env` 를 타고 있었다.** `.env` 에 `WARMUP_ON_STARTUP=true` 를 넣자마자
`test_lifespan_skips_warmup_by_default`(지금 이름은 `..._when_disabled`)가 깨졌다 — `Settings` 가 `PROJECT_ROOT/.env` 를
읽으므로 "기본값" 을 확인한다던 그 테스트가 실은 **개발자 머신의 설정**을 확인하고 있었다.
CLAUDE.md 가 임베딩 provider(2026-08-25)와 리랭커 장치(`test_rerank.py` 픽스처)에서 **이미
두 번 적어 둔 함정**인데 같은 세션에서 또 밟았다. 고친 방식도 같다 — `monkeypatch.setenv` 로
명시로 끄고, *기본값이 꺼짐* 은 `Settings(_env_file=None)` 을 쓰는 별도 테스트가 잠근다.

**커밋 훅이 잡았다는 것이 이 항목의 요점이다.** 켜기 전에는 통과했고 켠 뒤에 깨졌으니,
`.env` 를 안 켰으면 **이 테스트는 거짓 통과를 계속했을 것**이다.

**설정을 안 만들려던 판단도 되돌렸다** (2절 첫 항목). 되돌린 계기는 추측이 아니라
`grep -rn "with TestClient"` 였다 — *"API 테스트는 lifespan 을 안 돈다"* 는 것을
`test_index_route.py` 주석에서 읽고 사실로 믿었는데, **그 주석이 자기 파일 이야기였다.**
같은 폴더의 다른 파일 둘이 정반대로 하고 있었다. 문서를 읽어 얻은 전제는 그 문서가 말하는
범위까지만 참이다.

## 5. 회귀 테스트

`tests/api/test_warmup.py` 9건. 2절의 결정과 이렇게 대응한다.

| 결정 | 테스트 |
|---|---|
| 기본값 꺼짐 | `test_warmup_is_off_by_default` |
| lifespan 배선 | `test_lifespan_starts_warmup_when_enabled` · `test_lifespan_skips_warmup_when_disabled` (**둘 다 `monkeypatch.setenv` 로 `.env` 를 덮는다** — 4절) |
| 만들기가 아니라 **쓰기** | `test_warm_up_actually_uses_both_models` |
| 후보 2개 | `test_warm_up_feeds_the_reranker_more_than_one_candidate` |
| 리랭커 꺼짐이 정상값 | `test_warm_up_skips_a_disabled_reranker` |
| 실패해도 안 던진다 | `test_warm_up_does_not_raise_when_a_model_fails` |
| 락 | `test_getter_returns_one_instance` · `test_concurrent_getters_build_once` |

**못 막은 것**: 4절의 시그니처/호출부 불일치는 `tests/api` 의 기존 테스트가 잡았지만
**이 파일이 잡은 것은 아니다.** 그리고 워밍업 후 첫 질의가 실제로 빨라지는지는 과금 없이
못 재서 테스트가 없다.

## 7. 남은 것

- **워밍업 후 첫 질의의 실제 왕복을 못 쟀다** — 생성 LLM 1회가 과금된다. 지금 *약 4.3초로
  수렴할 것* 은 추론이고 측정이 아니다. 이 회차의 가장 큰 공백이다
- **워밍업 도중에 들어온 질의**는 락을 기다린다. 단위 테스트로 잠갔지만 실제 모델 적재
  중에 요청을 보내 보지 않았다
- **CPU 전용 머신**에서 배경 워밍업이 63.9초를 무는 동안의 모습을 안 봤다
- **이 머신의 `.env` 는 켰다**(사용자 결정). **저장소 커밋본은 꺼진 채다** — 켜자마자
  위 4절의 `.env` 의존 테스트가 깨진 것이 그 결정의 부수 효과였다
