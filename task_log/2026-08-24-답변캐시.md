## 2. 설계 결정

### 컬렉션은 가르되, 질문과 답은 한 point 에 넣었다

사용자의 첫 안은 *질문은 `user_query` 컬렉션, 답변은 `llm_response` 컬렉션* 이었다.
**가르는 것 자체는 맞다** — 문서와 섞으면 `iter_chunks()`(BM25 가 전량 훑는다)와
`list_documents()`(사이드바)가 캐시를 문서로 세고, 필터로 가르는 길은 `indexing.md` 가
`search(filters=...)` 를 안 만들기로 하며 이미 닫았다.

**질문과 답을 가르는 쪽을 버렸다.** qdrant 는 point 마다 벡터가 **필수**라, 답변 컬렉션을
만들면 *아무도 검색하지 않는 답변에 임베딩 비용*이 붙는다. 더 나쁜 것은 쓰기가 둘로 갈리는
것이다 — 질문만 저장되고 답변 저장이 실패하면 **캐시가 히트하면서 빈 답을 돌려준다.**
답은 검색 대상이 아니라 질문에 딸린 값이라 payload 가 제자리다.

### 이름은 `collection_name_for()` 를 반드시 거치게 했다

`qa_cache` 를 고정 이름으로 두면, 임베딩 모델을 갈아탄 뒤 **옛 모델 벡터가 든 캐시에 새 모델
질의 벡터로 유사도를 재게 된다.** 검색 품질만 조용히 나빠져 늦게 발각되는 종류다. 그래서
`prefix=` 인자를 열어 파생 규칙(`{prefix}_{model}_{dim}`)을 **공유**했다 — 캐시가 자기 규칙을
지어내는 안을 버렸다. 같은 세션에 임베딩 모델 비교를 진행 중인 `agentic-rag-proj-66` 이
독립적으로 같은 지적을 보내와 이 선택이 교차 확인됐다.

곁들여 그쪽이 준 정보 하나가 결정을 굳혔다 — **`collection_name_for()` 도 임베딩 캐시
`_salt` 도 `(model, dimensions)` 에서만 파생하고 `provider` 는 안 들어간다.** provider 축이
열리면 *같은 모델 이름을 두 provider 가 서빙할 때 키가 충돌한다*. 캐시가 파생을 직접 하지
않으므로 **그 결정이 자동으로 따라온다** — 여기서 별도 규칙을 만들면 그 추종이 깨진다.

### 클라이언트를 빌린다 — 두 번째 저장소를 안 연다

`get_store()` 를 한 번 더 부르는 안을 버렸다. qdrant 로컬 파일 모드가 디렉터리에 배타 잠금을
걸어 **같은 uvicorn 안에서 자기 자신과 충돌한다**(backend 는 `lifespan` 에서 이미 하나 열어
들고 있다). `.qdrant_cache` 로 경로를 가르는 안도 버렸다 — 잠금은 피하지만 프로세스가 파일
잠금 둘·클라이언트 둘을 들고 `lifespan` 이 둘을 여닫아야 한다.

한 클라이언트가 여러 컬렉션을 보는 것은 qdrant 의 정상 사용이고, **닫을 것은 여전히 하나다.**
`QdrantStore.client` 는 `_qdrant` 를 그대로 통과시켜 **게으름을 지킨다** — 참조만 들고 안 쓰면
파일이 안 열린다. `lifespan` 이 embedder·BM25 를 첫 질의로 미루며 지켜온 성질이다.

### 임계값에 기본값을 두지 않았다

이 기능의 위험은 하나다 — **임계값이 헐거우면 다른 질문에 옛 답을 준다.**
`plan_log/embedding.md` 가 semantic cache 를 7번(제일 뒤)으로 밀며 적어둔 이유가 정확히
그것이고, 근거는 평가 세트가 서야 나온다고 했다.

**세트는 생겼는데 근거는 아직 안 섰다.** 이번에 재보니 `qa_set.jsonl`(60)과
`qa_set_human.jsonl`(20)의 `gold_spans` 교집합이 **0건**이라 *같은 뜻 다른 말* 쌍이 한 쌍도
없다. 임계값을 정하려면 그 쌍의 분포와 서로 다른 질의의 분포를 대조해야 하는데, 양성 쪽이
통째로 비어 있다.

그래서 `0.95` 를 임시값으로 넣는 안을 버렸다. 이 저장소의 임계값은 전부 **분포의 틈**에서
나왔다 — 표 되붙이기 12pt(조각난 표 6.8 vs 별개 표 18.8 이상), 표시 면적비(음영 1.00 vs
표시 0.08~0.10, 그 사이에 값이 없다). 근거 없는 수를 기본값으로 두면 **그 사실이 조용히
묻힌다.**

대신 `answer_cache_threshold: float | None = None` 로 두고 **없으면
`get_answer_cache()` 가 `None` 을 돌려준다.** 근거 없는 수가 코드에 존재할 수 없는 모양이고,
켜는 것은 재고 나서 `.env` 에 숫자가 들어가는 순간이다.

**임계값은 임베딩 모델에 딸린 값이기도 하다.** 컬렉션 이름에 모델이 박히는 것이 *벡터
혼입*은 막아주지만 **임계값은 이름이 안 지켜준다.** `text-embedding-3-small` 에서 잰 0.9x 가
다른 모델에서 같은 뜻이라는 보장이 없다.

### 캐시 실패는 예외가 아니라 미스다

로더의 *빈 결과 + 경고* 규약이 성립하는 조건은 **내려갈 층이 있는가**이고 여기는 있다 —
정상 검색·생성이 그대로 돈다. embedding·indexing 이 예외를 던지는 것은 그 층이 없어서였다.
그래서 **새 예외를 안 만들었고 `_STATUS_BY_EXCEPTION` 에도 안 더했다**(빠뜨린 것이 아니다).

캐시가 죽어서 질의가 죽으면 최적화가 신뢰성을 깎은 것이 된다.

### 무효화는 근거 point 생존 + 텍스트 해시. TTL 을 버렸다

TTL 은 **축이 어긋난다** — 코퍼스가 안 바뀌면 한 달 전 답도 옳고, 바뀌면 1분 전 답도 틀리다.
시간은 그 둘을 못 가른다. 컬렉션 전체 지문(`count()`)도 버렸다 — 구현은 제일 짧지만 문서
하나만 바뀌어도 캐시가 전멸하고, 같은 수를 유지하는 수정은 못 잡는다.

`point_id_for()` 가 결정론적이라 **재색인해도 같은 청크는 같은 id** 다. 저장한 근거 id 를
되짚으면 *삭제*가 잡히고, 텍스트 해시까지 보면 *수정*도 잡힌다.

### 배지는 원 질문을 그대로 보여준다

*티 안 내기*를 버렸다. 임계값이 살짝 헐거워도 **오답이 아니라 사용자가 알아볼 수 있는
오류**가 되는 것이 이 표시의 값어치다. `cached: bool` + `cached_query` + `cached_at` 로 쪼개는
안도 버렸다 — *`cached=True` 인데 `cached_at` 이 없는* 못 쓰는 조합이 생기고 템플릿이 매번
방어하게 된다. `CacheOrigin` 한 덩어리를 `None` 로 두면 판정이 한 곳에서만 일어난다.
이 저장소가 두 번 같은 선택을 했다 — `RetrievedChunk` 의 경로별 점수 `float | None`,
`StoredChunk` 와 `SearchResult` 를 가른 것. 둘 다 *"0.0 과 없음은 다르다"* 였다.

## 4. 실패 분석

### `RetrievedChunk` 에 point id 가 있다고 가정했다

무효화 payload 를 `[source.id for source in answer.sources]` 로 짰다. **`RetrievedChunk` 에는
`id` 가 없다** — 저장소 신원을 든 것은 `StoredChunk.id` 인데 승격 과정에서 떨어진다.
테스트를 쓰다 필드 목록을 확인해서 잡았다.

무서운 것은 **이게 예외로 안 죽었을 수도 있다는 것**이다. `AttributeError` 는 `put()` 의
`except Exception` 이 삼켜 경고 하나로 끝나므로, 캐시가 조용히 아무것도 저장 안 하는 상태로
살았을 수 있다. `point_id_for(source.chunk_id)` 로 되만들도록 고쳤고,
`test_invalidation_looks_up_derived_point_ids` 가 **되짚는 id 목록 자체**를 단언한다 —
이 파생이 어긋나면 모든 히트가 조용히 미스가 되는 자리라 결과가 아니라 열쇠를 잠갔다.

### NFD 단언이 헛돌았다

`cache_point_id_for("…".encode().decode())` 로 자모 분리를 만들려 했는데 **무연산**이라
원본과 같은 문자열을 비교하고 있었다. 통과했지만 아무것도 검증하지 않았다 —
`verify-log` 0단계가 경고하는 *자기 확인*이다. `unicodedata.normalize("NFD", …)` 로 고치고,
**"NFD 결과가 원본과 실제로 다른지"를 먼저 단언**하도록 바꿨다.

### `query.py` docstring 이 붙는 자리를 틀리게 적어두고 있었다

*"semantic cache … 붙는 자리는 `retrieve()` 와 `generate_answer()` 사이다"* 로 적혀 있었다.
거기 두면 **검색은 이미 돌아버려** 아끼는 것이 LLM 호출 하나뿐이다. 앞에 두면 검색·생성이
통째로 빠진다. 문장을 고치고, `test_cache_hit_skips_retrieval_and_generation` 이
`retrieve.call_count == 0` 을 단언해 다시 뒤로 못 가게 막았다.

### backend 테스트가 `lifespan` 을 안 거친다는 것을 잊었다

`request.app.state.answer_cache` 로 직접 읽었더니 `tests/api` 5건이 `KeyError` 로 깨졌다.
그 테스트들은 **일부러** `with` 없이 `TestClient` 를 쓴다 — 아니면 개발자의 실제 `.qdrant` 를
열고 배타 잠금까지 잡는다. `getattr(..., None)` 으로 바꿨다. 기존 `_embedder`·`_bm25` 가
이미 같은 패턴이었는데 그것을 안 보고 짰다.

### 미스일 때 질의 임베딩이 두 번 일어난다 — 고치지 않기로 했다

캐시 조회와 `search_dense` 가 각자 `embed_query()` 를 부른다. `retrieve()` ·`hybrid` ·
`search_dense` 셋에 `query_vector=` 를 넘기는 안을 짜다 **되돌렸다** — 벡터를 넘기는 경로와
안 넘기는 경로가 갈려 *어느 쪽이 실제로 돌았는지*가 호출부마다 달라진다. `_embed_all()` 이
`ResultCache` 를 거쳐 같은 문자열은 API 를 다시 안 타므로 실제 비용은 디스크 읽기 하나다.
docstring 에 근거와 함께 남겨 다음 사람이 같은 길로 다시 안 들어가게 했다.

- **캐시 상한·퇴거 규칙.** 항목이 몇 개까지 늘지 안 쟀다. 수를 지어내지 않았다

  아니라 Conversation History(6번)다. 이번 범위 밖이고, 그 로그가 생기면 패러프레이즈 쌍의
  재료가 된다
