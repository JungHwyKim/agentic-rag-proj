# 리랭커를 `retrieve()` 안에 넣고, 바닥 2 × 구현체 2 비교를 배선했다

- 작업일: 2026-08-25
- 검증 방법: `ruff check .` + 전체 `pytest`. **외부 API 호출 없음** — 두 구현체 모두
  모듈 레벨 이음새(`_make_client()` · `_load_model()`)를 가짜로 갈아끼워 돌렸다.
  실파일 위 품질 측정은 **안 했다**(사용자 승인 대기 + 무료 갈래도 아직)

## 2. 설계 결정

### 리랭커를 `retrieve()` **안**에 넣었다 — 밖이 아니라

핸드오프가 *"리랭커에 `retrieve()` 의 `top_k` 가 아니라 후보 풀을 먹여야 한다"* 를
**제일 중요한 배선 요구**로 넘겼다. 트리와 대조하니 **전제가 틀렸다** — 후보 풀은 원래부터
밖에서 닿는다. `retrieve(top_k=50, bm25=...)` 이면 `limit = max(candidate_k, top_k)` 라 풀이
그대로 나오고, 여지를 잰 탐침이 정확히 그 방법을 썼다.

그래서 물음은 *"풀에 닿느냐"* 가 아니라 **"절단을 누가 하느냐"** 였다.

버린 안: **호출부가 `retrieve(top_k=candidate_k)` 로 받아 밖에서 리랭크·절단.** 시그니처
변경이 0 이라 매력적이었는데, `top_k` 의 뜻이 **"최종 개수"와 "후보 수"로 갈린다.**
`query.py`·`run_eval`·`backend/routes/query.py` 셋이 각자 풀 폭과 절단을 알아야 하고,
**한 곳만 빠뜨리면 조용히 리랭커 없이 돈다.** 풀 전체를 보는 자리는 `fuse()`/`_dense_only()`
하나뿐이라 절단을 거기 남겼다.

같이 버린 안: **새 진입점 `retrieve_and_rerank()`.** 호출부가 두 호출 규약을 동시에 알게
되는데, 2회차가 `HybridRetriever` 클래스를 기각한 이유가 정확히 그것이다.

딸린 수정 하나가 중요하다 — **dense-only 갈래도 풀을 넓혀야 한다.** 전에는
`limit = max(candidate_k, top_k) if use_bm25 else top_k` 였다. 그대로 두면 BM25 없이
리랭커만 켰을 때 리랭커가 볼 것이 `top_k` 개뿐이라 **이 회차가 노린 11~50위의 여지를
통째로 버린다.** 지금은 `use_bm25 or reranker is not None` 이 넓힘 조건이다.

### 실패는 **통째로 버린다** — 반쯤 채우지 않는다

이 저장소에 정반대 선례가 둘 있다. `표-경로.md` 11회차는 *"Vision 이 격자와 모양이 다른
답을 주면 통째로 버린다"* 이고, 13회차는 *"모델이 채운 만큼 쓰되 경고를 남긴다"* 이다.

앞을 골랐다. 근거는 **지금 이 단계를 재는 중**이라는 것이다 — 순서를 반쯤 바꾸면
*"리랭커가 나쁜가 응답이 반쪽이었나"* 를 못 가르고, 그 구분이 안 되면 2×2 비교표의 한 칸이
통째로 의미를 잃는다. 실사용 품질을 볼 때(켤 조합이 정해진 뒤) 13회차 잣대를 다시 본다.

버린 안 셋: 채운 만큼 쓰기 · 부족하면 한 번 재호출(12회차 잣대) · 예외를 던지기.
셋째는 규약 위반이다 — 내려갈 층(RRF 순서)이 **있으므로** 로더의 *빈 결과 + warn* 쪽이다.

구현으로는 `apply_scores(candidates, scores)` 가 `len(scores) != len(candidates)` 면
**아무것도 안 채우고 받은 순서를 그대로 돌려준다.** `RetrievedChunk.ranking_score` 가
`rerank_score` 없으면 `fused_score` 로 떨어지므로, 안 채운 것이 곧 RRF 순서다.

### 순위가 아니라 **점수**를 받는다

`rerank_score` 가 `float | None` 이다. 순위만 받으면 그 칸에 역순위 같은 **지어낸 수**를
넣게 되는데, 그것은 점수를 버리고 순위를 쓰는 RRF 를 한 번 더 하는 셈이다.

곁들여 얻은 것: cross-encoder 는 본래 점수를 내므로 **두 구현체의 반환 모양이 저절로
같아진다.** 순위로 맞췄으면 로컬 쪽에서 점수를 순위로 눌렀다가 다시 펴야 했다.

동점은 들어온 순서(=fused 순서)가 이긴다 — 정렬이 stable 이고, `fusion.py` 의
*"동점은 dense 가 이긴다"* 와 같은 모양이다.

### 구현체를 **둘** 만들었다 — 1회차의 "로컬 우선" 근거가 둘 다 무너져서

1회차는 *"Reranker 는 로컬 우선"* 을 확정하며 근거를 하나 댔다 — *"기본 pytest 는 키 없이
전부 통과를 지키는 것이 로컬뿐"*. **그 근거가 2회차에 이미 죽어 있었다**: 인자 주입
(`retrieve(reranker=None)`)이 자리잡으면서 유료든 무료든 안 넘기면 테스트가 안 깨진다.

두 번째 근거 *"torch 를 안 들인다"* 는 이 세션 도중에 죽었다. 다른 세션이 기본 임베더를
`nlpai-lab/KURE-v1` 로 갈아타며 `torch`·`sentence-transformers` 를 `requirements.txt` 본체로
옮겼다(`requirements-local.txt` 삭제).

**근거 둘이 다 없어졌다는 것을 알려준 것은 그 세션이다.** 안 들었으면 낡은 근거로 갔다.
그래서 사용자에게 다시 물었고 **둘 다 만들어 견주는 쪽**으로 갔다 — 1회차가 세운 비교 축
6번(*리랭커 로컬 vs 상용*)이 그것이다.

그 결과 `rerank_provider` 가 **살아 있는 설정**이 됐다. `embedding_provider` 가 두 번째
구현체가 생기며 살아난 것과 같은 자리이고, 같은 날 `answer_cache` 가 Protocol 을 안 만든
것과 갈리는 기준도 이것이다 — **두 번째 구현체가 실재하는가.**

### `RERANK_MODEL` 이 비면 꺼진다 — 기본값을 두지 않았다

`answer_cache_threshold` 와 글자 그대로 같은 모양이다. 이유는 다르다 — 저쪽은 *근거 없는
임계값이 코드에 존재할 수 없게* 하려는 것이고, 이쪽은 **켜는 순간 질의당 LLM 호출이 1→2**
가 되기 때문이다. 값을 하는지 재기 전에 과금이 먼저 붙는 것을 막는다.

버린 안: 기본 켜짐(모델 기본값을 둔다) · 평가 전용(설정 없이 러너에서만). 뒤엣것은
`bm25`·`cache` 가 전부 설정으로 살아 있는 것과 비대칭이 된다.

### `RerankConfig` 를 `RetrievalConfig` 에 안 섞었다

`EVAL_SETTINGS["retrieval"]` 이 그 블록을 통째로 고정한다. 섞으면 **리랭커를 안 켠
dense·hybrid 실행에도 모델 이름과 과금 설정이 실린다** — 리포트만 보고 그 실행이 무엇을
썼는지 판단하는 규약이 흐려진다.

### `rerank_device` 를 `EMBEDDING_DEVICE` 와 **이름 규칙까지** 맞췄다

같은 함정이라서다 — CPU 와 GPU 가 미세하게 다른 점수를 내면 같은 명령이 머신마다 다른
순위를 만들고 **비교표가 에러 없이 흔들린다.** `EVAL_RERANKERS["local"]` 에 `cpu` 를 못
박았고, **새 로컬 프로필이 그것을 빠뜨리면 실패하는 테스트**를 함께 넣었다
(`test_local_rerank_profiles_pin_the_device`).

이 축은 다른 세션이 임베딩 쪽에 걸어둔 가드를 그대로 베낀 것이고, 그쪽이 남긴 주석이
*"리랭커 축도 같은 함정이라 같은 이름 규칙으로 붙을 예정이다"* 라고 미리 적어 두었다.

### 기준선(`baseline.json`)을 **안 건드렸다** — 스스로 낸 안을 물렸다

면담 라운드 1에서 *"기준선을 hybrid 로 갱신"* 을 골랐다. 근거는 2회차의
*"기준선이 dense 라 그것이 곧 원하는 비교"* 를 그대로 이어받은 것이었다 — 이제 원하는
비교가 hybrid 대비이니 올리자는 것.

**다른 세션이 실측으로 막았다.** `evaluation/README.md` §3 이
*"대조군은 dense 다 — `--hybrid` 를 켜지 않는다"* 를 못 박아 뒀고 근거가 실측이다:
**겹침 0 구간에서 BM25 는 신호를 안 더하면서 잡음은 더한다**(그 구간 5건 악화, 둘은
`k=20` 밖). 그 구간이 진행 중인 임베딩 모델 비교가 **재려는 바로 그 자리**다.

직접 읽어 확인하고 사용자에게 다시 물어 **안 건드리는 쪽**으로 갔다. 실체는
*"어느 것이 더 나은 기준선인가"* 가 아니라 **한 파일이 두 자[尺] 노릇을 하려던 것**이었다.

딸려서 하나가 풀렸다 — **2회차가 "갈래별 기준선"을 기각한 사유가 더 이상 성립하지 않는다.**
기각 이유는 *"서로 다른 파일을 손으로 대조해야 한다"* 였는데, 그 사이
`evaluation/overlap.py` 가 **두 실행 라벨을 직접 받는** 저장소 코드로 승격됐다(2026-08-24).
**기각을 되살린 것이 새 논거가 아니라 새 도구다.**

### 후보 50 전부·청크 전량을 먹인다

버린 안 둘. **상위 20만**은 여지 측정이 반박한다 — `ai-03`(#30)·`ai-12`(#26)가 20 밖이라
자르면 Phase 3 을 시작한 이유를 일부 버린다. **청크를 앞 N 자로 자르기**는 N 이 근거 없는
수가 되는데(이 저장소의 임계값은 전부 분포의 틈에서 나왔다), 더 나쁜 것은 이 코퍼스의
정답 span 이 **마크다운 표의 행에 흩어져 있어** 앞을 자르면 헤더만 남는다는 것이다.

### 리랭커는 첫 질의에 만든다 — `embedder` 축이지 `bm25` 축이 아니다

`bm25` 를 미루는 이유는 *저장소의 게으름을 깨지 않으려고*이고, 리랭커는 저장소를 안 훑는다.
미루는 진짜 이유는 **로컬 갈래가 cross-encoder 가중치를 올린다**는 것 — startup 에서 만들면
그 시간만큼 서버가 안 뜨고, 모델을 못 받는 환경에서는 화면조차 못 본다. `embedder` 가
*"키가 없으면 그 자리에서 예외"* 라 미뤄진 것과 같은 축이다.

**`None` 이 정상값이라 만들었다는 사실을 따로 표시해야 했다.** `state.reranker is None` 으로
판정하면 **꺼져 있을 때 질의마다 다시 만든다** — 지금은 비용이 없지만 로컬 갈래에서는 그
자리가 곧 모델 적재다. `_rerank_ready` 플래그가 그것이다.

## 4. 실패 분석

### 회귀를 한 번 잘못 짚었다 — 남의 과도 상태를 내 결함으로 읽을 뻔했다

첫 전체 실행이 **5 failed** 로 끝났다. `test_indexing_real.py::test_every_chunk_finds_itself`
넷과 `test_indexing_pipeline.py::test_collection_name_is_reported` 하나다. 원인 문자열이
`shapes (103,1024) and (8,) not aligned` — **저장 벡터 1024차원 vs 질의 벡터 8차원**이다.

내가 만진 곳은 indexing 이 아니라 곧바로 남의 것으로 넘길 뻔했는데, **그것도 확인 없이는
같은 종류의 잘못**이라 다시 돌렸다. 같은 트리에서 `tests/ingestion/indexing` 107건이 전부
통과했다.

가른 것은 **시간과 stderr** 다. 실패한 실행은 35분 42초였고 stderr 에
`Loading weights: 391/391` 이 찍혔다. 재실행은 **99초**이고 그 줄이 없다. 그 35분 사이에
다른 세션이 `tests/conftest.py` 의 `_embedding` 에 `embedding_model="text-embedding-3-small"`
을 더했다 — **`provider` 만 박으면 모델 이름이 로컬 기본값(`nlpai-lab/KURE-v1`)으로 남는
앞뒤 안 맞는 설정**이 되고, 그 상태에서 픽스처가 KURE 가중치를 올려 1024차원을 만든다.

**내 35분짜리 실행이 그 고치기 전 상태를 스냅샷으로 잡았다.** 긴 실행일수록 이 위험이 크다 —
한 트리에 세션이 여럿이면 **전체 pytest 는 시작 시점이 아니라 실행 구간 전체의 트리를
본다.**

### `EVAL_RERANKERS` 를 정의하기 전에 참조했다

`EVAL_SETTINGS["rerank"] = EVAL_RERANKERS[...]` 를 파일 **위쪽** dict 에 넣고 정의를 아래
두어 `NameError` 로 5개 파일이 collection error 를 냈다. 훅이 즉시 잡았다. 대단한 실수는
아니지만 기록해 두는 이유는 **`EVAL_SETTINGS` 가 다른 dict 를 참조하는 구조가 이미 있고
(`embedding`) 그것을 베끼면서 순서를 안 봤다**는 것이다.

### `as_baseline()` 을 관대하게 만들 뻔했다

`keys` 에 `retriever`·`rerank_profile` 을 더하니 `test_profile_axis.py` 의 `_report()` 헬퍼가
`KeyError` 로 셋 깨졌다. **`report.get(key)` 로 바꾸면 즉시 초록이 된다** — 그리고 그것이
정확히 이 키가 고치려는 결함이다(빠진 키가 조용히 사라져서 기준선 파일만 보고 dense/hybrid 를
못 가렸다). 헬퍼 쪽을 고치고, **왜 관대하게 안 만들었는지**를 그 자리에 주석으로 남겼다.

`tests/evaluation/test_eval_config.py` — `rerank` 블록을 `_MODELS` 이름 가드에 넣었고,
프로필 축 가드 여섯을 임베딩과 같은 모양으로 더했다. 그중
`test_env_cannot_turn_the_default_off_profile_on` 이 **개발자 `.env` 가 꺼진 기본값을 켜서

## 7. 남은 것

> **이 절의 앞 다섯은 같은 날 무료 칸 측정으로 대부분 닫혔다** —
> `verify_log/2026-08-25-리랭커-2x2-무료칸.md`. 아래는 그 뒤 상태다.

- **2×2 비교표가 6칸 중 4칸 찼다.** 무료 칸(C1·E2·C2·E4)이 전부 끝났고 **과금 0 · 폴백 0건**
  이다. 요지 셋 — 리랭커는 값을 하고(`nDCG@5` +0.248 baseline · +0.133 KURE),
  **바닥이 좋아질수록 이득이 줄고**, **천장은 못 올린다**(`hit@50` 두 바닥 모두 불변).
  천장을 올린 것은 임베더 교체다 — 둘은 **보완재**다
- **유료 실행 둘(E1·E3)은 여전히 사용자 승인 대기.** 실행당 $1~2 **예상**이고 실제 값은
  리포트 `usage.rerank_tokens` 에 있다
- ~~**"풀 밖" `query_id`**~~ — **넘겼다.** `sih-07` 하나뿐이고(baseline 때 7건),
  6건을 끌어온 것은 리랭커가 아니라 임베더 교체다
- ~~**로컬 CE 의 CPU 지연**~~ — **쟀다. 쌍당 1.03초 · 질의당 51초로 화면에 못 쓴다.**
  같은 색인 경로 대조군이 21초인데 리랭커 실행이 2,383초다. *"느리면 그 사실 자체가 결과"*
  라고 적어둔 것이 그대로 됐다
- **한국어 CE 는 절반 닫혔다** — `bge-reranker-v2-m3` 는 쟀고, `ko-reranker` 는 **컨텍스트
  상한만** 봤다(512, 우리 청크 14.7%를 자른다). **기각이 아니라 감수**다 — 되살릴 11건 중
  512 초과가 0개이고, `sch-13`·`sch-14` 가 자연 대조군이 된다
- **새로 열린 것 둘** — 시행령이 `sih-06` **1→12** 로 나빠진 이유, KURE 바닥 겹침 0 구간의
  **↑8 ↓6**(3회차가 달아둔 융합 재판정 조건이 여기서 발화한다). **리랭커를 켤지 정하기 전에
  둘 다 봐야 한다**
