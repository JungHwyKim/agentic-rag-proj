# 평가 baseline 을 재현 가능하게 만든다 — 수치는 있었지만 기준선은 없었다

- 작업일: 2026-08-23
- 검증 방법: `ruff` · `pytest` 전체 · `run_eval --check` · `run_eval --dense`(사용자 승인).
  **실제 청구 0** — 임베딩이 문서·질의 둘 다 캐시 적중이라 `usage` 가 0토큰이었고,
  `vision_calls` 도 네 문서 모두 0 이다

## 1. 무엇을 바꿨나

- `evaluation/config.py` (신설)
  `EVAL_SETTINGS` 와 `eval_config()`. 평가가 쓰는 적재 설정을 코드에 못 박는다.
- `evaluation/corpus.py`
  `--check` 의 파싱이 `IngestConfig()` → `eval_config()`. **`--dense` 와 같은 설정을 써야
  하는 쪽**이다.
- `evaluation/run_eval.py`
  한 번 검색해 여러 k 로 채점(`by_k`) · 적재 카운터 수집 · `--save-baseline` ·
  기준선 대비 질의별 승·패·무.
- `rag_pipeline/ingestion/pipeline.py`
  `IndexResult` 에 `metadata: DocumentMetadata`. 적재 카운터로 가는 길이 없었다.
- `tests/evaluation/test_eval_config.py` (신설)
  `.env` 가 못 흔드는지 · 오타가 조용히 무시되는 자리 · 두 경로가 같은 설정을 쓰는지.
- `evaluation/README.md`
  새 플래그와 고정 설정, 그리고 기준선 수치.
- `evaluation/baseline.json` (신설)
  첫 재현 가능 기준선. `--save-baseline` 이 만든다.
- `.claude/hooks/task_log_check.py` · `tests/hooks/test_record_hooks.py`
  `SOURCE_PREFIXES` 에 `evaluation/` 을 더했다. 이 작업이 스스로 연 구멍을 닫는다.

## 2. 설계 결정

### 이 단계의 품질 검사는 chunking 과 축이 다르다 — 그래서 "순서"의 답이 바뀐다

사용자가 *"chunking까지 품질 검사 진행했어. 이제 embedding-vectordb 차례인데 순서"* 를
물었다. **`embedding → vectordb` 가 답이 아니다.** chunking 까지는 산출을 원문과 눈으로
대조했는데 1536개 실수에는 대조할 원본이 없다. 축이 둘로 갈리고 한쪽은 이미 닫혀 있다 —
`tests/ingestion/indexing/` 9파일과 `verify_log/2026-08-18-indexing-실벡터.md` 가 기계적
정합성을 덮는다. 남은 것은 **검색으로 재는 것 하나**이고, 그것이 `plan_log/평가-세트.md`
2회차가 예약해 둔 첫 dense 측정이다. 그래서 순서는 **정합성(끝남) → 검색 품질(지금)** 이다.

### 수치는 이미 있었다. 없는 것은 기준선이었다

작업 도중 다른 세션이 이미 dense 를 돌린 것을 발견했다(2026-08-22 16:42,
`hit@10 0.483 · MRR 0.253 · misses 31/60`). 그런데 그 실행은 **개발자 `.env` 로 돌았고,
`k=10` 이라 후보 상한을 못 보며, 적재 카운터가 없고, `.gitignore` 된 `.cache/` 로 갔다.**
`평가-세트.md` 가 요구한 것은 *"이후 모든 비교의 기준선"* 인데, 같은 명령이 머신마다 다른
수치를 내면 그 목적이 성립하지 않는다. 이번 작업이 고친 것이 정확히 그 넷이다.

**기존 실행 JSON 을 `baseline.json` 으로 변환하는 안은 기각했다.** 고정 설정으로 쟀다고
적힌 파일이 실제로는 `.env` 로 잰 값이 되어, 형식만 맞고 내용이 거짓이 된다.

### 고정 설정을 러너가 아니라 별도 모듈에 뒀다 — 소비자가 둘이다

`run_eval.py` 안에 두는 것이 간단하지만, 그러면 `--check` 의 파싱(`corpus.py`)이 계속
`.env` 를 탄다. 그 검사가 확인하는 것이 *"정답 span 이 청크 하나 안에 있다"* 인데, 설정이
갈리면 **검증한 청크와 실제로 색인되는 청크가 다른 것**이 된다. `embedding.provider` 를
*"합법값이 하나뿐인 죽은 설정"* 이라며 안 만든 잣대가 여기서는 반대로 작동한다 — 소비자가
둘이라 죽은 모듈이 아니다.

### 고정하지 않은 것 둘 — API 키와 `tesseract_cmd`

**머신마다 달라야 하는 것**이라 고정 대상이 아니다. 키가 없으면 폴백이 도는데 그것도 관측
대상이고, tesseract 설치 경로는 애초에 저장소가 알 수 없다.

### `image_handler="hybrid"` 를 유지하고 카운터를 함께 남긴다

무료·결정론적인 `ocr` 로 고정하는 안을 기각했다. `.env` 운영값이 `hybrid` 라 **평가가 운영
산출을 대표하지 못하게 되고**, 이미지가 든 문서의 질의가 실제보다 낮게 나오는데 그 차이를
재본 적이 없다.

대신 재현성 쪽을 포기한 만큼을 **보이게** 했다. Vision 은 LLM 이라 응답이 실행마다 다르다
(`plan_log/표-경로.md` 12회차: 같은 쪽을 1회차 호출은 10/10, 2회차는 6/10). `.cache/content`
가 첫 응답을 얼려 주지만 캐시를 잃으면 산출이 움직인다. 그때 `vision_calls`·`ocr_applied`·
`warnings` 가 리포트에 없으면 **검색이 변한 것인지 적재가 변한 것인지** 가릴 수 없다.

**"캐시를 baseline 의 일부로 못 박는" 안은 기각했다** — 대표성과 재현성을 둘 다 얻지만,
캐시가 지워지면 baseline 이 **조용히** 무효가 되고 그 사실이 어디에도 안 드러난다.

### 카운터를 얻으려고 `IndexResult` 를 넓혔다

`IndexResult` 에는 `document_id`·`collection`·`chunk_count`·`indexed_count`·`usage` 뿐이라
카운터로 가는 길이 없었다. **러너가 `ingest()` 를 한 번 더 불러 얻는 안은 기각했다** —
Vision 이 비결정적이라 그 두 번째 파싱이 실제로 색인된 것과 다를 수 있고, **다른 파싱의
카운터는 애초에 쓸모가 없다.** `indexing.md` 가 `count()` 를 더할 때 쓴 잣대(*"소비자가
실재하므로 죽은 메서드가 아니다"*)와 같은 자리다. 소비자가 `pipeline.py` 3곳뿐이고 backend
에 색인 엔드포인트가 없어 지금은 공개 스키마가 아니다.

### k 를 20 까지 받고 주지표는 10 — 검색이 공짜라서 가능한 것

과금은 질의 임베딩에서만 나고 qdrant 검색은 로컬이다. 그래서 후보를 20까지 한 번에 받아
`1·3·5·10·20` 으로 각각 채점한다. 공짜로 딸려오는 것이 둘 — 비교 4번(*"`recall@top_k`(상한)
vs `nDCG@5`(실효)"*)과 `indexing.md` 의 `top_k` 기본값 근거.

**`per_query` 는 주지표 k 가 아니라 `--k` 채점을 남긴다.** k=10 으로 남기면 `rank` 가 11~20
인 질의가 전부 `None` 이 되어 *"후보를 늘리면 잡히나"* 를 못 읽는다.

### baseline 파일에서 `usage` 를 뺐다 — 실측이 뒷받침했다

다른 세션의 실행이 `usage.tokens` **1,399** 를 남겼다. 문서 임베딩이 전부 캐시 적중이고
질의 60건만 과금된 값이다. 캐시가 없는 머신에서 같은 실행은 십만 단위다. **같은 산출인데
값이 100배 흔들리는 필드**라 기준선에 담으면 diff 노이즈만 된다. 반대로 `indexed` 의 청크
수는 담는다 — 적재가 바뀌었는지 보는 신호다.

### 오타 방어를 테스트로 — 설정 클래스가 전부 `extra="ignore"` 다

`ContentRoutingConfig(**{"typo": 1})` 이 **예외를 안 낸다.** `EVAL_SETTINGS` 에 이름을
틀리면 그 항목만 조용히 안 먹고, 고정했다고 믿는 값이 실은 `.env` 를 탄다. 이름 대조
(`model_fields` 와 집합 차)와 값 대조를 **두 겹**으로 뒀다 — 이름이 맞아도 안 실리는 경우가
따로 있다.

같은 파일이 *"`corpus.py` 와 `run_eval.py` 가 같은 설정을 쓴다"* 도 AST 로 강제한다.
산문으로 적어두면 다음 사람이 안 읽는다.

### 기록 경계에서 두 훅이 갈려 있었다

이 작업이 진행되는 동안 드러났다 — `evaluation/` 은 `auto_test_check.py` 의
`SOURCE_PREFIXES` 에는 **있고** `task_log_check.py` 의 것에는 **없었다.** 평가 하네스만 고친
세션은 회고 없이 끝날 수 있었다는 뜻이고, 이번에도 `pipeline.py` 를 함께 고쳐서 걸린 것이지
평가 코드 때문이 아니었다.

넣은 근거는 `.claude/hooks/` 를 넣은 것과 **같은 종류**다: **틀려도 조용하다.** 훅이
무력화되면 기록이 안 남고, 채점기가 어긋나면 **그럴듯한 숫자가 계속 나온다.** 실제로
`evaluation/` 의 판단은 코드를 읽어서는 알 수 없는 것뿐이다 — `recall` 의 분모를 청크로
잡으면 포맷 비교가 깨지고, 대조는 공백을 지우고 해야 하고, 겹침과 반복은 청크 자리 번호의
연속 여부로 가른다.

**`tests/evaluation/` 은 안 넣었다.** `tests/hooks/` 를 특별 취급한 근거(*"훅 로직만 넣고
테스트를 빼면 경계가 반쪽"*)가 여기서는 약하다 — 평가 코드를 고치면 `evaluation/` 프리픽스가
이미 걸리고, 테스트만 홀로 고치는 세션은 드물다. **넓히는 쪽도 위험하다**는 것이 이 훅이
스스로 적어둔 경계다(`SKIP_TASKLOG=1` 이 습관이 된다). 다시 볼 조건은 평가 테스트만 고친
세션이 실제로 기록 없이 지나가는 것을 볼 때다.

`qa_set.jsonl` 과 `README.md` 는 `.py` 가 아니라 자동으로 빠진다 — **질의 한 줄 고칠 때마다
7절을 채우게 하면** 딱 그 습관이 든다.

## 4. 실패 분석

**하나. 계획서의 전제가 쓰는 동안 낡았다.** 설계 단계에서 `.cache/evaluation/runs/` 가 비어
있는 것을 확인하고 *"dense baseline 은 아직 한 번도 안 돌았다"* 를 계획서 Context 에 박았다.
그런데 같은 저장소의 다른 세션이 그 사이에 돌렸다. 결론(할 일)은 안 바뀌었지만 **근거 문장이
거짓이 됐고**, README 를 고치려다 그쪽이 이미 쓴 수치를 보고서야 알았다. 동시 편집 중인
저장소에서 *"아직 없다"* 류의 전제는 **쓰는 순간 낡는다** — 이번에는 다행히 결론이 같았다.

**둘. `plan_log/평가-세트.md` 에 5회차를 썼는데 그 번호가 이미 있었다.** 상대 세션이 5·6회차
를 먼저 넣어 한 파일에 `## 5회차` 가 둘이 됐다. 7회차로 옮기고 본문의 상호 참조도 함께
고쳤다. 회차 번호가 **파일 안의 순서에 의존**하는 형식이라 동시 편집에 약하다. 이건 기록
형식의 문제라 고치지 않고 남긴다.

**셋. Bash heredoc 으로 `run_eval.py` 를 쓰려다 실패했다.** 따옴표 섞인 한국어 본문이
셸 파싱을 깨서 `unexpected EOF` 가 났다. 파일이 안 바뀐 것을 확인하고 `Write` 로 갔다.
손해는 없었지만, **확인 없이 재시도했으면 반쯤 쓰인 파일 위에 덧썼을 것**이다.

사람이 발견한다.

## 7. 남은 것

- **진 질의 해부가 이 품질 검사의 본체이고 아직 시작 안 했다.** `k=20 에서도 23건(38%)`
  이 안 잡히고 AI 가이드 그룹이 `hit@10 0.333`(miss 10/15)으로 제일 낮다 — `평가-세트.md`
  미결 *"AI 가이드 질의가 상세절에 몰려 있나"* 의 첫 신호로 보이지만 **확인은 안 했다.**
  후보 수로 해결되는 문제가 아니라는 것까지가 지금 아는 전부다
- **`vision_calls` 가 넷 다 0 인 이유를 안 봤다.** 표시 크기 필터인지 `classify()` 판정인지
  갈리지 않았다. 걸러진 이미지는 조용히 SKIP 되어 `warnings` 에도 안 남는다 —
  `plan_log/이미지-경로.md` 가 이미 열어둔 미결과 같은 자리다
