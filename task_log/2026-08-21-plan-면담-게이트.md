# plan mode 에서 사용자가 허락하기 전까지 계획 확정을 막는 게이트

- 작업일: 2026-08-21
- 검증 방법: 훅 단위 테스트(합성 payload) + 실제 subprocess 5건 + `claude.exe` 바이너리에서 `permission_mode` 실재 확인. **외부 API 호출 없음** (`-m integration` 안 돌림)

## 1. 무엇을 바꿨나

- `.claude/hooks/plan_interview_check.py` (신설)
  세 이벤트를 한 스크립트가 처리한다 — 문구를 보고 표시를 만들고(`UserPromptSubmit`),
  표시가 없으면 `ExitPlanMode` 를 막고(`PreToolUse`), 계획이 나가면 표시를 지운다(`PostToolUse`).
- `.claude/hooks/_hookutil.py`
  `clear_marker()` 를 더했다. `touch_marker()` 는 있는데 지우는 짝이 없었다 — 세션 마커가
  전부 "한 번 켜지면 끝"이었기 때문이다. **켰다 껐다 하는 게이트는 이번이 처음**이다.
- `.claude/settings.json`
  `UserPromptSubmit` 기존 그룹에 한 줄, `PreToolUse`·`PostToolUse` 에 `ExitPlanMode` 전용
  새 그룹 둘.
- `.claude/skills/plan-interview/SKILL.md` (신설)
  라운드를 어떻게 도는가. **`plan-log` 의 내용을 복제하지 않고 가리킨다.**
- `tests/hooks/test_hook_wiring.py`
  `test_pretooluse_covers_both_shells` 의 적용 범위를 좁히고, 예외가 썩지 않게 지키는
  테스트를 하나 더했다.
- `tests/hooks/test_plan_interview_check.py` (신설)
- `CLAUDE.md`
  "plan mode 면담 게이트" 절 신설.

## 2. 설계 결정

### 게이트를 스킬 호출이 아니라 `ExitPlanMode` 호출로 무장시킨다

`plan_log_check.py` 는 "이 세션이 설계 논의인가"를 스킬 마커로 판정한다. 설계 논의 세션은
코드를 한 줄도 안 고쳐서 git 으로 알 방법이 없기 때문이다. **그 구조를 그대로 베끼는 것을
기각했다.** 여기서는 `ExitPlanMode` 가 불렸다는 사실 자체가 plan mode 라는 증거라서, 표시를
따로 만들 이유가 없다.

차이가 그냥 간결함이 아니다. 스킬 마커로 무장하면 **스킬을 안 부른 세션은 게이트가 통째로
없다.** 2026-08-17 에 실제로 그런 세션이 있었고(`plan_log_check` docstring), 그게 이 저장소가
아는 실패 모드다. 이쪽은 모델이 무엇을 부르든 막힌다.

### 표시를 `PostToolUse` 에서 지운다 — `PreToolUse` 에서가 아니라

처음 안은 `PreToolUse` 에서 통과시키면서 같이 지우는 것이었다. 한 도구 호출로 끝나 단순하다.
**설계 중에 되돌렸다** — 사용자가 계획을 보고 거절하며 "여기 고쳐서 다시 줘"라고 하는 경로가
막힌다. 표시는 이미 소비됐으므로 다음 `ExitPlanMode` 가 또 deny 되고, 사용자는 문구를 다시
말해야 한다.

그 값이 단순한 짜증이 아니라는 판단은 이미 이 저장소에 있다 — `tests/hooks/test_record_hooks.py`
의 docstring 이 "일을 하고도 막히는 게이트는 `SKIP_*=1` 을 습관으로 만들어 검사 자체를
죽이므로, 무력화의 한 형태"라고 적어 뒀다. 거절된 도구는 `PostToolUse` 가 안 돌므로 그쪽에서
지우면 재시도가 살아난다.

감수한 것: `PostToolUse` 가 아예 안 오는 하네스에서는 그 세션의 게이트가 열린 채 남는다.
**사용자를 가두는 쪽이 아니라 통과시키는 쪽이라** 공통 규약("판단이 서지 않으면 막지 않는다")과
방향이 같다.

### 부정어를 메시지 전체가 아니라 문구 **바로 옆**에서 찾는다

`plan_log_check` 의 두-목록 방식(`_DESIGN_PHRASES` vs `_CODE_PHRASES`)을 가져오되, 검사 범위를
문구 앞 8자·뒤 12자로 좁혔다. 전체에서 찾도록 두면
`아직 못 정한 게 남아 있지만 여기까지 하고 설계서 작성해줘` 가 **닫힌다** — `아직` 하나 때문에.
실측 12건 중 이 한 줄이 창의 크기를 정했고, 반대쪽(`아직 설계서 작성하지 마`,
`설계서 작성하지 말고 질문 더 해줘`)은 부정어가 문구에 붙어 있어 좁은 창으로도 걸린다.

### `test_pretooluse_covers_both_shells` 를 없애지 않고 좁혔다

그 테스트는 PreToolUse 의 **모든** matcher 에 `Bash`·`PowerShell` 둘 다를 요구한다.
`matcher: "ExitPlanMode"` 그룹을 넣으면 깨진다. 이건 알려진 벽이다 — `auto_test_check.py` 의
docstring 이 "그래서 이쪽이 비켜간다"며 PostToolUse 를 고른 이유로 적어 뒀다.

세 안 중에 골랐다.

| 안 | 왜 안 골랐나 |
|---|---|
| 테스트를 지운다 | 그 테스트가 막는 것은 실재한다 — 셸 훅이 한쪽만 덮으면 도구를 바꾸는 것만으로 커밋 전 검사·유료 테스트 차단이 통째로 우회된다 |
| 게이트를 PostToolUse 로 옮긴다 | `ExitPlanMode` 는 PostToolUse 시점에 **이미 계획이 나간 뒤**라 막을 것이 없다 |
| **예외 집합을 명시한다** (고름) | `UNMAPPED_BY_DESIGN`·`LIBRARY_MODULES` 와 같은 모양이고, 이 저장소가 이미 쓰는 수법이다 |

핵심은 **기본값의 방향**이다. `NON_SHELL_PRETOOLUSE` 에 **없는** 훅을 셸 대상으로 본다.
그래서 새 PreToolUse 훅을 무심코 추가하면 테스트가 깨져 "이건 셸을 보는 훅인가"를 답하게
만든다. 반대로 빠지는 쪽이 기본이면 검사는 시간이 지나며 저절로 헐거워진다 — 이 저장소가
2026-08-17 에 `plan_log/` 미커밋 3건으로 겪은 것과 같은 종류의 부식이다.
예외 목록이 썩지 않게 `test_non_shell_exceptions_are_wired_to_pretooluse` 를 함께 박았다.

### 스킬은 `plan-log` 를 복제하지 않고 가리킨다

논의를 어떻게 하는가(근거 읽을 곳 표, 실측 없이 수치를 단정하지 않기, 못 재는 것을 잰 것처럼
말하지 않기, 선택지 좁히기)는 전부 `plan-log` 2단계에 이미 있다. 옮겨 적으면 한쪽만 고쳐진다.
`plan-interview` 에는 **저쪽에 없는 것만** 뒀다 — 한 라운드의 모양, 물을 게 떨어졌을 때
지어내지 않는 것, 그리고 아래 순서.

### `plan-log` 호출을 `ExitPlanMode` **승인 뒤로** 못 박았다

plan mode 안에서는 플랜 파일 말고 아무것도 못 고친다. 그런데 `plan-log` 스킬을 부르면
`plan_log_check` 의 Stop 검사가 무장된다. **계획 확정 전에 부르면 기록을 남길 방법이 없는
채로 검사만 켜져 세션이 막힌다.** 승인 뒤에 부르면 무장과 기록이 곧바로 이어진다.
SKILL.md 4단계에 순서와 이유를 함께 적었다.

## 4. 실패 분석

**`permission_mode` 를 "모르는 채로" 두려다 실물로 확인했다.**
설계 단계에서 이 필드가 훅 입력에 오는지 확인할 방법이 없다고 보고 fail-open(없으면 리마인더를
안 냄)으로 짰다. 그대로 뒀으면 **영영 안 도는 코드**를 하나 넣은 채 "동작은 한다"고 적을
뻔했다. 배포된 `claude.exe` 에서 payload 생성부를 직접 찾아 확인했다 —
`{session_id, transcript_path, cwd, prompt_id, permission_mode, ...}` 공통부에 있고 값은
`"plan"` 이다. 훅 docstring 의 가정법을 현재형으로 바꿨다. **fail-open 설계는 그대로 뒀다** —
확인한 것은 이 버전의 사실이지 계약이 아니다.

**중간 상태에서 자동 테스트 훅이 막았다.**
`NON_SHELL_PRETOOLUSE` 예외와 그 가드 테스트를 훅 파일보다 **먼저** 넣었더니, 가드가
"`plan_interview_check.py` 가 PreToolUse 에 배선돼 있지 않다"로 정확히 실패해
`auto_test_check` 가 종료를 막았다. 검사가 옳게 동작한 것이라 고칠 것은 없었지만, 교훈은
있다 — **서로를 가리키는 파일들은 한 도구 호출로 묶어 쓴다.** 훅 파일 생성과 `settings.json`
배선을 한 번에 했더니 그다음부터는 안 걸렸다.

막다른 길로 끝난 시도는 없었다.

## 5. 회귀 테스트

| 4절·2절 항목 | 막은 테스트 |
|---|---|
| `PreToolUse` 에서 표시를 소비하지 않는다 | `test_pre_tool_use_does_not_consume_the_marker` |
| `PostToolUse` 가 표시를 지운다 | `test_gate_closes_again_after_the_plan_is_presented` |
| 부정어 창을 넓히면 정상 요청이 닫힌다 | `test_negation_far_from_the_phrase_does_not_close_the_gate` |
| 문구 변형을 받는다 / 부정형을 거른다 | `test_open_phrases_arm_the_gate` · `test_other_prompts_leave_the_gate_closed` |
| deny 사유에 해제 문구가 있어야 한다 | `test_exit_plan_mode_is_denied_without_the_phrase` |
| `UserPromptSubmit` 이 프롬프트를 지우면 안 된다 | `test_user_prompt_submit_never_exits_nonzero` (subprocess 5건) |
| matcher 를 넓혀도 엉뚱한 도구를 막지 않는다 | `test_other_tools_are_untouched` |
| 탈출구가 산다 | `test_skip_env_disables_the_gate` |
| 예외 목록이 썩지 않는다 | `test_non_shell_exceptions_are_wired_to_pretooluse` |
| 배선이 살아 있다 | 기존 `test_wired_scripts_exist` · `test_every_hook_script_is_wired` |

**못 막은 것 하나.** `permission_mode` 를 읽어 리마인더를 내는 경로는 합성 payload 로만 쟀다.
하네스가 그 필드 이름을 바꾸면 리마인더가 조용히 사라지고 **아무 테스트도 안 깨진다.**
게이트 본체는 이 필드를 안 쓰므로 영향이 리마인더 한 줄에 그친다.

## 7. 남은 것

- **실제 plan mode 왕복을 사람이 한 번 확인해야 한다.** 단위 테스트는 handler 를 직접 부르고
  `test_hook_wiring.py` 는 배선을 정적으로만 본다 — 그 사이가 비어 있다. 절차:
  ① plan mode 진입 후 설계 질문 → 리마인더 한 줄이 뜨는가
  ② 문구 없이 계획을 재촉 → deny 되고 사유에 `설계서 작성해줘` 가 보이는가
  ③ `설계서 작성해줘` → 통과하는가
  ④ 같은 세션에서 plan mode 재진입 → 다시 막히는가
- **이번 논의를 `plan_log/` 에 남길지 정해야 한다.** `test_pretooluse_covers_both_shells` 의
  적용 범위를 좁힌 것은 기존 계약 변경이라 설계 기록 대상으로 볼 수 있다. 이 세션은
  `plan-log` 를 부르지 않아 Stop 검사가 무장되지 않았다 — 넣는다면 `plan_log/plan-면담.md`.
- **`.claude/skills/**` 는 `is_recordable()` 대상이 아니다.** 그래서 `plan-interview/SKILL.md`
  를 나중에 고쳐도 이 게이트가 회고를 요구하지 않는다. 의도된 경계지만, 스킬 본문이 훅 동작을
  설명하고 있으므로 **훅을 고칠 때 SKILL.md 를 같이 보는 것은 사람 몫**이다.
