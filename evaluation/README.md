# 검색 품질 평가 세트

검색·생성 단계의 모든 수치 결정이 여기 걸려 있다. 설계 근거는 `.claude/wiki/plan_log/평가-세트.md`,
이것을 쓰는 쪽 설계는 `.claude/wiki/plan_log/검색-생성.md` 다.

## 왜 이것이 먼저인가

`recall@k` 도 `MRR` 도 **정답이 있어야 잰다.** 정답 세트 없이 만든 retriever 는 잘 도는지만
알 수 있고 잘 찾는지는 모른다. hybrid 가 dense 보다 나은지, 리랭커가 값을 하는지, 청킹을
어느 쪽으로 잡아야 하는지가 전부 이 파일 하나에 막혀 있었다.

## 레코드

`qa_set.jsonl` — 한 줄 한 질의.

```json
{"query_id": "sih-01",
 "query": "행정정보 데이터세트 기록관리 의무는 언제부터 지켜야 하나요?",
 "source_doc": "시행령-개정안-안내서",
 "gold_spans": ["(시행)공포 후 6개월의 유예기간(기관별 준비 실시, 2020.10.1.)"],
 "answer_type": "text",
 "reviewed_by": "pending",
 "note": "",
 "gold_page": {"hwpx": 3, "pdf": 3, "hwpx-가로": 5}}
```

- **`source_doc` 은 파일명이 아니라 그룹 키다** (`documents.py`). 한 질의가 그 문서의 **모든
  포맷**을 함께 잰다 — 그래야 "같은 문서를 HWPX 로 넣는 것과 PDF 로 넣는 것 중 어느 쪽이
  검색에 유리한가"를 같은 기준으로 잴 수 있다. **신뢰가능 AI 가이드만 PDF 하나다** — 아래
  "제외한 것" 참고
- **`gold_spans` 는 `chunk_id` 가 아니다.** 청킹을 고치면 chunk_id 는 전부 무효가 되는데,
  청크 상한 재판정이 이 세트의 목적 중 하나라 그러면 자기 자신을 못 잰다. 두 포맷의 chunk_id
  가 애초에 다르다는 문제도 있다
- **`gold_spans` 는 "아무거나 하나"가 아니라 "전부"다.** `recall` 의 분모다
- `reviewed_by` 가 `pending` 이면 **아직 사람이 안 봤다**는 뜻이다. `human` 으로 바꾸는 것은
  사람만 한다. **`reviewed_hash` 가 그 도장을 그때 본 문장에 묶는다** — 검수 뒤에 질의나
  정답을 고치면 해시가 어긋나고 검증이 재검수를 요구한다. 안 그러면 검수자가 보지 않은
  문장에 도장이 남는데 아무 에러도 안 난다
- **`gold_page` 는 요소에서 뽑고 PDF 원본과 대조한다.** 청크의 `page` 는 **시작 쪽**이라,
  쪽을 넘긴 청크의 뒷부분에 있는 span 은 한 쪽 앞으로 보고된다(사람 검수가 `sih-11`·`sch-13`·
  `sch-14` 셋을 이렇게 잡아냈다). `evaluation/pages.py` 가 60건 전부를 PDF 파일과 맞춰 보고
  `tests/evaluation` 이 그것을 지킨다
- **`gold_page` 는 채점에 안 쓴다.** 검수자가 원문을 바로 열게 하는 것이 목적이다. 한 개의
  숫자로 못 두는 이유는 실측이다 — 시행령·중등은 두 형식의 쪽이 **정확히 같은데** 학교기록물은
  **PDF 가 +1** 이다(15건 중 14건, `sch-01` 만 둘 다 2쪽). 뺀 AI 가이드 HWPX 는 −1~−56 까지
  벌어졌다. 즉 **문서마다 다르고 보정 상수로 못 고친다.** 키는 `documents.py` 의 포맷
  라벨이고, 라벨을 바꾸면 세트를 함께 고쳐야 한다(검증이 강제한다)

## 쓰기

```powershell
# 세트가 성립하는지만 본다. 과금 없음
.\.venv\Scripts\python.exe -m evaluation.run_eval --check

# 로더를 고쳤으면 파싱 캐시를 버린다
.\.venv\Scripts\python.exe -m evaluation.run_eval --check --refresh

# dense baseline. **OpenAI 과금이 일어난다** (PDF 4개 문서 + 질의 60개 ≈ $0.003)
# --save-baseline 을 붙였을 때만 baseline.json 을 굳힌다
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format pdf --save-baseline

# 기준선이 있는 상태에서 그냥 돌리면 **질의별 승·패·무**가 나오고 기준선은 안 건드린다
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format pdf --label 실험이름

# 다른 임베딩 모델로 재려면 프로필 이름을 준다 (evaluation/config.py 의 EVAL_EMBEDDINGS).
# 안 주면 baseline 이라 지금까지와 같은 실행이다
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format pdf --embedding 프로필이름 --label 실험이름

# **GPU 로 돌리려면 프로필 이름으로 준다** — 이 러너는 .env 를 일부러 안 본다 (아래 「GPU 로 돌리기」)
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --embedding kure-v1-gpu --rerank local-gpu --k 50 --report-k 10 --label 실험이름

# 포맷 비교·모델 비교는 이 한 줄로 안 된다 — 아래 "…를 돌리려면" 절을 그대로 따른다
```

## GPU 로 돌리기

**`.env` 에 `EMBEDDING_DEVICE=cuda` 를 넣어도 이 러너는 CPU 로 돈다.** 버그가 아니라
재현성 장치다 — `evaluation/config.py` 의 프로필이 장치를 못 박고 `.env` 를 이긴다
(*"baseline 은 재현될 때만 기준선"*). 그래서 **GPU 는 프로필로 고른다.**

```powershell
# 저장소 루트에서. 과금 0 (둘 다 로컬 모델)
$env:PYTHONIOENCODING = "utf-8"
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid `
  --embedding kure-v1-gpu --rerank local-gpu --k 50 --report-k 10 --label 실험이름
```

| 축 | CPU 프로필 | GPU 프로필 |
|---|---|---|
| 임베딩 | `kure-v1` | **`kure-v1-gpu`** |
| 리랭킹 | `local` | **`local-gpu`** |

**갈아끼지 않고 더한 것이 규칙이다** — 이름이 곧 실험의 정체라, 갈아끼면 이미 나온 수치가
어느 장치로 재졌는지를 파일이 못 말한다.

**컬렉션은 안 갈린다.** `collection_name_for()` 가 모델·차원에서 파생하므로 `kure-v1` 과
`kure-v1-gpu` 가 같은 컬렉션을 연다 — **재색인이 없다.** 캐시 salt 도 같다
(`cache_salt_for()` 에 device 가 없다). 근거는 실측이다: 실제 청크 414개에서 CPU/GPU 벡터가
`1−cos` 최대 **1.354e-09** 이고, E2E 로 지표 49개·질의 60건이 **전건 동일**이었다
(`.claude/wiki/verify_log/2026-08-26-스레드-발열-GPU.md`).

**그래서 장치를 바꿔 견주는 실행은 캐시를 갈라야 한다.** 안 가르면 GPU 실행이 CPU 가 만든
벡터를 그대로 읽어 **모델이 한 번도 안 돈다** — 실제로 그렇게 돌린 첫 실행이
`usage.calls == 0` 이었다. `usage.calls` 가 0인 비교는 근거가 아니다.

```powershell
$env:EMBEDDING_CACHE_DIR = "<임시경로>"
$env:RERANK_CACHE_DIR    = "<임시경로>"
```

**얼마나 빨라지나** — 임베딩 색인이 CPU-초 1,856.7 → 15.8(**117배**), 리랭킹이 질의당
63.9초 → 2.988초(**21.4배**)다.

`--format` 은 확장자가 아니라 **포맷 라벨**이다(`documents.py`). 그 그룹에 그 형식이 없으면
**조용히 넘어가지 않고 멈춘다** — 넘어가면 그 그룹 질의가 문서 없이 채점되어 점수가 가짜로
낮아진다.

### 적재 설정은 `.env` 가 아니라 코드에 고정돼 있다

`evaluation/config.py` 의 `EVAL_SETTINGS` 다. baseline 이 *"이후 모든 비교의 기준선"* 이려면
**같은 명령이 머신마다 같은 수치를 내야** 하는데, `IngestConfig()` 를 그냥 만들면 개발자
`.env` 를 그대로 탄다. 고정하지 않는 것은 둘뿐이다 — **API 키**와 **`tesseract_cmd`**
(머신마다 달라야 하는 것들이다).

설정 클래스들이 `extra="ignore"` 라 `EVAL_SETTINGS` 에 오타가 나면 **아무 에러 없이 그 항목만
조용히 안 먹는다.** `tests/evaluation/test_eval_config.py` 가 필드 이름을 대조해 막는다.
같은 테스트가 **`corpus.py` 와 `run_eval.py` 가 같은 설정을 쓰는 것**도 강제한다 — 한쪽만
`IngestConfig()` 를 쓰면 *"정답 span 이 청크 하나 안에 있다"* 는 검증이 실제로 색인된 청크와
갈린다.

### `--k` 와 `--report-k`

검색은 로컬 qdrant 라 **k 를 키워도 비용이 0** 이다(과금은 질의 임베딩에서만 난다). 그래서
후보를 `--k`(기본 20)까지 한 번에 받아 `1·3·5·10·20` 으로 각각 채점하고 `summary` 는
`--report-k`(기본 10)로 낸다. 공짜로 얻는 것이 둘이다 — 비교 4번(*"`recall@top_k`(상한) vs
`nDCG@5`(실효)"*)과 `.claude/wiki/plan_log/indexing.md` 의 `top_k` 기본값 근거.

`per_query` 는 **`--k` 채점**을 남긴다. 주지표 k 로 남기면 `rank` 가 그보다 뒤인 질의가 전부
`None` 이 되어 *"후보를 늘리면 잡히나"* 를 못 읽는다.

### 결과가 가는 곳 둘

- `.cache/evaluation/runs/` — 매 실행. 실험 기록이라 gitignore 다
- `evaluation/baseline.json` — **`--save-baseline` 을 명시했을 때만.** 기준선은 저장소에
  살아야 다른 머신·다른 세션이 견줄 대상을 본다(`regression/baseline.json` 선례).
  **수치가 달라졌다고 자동으로 덮어쓰지 않는다** — 의도한 개선과 회귀를 가르는 것은 사람 몫이다

`usage` 는 baseline 파일에 **안 담는다.** 캐시 적중에 따라 흔들려 diff 노이즈가 된다
(실측: 문서 임베딩이 전부 캐시에 있으면 같은 실행이 1,399토큰, 없으면 십만 단위다).

### 적재 카운터를 함께 읽는다

`image_handler="hybrid"` 는 Vision 을 부르고 **Vision 응답은 실행마다 다르다**
(`.claude/wiki/plan_log/표-경로.md` 12회차). `.cache/content` 가 첫 응답을 얼려 주지만 **캐시를 지우면
baseline 이 조용히 흔들린다.** 막을 방법이 없어 보이게 했다 — 리포트의 `indexed` 가 문서별
`vision_calls`·`ocr_applied`·`warnings` 를 담는다. 검색 수치가 움직였을 때 **검색이 변한
것인지 적재가 변한 것인지**를 이걸로 가른다.

## 지금까지의 수치

기준선은 [`baseline.json`](baseline.json) 이다 (PDF 4개 문서 414청크, 한 컬렉션, 2026-08-23).

| k | 1 | 3 | 5 | 10 | 20 |
|---|---|---|---|---|---|
| `hit@k` | 0.150 | 0.300 | 0.400 | **0.483** | 0.617 |
| miss | 51 | 42 | 36 | 31 | 23 |

`MRR` 0.253 · `nDCG@10` 0.314. 그룹별 `hit@10` — 중등 0.667 / 시행령 0.467 /
학교기록물 0.467 / **AI 가이드 0.333**.

**읽을 것 둘.** (1) 후보를 10에서 20으로 늘리면 8건이 더 잡힌다 — `top_k` 를 정할 때 쓸
근거다(`.claude/wiki/plan_log/indexing.md` 미결). (2) **k=20 에서도 23건(38%)이 안 잡힌다.** 후보 수로
해결되는 문제가 아니라는 뜻이고, 그 23건을 직접 읽는 것이 다음 일이다.

**이 실행에서 `vision_calls` 가 네 문서 모두 0 이었다.** `image_handler="hybrid"` 인데도
이미지가 전부 OCR 로 갔다는 뜻이라, **적어도 이 PDF 넷에서는 Vision 비결정성이 기준선을
흔들지 않는다.** 다른 코퍼스·다른 포맷에서는 다시 봐야 한다.

전문과 질의별 결과는 `baseline.json` 과
[.claude/wiki/verify_log/2026-08-23-평가러너-고정설정.md](../verify_log/2026-08-23-평가러너-고정설정.md).
매 실행 JSON 은 `.cache/evaluation/runs/` 에 남는다(gitignore).

`--check` 가 보는 것은 셋이다.

1. **본문에 있는가** — 요소 텍스트로 본다. 청크 텍스트로 보면 틀린다: 청크 앞에 붙는
   `[제목 > 경로]` 가 포맷마다 달라 본문이 같아도 다르게 나온다
2. **청크 하나 안에서 찾을 수 있는가** — 채점이 청크 단위라, span 이 청크 경계에 걸리면
   **어떤 검색기로도 못 맞힌다.** 그런 질의가 세트에 섞이면 성능이 아니라 세트가 점수를 깎는다
3. **정답 청크가 하나뿐인가** — 같은 문장이 문서에서 되풀이되면 정답이 둘·셋이 되고, 그
   질의는 **다른 것을 잰다**(상위 k 안에 들 확률이 그만큼 높다). 실측으로 신뢰가능 AI 가이드가
   요약절과 상세절에 같은 문장을 되풀이해 15건 중 10건이 그 상태였고, 상세절에만 있는 문장으로
   바꿨다

### 겹침과 진짜 반복을 가른다

3번 검사를 *"정답 청크가 2개면 실패"* 로 짜면 **멀쩡한 질의를 버린다.** `chunk_overlap_chars`
가 상한 초과로 쪼갠 구간에 겹침을 주므로, 겹친 자리에 걸린 span 은 인접한 두 청크에
**정상적으로** 나타난다.

그래서 **청크 자리 번호가 연속이면 겹침으로 보고 하나로 센다**(`_distinct_runs`). 실측으로
둘이 깨끗하게 갈렸다 — 다중 출현 24건 중 겹침은 `sih-05`(PDF 청크 17·18, 같은 5쪽) 하나뿐이고
나머지는 전부 비연속이다(`ai-02` 는 청크 5·21·23, 쪽 9·22·40).

**쪽으로 판정하면 안 된다.** `sih-08` 은 같은 1쪽 안에서 되풀이돼 쪽으로는 안 갈렸다

## 대조는 공백을 지우고 한다

PDF 경로가 한국어 낱말 사이 공백을 잃는다(실측: 같은 문장이 HWPX 는
`데이터세트는 물리적 이관시 그 특성이 변할 수 있어`, PDF 는
`데이터세트는물리적이관시그특성이 변할수있어`). 공백을 살려 대조하면 PDF 파일이 **정답을 못
맞힌 게 아니라 띄어쓰기 때문에** 0점이 되고, 포맷 비교가 검색이 아니라 추출 품질을 재게 된다.
그래서 `scoring.squash()` 하나로 채점과 검증이 같은 규칙을 쓴다.

## 지표를 축마다 가르는 이유

**리랭커를 `recall@후보수` 로 재면 차이가 정의상 0 이다.** 후보 집합을 안 바꾸고 순서만
바꾸기 때문이다. 이것으로 재고 "리랭커가 효과 없다"고 결론 내리는 것이 이 평가에서 제일
하기 쉬운 실수다.

| 비교 | 주지표 |
|---|---|
| dense vs hybrid | `hit@10` · `recall@10` · `MRR` |
| 리랭커 유무 | `nDCG@5` · `precision@3` · `recall@5` |
| 리랭커 로컬 vs 상용 | 위 + p50/p95 지연 + 질의당 비용 |
| 후보 수 (`top_k` → `top_n`) | `recall@top_k`(상한) vs `nDCG@5`(실효) |
| 같은 문서 HWPX vs PDF | `hit@10` · `recall@10` |
| BM25 토크나이저 | `hit@10` · `recall@10` |

## 판정은 수치 하나로 하지 않는다

질의 60개에서 `recall@10` 5%p 차이는 **질의 3개**다. 잡음과 안 갈린다. 그래서 요약과 함께
질의별 결과(`per_query`)를 남기고, **진 질의를 직접 읽는다** — 표 청크가 지는 것과 본문
청크가 지는 것은 고칠 곳이 다르다.

## 제외한 것

**신뢰가능 AI 가이드의 HWPX 파일을 뺐다.** 한컴이 이 문서의 표를 레이아웃 상자로 그려서 표
청크가 **0개**인데 PDF 파일은 10개다. 같은 문서의 두 형식이라기에는 구성이 달라, 이 짝에서만
포맷 비교의 전제가 성립하지 않는다. 쪽 번호도 이 문서만 두 형식이 **−1~−56** 으로 벌어진다
(다른 셋은 0 또는 +1).

그래서 **포맷 비교(비교 5번)는 3쌍**으로 돈다 — 학교기록물 · 중등 기초학력 · 시행령(가로쪽
포함 세 파일). AI 가이드의 15건은 PDF 하나로만 재고, 포맷 비교에는 안 들어간다.

CLAUDE.md 가 미해결로 적어둔 PDF 제목 유실(22.9~39%)·낱말 공백 손실이 검색에서 얼마인지는
아직 아무도 모르고, 그 답이 **진 질의의 갈래를 가른다**(`.claude/wiki/verify_log/2026-08-23-진질의-해부.md`
의 "확인 필요" 10건 — 18덩어리 중 13개가 비교 가능하다).

### 1. 시작 전에 트리와 대조한다

**아래는 이 문서를 쓴 시점의 가설이지 지금의 사실이 아니다.** 같은 저장소를 세션 여럿이 쓴다.

| 확인 | 왜 |
|---|---|
| `evaluation/baseline.json` 의 `format` 이 `pdf` 인가 | 대조군의 정체다 |
| HWPX 세 파일이 `tests/fixtures/` 에 있는가 | 없으면 그 그룹이 통째로 빠진다 |
| `git log -- rag_pipeline/ingestion/loader/` 가 baseline 이후 움직였나 | 움직였으면 **PDF 쪽도 다시 재야** 두 실행이 같은 로더 위에 선다 |

### 2. 대조군을 다시 만든다 — 제일 틀리기 쉬운 자리다

`baseline.json` 은 **4그룹 414청크를 한 컬렉션**에 넣은 실행이다. HWPX 는 3그룹뿐이라 그대로
견주면 **경쟁 집합이 다르다** — PDF 쪽 질의는 AI 가이드 청크와도 경쟁했고 HWPX 쪽은 안 했다.
같은 3그룹으로 **양쪽 다** 돌려야 성립한다.

```powershell
$g = "학교기록물-관리지침","중등-기초학력-보장계획","시행령-개정안-안내서"
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format pdf  --groups $g --label fmt-pdf
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format hwpx --groups $g --label fmt-hwpx
```

**`--save-baseline` 을 붙이지 않는다.** 기준선은 4그룹 PDF 파일이고 이 둘은 실험이다.

### 3. 비용이 PDF 실행과 다르다

기준선 실행은 `vision_calls` 가 네 문서 모두 **0** 이었다. **HWPX 는 다를 수 있다** — 이미지가
bmp·jpg·MPO 라 `_normalize_for_vision()` 을 타고 Vision 이 실제로 날 수 있다(CLAUDE.md
"Vision 에 보낼 이미지 포맷"). 문서 임베딩도 HWPX 청크는 캐시에 없을 수 있다.
**사람 승인을 받고 돌린다** — `paid_test_check.py` 는 스크립트를 안 막는다.

### 4. 대조는 사람이 한다 — 도구가 일부러 거부한다

`run_eval.compare_to_baseline()` 은 포맷이 다르면 *"직접 비교하지 않습니다"* 로 물러선다.
**그 가드가 옳다** — 60건 요약과 45건 요약을 견주는 사고를 막는다. 두 실행 JSON 의
`by_group` 과 `per_query` 를 3그룹으로 맞춰 읽는다. 질의 45건에서 5%p 는 **질의 2.25개**라
위 "판정은 수치 하나로 하지 않는다" 가 그대로 적용된다.

주지표는 `hit@10`·`recall@10`·`MRR` 이다 — 후보 **집합이 바뀌는** 비교라서(위 지표 표).

### 5. 무엇이 나오면 무슨 뜻인지 먼저 적어둔다

| 나온 것 | 뜻 | 다음 행동 |
|---|---|---|
| HWPX 가 뚜렷이 높다 | PDF 적재가 검색을 깎고 있다 | 그 13덩어리를 **적재 문제**로 옮긴다. 로더(제목 유실·공백 손실)가 우선순위를 얻는다 |
| 차이가 잡음 수준 | 두 형식이 검색에서 대등하다 | PDF 결함은 **검색에서는 싸다.** 원인은 적재 밖이고 BM25·모델 비교가 우선순위를 얻는다 |
| PDF 가 높다 | 예상 밖 | **질의별로 읽는다.** HWPX 청크가 성긴 것이 원인 후보다 |

### 6. 곁가지 — 낡은 수치 하나를 새로 낸다

CLAUDE.md 의 *"시행령 안내서가 HWPX 45청크 vs PDF 104청크로 2.3배"* 는 **낡았을 가능성이
크다.** 그 뒤로 로더가 여러 번 바뀌었다(표 되붙이기·격자 구멍·제목 승격). 두 실행의 `indexed`
가 **권위 있는 값**을 내므로 그때 CLAUDE.md 를 갱신한다. 파싱 캐시에서 읽은 값으로 미리
고치지 않는다 — 그 캐시가 어느 설정으로 만들어졌는지 모른다.

**왜 이것이 지금 남은 유일한 축인가.** 세 번의 측정이 갈래를 하나로 좁혔다.

```
진 질의 23건 → 정답 청크 18덩어리 → "확인 필요" 10건
  ├ 포맷 비교(2026-08-23) → 6건이 두 형식 모두에서 못 잡힘 = 적재 밖. 로더로 못 고친다
  ├ hybrid(BM25)         → 그 6건을 hit@10 에서 0/6. 어휘 불일치가 아니다
  └ 겹침 분석(2026-08-24) → 겹침 0 구간(질의의 1/3)에서 BM25 이득 ±0.000
남은 것: 임베딩의 한국어 변별력
```

근거는 `.claude/wiki/verify_log/2026-08-23-포맷비교.md` · `2026-08-23-hybrid-측정.md` ·
`2026-08-24-어휘겹침.md` 셋이고, 설계 미결은 `.claude/wiki/plan_log/embedding.md` 의 **모델·차원**이다.

### 1. 시작 전에 트리와 대조한다

포맷 비교 절의 표를 그대로 쓰되 **한 줄을 더한다.**

| 확인 | 왜 |
|---|---|
| `evaluation/baseline.json` 의 `settings.embedding` | 대조군이 어느 모델로 잰 값인지가 거기 있다 |
| `git log -- rag_pipeline/ingestion/{loader,splitter,embedding}/` | 움직였으면 청크가 달라져 **양쪽을 다시 재야** 한다 |
| **같은 트리에 다른 세션이 `evaluation/` 을 쓰고 있나** | `EVAL_SETTINGS` 가 두 실행 **사이에** 바뀌면 비교가 통째로 무효인데 **아무 에러도 안 난다**. 2026-08-23 에 실제로 겪었고 그 세션에 동결을 요청해 넘겼다 |

### 2. 모델 축 — **만들어졌다** (2026-08-24)

`--embedding <프로필>` 이다. 프로필은 `evaluation/config.py` 의 `EVAL_EMBEDDINGS`(이름 → 설정)
이고 기본은 `baseline` 이라 **아무것도 안 주면 지금까지와 같은 실행**이다.

```powershell
# 지금 있는 프로필: baseline (text-embedding-3-small) · kure-v1 (KURE-v1, 로컬 CPU) · kure-v1-gpu (같은 모델, cuda)
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --format pdf --embedding kure-v1 --label kure-v1
```

**`kure-v1` 은 로컬 갈래이고 2026-08-25 부터 그것이 운영 기본값이다** — `torch`·
`sentence-transformers` 가 `requirements.txt` 본체로 들어와 따로 깔 것이 없다(그전에는
`requirements-local.txt` 였다). 그래도 안 깔린 환경에서 부르면 `EmbeddingError` 가 설치
안내를 담아 나온다 — 조용히 다른 모델로 떨어지지 않는다.

**반대로 `baseline` 쪽이 이제 키를 요구하는 갈래다.** 기본 프로필은 여전히 `baseline` 이라
(`DEFAULT_EMBEDDING_PROFILE`) `--embedding` 없이 부르면 OpenAI 를 쓴다 — 운영 기본값과
평가 기본 프로필이 **일부러 다르다**. 옮기지 않은 이유는 아래 8-3 에 있다.

새 모델을 재려면 **`EVAL_EMBEDDINGS` 에 프로필을 먼저 더한다.**

**`embedding_dimensions` 를 언제 적어야 하는지가 갈린다**(3회차에 범위를 좁혔다).
캐시 salt 와 컬렉션 이름이 `(모델, 차원)` 에서 파생하므로 —

- **모델 이름이 같고 차원만 다르면 반드시 적는다.** 안 적으면 두 실험이 같은 자리를 본다
- **모델 이름이 다르면 안 적어도 된다.** 파생이 이미 갈린다. `kure-v1` 이 이 경우다
- **로컬 provider 에서는 적으면 안 된다.** bge-m3 계열은 MRL 미학습이라 못 줄이고,
  `LocalEmbedder` 가 값이 오면 `EmbeddingError` 로 거절한다. 필드의 뜻은 provider 를 안
  탄다 — *"차원을 줄여라"* 하나이고, 못 하는 쪽은 거절하는 것이 맞다

`.claude/wiki/plan_log/평가-세트.md` 가 기각한 `--config-env` 를 **뒤집은 것이 아니다.** 이름 붙인 프로필은
기각 사유 둘을 다 피한다 — 값이 둘 이상 실재해 죽은 설정이 아니고, 저장소에 커밋된 **닫힌
집합**이라 고정을 통째로 푸는 것도 아니다. `baseline.json` 만 보고 어느 설정으로 잰 값인지
안다는 성질이 그대로 산다.

**축이 산출을 안 바꾼다는 것은 실측으로 닫혔다** — `--embedding baseline` 2회가 대조군과 전
항목 일치했다(60건 `hit@10 0.4833`, 순위 이동 0건 · 20건 `0.4000`). 그러니 새 프로필에서
수치가 움직이면 **그것은 모델 탓이다.**

리포트는 `embedding_profile`(이름)과 `settings.embedding`(값)을 **둘 다** 싣는다. 그리고
`compare_to_baseline()` 이 **프로필이 다르면 물러선다** — 포맷 가드와 같은 이유다. 그래서
새 모델 실행은 기준선 대비 승·패가 안 나오고, **4번의 구간별 채점으로 읽는 것이 정상 경로다.**

### 3. 대조군은 dense 다 — `--hybrid` 를 켜지 않는다

근거 둘. 기준선이 dense 이고, **겹침 0 구간에서 BM25 는 신호를 안 더하면서 잡음은 더한다** —
그 구간에서 5건이 나빠졌고 둘은 `k=20` 밖으로 밀렸다(`2026-08-24-어휘겹침.md` 3-4).
**재려는 바로 그 구간에 분산만 얹는 셈이다.**

### 4. 채점을 겹침 구간별로 한다 — 제일 틀리기 쉬운 자리다

**총합 `hit@10` 만 보면 겹침 0 구간(질의의 1/3)의 변화가 나머지 3분의 2에 묻힌다.**

이 실수를 실제로 했다. `±0.000` 을 *"아무 일 없음"* 으로 읽었다가 **그 구간에서 11건이
흔들린 것**(↑6 ↓5, 둘은 후보 창 밖)을 통째로 놓쳤고, 다른 세션이 잡아서 고쳤다.
**모델을 바꾸면 정확히 그 구간이 움직일 것으로 기대하는 것**이므로, 총합으로 재면 찾으려던
것을 못 본다.

겹침은 **BM25 가 실제로 보는 토큰**(`rag_pipeline/retrieval/tokenize.py` 의 `tokenize()`)으로
`|질의∩정답| / |질의|` 를 재고 3분위로 가른다. **공백 분리로 재면 조사 때문에 과소평가된다.**

**스크립트는 이제 저장소 코드다** — `evaluation/overlap.py` (2026-08-24 승격. 그전에는
`.claude/wiki/verify_log/2026-08-24-어휘겹침.md` 6절 인라인이었다). 인라인을 복사해 쓰지 말 것 —
**복사본 둘이 미세하게 갈리면 두 실행이 다른 기준으로 재는데 아무 에러도 안 난다.**

```powershell
# 과금 없음 — 기존 실행 JSON 과 세트 파일만 읽는다
$env:PYTHONIOENCODING = "utf-8"
.\.venv\Scripts\python.exe -m evaluation.overlap <대조군-label> <실험-label>
.\.venv\Scripts\python.exe -m evaluation.overlap <대조군> <실험> --qa-set evaluation/qa_set_human.jsonl --buckets 2
```

**분위 경계는 실행마다 다시 안 자른다.** 겹침은 `질의 ∩ 정답span` 이라 검색 결과와 무관해,
같은 세트를 쓰는 두 실행은 구성상 같은 구간표를 갖는다. 한쪽에만 있는 질의를 만나면
**조용히 버리지 않고 멈춘다** — 버리면 구간 크기가 달라지는데 신호가 없다.

경계값 `0.12` 는 **임계값이 아니라 순서 컷**이다(분포에 틈이 없다). 인용하지 말 것.

### 5. 두 세트를 다 돌린다

`qa_set.jsonl` 60건과 `--qa-set evaluation/qa_set_human.jsonl` 20건. 겹침 축이 양쪽에 있고
**사람 세트가 낮은 쪽이 두텁다**(겹침 중앙 0.128 대 0.200). 재려는 구간의 표본이 그만큼 는다.

### 6. 비용이 지금까지와 다르다 — 여기서 제일 잘못 예상한다

포맷 비교·hybrid 측정·겹침 분석이 전부 **실제 청구 $0.00** 이었다. **임베딩 캐시가 전량
적중해서지 이 작업들이 원래 공짜라서가 아니다.**

**모델이 바뀌면 캐시 salt 가 바뀌어 한 건도 안 맞는다.** 문서 청크 전량 + 질의 전량을 새로
임베딩한다(참고: 전 문서 139,438토큰). 재색인도 함께 일어나는데 **컬렉션은 자동으로 갈린다** —
`collection_name_for()` 가 모델·차원을 이름에 담는다. 포맷 비교처럼 경로를 손으로 가를 필요는
없지만 **`--label` 은 갈라야** 결과 JSON 이 안 덮인다.

**갈래가 로컬로 정해져 단가가 0 이다**(8번). 대가는 설치 용량과 계산 시간으로 옮겨갔다 —
위 문단의 "전량 재임베딩"은 그대로지만 그것이 **돈이 아니다.** 구체적으로는 가중치
**2.27GB** 를 첫 실행에 한 번 받고, 그 뒤로는 `.cache/embedding` 이 받는다.
**CPU 로 도는 시간은 아직 안 쟀다** — `device` 를 `cpu` 로 두는 것은 재현성 때문이고
(같은 명령이 머신마다 다른 벡터를 내면 안 된다), 그 시간이 얼마인지는 아직 실측이 없다.

**`device` 는 2026-08-25 에 설정이 됐다**(`EMBEDDING_DEVICE`). 그래도 **평가는 안 흔들린다** —
`EVAL_EMBEDDINGS["kure-v1"]` 이 `"embedding_device": "cpu"` 를 못 박아, `.env` 에 GPU 를
켜 두어도 이 러너는 CPU 로 돈다. 이 파일이 `.env` 를 통째로 막은 것과 같은 기준이다.

**`paid_test_check.py` 는 스크립트를 안 막는다. 사람 승인을 받고 돌린다** — 로컬 갈래로
청구가 0일 것으로 **예상**되더라도 마찬가지다. 예상과 실측은 다르고, 실제로 얼마였는지는
결과 JSON 의 `usage` 가 답한다(축을 낸 회차의 동일성 실행은 `tokens 0 · calls 0` 이었다).

### 7. 무엇이 나오면 무슨 뜻인지 먼저 적어둔다

| 나온 것 | 뜻 | 다음 행동 |
|---|---|---|
| **겹침 0 구간만 오른다** | 찾던 답이다. 그 구간은 뜻으로 찾아야 하는 자리였고 임베딩이 못 하고 있었다 | 모델 교체가 우선순위를 얻는다. 비용·지연을 함께 잰다 |
| 전 구간이 고르게 오른다 | 모델이 그냥 낫다. **이 미결의 답은 아니다** | 갈아탈 근거는 되지만 겹침 0 구간은 여전히 안 풀린 채다 |
| 안 움직인다 | **임베딩 축도 아니다** | 갈래가 다시 열린다. 남은 후보는 세트(정답 span 이 표 조각·문맥 없는 짧은 줄)와 청킹이다 — `2026-08-24-어휘겹침.md` 3-3 의 관측이 그때 승격 후보가 된다 |

### 8. 어느 모델인가 — **`nlpai-lab/KURE-v1` 로 정해졌다** (2026-08-24, 3회차)

사용자가 **로컬 한국어 모델**을 골랐고(2회차), **어느 것인지도 정해졌다**(3회차).
프로필 이름은 `kure-v1` 이다. 버린 갈래와 이유는 이렇다.

| 갈래 | 판정 |
|---|---|
| **로컬 한국어 모델** | **고름.** 겹침 0 구간은 정의상 낱말이 아니라 **뜻으로** 찾아야 하는 자리라 가능성이 제일 크고, 계열·토크나이저가 진짜 달라 **7번 표의 셋째 줄("안 움직인다 = 임베딩 축도 아니다")이 성립한다** |
| `text-embedding-3-large` | 버림. 코드 ≈0 에 ≈$0.02 로 싸지만 **같은 계열·같은 토크나이저**라 **안 움직여도 임베딩 축을 못 닫는다** — 7번 표의 셋째 줄을 못 쓰면 이 회차의 값어치가 반이다 |
| `embedding_dimensions` 만 | 버림. 모델이 아니라 차원 축을 잰다 |

**순위표로 고르지 않았다 — 그것이 이 선택의 방법론이다.** KURE 저장소 표는
`KURE-v1 0.6947 > BGE-m3-ko 0.6875 > bge-m3 0.6872 > mE5 0.6637 > openai-3-large 0.6167`
이고 arctic-ko 카드 표는 `arctic-ko 0.740 > BGE-m3-ko 0.730 > KURE-v1 0.728` 인데,
**두 표를 섞을 수 없다** — 같은 KURE-v1 이 0.695 와 0.728 로 스케일이 다르고 뒤엣것은 저자
자신의 표다. 0.012 차로 고르는 것이 곧 `.claude/wiki/plan_log/이미지-경로.md` 1회차의 `50pt 탐침값`이다.
**순위는 우리 60건이 답한다.**

대신 2회차가 예고한 기준 넷을 **실제 모델 카드**로 채웠다.

| 모델 | 차원 | 컨텍스트 | 가중치 | 질의 접두사 | 라이선스 |
|---|---|---|---|---|---|
| **`nlpai-lab/KURE-v1`** | 1024 | 8192 | 2.27 GB | **없음** | MIT |
| `dragonkue/snowflake-arctic-embed-l-v2.0-ko` | 1024 | 8192 | 2.27 GB | 필요(`query: `) | Apache-2.0 |
| `BAAI/bge-m3` | 1024 | 8192 | 2.27 GB | 없음 | MIT |
| `Qwen/Qwen3-Embedding-0.6B` | 32~1024(MRL) | 32K | 1.19 GB | 필요(Instruct) | Apache-2.0 |
| ~~`intfloat/multilingual-e5-large`~~ | 1024 | **512** | 2.24 GB | 필요 | MIT |

**네 기준 중 컨텍스트가 유일하게 후보를 걸러냈다** — `multilingual-e5-large` 는 상한이
512 토큰인데 이 저장소 실측 최대 청크가 1,201토큰이라 잘린다. 차원은 넷 다 1024 이고
용량도 거의 같아 가르지 못했다.

KURE-v1 을 고른 이유 셋. (1) 벤치 코퍼스(AutoRAGRetrieval — 금융·공공·의료·법률)가 이
저장소의 **공공 지침 4종과 성격이 가장 가깝다.** (2) **접두사가 없어 배선에서 틀릴 자리가
하나 적다**(`config_sentence_transformers.json` 이 `prompts: {}`). (3) 한국어 검색으로
파인튜닝돼 있어, 안 움직였을 때 *"모델이 한국어를 못 한 것"* 과 *"임베딩 축이 아닌 것"* 이
안 섞인다 — 7번 표 셋째 줄이 성립하려면 이것이 필요하다.

**모델을 골랐다는 것이 갈아탔다는 뜻이 아니다.** 운영 기본값은 `text-embedding-3-small`
그대로이고 KURE-v1 은 평가 프로필로만 실재한다. 갈아탈지는 아래를 돌려 **겹침 구간별로**
읽은 뒤 사람이 정한다.

### 8-1. 로컬 갈래를 열며 함께 한 것 셋 — **끝났다** (3회차)

**세 개가 한 변경이었고 셋 다 처리됐다.** 아래는 무엇을 왜 그렇게 했는지의 기록이다.

| 무엇 | 어떻게 했나 |
|---|---|
| `EmbeddingConfig.embedding_provider` + `get_embedder()` 분기 | **열었다.** `.claude/wiki/plan_log/embedding.md` 가 *"구현체가 하나면 죽은 설정"* 으로 기각하며 단 다시 볼 조건이 **"로컬 구현체가 생길 때"** 였고, `LocalEmbedder` 가 그 조건이다. 추상화를 먼저 두고 설정을 나중에 연 덕에 **호출부는 한 줄도 안 바뀌었다** |
| **`tests/conftest.py` 의 `offline_config` 방어** | **`embedding_provider="openai"` 를 못 박았다.** 지금까지의 방어는 *"키를 지운다"* 인데 **로컬 모델은 키가 없어도 돈다** — 개발자 `.env` 에 `EMBEDDING_PROVIDER=local` 이 있으면 기본 pytest 가 가중치 2.27GB 를 받는 경로가 **아무 에러 없이** 열린다. `test_local_embedder.py` 가 이 픽스처를 검사해 나중에 지워지는 것을 막는다 |
| `cache_salt_for()` 에 provider·질의 접두사 | **안 넣기로 결정했다.** 아래 |

**셋째는 열지 않기로 결정했다** — 미결이 아니라 결정이다. provider 는 **모델 이름을
통해서만** 벡터를 바꾸고 두 이름 공간이 안 겹친다(OpenAI 는 `text-embedding-*`, 로컬은
`org/name` 꼴로 슬래시를 갖는다). 넣었다면 얻는 것 없이 `.cache/embedding` 이 전량 미스가
되고 개발자 `.qdrant` 컬렉션이 고아가 되며, 2회차가 닫은 *"동일성 실행 `tokens 0`"* 이
깨졌다. `tests/ingestion/embedding/test_cache_salt.py` 가 **provider 가 두 파생 어디도 안
움직인다**와 **두 이름 공간이 안 겹친다**를 함께 잠근다.

질의 접두사도 여전히 죽은 축이다 — KURE-v1 이 안 쓴다. E5·arctic 계열을 붙이는 날
`cache_salt_for()` 와 `collection_name_for()` 를 **같은 자리에서** 함께 연다.

**넷째가 하나 더 있었다** — 의존성이다. `torch`·`sentence-transformers` 가
**`requirements-local.txt`** 에만 있어 기본 설치에 안 들어갔고, 그래서 **기본 pytest 환경에
`torch` 가 아예 없으면 가중치를 조용히 내려받는 경로가 구조적으로 없다**는 것이 실제 근거였다
(용량은 부차적이었다). `offline_config` 방어와 두 겹이었다.

> **2026-08-25 정정 — 그 겹이 없어졌다.** 기본 임베더가 KURE-v1 로 가면서 `torch` 가
> `requirements.txt` 본체로 왔다(안 쓰는 사람이 없어졌다). 지금 막는 것은 `offline_config`
> 의 provider 핀 **한 겹뿐**이고, 그 한 겹은 실제로 뚫린 적이 있다 — 이관 당일
> `tests/ingestion/embedding/conftest.py` 가 provider 를 안 박고 있어 OpenAI 갈래 테스트
> 27개가 로컬로 새어 **2.2GB 를 적재했다**(그 폴더가 241초). **새 픽스처는 provider 를
> 반드시 박는다.**

### 8-2. 표적이 한 겹 더 좁다 — 아직 안 잰 교차

`.claude/wiki/verify_log/2026-08-24-리랭커-여지.md`(커밋 `831be39`)가 hybrid 후보 풀(50) **밖**에 있는
정답을 LLM 60건 중 **7건(0.117)** · 사람 20건 중 **1건(0.050)** 으로 셌다. **그 자리는
리랭커로도 못 고쳐 dense 변별력이 유일한 수단**이다.

**그 7건과 겹침 0 구간이 얼마나 겹치는지는 아직 안 쟀다.** `overlap.py` 로 무료로 잰다.
축을 낸 회차에 일부러 안 쟀는데, 그때 재면 다음 회차에서 *모델이 움직인 것*과 *표적이 원래
좁았던 것*이 섞이기 때문이다. **모델 비교와 같은 회차에 재는 것이 맞다.**

### 8-3. 갈아탔다 — 다만 **운영만** 이다 (2026-08-25, 5회차)

**운영 기본값이 `nlpai-lab/KURE-v1` 이 됐다**(`rag_pipeline/config.py`). 근거는 이 러너가
낸 실측이다 — 같은 60건에서 `hit@10` 0.4833 → **0.8500**, miss 31 → 9.

**그런데 `DEFAULT_EMBEDDING_PROFILE` 은 `baseline` 그대로다.** 일부러 안 옮겼고 이유가
이 러너 안에 있다.

`compare_to_baseline()` 은 프로필을 `baseline.get("embedding_profile", DEFAULT_EMBEDDING_PROFILE)`
로 읽는다. **새 리포트는 라벨을 항상 쓰지만 커밋된 `baseline.json` 에는 그 키가 없었다.**
그래서 기본 프로필을 옮기는 순간, OpenAI 로 잰 그 파일이 **`kure-v1` 이라는 이름으로 읽히고**
프로필 가드가 통과해 버린다 — 다른 모델로 잰 두 실행이 나란히 놓여 승·패가 나오는데
**아무 에러도 안 난다.**

**피하는 것과 닫는 것은 다르다.** 기본값을 안 옮기는 것만으로는 *오늘* 안 터질 뿐이고,
언젠가 다른 이유로 `DEFAULT_EMBEDDING_PROFILE` 이 바뀌면 같은 함정이 그대로 재현된다.
그래서 **`baseline.json` 에 `"embedding_profile": "baseline"` 을 명시로 박았다.** 이제
그 파일은 fallback 에 안 기대고, 비교는 늘 *실제 라벨 대 실제 라벨* 이다.
`tests/evaluation/test_profile_axis.py` 가 라벨의 **존재와 값**을 둘 다 잠근다
(라벨만 있고 값이 틀리면 fallback 보다 나쁘다 — 틀린 이름을 확신을 갖고 들게 된다).

**그래서 KURE 로 재려면 `--embedding kure-v1` 을 명시해야 한다.** 그때 가드가 정상적으로
물러서서 *"기준선은 'baseline' 임베딩이라 'kure-v1' 과 직접 비교하지 않습니다"* 를 낸다 —
그것이 고장이 아니라 이 축이 도는 모습이다. KURE 실행끼리 견주는 것은 `overlap.py` 다.

> 남은 것은 재는 일 하나다.

**무엇을 정하는 건가.** `ANSWER_CACHE_THRESHOLD` — 이 값 이상이면 *같은 질문*으로 보고
이전 답변을 그대로 돌려준다. 지금은 **비어 있고 그래서 캐시가 통째로 꺼져 있다.**
빈 값이 미완성이 아니라 결정이라는 것과 그 근거는 `.claude/wiki/plan_log/시맨틱-캐시.md` 에 있다.

**전제 둘 — 이제 둘 다 닫혔다.**

| 전제 | 왜 | 어디서 닫히나 |
|---|---|---|
| ~~**임베딩 모델 확정**~~ | 임계값은 모델에 딸린 값이다 | **닫혔다** (2026-08-25, 위 8-3) — 운영 기본값이 `nlpai-lab/KURE-v1`(local·**1024차원**)이다. **`text-embedding-3-small` 로 잰 유사도는 이제 근거가 못 된다**, 그리고 로컬이라 **임베딩 과금이 0** 이다 |
| ~~**쌍 사람 검수**~~ | **겹침 수치는 *낱말이 다른가* 만 말하고 *뜻이 같은가* 는 말하지 않는다** | **닫혔다** (2026-08-25) — **80/80 `reviewed_by="human"`**, 25쌍을 고쳐 썼다. 무엇을 보고 무엇을 고쳤는지는 아래 4절 |

### 1. 무엇을 재나 — 분포 둘이고 하나는 공짜다

- **양성** — `paraphrase_pairs.jsonl` 80쌍의 `base_query` ↔ `paraphrase` 유사도
- **음성** — 서로 다른 `query_id` 조합. `qa_set.jsonl`(60) + `qa_set_human.jsonl`(20) 으로
  **새로 만들 것 없이** 나온다. **같은 문서 안의 조합을 반드시 포함한다** — 어려운 음성이
  거기 있고, 빼면 틈이 실제보다 넓어 보인다

임계값은 그 **두 분포 사이의 틈**에서 고른다. 이 저장소의 임계값이 전부 그렇게 나왔다
(표 되붙이기 12pt, 표시 면적비 0.08 vs 1.00).

### 2. 판정 규칙을 재기 전에 못 박는다

- 두 분포가 **안 겹치면** 그 틈의 중앙을 쓴다
- **겹치면 "못 정한다" 로 닫고 캐시를 안 켠다.** 코드는 그대로 두고 `.env` 를 비워 둔다

**돌린 뒤에 규칙을 만들면 아무것도 검증하지 않는다.** 이 저장소는 제목 가설을 세 번
연속 기각한 적이 있다 — 겹친 분포에서 값을 고르는 것이 그때와 같은 실수다.

### 3. 제일 틀리기 쉬운 자리 — 오염의 **방향**

원문 낱말을 그대로 쓴 쌍이 섞이면 양성 분포가 **위로** 밀린다. 그래서:

- 임계값이 *헐거워지는 것이 아니라* **높아진다.** 서빙에서는 미스가 늘어 **오히려 보수적**이다
- **진짜 위험은 착시다** — 제대로 된 세트였으면 겹쳐서 *"못 정한다"* 로 닫혔을 것을
  **"켜도 된다"로 뒤집는다.** 이 설계의 안전장치가 *겹치면 안 켠다* 하나뿐이라, 그 착시는
  임계값을 조금 틀리게 하는 게 아니라 **안전장치를 통째로 무력화한다**

**방향을 헷갈리면 막는 방법이 달라진다.** "헐거워진다"로 읽으면 임계값을 좀 더 올려
대비하게 되는데 이 오염에는 **아무 효과가 없다**(이미 높은 쪽으로 틀려 있다). 착시로 읽어야
**세트 자체를 거르는** 쪽으로 간다 — 그래서 쌍마다 `overlap` 이 실려 있다.

지금 세트의 겹침(2026-08-25 **검수 완료 뒤**): 중앙값 **0.143** · 평균 0.165 · 0인 쌍 15 · 최대 0.500.

**검수가 이 분포를 위로 밀었다** — 검수 전은 중앙 0.111 · 평균 0.117 · 0인 쌍 20 이었다.
**오염이 아니라 교정 때문이다**: 답을 가르는 낱말(`비품`·`차시`·`지침`·`기록물`·`시스템`·`연수`)을
되돌리면 겹침이 오른다. 위에 적은 방향 그대로이고, **임계값을 재기 전에 알고 있어야 할 수치다** —
다만 이것은 *어휘* 겹침이지 임베딩 유사도가 아니라, 양성 분포가 실제로 어디에 앉는지는 재봐야 안다.
**대조군이 있어야 이 수가 말을 한다** — 기존 LLM 세트는 겹침 0 구간이 60건 중 **8건**뿐이다.

**여기 경계값을 적어두지 않는다.** `overlap.py` 가 스스로 적은 대로 *경계값은 그때그때 관측이지
규칙이 아니다* — 기계가 가리키는 검수 대상은 `tests/evaluation/test_paraphrase_pairs.py` 의
`_REVIEW_HINT` 하나이고, 그 목록은 pytest 가 돌 때 출력된다. 두 자리에 두 수를 적어두면
어긋난다(실제로 어긋나 있었다: 테스트 0.5 · 이 절 0.30 이라 **알림이 한 번도 발화한 적이 없었다**).

### 4. 검수는 문서 그룹별로 — 겹침 순서가 아니다

**1차(2026-08-25)에 겹침 0.30 이상 6건을 읽어 통과 2 · 지적 4 가 나왔고, 그 결과가 나머지
74건의 순서를 바꿨다.**

**겹침 순서는 오염 순서가 아니다.** `tokenize()` 가 글자 bigram 이라 어미가 그대로 실린다
(`나요` 는 160개 질의 중 **90**). 흔한 토큰을 빼고 다시 재면 순위가 흔들린다 — `p-bas-06` 은
겹친 셋이 `나요`·`되나`·`비를` 로 **전부 어미**라 0.300 이 측정 부산물이었고, 반대로 raw 0.30
컷이 못 집은 자리가 다섯 있었다(`p-sch-10`·`p-hsch-12`·`p-sih-05`·`p-ai-11`·`p-sih-10`).

**그리고 제일 무거운 지적은 겹침으로 안 잡혔다.** `p-bas-08` 은 *비품 → 물품* 이라 원문의 답
(`비품 구입 불가`)과 패러프레이즈의 답(*교구는 가능*)이 갈리는데, 그것은 `gold_spans` 를 읽어야
보인다. 그래서 **문서 그룹 단위로** 본다 — 같은 문서의 gold 를 한 번에 펴놓는 것이 그 판정을
싸게 만든다. 각 쌍에서 보는 것 셋:

1. **답이 같은가** — 그 `gold_spans` 가 패러프레이즈도 그대로 답하는가 (`p-bas-08` 이 걸린 축)
2. **혼자 서는가** — 지시어·생략 없이 캐시 질의로 도착해도 뜻이 통하는가.
   `p-sch-12` 의 *"그 대장을…"* 이 걸렸다 — 캐시 질의는 앞말 없이 도착한다
3. **낱말을 바꿨는가** — 안 바꿨으면 왜 못 바꾸는지가 설명되는가. `p-sch-08`(`서고`·`지하`)은
   바꾸면 뜻이 달라져 통과이고, `p-sch-09` 는 같은 변명이 안 서서 지적이다

**뜻을 고치면 겹침이 오른다.** 지적 4건을 고쳐 쓰니 셋이 위로 갔다(`p-sch-12` 0.462→**0.500**,
`p-bas-11` 0.385→**0.462**, `p-bas-08` 0.400 유지). 3절의 오염 방향 그대로다 — 겹침이 높은 것은
**틀렸다는 뜻이 아니라 사람이 볼 자리라는 뜻**이고, 짧은 질의에서 답을 가르는 낱말
(`비품`·`차시`)은 **일부러 그대로 둔다.** 바꾸면 다른 질문이 된다.

**검수 도장은 `overlap` 이 못 지킨다.** 겹침 값은 *바뀌는* 수정만 잡아서, 겹침 0.0 인 20건은
0 을 유지하는 어떤 재작성도 조용히 통과한다(실제로 확인했다 — `test_overlap_is_current` 는
통과하는데 도장만 깨진다). 그래서 `qa_set` 과 같은 `reviewed_hash` 를 쌍에도 찍는다.
지문은 `qa_set.content_hash(base_query, [paraphrase])` 이고 새 함수를 만들지 않았다.

**끝난 결과 — 80/80 · 25쌍 재작성.** 그룹별 지적 수는 `sih` 4 · `ai` 2 · `sch` 2(+1차 3) ·
`bas` 3(+1차 1) · `h*` 7 이다. 걸린 축은 셋뿐이었고, **겹침이 재는 것은 그중 하나다.**

### 4-1. 기준 — 바꾼 낱말이 **이 문서 안에서** 다른 것을 가리키나

검수 중에 굳은 기준이다. *"gold 용어를 바꿨나"* 가 아니다 — 그러면 멀쩡한 바꿔 말하기가 다 걸린다.

| 걸린 것 | 왜 |
|---|---|
| `비품` → `물품` | gold 가 `교구 구입(비품 구입 불가)` 라 답이 *불가* ↔ *일부 가능* 으로 갈린다 |
| `지침` → `안내서` (`sih` 3건) | `안내서` 는 **그 문서 자신의 이름**(`시행령 개정안 안내서`)이다 |
| `기록물` → `문서` (`sch`·`h*`) | `문서` 는 기록물의 **한 유형**이다 — 분류표에 `문서(대장 포함), 도면, 카드` 로 박혀 있다 |
| `연수` → `교육 과정` | 학교 문서에서 *교육과정* 은 커리큘럼을 가리키는 별개 용어다 |
| `(정보)시스템` → `설비` | 물리 장비로 읽힌다. gold 는 `시스템 등록여부 확인` |
| **안 걸린 것** | `원칙`→`준칙` · `시범사업`→`파일럿` · `인벤토리`→`목록` · `간행물`→`발간물` — **이 문서 안에 그 이름을 가진 다른 것이 없다** |

**같은 낱말이 자리에 따라 갈린다.** `p-sch-01` 의 `**이** 문서를` 는 지시어가 이 지침 자신을
가리켜 통과이고, `p-sch-03` 의 `문서 생산` 은 그 닻이 없어 걸렸다.

**범위를 *코퍼스* 로 넓히지 않았다** — `p-hai-06` 의 `가이드라인 → 지침` 이 그 물음을 만들었다
(AI 가이드 안에서는 안 걸리는데 옆 문서 둘에서는 `지침` 이 고유 용어다). 안 넓힌 이유는
**이 기준이 하는 일이 둘로 갈리기 때문**이다 — (1) *이 쌍이 아직 양성인가* 라는 라벨링과
(2) *캐시가 다른 문서와 잘못 맞물릴 수 있는가* 라는 위험 탐지다. `gold_spans` 가 한 문서 안의
조각인 이상 (1)의 범위는 문서가 맞고, **(2)는 사람이 쌍 단위 직관으로 답할 것이 아니라 실제
임베딩 유사도가 답할 문제다.** 그 물음은 `.claude/wiki/plan_log/시맨틱-캐시.md` 미결로 넘겼다.

### 4-2. 보는 축 셋 — 겹침이 재는 것은 하나뿐이다

1. **답이 같은가** — 그 `gold_spans` 가 패러프레이즈도 그대로 답하는가.
   `비품→물품` · `어느 단계→몇 번째` · `어떤 걸→어떤 재질로` · `캠프→합숙 활동`(gold 가 숙박을
   안 말한다) · `누구로→어느 직위로` 가 이 축에서 걸렸다. **겹침으로는 안 보인다**
2. **혼자 서는가** — 지시어·생략 없이 캐시 질의로 도착해도 뜻이 통하는가.
   `그 대장을` · `그 안내 문서를` · `그 협의체를` · `그 자료 묶음이` · `그 명단에` 다섯이 걸렸다.
   **캐시 질의는 앞말 없이 도착한다** — 검색 평가 세트에는 없던 축이고, 이 기능의 성질에서 나온다
3. **낱말을 바꿨는가** — 4-1 의 기준. 안 바꿨으면 왜 못 바꾸는지가 설명되는가

**보류한 축 후보가 하나 있다 — *발화 생략*.** `p-hbas-05` 가 용도(`기초학력 지도에`)를 통째로
빼서 뜻은 안 틀렸는데 문맥을 잃었다. 이번엔 되살렸지만 **표본 1건으로 전역 규칙을 만들지 않았다** —
이 저장소가 제목 가설로 세 번 데인 그 자리다. **같은 모양(용도·대상·방법의 생략)이 2건 더
나오면** 정식 축으로 올릴지 본다. 그 전까지는 건별 판단이다.

### 5. 쓸 것 — 이름을 못 박지 않는다

```python
from evaluation.overlap import overlap_ratio        # 겹침(무료·로컬). 세트 검사용
from rag_pipeline.ingestion.embedding import get_embedder
from rag_pipeline.ingestion.indexing import collection_name_for   # 이름이 필요하면 이것으로
```

**모델 이름·차원을 스크립트에 적지 않는다.** `collection_name_for(...)` / `cache_salt_for(...)`
를 그대로 부르면 모델이 바뀌어도 따라온다. 참고로 KURE-v1 은 `embedding_dimensions` 가
`None` 이라 **이름에는 `default` 가 박히고 실제 벡터는 1024차원**이다 — 이름의 `default` 와
실제 1024 가 다른 것이 헷갈릴 자리다(이름은 선언값, 컬렉션은 벡터에서 읽은 실제값).

`EVAL_SETTINGS` 를 쓴다 — 안 쓰면 같은 명령이 머신마다 다른 수치를 낸다.

### 6. 비용

짧은 질의 **160건**(80쌍 × 2) 임베딩. OpenAI 갈래면 약 3천 토큰이고, 로컬 갈래면 과금이
없는 대신 모델 적재 시간이 든다. **모델을 바꾸면 캐시 salt 가 바뀌어 한 건도 안 맞는다** —
"지금까지 청구가 0이었다"를 근거로 예상하지 않는다. 사용자 승인을 받고 돌린다.

다시 재는 길"* 은 사실상 닫혔다 — 다만 **모델 둘로 *어떤 모델로도* 를 말하지는 않는다.**

`.claude/wiki/plan_log/시맨틱-캐시.md` 의 남은 미결 둘**(검색 파이프라인 변화 · 캐시 상한)**을 함께 본다** —
캐시가 켜지는 순간 둘 다 발화한다.

### 8. `exact` 를 켰다 — **언제 무엇을 보고 끄나** (2026-08-28)

> semantic 은 위 7절 그대로 **꺼져 있다.** 켠 것은 완전 일치 갈래(`ANSWER_CACHE_MODE=exact`)이고
> `.env` 한 줄이다 — `.env.example` 과 저장소 커밋본은 `semantic` + 빈 임계값이라 그대로 꺼진 채다.

**이 축에는 안전 컷이 없다.** 정규화한 문자열이 같을 때만 히트하므로 오답 위험이 0이고,
재는 것은 *"값을 하는가"* 하나다(`.claude/wiki/plan_log/시맨틱-캐시.md` 6회차). 그래서 판정 규칙을
안전이 아니라 **값어치**에 건다 — 그리고 **돌리기 전에 정한다.** 2절과 같은 이유다.

| 무엇 | 값 |
|---|---|
| **언제 읽나** | `data/queries.jsonl` 에서 `source == "user"` 인 줄이 **50줄** 쌓였을 때(2026-08-28 기준 **17줄**) |
| **무엇을 읽나** | 그 줄들의 `cached=true` 비율(적중률). **`key` 중복률과 나란히 본다** |
| **컷** | 적중률 **5% 미만이면 끈다** — `.env` 의 `ANSWER_CACHE_MODE` 줄을 지우면 꺼진 상태로 돌아간다 |

**5%는 지어낸 수가 아니라 지금 관측된 값이다** — 실사용 17줄 중 완전 일치 반복이 1건(5.9%)이라
*"지금 보이는 만큼도 안 나오면 끈다"* 는 뜻이다. **이 축은 임계값과 달리 분포의 틈에서 못 고른다**
(양성·음성 분포라는 것이 없다). 그래서 대조군이 자기 자신이다.

**적중률과 반복률을 함께 보는 이유** — `key` 가 중복인데 미스인 줄이 곧 **무효화가 문 횟수**다
(파이프라인 지문 불일치 · 근거 청크 소멸). 정의상 적중률 ≤ 반복률이고 **그 차이는 캐시를 켜야만
관측된다.** 둘이 크게 벌어지면 읽을 것은 캐시가 아니라 *무엇이 지문을 바꿨나* 다.

**`source` 칸이 이 절의 전제다**(2026-08-28 신설). 이 로그의 갈래가 넷인데 셋이 오염이고
방향이 **양방향**이라 — uuid 꼬리 프로브 28줄과 cp949 깨짐 4줄은 반복률을 아래로, 같은 질의를
되풀이한 서버 E2E 4줄은 위로 민다 — 합계 하나로는 못 읽는다. 53줄에서 **실사용은 17줄뿐이었다.**
그러니 **측정 트래픽에는 `X-Query-Source` 헤더를 붙인다.** 값은 자유 문자열이고(화이트리스트가
없는 이유는 `backend/app/core/query_log.py` docstring), 안 붙이면 `user` 로 세어진다.

```python
# 실사용 줄만 세어 적중률과 반복률을 함께 읽는다 (PYTHONIOENCODING=utf-8 로 돌린다)
import json

rows = [json.loads(line) for line in open("data/queries.jsonl", encoding="utf-8")]
used = [r for r in rows if r.get("source") == "user"]
keys = [r["key"] for r in used]
print("실사용", len(used), "· 적중", sum(1 for r in used if r["cached"]), "· 반복", len(keys) - len(set(keys)))
```

**옛 줄에는 `source` 키가 아예 없다** — `r.get("source")` 가 `None` 이라 실사용에서 빠진다.
이 형식 이전의 53줄은 위 갈래를 손으로 갈라야 하고, 그 분류는
`.claude/wiki/verify_log/2026-08-28-답변캐시-파이프라인지문.md` 3절에 있다.

**2026-08-29 에 라벨을 한 번 고쳤다 — 그리고 이 문단이 그 유일한 기록이다.** 브라우저로 넣은
측정 질의 3줄(64~66)이 `X-Query-Source` 없이 들어가 `user` 로 적혔다. 64/65 가 완전 일치
반복이고 65가 `cached=true` 라, 그 3줄만으로 50줄 분모에 적중 1건이 **고정으로** 얹힌다 —
**+2.0%p 이고 컷 5%의 40%다.** 그래서 셋 다 `probe` 로 고쳤다(67번과 같은 세션·같은 질의라
한 라벨이다). **관측 칸은 안 건드렸다** — 되돌리면 바이트가 같은 것을 확인했다.

**지운 것이 아니라 고친 것이고, 둔 것도 아니다.** 지우면 65의 `cached=true · elapsed_ms=1`
(64는 6837)이 사라지는데 그것이 `exact` 가 화면 경로에서 실제로 문 유일한 관측이다. 두면 안
되는 이유는 **옛 53줄과 성질이 반대**라서다 — 저쪽은 `source` 키가 없어 위 스니펫에서
**자동으로 빠지지만**(fail-safe) 이 3줄은 `user` 라고 **적혀 있어 자동으로 들어간다**
(fail-open). 산문에 *"그 3줄은 빼고 읽으세요"* 를 적어도 스니펫은 계속 세므로, 그것은 사람이
기억해야 하는 규약이 되고 안 지킨 회차에만 깨진다. `source` 는 관측이 아니라 **갈래 라벨**이고
(`backend/app/core/query_log.py` docstring: *"갈래를 데이터에 남기는 것"*) 그 갈래를 아는
authority 는 사람이다 — 옛 53줄도 결국 손으로 갈랐다.

**`data/` 는 `.gitignore` 라 이 편집에는 diff 가 없다.** 그래서 새 키(`source_note`)를
만들지 않고 여기 적는다 — 3줄만 키를 더 갖는 것은 `verdict`·`rewrite` 가 지키는
*"키를 늘 쓴다"* 를 어긴다. **이 사고는 `source` 칸이 막을 수 있는 종류가 아니다**
(기본값이 `user` 인 것은 안전한 쪽이 아니라 정직한 쪽이라는 그 문단 그대로다). 한 번 났고,
남는 것은 *다음 측정에 헤더를 붙인다* 하나다.

## 리랭커를 재려면

`.claude/wiki/plan_log/검색-생성.md` 5회차가 정한 **바닥 2 × 구현체 2** 비교다. 채우는 표와 기각한 안은
그쪽에 있고, 여기는 절차만 적는다.

### 1. 재는 기준을 먼저 맞춘다 — 여기서 제일 틀리기 쉽다

리랭커는 **후보 집합을 안 바꾸고 순서만 바꾼다.** 그래서

- `recall@후보수` 로 재면 차이가 **정의상 0** 이다(위 "지표를 축마다 가르는 이유")
- `hit@10` 으로 재도 바닥이 좋으면 여지가 실제보다 **작아 보인다**

바닥은 `hit@1` 이고 천장은 `hit@후보수` 다. KURE+BM25 에서 `hit@1` 0.4333 · `hit@20` 0.9333
이라 여지가 `+0.500` 인데, `hit@10`(0.8167→0.9333)으로 보면 작아 보인다. **두 세션이 각각
한 번씩 이 자리에서 틀렸다.** 주지표는 `nDCG@5`·`precision@3`·`recall@5` 다.

### 2. 축은 프로필 이름이다

`--rerank <프로필>` 이고 값은 `evaluation/config.py` 의 `EVAL_RERANKERS` 에 있다 —
`off`(기본) · `openai` · `local`(CPU) · `local-gpu`(cuda). **없는 이름을 주면 멈춘다** — 조용히 꺼짐으로 떨어지면
리랭커를 켠 줄 알고 대조군을 두 번 재게 되고, 두 실행이 같은 수치를 내는 것이
*"리랭커가 효과 없다"* 로 읽힌다(`--embedding` 과 같은 가드다).

**`--dense` 없이 주면 멈춘다.** 안 그러면 세트 검증만 돌고 `통과` 를 찍는데, 리랭커를
켰다고 믿은 사람은 그것을 성공으로 읽는다.

### 3. 기준선을 안 건드린다

`--save-baseline` 을 어느 명령에도 안 붙인다. `baseline.json` 은 **모델 비교의 대조군**이고
위 3절이 *"대조군은 dense"* 로 못 박아 뒀다. 비교는 실행 라벨끼리 `overlap.py` 로 한다 —
포맷 비교가 밟은 길이다.

```powershell
# 대조군 둘 (무료 — baseline 은 임베딩 캐시, kure-v1 은 로컬)
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --k 20 --report-k 10 --label c1-baseline
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --embedding kure-v1 --k 20 --report-k 10 --label c2-kure

# 실험 넷. local 갈래는 무료다
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank openai --k 20 --report-k 10 --label e1-baseline-llm
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank local  --k 20 --report-k 10 --label e2-baseline-ce
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank openai --embedding kure-v1 --k 20 --report-k 10 --label e3-kure-llm
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank local  --embedding kure-v1 --k 20 --report-k 10 --label e4-kure-ce

# 대조 — 총합이 아니라 겹침 구간별로 (위 4절)
$env:PYTHONIOENCODING = "utf-8"
.\.venv\Scripts\python.exe -m evaluation.overlap c2-kure-pdf e3-kure-llm-pdf
```

**`--k 20` 이어도 리랭커는 풀 50을 본다.** 풀 폭은 `candidate_k` 가 정하고 `top_k` 는 자르는
수다 — 그것이 이 단계 배선의 요점이라 `retrieve()` **안**에서 자른다.

### 4. 비용은 추정하지 말고 리포트에서 읽는다

유료는 `openai` 프로필 둘뿐이다. 질의당 후보 50 × 최대 1200자라 입력이 대략 6만 토큰이고
60건이면 실행당 $1~2 로 **예상**되는데, 실제 값은 리포트 `usage` 의 `rerank_calls` ·
`rerank_tokens` 에 있다. `ResultCache` 가 재실행을 $0 으로 만든다.

**로컬 갈래의 비용은 토큰이 아니라 지연이다** — `usage.reranked`(채점한 후보 수)가 그
지표이고, CPU 에서 50후보 × 60질의가 얼마나 걸리는지는 **아직 안 쟀다.** 화면에 못 쓸 만큼
느리면 그 사실 자체가 결과다.

**⚠ 캐시가 비용과 실패를 가린다.** `rerank_cache_enabled` 가 켜져 있어 **같은 (질의, 후보
집합)을 다시 돌리면 API 를 아예 안 탄다.** 재실행을 공짜로 만드는 것이 목적이지만, *비용을
재거나 실패 경로를 확인할 때는* 그것이 곧 가림막이다 — 다른 세션이 그림자 색인 실패를
만들려고 키를 깨고 재업로드했는데 **임베딩 캐시가 적중해 성공해 버린** 일이 실제로 있었다.
비용·실패를 볼 때는 캐시에 없는 입력으로 재거나 `.cache/rerank` 를 비운다.

### 5. 모델 후보는 순위표가 아니라 **컨텍스트 상한**으로 먼저 거른다

cross-encoder 는 `(질의, 청크)` 를 **한 입력으로 함께** 넣는다. 이 코퍼스의 실측 최대 청크가
**1,201토큰**이라 상한이 짧은 모델은 정답이 든 뒷부분을 잘라 버리는데, **에러가 아니라 낮은
점수로만** 드러난다. 임베더를 고를 때 `multilingual-e5-large` 를 탈락시킨 것이 이 필터이고
(상한 512), 리랭커에서는 질의까지 같이 들어가 **더 빡빡하다.**

순위표로 고르지 않는 이유는 임베더 때와 같다 — 같은 모델을 두 표가 0.6947 과 0.728 로
내놓아 스케일이 안 섞인다. **한국어 튜닝 여부는 함께 본다**: 다국어 리랭커를 한국어 튜닝
retriever 위에 얹는 조합이 될 수 있고, 그 축의 반대편이 이번 임베더 교체(0.4833 → 0.8500)다.
그래서 **두 후보를 같은 회차에 함께 잰다** — 한쪽만 재면 *"리랭커가 효과 없다"* 와
*"이 리랭커가 한국어를 못 본다"* 가 안 갈린다.

### 6. 폴백을 결과와 안 헷갈린다

리랭커 실패는 예외가 아니라 **RRF 순서로 내려가는 폴백**이다. 그래서 리포트의
`retriever.rerank_warnings` 를 **먼저** 본다 — 비어 있지 않으면 그 실행은
*"리랭커가 값을 못 했다"* 가 아니라 *"리랭커가 안 돌았다"* 다.

### 7. 사람 세트는 이긴 칸에만

2×2 를 8칸으로 늘리지 않는다. 20건에서는 질의 1개가 5%p 라 네 칸을 서로 가를 힘이 없다.

### 8. 총합이 나빠진 그룹은 **질의 단위로 열어 본다**

리랭커는 집합을 안 바꾸고 순서만 바꾼다. 그래서 그룹 `hit@10` 이 내려갔을 때 원인은 거의
늘 **질의 한둘**이고, 총합으로는 그 둘이 안 보인다. 여는 도구가 `evaluation/rerank_diff.py`다.

```powershell
$env:PYTHONIOENCODING = "utf-8"
# 나빠진 질의 전부 — 겹침 오름차순으로 줄을 세운다
.\.venv\Scripts\python.exe -m evaluation.rerank_diff ceiling-kure-pdf e4-kure-ce-pdf --worse-only --json
# 특정 질의만 자세히
.\.venv\Scripts\python.exe -m evaluation.rerank_diff ceiling-kure-pdf e4-kure-ce-pdf --query sih-06 --top 12
```

**재는 것이 아니라 읽는 것이다** — 색인을 안 하고, 그 실행이 남긴 컬렉션과 실행 JSON 만
본다. 프로필도 인자로 안 받고 **리포트에서 읽는다**(다른 모델로 재현한 풀을 그 실행의
풀이라고 부르지 않기 위해서다).

**공짜로 도는 조건이 하나 있다.** 리랭커 캐시 키가 `(질의, 후보 신원 순서, 모델, 장치,
프롬프트)` 라, 풀이 그대로 재현되면 그때 그 점수를 **모델 적재 없이** 읽는다. 출력 머리의
`점수 출처` 가 그것을 말한다 — `캐시 (채점한 쌍 0)` 이면 그때 그 점수이고, `이번에 새로
채점` 이면 지금 다시 잰 값이다. **둘을 안 가르면 옛 실행을 읽는다고 믿으면서 새 값을 본다.**

읽는 순서는 셋이다.

1. **경고가 있나.** 재현한 순위가 리포트의 `per_query.rank` 와 다르면 그 행에 경고가 붙는다.
   붙었으면 **그 행의 수치를 인용하지 않는다** — 풀이 그 실행의 풀이 아니다
2. **밀어낸 후보가 BM25 전용인가**(`[BM25전용]` 표시 = dense 가 안 뽑은 것). 융합이 풀에
   잡음을 넣었는지가 이 칸이다. **다만 개수만으로 판정하지 않는다** — 실측(2026-08-25)으로
   겹침 0 구간 진 6건에서 27%가 BM25 전용인데 **전부 빼도 `hit@10` 이 되살아나는 것은 1건**
   이었다. 세어야 하는 것은 비율이 아니라 *빼면 정답이 제자리로 오는가* 다
3. **정답 span 이 청크 본문에 있나 제목 머리에만 있나.** 후자면 리랭커가 내린 것이 옳을 수
   있다 — 본문을 읽는 단계에게 그 청크는 각주 한 줄이다(위 「지금 세트의 감수 사항」).

**`--tokens` 는 기본이 꺼져 있다.** 켜면 후보마다 토큰 수를 세는데 토크나이저를 받으러
나간다. 컨텍스트 상한이 다른 모델(5절)을 견줄 때만 켠다.

### 9. 여기서 잰 것을 실사용 질의로 일반화할 때의 감수 사항

**`qa_set` 질의는 사람이 문서를 앞에 두고 던진 것이라 "혼자 선다".** 실사용 질의는 그렇지
않을 수 있다 — 앞말 없이 도착해 `그 대장을`·`그 명단에` 같은 지시어가 성립하지 않는 축이
있고, 그것은 **이 세트에 아예 없다**(축의 정체는 위 「답변 캐시 임계값을 재려면」의
`### 4-2` 에 있다).

리랭커는 `(질의, 청크)` 를 함께 보므로 **질의가 혼자 못 서면 그 어려움을 그대로 떠안는다.**
여기서 나온 수치는 *"혼자 서는 질의에서의 리랭커 이득"* 이고, 실사용으로 옮길 때 그 차이가
얼마인지는 **안 쟀다.**

## 판정(Evaluator)을 재려면

**`run_eval` 이 아니다.** verdict 는 순위를 안 바꾸므로 `hit@k`·`MRR`·`nDCG` 는 판정이 맞든
틀리든 **같은 수**를 낸다 — 리랭커를 `recall@후보수` 로 재면 차이가 정의상 0 이던 것과 같은
함정이다. 재는 도구는 `evaluation/verdicts.py` 이고 내는 것은 **혼동행렬 + 실패 열**이다.

```powershell
$env:PYTHONIOENCODING = "utf-8"
# 분모를 만드는 실행 — 사람 세트를 리랭커 켜고 (무료)
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank local-gpu `
    --embedding kure-v1 --qa-set evaluation/qa_set_human.jsonl --k 50 --report-k 10 --label h-ce-gpu
# 판정 채점 (**과금** — 질의 수 × --top-k 개수만큼 LLM 호출)
.\.venv\Scripts\python.exe -m evaluation.verdicts --label h-ce-gpu --format pdf `
    --qa-set evaluation/qa_set_human.jsonl --rerank local-gpu --top-k 5 10 --wrong --json
```

읽는 법 넷.

- **기대 verdict 는 세트가 아니라 그 실행의 순위에서 나온다.** 부정 22건은 늘 *불충분* 이
  옳지만 **긍정 20건은 아니다** — 검색이 근거를 안 물어왔으면 *불충분* 이 옳은 답이다.
  실측(`h-ceiling-kure`, 리랭커 off)으로 `hit@5` 8/20 · `hit@10` **14/20** 이라 `@10` 에서도
  여섯 건이 근거 없이 온다. 정답표를 세트에 고정하면 그 여섯이 오답으로 세어지고, 그 순간
  이 표는 Evaluator 가 아니라 **검색기를 잰다**
- **실패는 칸이 아니라 열이다.** `verdict="failed"` 는 판정이 아니라 판정을 못 한 것이라
  맞은 것으로도 틀린 것으로도 안 센다. 섞으면 **죽은 Evaluator 가 부정 22건에서 만점**을
  받아 점수가 실력이 아니라 실패율을 잰다. **표를 읽기 전에 실패 버킷이 0인지 먼저 본다**
- **`--top-k` 를 둘 이상 준다.** 판정 대상 수가 분모를 통째로 바꾼다 — 5면 기대가
  *충분 9 / 불충분 12*, 10이면 *충분 17 / 불충분 4* 이다(부정 22는 그대로). 그리고
  `GENERATION_TOP_K=5` 는 *"대가를 재는 쪽이 없어 못 정한다"* 로 적힌 임시값인데, 이 채점이
  그 대가를 재는 첫 자다
- **판정 설정은 `EVAL_SETTINGS["evaluator"]` 가 고정한다.** `.env` 의 `EVALUATOR_MODEL` 이
  비어 있어도(그것이 저장소 기본이다) 채점은 돈다 — 대신 운영에서 켜려면 `.env` 에 이름을
  넣어야 하고, 켜는 순간 질의당 LLM 호출이 1→2 가 된다

## 답변 품질을 재려면

**`run_eval` 도 `verdicts` 도 답변 본문을 한 글자도 안 본다.** 앞은 순위를, 뒤는 판정을
잰다. 재는 도구는 `evaluation/answer_eval.py` 이고, 이것이 **Phase 10 의 DoD 를 대신하는
출력**이다 — 스펙이 요구한 Faithfulness·Hallucination rate 는 **골든 답변이 없어 그 이름대로
못 재고**, 대신 골든 없이 재는 **다섯**을 낸다.

| 무엇 | 유료 | 무엇을 내나 |
|---|---|---|
| **인용 정합성** — 답변이 인용한 `[n]` 청크가 `gold_span` 을 담나 | 0 | 비율 |
| **근거 지지** — 답변 문장이 근거로 뒷받침되나 (LLM) | 판정당 1 | 판정 |
| **음성 대조군** — 같은 답변에 **남의 근거**를 물려 같은 판정 | 판정당 1 | 판정 |
| **필수 사실** — 담아야 할 값을 담았나 (값=결정적 · 서술=어휘 탐침) | 0 | 비율 + 탐침 |
| **단정 금지** — 미리 적어 둔 오류를 냈나 | 0 | **후보 목록** |

**마지막 줄만 수치가 없다.** 실측으로 「금지어가 답변에 있나」는 문 넷 중 둘에서 **부정문**을
잡는데, 그 둘은 틀린 전제를 바로잡은 제일 좋은 답변이다(금지어가 곧 질의의 낱말이라
구조적이다). 그래서 후보 문장만 찍고 **읽는 것은 사람이다** — 후보는 오류가 아니고,
**후보 0 도 «오류 없음» 이 아니다**. 근거는 `.claude/wiki/verify_log/2026-08-29-단정금지-채점.md`.

```powershell
$env:PYTHONIOENCODING = "utf-8"
# 분모를 만드는 실행 — 그 라벨의 컬렉션을 이 도구가 그대로 연다
.\.venv\Scripts\python.exe -m evaluation.run_eval --dense --hybrid --rerank cohere `
    --embedding kure-v1-gpu --qa-set evaluation/qa_set_human.jsonl --k 50 --report-k 10 --label L
# 채점 (**생성이 과금이다** — 질의 수만큼 LLM 호출. 판정은 기본이 꺼짐)
.\.venv\Scripts\python.exe -m evaluation.answer_eval --label L --format pdf `
    --qa-set evaluation/qa_set_human.jsonl --rerank cohere --top-k 5 --json
```

### 1. 기본이 `--judge off` 다 — 그것이 곧 과금 여부다

`EVAL_RERANKERS` 와 같은 «기본값이 곧 과금 여부» 이고, 2026-08-29 에 `mini` 에서 내렸다.
지지 판정이 **다섯 실행 연속 포화**라(사람 43건 28/28 · LLM 60건 네 실행 240/240 · 생성모델 짝
16/16 · 58/59) 조건을 견주는 실행에서 아무것도 안 가르는데 호출은 **판정 대상의 2배**(원래 근거 +
대조군)가 나간다. 그 58/59 의 유일한 미지지마저 채점자의 **거짓 음성**이었다.

**켜는 자리는 셋뿐이고 전부 «답변 본문이 실제로 달라지는» 축이다** — 생성 모델(`--generation`) ·
생성 프롬프트(`GENERATION_PROMPT_VERSION`) · `generation_top_k`. 리랭커나 재작성을 바꾼 실행에서
켜면 돈만 나간다.

### 2. 회계 게이트를 지표보다 **먼저** 읽는다

Cohere 한도 초과가 품질 저하로 읽힌 선례(2026-08-27) 그대로다. `_print()` 가 먼저 찍는다.

- 켠 회차: `judge_calls + judge_cache_hits == 판정 대상`
- **끈 회차: 게이트가 뒤집힌다** — *정말 호출이 0이었나* 를 묻는다. 지지 칸은 `0` 이 아니라
  **`None`** 으로 나온다(`0` 으로 내면 «전건 미지지» 와 «안 돌렸다» 가 안 갈린다)
- **음성 대조군이 `supported` 를 하나라도 내면 그 회차의 지지 수치는 못 쓴다**

### 3. 읽는 법은 통과선이 아니라 관측값이다

**«전건 `supported`» 를 통과선으로 박으면 안 된다.** 박았으면 위 거짓 음성이 멀쩡한 회차를
실패로 만들었다. 그래서 미지지 수는 회계 게이트와 **분리된 줄**로 찍히고, 한 건을 보면
**근거를 열어 확인한 뒤에 기록한다**(안 열었으면 *모델이 근거 없이 답했다* 를 적을 뻔했다).

### 4. 인용 정합성은 **대조군 둘과 함께** 읽는다 (2026-08-29)

0.47 이라는 수 하나로는 좋은지 나쁜지 말할 수 없다. 그래서 같은 행에서 둘을 더 낸다 —
전부 **무료·결정적**이라 `--judge off` 에서도 나온다.

| 칸 | 식 | 뜻 |
|---|---|---|
| `citation_groundedness` | `Σ hits / Σc` | 관측 |
| `citation_groundedness_chance` | `Σ(c·G/k) / Σc` | 같은 근거에서 **아무렇게나** 골랐을 때의 기대 |
| `citation_groundedness_ceiling` | `Σ min(c,G) / Σc` | 그 답변이 **인용한 개수 안에서** 낼 수 있는 최대 |
| `cited_gold_ceiling` | `Σ min(c,G)` | 그 최대의 **분자**(정수). 아래 칸의 분모다 |
| **`citation_groundedness_vs_ceiling`** | **`Σ hits / Σ min(c,G)`** | **최대 대비. 조건 둘을 견줄 때 읽는 수다** |

`c` = 그 답변이 범위 안으로 인용한 청크 수 · `G` = 근거 안에 정답을 담은 청크 수 ·
`k` = 근거 수(`top_k`).

- **최대를 안 보면 관측을 잘못 읽는다.** 실측 7회에서 최대가 **0.441~0.532** 다 — 정답 청크가
  하나뿐인데 답변이 둘 셋을 인용하면 상한이 이미 그만큼이라, **1.0 은 도달 가능한 값이 아니다.**
  0.472 는 «절반도 못 맞힌다» 가 아니라 **최대의 100%** 다
- **k 가 다른 실행끼리 관측값만 견주면 안 된다.** `top_k` 를 5→10 으로 늘리면 무작위가
  0.165→0.094 로 반이 되고 관측도 0.466→0.433 으로 내려가는데, **최대 대비로는 94%→98% 로
  오른다.** 분모가 달라진 것을 품질 변화로 읽는 자리다
- **그래서 조건 둘을 견줄 때 읽는 것은 `_vs_ceiling` 이다** (58회차). 관측은 `c`(인용 개수)에
  지배되는데 — 답변을 한 글자도 안 바꾸고 모두가 1개씩만 인용했다고 치면 최대가
  0.474 → **0.876** 이 된다 — 이쪽은 `c >= G` 인 행에서 `min(c,G) == G` 라 **분모가 인용
  개수와 무관**하다(7회 **329/330**). 뜻은 «근거에 들어온 정답 청크 중 답변이 실제로 인용한
  비율» 이고 7회 합이 **0.953**(282/296)이다. **분모가 `ΣG` 가 아니라 `Σmin(c,G)` 인 것은
  `_ceiling` 과 같은 분자라야 이름이 참이 되기 때문이고**, 감수 사항은 `c < G` 인 행(330 중
  **1**)에서 그 뜻에서 살짝 벗어나는 것이다 — **정답 span 이 여럿인 세트에서는 다시 봐야 한다**
- **통과선이 아니다.** 회계 게이트에도 안 섞는다 — 관측이 무작위 **아래로** 나올 수도 있고
  그것도 답이다. 그래서 테스트도 `ceiling >= 관측` 하나만 잠근다
- **최대 대비도 통과선이 아니다 — 두 수는 서로 반대 방향으로 속는다.** 관측은 인용을 **덜**
  달면 오르고, 최대 대비는 근거를 **전부** 인용하면 `hits == G == min(c,G)` 라 **1.0** 이 된다.
  그래서 화면 한 줄에 **관측·분수·최대 대비를 함께** 찍는다 — 어느 하나만 보면 조작이 안 보인다

### 5. 이미 낸 리포트에 소급한다 — `--backfill` (유료 0)

대조군 칸이 없던 옛 리포트는 다시 돌릴 필요가 없다. **생성을 다시 돌리면 안 된다** —
온도가 0.2 이고 생성에는 캐시가 없어 **답변 자체가 달라진다.**

```powershell
# 찍기만 한다
.\.venv\Scripts\python.exe -m evaluation.answer_eval --backfill <리포트.json>
# 리포트에 실제로 넣는다 (자기 검증을 통과할 때만 쓴다)
.\.venv\Scripts\python.exe -m evaluation.answer_eval --backfill <리포트.json> --write
```

읽는 재료는 리포트가 이미 든 원자료(답변 원문 · 근거 `chunk_id` 목록)와 그 실행의 컬렉션뿐이다.
임베더를 안 만든다 — 청크 **텍스트만** 읽는다.

**자기 검증이 이 경로의 핵심이다.** 되살린 근거로 인용 네 칸을 다시 계산해 저장된 값과
대조하고, 하나라도 어긋나면 **아무것도 안 쓴다.** 지도가 한 자리만 어긋나도
`evidence_gold_chunks` 가 조용히 작아지고, 그러면 무작위 기대값이 낮게 나와 *"생성이 근거를
잘 고른다"* 라는 **틀린 결론이 그럴듯하게** 나온다. 실제로 첫 실행이 이 검사에 걸렸다 —
**기권 행은 `score_answers()` 가 인용 칸을 아예 안 계산하는데** 백필이 다시 돌려 `None` 이
`0` 이 됐다(4/316행).

### 6. 기본 세트가 `verdicts.py` 와 다르다

저쪽은 `qa_set.jsonl`(60건)이고 여기는 **`qa_set_human.jsonl`(43건)** 이다. 이 도구의 첫
지표가 기권율인데 **기권이 정답인 질의(부정 예시 25건)가 사람 세트에만 있다.**

### 7. 비용

- **생성이 질의 수만큼** 든다(캐시 없음). 43건이면 43호출
- **판정은 켰을 때만, 판정 대상의 2배**(본판 + 음성 대조군). 캐시가 있어 같은 (답변, 근거)면 공짜
- **인용 정합성과 대조군은 0**이다. `--backfill` 도 0

  이것부터 의심한다

  기본 세트 60건은 여전히 전부 정답이 실재하므로 **이 세트로는 Phase 4(Evaluator)와
  Phase 10(Hallucination)을 못 잰다** — "항상 충분"이라고만 답하는 Evaluator 가 100점을
  받는다. 사람 세트가 긍정 18 + 부정 25 로 그 자리를 채운다(**43/43 사람 검수 완료**, 2026-08-27). **긍정·부정 어느 쪽도 고정값이 아니라 검수 상태다** — 이 수는 검수가 되돌린 결과이고 또 움직일 수 있다. 부정은 `answerable: false` 이고
  `gold_spans`·`gold_page` 가 비어 있으며, **검색 채점에서는 빠진다**(`run_eval` 의
  `split_scorable`, 리포트의 `skipped_unanswerable`). 이유는 `qa_set.py` 모듈 docstring
- **부정 라벨은 문서 축이지 검색 축이 아니다.** *"이 코퍼스에 답이 없다"* 여야 하고
