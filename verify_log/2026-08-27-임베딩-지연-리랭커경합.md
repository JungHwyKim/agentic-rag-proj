## 1. 확인하려 한 것

핸드오프의 한 줄: **적재가 느린 원인이 리랭커와의 GPU 메모리 경합인가.**

**임계값이 아니라 "축이 맞나" 다.** 그래서 핸드오프 4절이 판정 기준을 미리 못 박아 뒀고,
그것을 그대로 쓴다 — *두 중앙값이 2배 이상 갈리고, 각 조건 안의 3회 편차가 그보다 작으면
경합 확정.* 기준을 먼저 고정한 것이 이 건의 핵심이다. 이 질문은 **이미 세 번 헛짚었고**
셋 다 사후에 그럴듯한 그림을 골라잡은 것이었다.

## 2. 가상 데이터

### A/B — 리랭커를 함께 올리는가 (변인 하나)

전제 넷은 핸드오프 3절 그대로다: **서버를 내리고**(사용자 승인) · **회차마다 3회 이상** ·
**A B A B A B 로 섞고** · **임베딩 캐시를 끈다**(`embedding_cache_enabled=False`).
**회차마다 프로세스를 새로 띄운다** — 한 프로세스에서 리랭커를 내릴 수단이 없다.

적재 시간은 **타이머 밖**이다(리랭커 적재 → 임베더 1청크 워밍업 → `usage.reset()` → 계측).

| 회차 | 리랭커 | 리랭커 적재 | 임베더 적재 | **181청크 임베딩** |

| 1 | X | — | 21.45초 | **120.90초** |
| 1 | O | 15.22초 | 31.77초 | **391.23초** |
| 2 | X | — | 18.51초 | **40.29초** |
| 2 | O | 12.80초 | 8.55초 | **192.80초** |
| 3 | X | — | 12.53초 | **46.28초** |
| 3 | O | 10.64초 | 8.78초 | **206.92초** |

| 조건 | 중앙값 | 최소 | 최대 | 조건 내 편차 |
|---|---:|---:|---:|---:|
| 리랭커 X | **46.28초** | 40.29 | 120.90 | 3.00배 |
| 리랭커 O | **206.92초** | 192.80 | 391.23 | 2.03배 |

- **중앙값 비 4.47배** · 조건 내 최대 편차 **3.00배** → 핸드오프 4절 기준 충족
- **범위가 안 겹친다** — `min(O) 192.80 > max(X) 120.90`. 최악으로 잡아도 **1.59배** 차이라,
  *리랭커를 올린 여섯 회차 중 어느 하나도 안 올린 어느 회차보다 빠르지 않다.* 중앙값보다
  이쪽이 강한 진술이고, 이 건처럼 편차가 큰 데이터에서는 이것이 판정의 근거다
- **양쪽 모두 1회차가 이상값이다**(120.90 / 391.23). 그 둘을 빼면 X 는 편차 1.15배 · O 는
  1.07배로 접히고 비는 **4.62배**로 오히려 커진다. 즉 1회차 이상값은 결론을 흔드는 쪽이
  아니라 **누그러뜨리는** 쪽이었다

### 리랭커가 실제로 올라왔는가 (별도 가드)

**`rerank()` 는 캐시에 걸리면 0.00초에 돌아오고 가중치가 안 올라온다.** 그러면 "리랭커 O"
회차가 실은 X 회차가 되어 A/B 가 통째로 무의미해진다. 질의를 `uuid4` 로 만들어 늘 미스가
나게 했고, **적재 시간을 stderr 로 찍어 확인했다** — 15.22 / 12.80 / 10.64초로 셋 다
0.00초가 아니다. 이 함정은 핸드오프 스니펫에 없었고 피어 세션(`reindex-single-document-api`)
이 알려줬다(그쪽은 한 번 밟았다).

### GPU 를 다른 세션이 안 쓰고 있었는가

핸드오프가 세 번 헛짚은 공통 원인이 오염이라, **측정창이 깨끗했는지를 따로 확인했다.**

| 사건 | 시각 | 출처 |
|---|---|---|
| 피어의 마지막 GPU 작업 종료 | 02:27:43 | 피어 자진 보고 |
| `.cache/rerank` 최신 mtime | **02:03:04** — 이후 없음 | **독립 확증** |
| 내 prep 종료 (`texts.json`) | 02:43:37 | 파일 mtime |
| 내 1회차 종료 → 시작 역산 | 02:48:27 → **≈02:46:05** | 출력 mtime − (120.90 + 21.45) |

피어의 GPU 작업이 끝난 뒤 **약 18분** 지나 시작했다. 피어 진술과 `.cache/rerank` mtime 이
서로 독립적으로 같은 말을 한다.

한 회차를 재는 본체다. **회차마다 프로세스를 새로 띄우는 것이 전제**라 이 파일은 한 회차만 잰다.

```python
# round.py — usage: python round.py <texts.json> <0|1 리랭커>
texts = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
with_reranker = sys.argv[2] == "1"

cfg = IngestConfig()
# 캐시를 끈다 — 안 끄면 두 번째 회차부터 전량 히트라 0초가 나온다
cold = EmbeddingConfig(**{**cfg.embedding.model_dump(), "embedding_cache_enabled": False})

e = get_embedder(cold)

if with_reranker:
    r = get_reranker(cfg.rerank)
    q = str(uuid.uuid4())          # 캐시에 걸리면 가중치가 안 올라온다 (0.00초로 드러난다)
    t0 = time.perf_counter()
    r.rerank(q, _warmup_candidates(q))
    print(f"# 리랭커 적재 {time.perf_counter() - t0:.2f}s", file=sys.stderr)

e.embed_documents(texts[:1])       # 가중치 적재를 시간에서 뺀다
e.usage.reset()                    # max_embedding_tokens_per_doc 이 회차 간에 누적된다

t = time.perf_counter()
e.embed_documents(texts)
print(f"{time.perf_counter() - t:.2f}")
```

`usage.reset()` 이 없으면 안 된다 — 이 문서 한 벌이 약 76K 토큰이라 한 프로세스에서 3회
연속이면 `max_embedding_tokens_per_doc`(200,000) 가드에 걸려 죽는다(피어가 실제로 걸렸다).

## 7. 재지 못한 것

- **조건 내 편차 2.03~3.00배의 원인** — 축은 갈렸지만 편차는 그대로다. 1회차가 양쪽 다
  이상값이라 **순서·예열 효과**로 보이나, 회차가 3뿐이라 그것도 단정 못 한다
- **경합의 기전** — *리랭커가 VRAM 을 먹어서* 인지 *WDDM 이 페이징해서* 인지 안 갈렸다.
  **이 머신에서는 못 가른다** — `nvidia-smi` 의 `memory.used` 가 유휴 프로세스 하나에서도
  7GB 넘게 요동치고 `--query-compute-apps` 는 프로세스별 메모리를 전부 `[N/A]` 로 낸다
- **`EMBEDDING_BATCH_SIZE` 축** — 변인 하나 규칙 때문에 일부러 안 섞었다. 리랭커 축이
  닫혔으니 이제 열 수 있다
- **`RERANK_DEVICE=cpu` 로 옮겼을 때 적재가 실제로 빨라지는가** — 이번에 **안 쟀다.**
  경합을 확인한 것과 *그 처방이 듣는다*는 다르다. 대가(질의당 63.9초)도 함께 재야 한다
- **화면 E2E** — 업로드 진행이 실제로 얼마나 줄어드는지는 브라우저에서만 보인다
