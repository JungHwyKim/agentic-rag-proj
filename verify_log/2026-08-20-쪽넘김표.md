# 쪽 넘김 표 — PDF 가 쪽 경계에서 세로 병합과 셀을 잃는다

- 검증일: 2026-08-20
- 대상: [plan_log/표-경로.md](../plan_log/표-경로.md) 7회차
- 비용: **외부 API 호출 없음.** `ingest()` 와 HWPX XML 직접 파싱만 썼다

## 1. 확인하려 한 것

사용자가 24~25쪽 경계를 이어 붙인 화면을 보내며 **"열은 해결됐는데 행 내용이 손실됐다"**
고 했다. 직전 회차(6회차, 병합 헤더)가 고친 것과 같은 결함인가, 다른 것인가.

## 2. 가상 데이터

없음. 쪽 경계는 합성 문서로 만들 수 있지만 **이번 질문은 실파일에서 무엇이 깨졌나**이고,
고칠 규칙을 아직 안 정해 고립시킬 대상이 없다.

## 3. 실제 데이터

파일 신원은 [2026-08-19-이미지-표시크기.md](2026-08-19-이미지-표시크기.md) 3절과 같다.

### 무엇이 깨졌나

시행령 PDF 의 24~25쪽에 걸친 표에서 리전 경계를 잘랐다.

```
[order=423  page=24  33행]  마지막 행
  업무 정보 | 업무정보    | 업무명      | 설문평가                    | 필수

[order=425  page=25  35행]  첫 데이터 행
           | (4)      | 업무 내용    | 관리자가 설문을 하고 결과 조회…  | 필수
```

두 갈래다.

1. **세로 병합 앵커 유실** — `업무 정보`(영역)가 24쪽에서 시작해 25쪽까지 이어지는데
   25쪽 리전에 앵커 셀이 없어 **첫 열이 통째로 빈다**
2. **셀 분할** — `업무정보 (4)` 가 24쪽 `업무정보` + 25쪽 `(4)` 로 갈렸다

**같은 표를 HWPX 는 67행 하나로 온전히 잡는다.** 5회차가 "두 포맷이 같다"고 닫은 것은
4쪽 표였고 쪽을 넘기는 표는 그 대조에 없었다.

### 규모

다음 쪽 리전이 앞 리전과 **같은 헤더 행으로 시작하는** 경우를 셌다(= 문서가 헤더를 쪽마다
되풀이한다는 신호).

| 문서 | 쪽 넘긴 표 | 그중 첫 열이 빈 것 |
|---|---:|---:|
| AI가이드 PDF | 5 | 0 |
| 시행령 PDF | **1** | **1** |
| 2026중등 PDF · 학교기록물 PDF · 아동정책 PDF | 0 | 0 |
| **합계** | **6** | **1** |

셀 분할은 HWPX·PDF 셀값 대조에서도 잡힌다 — 고유 셀값 **124 vs 124** 중 다른 것이
`업무정보(4)`(HWPX) vs `(4)`(PDF) **하나뿐**이다.

**오검출은 안 셌다.** 이 6건이 전부 진짜 이어지는 표인지는 확인하지 않았고, 그것이
다음 회차의 첫 일이다.

### 헛짚은 곳 넷 — 전부 이상 없음

"행 내용이 손실됐다"를 듣고 먼저 엉뚱한 데를 뒤졌다. 다음 사람이 다시 파지 않도록 남긴다.

| 의심한 곳 | 잰 값 | 결과 |
|---|---|---|
| HWPX 24쪽 표의 행 수 | 원본 `rowCnt=67` · `tr=67` / 조각 합계 67행 | 일치 |
| 그 표의 셀 내용 | XML 셀 219개(내용 있는 것 216) 중 격자에서 못 찾은 것 **0** | 누락 없음 |
| HWPX vs PDF 셀값 | 124 vs 124, 차이 1건 | 위 셀 분할 하나 |
| 마크다운 렌더링 | 내용 있는 행이 버려진 사례 **0** | 손실 없음 |

### 넷째에서 딸려 나온 것 — 두 표현이 어긋난다

`rows_to_markdown()` 이 빈 행을 버려 `metadata["rows"]` 와 본문 행 수가 다르다.

```
학교기록물 HWPX   172행 → 154행   (-18)
2026중등 HWPX    283행 → 272행   (-11)
학교기록물 PDF     125행 → 117행   ( -8)
시행령 HWPX       175행 → 170행   ( -5)
2026중등 PDF      238행 → 236행   ( -2)
아동정책 PDF        3행 →   2행   ( -1)
```

**손실은 아니다** — 버려지는 것이 전부 내용 없는 구분행이고, 내용 있는 행이 버려진 사례는
0이다. 다만 CLAUDE.md 가 cleaner 에 못 박은 *"표는 `text` 와 `metadata["rows"]` 를 함께
고친다. 한쪽만 고치면 같은 표의 두 표현이 어긋난다"* 와 같은 형태라 미결에 넣었다.

## 5. 판정

**직전 회차로 안 끝났다.** 사용자 지적이 맞고, 6회차가 고친 병합 헤더와 **다른 결함**이다.
원인은 `_merge_split_tables()` 가 쪽 안에서만 도는 구조이고, 고치려면 **쪽을 가로지르는
"같은 표" 판정 기준**이 필요하다. 같은 쪽에서 쓴 12pt 는 쪽이 바뀌면 축 자체가 사라진다.

**이번에 안 고쳤다.** 후보 규칙이 6건을 잡지만 오검출을 안 셌고, 표 되붙이기 12pt 를 정할
때 관측값을 그대로 쓰지 않았던 순서를 지킨다.

## 6. 재현

```powershell
.\.venv\Scripts\python.exe -m pytest
```

3절 수치는 픽스처를 `ingest()` 로 돌려 `metadata["rows"]` 를 가진 요소를 쪽 순으로 훑고,
다음 쪽 리전의 첫 행이 앞 리전의 첫 행과 같은지 비교해 얻었다. HWPX 셀 대조는
`Contents/section0.xml` 의 `hp:tc` 를 `cellAddr`·`cellSpan` 과 함께 직접 읽어 격자와 맞췄다.

## 7. 재지 못한 것

- **헤더 반복 규칙의 오검출** — 6건이 전부 진짜인지 확인하지 않았다. 다음 회차의 첫 일
- **쪼개진 셀이 몇 건인가** — 표본이 `업무정보 (4)` 하나다. 덮을지 이을지 정하려면 더 필요하다
- **이어 붙인 뒤 세로 병합을 어떻게 채우나** — `_fill_merged_cells()` 는 PyMuPDF 의 쪽별
  셀 기하에 기대는데 이어 붙인 표에는 그 기하가 없다
- **빈 구분행이 검색에 쓸모가 있는가** — 정답 질의 세트 대기
