# 리랭커가 건드릴 수 있는 것이 얼마인가 — 후보 풀 안에서 정답의 자리

- 검증일: 2026-08-24
- 대상: Phase 3(리랭커) 착수 전, **상한을 먼저 안다**
- 비용: **외부 API 호출 0.** 임베딩 캐시가 문서·질의를 전부 덮었다

## 1. 확인하려 한 것

세션 끝에 *"리랭커는 후보 안에서 순서만 바꾸니 `top_k=20` 밖으로 나간 2건은 회수 불가"* 라고
적었다. **그것이 맞는지부터 봤다** — 맞으면 융합을 먼저 손봐야 하고, 틀리면 리랭커가 먼저다.

## 2. 가상 데이터

없음.

## 3. 실제 데이터

### 3-1. 먼저 그 2건의 자리

| | dense | hybrid | 후보 풀(50) 안? |
|---|---:|---:|---|
| `ai-03` | #20 | #30 | **있다** |
| `ai-12` | #11 | #26 | **있다** |

**둘 다 풀 안이다. "회수 불가" 는 틀렸다.** `retrieve()` 가 `top_k=20` 만 돌려주기 때문에
안 보였을 뿐이고, 리랭커에 풀을 먹이면 닿는다.

### 3-2. 그러면 여지가 전부 얼마인가

hybrid 로 후보 풀 50을 받아, 정답 청크가 그 안 어디에 있는지 셌다.

| | LLM 60건 | 사람 20건 |
|---|---:|---:|
| top10 안 (지금 `hit@10`) | 0.667 (40) | 0.600 (12) |
| **11~50위 — 리랭커가 건드릴 수 있는 것** | **+0.217 (13)** | **+0.350 (7)** |
| 풀 밖 — 리랭커로 못 고침 | 0.117 (7) | 0.050 (1) |
| **리랭커가 완벽할 때 상한** | **0.883** | **0.950** |

**검색 단계는 이미 정답의 88~95%를 후보 풀에 넣고 있다.** 실패하는 것은 **풀 안에서의
순서**다. 그것이 정확히 리랭커의 일이다.

**여지가 hybrid 자신의 이득보다 크다** — hybrid 가 dense 에서 얻은 것이 `+0.183`(LLM) ·
`+0.200`(사람)인데, 리랭커 여지는 `+0.217` · `+0.350` 이다.

### 3-3. 사람 질의가 "어렵다" 의 뜻이 바뀐다

사람 세트의 상한(0.950)이 LLM 세트(0.883)보다 **높다.** 풀 밖으로 나가는 것이 1건뿐이다.
즉 사람 질의는 **찾기 어려운 것이 아니라 순서 매기기 어려운 것**이다. `hit@10` 만 보면
사람 세트가 낮아(0.600 vs 0.667) 반대로 읽힌다.

## 4. 테스트 스위트

안 돌렸다. **코드를 안 고쳤다** — 읽기만 하는 측정이다.

## 5. 판정

- **"리랭커로 회수 불가" 는 기각.** 잃은 2건이 둘 다 풀 안이다
- **작업 순서가 뒤집힌다** — 리랭커가 먼저다. RRF 순서 오류는 리랭커가 풀을 다시 정렬하면
  대부분 지워지므로, 융합을 먼저 고치는 것은 상당 부분 헛일이다
- **배선 요구가 하나 생겼다** — 리랭커는 `retrieve()` 의 `top_k` 가 아니라 **후보 풀**을
  받아야 한다. 그냥 뒤에 붙이면 위 여지를 통째로 버린다

**이 수치는 상한이지 예측이 아니다.** 실제 리랭커가 저 13건·7건을 몇 개나 top10 으로
끌어올릴지는 전혀 다른 문제이고, 그것은 붙여봐야 안다.

## 7. 재지 못한 것

- **실제 리랭커 성적** — 아직 구현이 없다. 위는 상한일 뿐이다
- **풀 크기를 늘리면 상한이 어디까지 오르나** — `candidate_k=50` 에서만 쟀다. 100·200 에서
  풀 밖 7건·1건이 줄어드는지는 안 봤다
- **리랭커에 50개를 먹이는 지연** — 로컬 cross-encoder 는 후보 수에 선형이다
