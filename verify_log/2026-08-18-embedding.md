  `config.py`(`EmbeddingConfig`) · `exceptions.py`(`EmbeddingError`) ·
  `backend/app/main.py`(503 매핑) · `tests/ingestion/embedding/`.
  설계는 [plan_log/embedding.md](../plan_log/embedding.md) 1회차
- 비용: 2~4절은 **외부 API 호출 없음**(가상은 `_make_client()` 를 가짜로 갈아끼웠고, 실파일은

  `ALLOW_PAID_TESTS=1` 로 승인해 직접 돌렸고 **총 2회 실행 · 약 400토큰 · $0.000008** 이다

## 1. 확인하려 한 것

셋이다.

1. **길이 계약이 실제로 지켜지는가.** 이 단계의 유일한 계약이 `len(반환) == len(입력)`
   이거나 예외인데, 이건 **정상 응답에서는 저절로 성립해 보인다.** 깨지는 자리는 배치 분할,
   순서 뒤섞임, 부분 캐시, 손상된 응답이라 **가상으로만 만들 수 있다**
2. **캐시 salt 가 모델·차원을 실제로 가르는가.** 안 가르면 모델을 바꿔도 옛 벡터가 나오는데
   **아무 에러도 안 난다** — 검색 품질이 조용히 떨어질 뿐이라 테스트로만 잡힌다
3. **한국어 청크가 몇 토큰인가.** 이건 반대로 가상이 못 답한다. 합성 문서의 토큰 비율은
   만든 사람이 쓴 어휘를 그대로 반영해 자기 확인이 된다. 실파일이 필요하다

1·2는 2절, 3은 3절이다.

## 2. 가상 데이터

무엇을 고립시켰나: **응답의 모양 한 축만** 바꿨다. `_make_client()` 가 돌려주는 객체를
`FakeClient` 로 갈아끼우고 정상 / 뒤섞임 / 개수부족 / 손상 / 차원불일치를 각각 만들었다.
벡터는 텍스트 sha256 에서 만들어 **같은 텍스트면 항상 같은 값**이라 자리 밀림이 드러난다.

생성 코드는 `tests/ingestion/embedding/conftest.py` 에 있다(스크래치패드가 아니라 저장소에
남겼다 — 회귀 테스트가 계속 쓴다).

기대값을 먼저 적고 돌렸다.

| 고립시킨 축 | 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|---|
| 정상 | 3건, batch 100 | 벡터 3, 호출 1 | 3 / 1 | 기대와 같음 |
| 배치 분할 | 7건, batch 3 | 호출 3, 묶음 `[3,3,1]`, 순서 보존 | 3 / `[3,3,1]` / 보존 | 기대와 같음 |
| **응답 순서 뒤집힘** | 4건 | `index` 로 제자리 복구 | 복구됨 | 기대와 같음 |
| **개수 부족** (1개 뺌) | 3건 | `EmbeddingError` | `EmbeddingError` | 기대와 같음 |
| **손상된 embedding** (`None`) | 1건 | `EmbeddingError` | `EmbeddingError` | **처음엔 달랐다 — 4절** |
| 항목마다 차원 다름 | 2건 | `EmbeddingError` | `EmbeddingError` | 기대와 같음 |
| 요청 차원 ≠ 응답 차원 | 1건 | `EmbeddingError` | `EmbeddingError` | 기대와 같음 |
| 키 없음 | 1건 | `EmbeddingError` (빈 리스트 **아님**) | `EmbeddingError` | 기대와 같음 |
| 빈 문자열 | `""`·`"   "`·`"\n\t"` | `EmbeddingError`, 호출 0 | 셋 다 / 0 | 기대와 같음 |
| API 예외 | 1건 | `EmbeddingError`, 카운터 0 | `EmbeddingError` / 0 | 기대와 같음 |
| 토큰 상한 초과 | 상한 1 | 예외, **호출 0** | 예외 / 0 | 기대와 같음 |

**순서 뒤집힘과 부분 캐시는 실파일이 절대 만들지 못한다.** "실제 응답은 순서를 지키므로
`index` 재정렬 코드가 한 번도 안 돈다"는 이때 추측이었는데, 3-2절 유료 호출에서
**실제로 순서를 지킨다는 것이 확인됐다**(3/3 자기 짝이 최대). 그래도 재정렬을 지운다는 뜻은
아니다 — 보장된 적이 없고, 밀리면 아무 에러 없이 검색이 틀린다.

캐시 salt (`embed:{model}:{dim}`):

| 바꾼 것 | 기대 | 실측 (API 호출 수 / cache_hits) | 판정 |
|---|---|---|---|
| 아무것도 (같은 텍스트 2회) | 캐시 적중 | 1 / 1 | 기대와 같음 |
| `embedding_model` | **미스** | 2 / 0 | 기대와 같음 |
| `embedding_dimensions` | **미스** | 2 / 0 | 기대와 같음 |
| 문서 → 질의 (같은 글자) | 적중 | 1 / 1 | 기대와 같음 |
| 가운데 하나만 미리 캐시 | 나머지만 API, 순서 보존 | API 입력 `["가","다"]` / 순서 보존 | 기대와 같음 |

캐시 적중 시 `total_tokens` 가 0으로 남는 것도 확인했다 — 과금 안 된 것을 세면 안 된다.

### 실제 API 응답 (유료 · `test_embedding_integration.py`)

여기까지는 전부 `_make_client()` 를 가짜로 갈아끼운 결과다. **가짜가 흉내내는 모양이 실제와
같은지**를 확인하려고 유료 호출을 두 번 돌렸다(사용자 승인, 직접 실행).

**1차 (5건 중 2건 실패)** — 실패한 둘은 제품이 아니라 **단언이 틀렸다.** 서로 다른 두 호출의
벡터를 `abs(a - b) < 1e-6` 로 비교했는데 OpenAI 는 호출 간 비트 재현성을 보장하지 않는다.
더 나쁜 것은 그 형태로는 **자리 밀림과 부동소수점 잡음을 구분조차 못 한다**는 점이다(둘 다
`assert False` 로만 보인다). 코사인 유사도 판정으로 바꿔 2차를 돌렸다.

**2차 (5건 전부 통과)**

| 잰 것 | 값 | 무엇을 말하나 |
|---|---|---|
| `usage.total_tokens` (3문장) | **46** | tiktoken 로컬 추정과 **정확히 일치**(16+16+14). 토큰 상한 사전 검사가 어림이 아니다 |
| 기본 차원 | 1536 | 문서화된 값과 같다 |
| 벡터 길이 (3건) | 0.999797 / 1.00051 / 1.000027 | **단위 길이다.** indexing 이 Cosine 대신 Dot 을 쓸 수 있다 |
| **256차원 축소 벡터의 길이** | 0.999942 | **축소해도 정규화가 유지된다** — 재정규화 불필요 |
| 뜻이 다른 두 문장의 코사인 | 0.162641 | 벡터가 실제로 내용을 반영한다 |
| `embed_query` vs `embed_documents([t])` | 코사인 **1.000000000** / 최대 원소차 **0.0** | 같은 배치 구성이면 **비트 단위로 같다** |
| 배치 나눔 시 순서 | 3/3 자기 짝이 최대 | 자리 밀림 없음. 비대각선 0.162~0.325 로 판별 여백이 크다 |

**호출 간 재현성에 대한 결론을 정정한다.** 1차 실패를 보고 "임베딩은 호출마다 다르다"로
단정했는데 2차에서 최대 원소차가 **정확히 0** 이 나왔다. 정확한 사실은 **보장되지 않는다**
이고 두 동작을 다 관측했다. 배치 구성이 영향을 준다는 증거는 순서 테스트 안에 있다.

```
cos(single[0], batched[2]) = 0.184495
cos(single[2], batched[0]) = 0.184417   ← 같은 값이어야 하는데 7.8e-5 다르다
```

`single` 은 3개짜리 배치 한 번, `batched` 는 1개짜리 배치 세 번이다. **배치 구성이 다르면
벡터가 ~1e-4 수준으로 흔들리고, 같으면 정확히 일치한다.** 1차의 실패는 둘 다 1개 배치라
이것만으로는 설명되지 않으므로 서버 쪽 간헐적 요인이 겹친 것으로 본다 — **원소별 비교를
쓰지 않는다**는 결론은 어느 쪽이든 같다.

  어떻게 나오는지는 모른다. 5문서 전체는 139,438토큰 ≈ $0.003 이라 비용이 이유는 아니고,
  **소비할 곳(indexing)이 없어 지금 재도 쓸 데가 없다**
- **호출 간 재현성의 조건** — 1차는 다르고 2차는 정확히 같았다. 배치 구성이 영향을 준다는
  것까지는 봤지만 **1차 실패의 원인은 특정하지 못했다.** 서버 부하로 추정할 뿐이고 확인 못 했다
- **모델 간 검색 품질** — 정답 질의 세트가 없다(`plan_log/평가-세트.md`).
  **비용이 싸다는 것($0.003/5문서)은 품질 근거가 아니다.** 모델·차원은 임시값으로 남는다
- **표 마크다운이 검색에 유리한가** — 장식 비용이 작다는 것만 쟀다. 그 형식이 실제로 잘
  검색되는지는 위와 같은 이유로 못 잰다
- **`embedding_batch_size` 의 상한 쪽** — 문서당 청크가 45~102개라 배치 100 이면 대부분 1회
  호출이다. **100을 넘겨 여러 배치가 되는 경우는 가상으로만 쟀다**(batch 3 으로 줄여서).
  실파일에서 배치가 여러 번 나가는 문서는 이 코퍼스에 없다
