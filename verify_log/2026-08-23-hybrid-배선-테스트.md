## 2. 가상 데이터

무엇을 고립시켰나: **저장소·임베더·BM25 를 전부 가짜로 두고 배선만 남겼다.** 키가 없어도
돌아야 하고, 실파일이 있으면 청크 내용이 섞여 "합류가 됐는가"만 보기 어렵다.

BM25 후보 판정을 재려면 코퍼스 크기가 결과를 바꾸므로 **문서 2개짜리 최소 코퍼스**를 썼다.

```python
from rag_pipeline.retrieval.bm25 import Bm25Index
from rag_pipeline.schemas.vector import StoredChunk

def _stored(cid, text):
    return StoredChunk(id=f"uuid-{cid}", text=text, document_id="안내서.pdf",
                       chunk_id=cid, metadata={"source_name": "안내서.pdf"})

index = Bm25Index([_stored("a", "위약금 조항"), _stored("b", "손해배상 예정액")])
print(index.search("손해배상", 5))
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `tokenize("시행령은")` ∩ `tokenize("시행령")` | 겹치는 토큰 ≥ 1 | `{시행, 행령}` | 통과 |
| `tokenize("AI")` | `["ai"]` (bigram 아님) | `["ai"]` | 통과 |
| `tokenize("제3조")` | 숫자가 한글 구간을 가른다 | `["제","3","조"]` | 통과 |
| `tokenize("ㄱㄴㄷ")` | 자모는 경계 → 토큰 0 | `[]` | 통과 |
| 위 코드의 `search("손해배상", 5)` | 청크 `b` 가 후보 | **처음엔 `[]`** | **실패 → 고침** |
| 고친 뒤 같은 입력 | 청크 `b` 가 후보 | `b` 1건 | 통과 |
| `fuse(dense=[a], sparse=[b])` 의 `a.bm25_score` | `None`(0.0 아님) | `None` | 통과 |
| BM25 점수 0.001 vs 9999 로 `fuse` | `fused_score` 동일 | 동일 | 통과 |
| `retrieve(bm25=None)` 의 `fused_score` | 저장소 점수 그대로 | 그대로 | 통과 |

**다섯째 줄이 이 회차의 유일한 진짜 발견이다.** `rank_bm25` 의 `BM25Okapi` 는 문서 2개
코퍼스에서 한쪽에만 있는 낱말의 IDF 를 **정확히 0** 으로 준다. 후보 판정을 `score > 0.0`
으로 하고 있어서 낱말이 겹치는 청크가 통째로 버려졌다. 코퍼스가 커도 **흔한 낱말에서 같은
일이 난다.** 판정을 낱말 겹침으로 바꿨다.

- **`candidate_k`·`rrf_k` 가 맞는 값인지** — 위와 같은 이유. 지금은 임시값이다
- **`requirements.txt` 가 진짜 고쳐졌는지** — 깨끗한 환경에서만 증명된다. 이 `.venv` 에는

- **`evaluation/` 쪽 배선**(`EVAL_SETTINGS` 의 `retrieval` · `--hybrid`) — 아직 안 넣었다
- 곁들여 발견: `regression/measure.py` 가 **달라진 항목이 있을 때만** 마지막 요약 줄에서
  `UnicodeEncodeError`(cp949)로 죽는다. 그 줄의 `—`(em dash)가 원인이고, `-X utf8` 을 붙이면
  안 난다. **하필 차이가 있을 때만 터진다** — 대조 결과가 필요한 바로 그때다. 리포트 본문은
  그 앞에 다 나오므로 판정 자체는 가능하다. 이 작업 밖이라 안 고쳤다
