# 재작성 흔적을 Answer·화면·query_log 로 흘려보내는 배선

- 검증일: 2026-08-27
- 대상: `task_log/2026-08-27-재작성-흔적.md` (미커밋 작업 트리)
- 비용: **OpenAI gpt-4.1-mini 재작성 2회**(격리 탐침 1 · 라이브 질의 1) · **생성 1회** · **Cohere 리랭킹 1회**.
  `-m integration` 은 안 돌렸다. 사용자 질의 2회(21:37 · 22:02)는 사용자가 직접 넣은 것이라
  내 비용에 안 넣었지만 3절에서 관측값으로 쓴다

## 1. 확인하려 한 것

**규칙이 도는가**다. 임계값을 정하는 작업이 아니다 — 새 수치도 새 설정도 없고, 이미 도는
재작성의 결과를 `Answer` → 화면 · `query_log` 로 흘리는 배선만 넣었다. 그래서 무게는 2절이고,
3절은 *"배선이 실제 서버에서도 이어졌나"* 를 한 번 확인하는 자리다.

가설 셋을 갈라 잡았다.

1. 재작성이 걸린 질의는 화면에 한 줄이 그려지고 `query_log` 에 두 칸이 찬다
2. **재작성이 안 걸린 질의는 셋 다 아무것도 안 남긴다**(꺼짐·폴백·캐시 히트)
3. **폴백이 앞 질의의 재작성을 물려받지 않는다** — 여기가 이번 작업에서 유일하게 조용히
   틀릴 수 있는 자리다

## 2. 가상 데이터

무엇을 고립시켰나: **재작성기의 성공/실패만** 바꾼다. 저장소·임베더·LLM 은 전부 가짜라
질의 내용도 코퍼스도 결과에 안 들어간다. 3번 가설은 *한 인스턴스에 두 번 부르는 것* 이
축이라 호출 순서를 축으로 세웠다.

```python
# tests/test_query.py — Answer 로 흘렀는지
class _FakeRewriter:
    def __init__(self, last_rewritten: str | None = None, mode: str = "fuse") -> None:
        self.last_rewritten = last_rewritten
        self.mode = mode

# tests/retrieval/test_rewrite.py — 폴백이 앞 값을 물려받는지 (핵심)
mocker.patch.object(
    rewrite_mod,
    "_make_client",
    side_effect=[FakeClient('{"query": "다시 쓴 질문"}'), FakeClient(error=RuntimeError("429"))],
)
rewriter = get_rewriter(_config(tmp_path))
rewriter.rewrite(_ORIGINAL, _context())      # 성공
rewriter.rewrite("다른 질문", _context())     # 실패 -> 폴백
# rewriter.last_rewritten 이 여기서 None 이어야 한다
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 재작성 성공 1회 | `last_rewritten == "다시 쓴 질문"` | 같음 | 통과 |
| 성공 뒤 API 실패(429) | `last_rewritten is None` | `None` | 통과 |
| 성공 뒤 빈 context | `last_rewritten is None` | `None` | 통과 |
| 캐시 히트 | `last_rewritten` 에 값 있음 · `api_calls == 0` | 값 있음 · 0 | 통과 |
| `_FakeRewriter("…", "fuse")` | `Answer.rewrite.query/mode` 가 그대로 | 같음 | 통과 |
| `_FakeRewriter(None)` | `Answer.rewrite is None` | `None` | 통과 |
| `rewriter` 미전달 | `Answer.rewrite is None` | `None` | 통과 |
| `RewriteTrace(mode="fuse")` 렌더 | `도 함께 검색했습니다` | 같음 | 통과 |
| `RewriteTrace(mode="replace")` 렌더 | `로 바꿔 검색했습니다` · `도 함께` 없음 | 같음 | 통과 |
| `rewrite=None` 렌더 | 조각에 `rewrite-row` 없음 | 없음 | 통과 |
| `rewrite=None` 로그 | `rewritten`·`rewrite_mode` 키가 **있고** 값이 `null` | 같음 | 통과 |

**두 번째 줄이 이 표의 요점이다.** 되돌리기(`rewrite()` 맨 앞의 `self._last_rewritten = None`)를
빼면 이 줄만 깨지고 나머지 열은 전부 통과한다.

## 3. 실제 데이터

실파일(`tests/fixtures/`)이 입력이 아니다. 입력은 **띄워 둔 서버에 넣은 라이브 질의**이고,
색인은 개발 머신의 `.qdrant`(문서 10건)다. 그래서 신원 표는 파일이 아니라 회차로 적는다.

| 시각(KST) | 질의 | 재작성 결과 | mode | elapsed | 넣은 사람 |
|---|---|---|---|---:|---|
| 21:37:23 | `지원 방식 알려줘` | `2026 중등 기초학력 보장 사업의 지원 방식 및 운영 방법 안내` | fuse | 9223ms | 사용자 |
| 21:57:22 | `기초학력 지원 어떻게 하나요 (462ba5)` | `기초학력 지원 사업 신청 및 운영 절차와 지원 내용에 관한 안내` | fuse | 11601ms | 나 |
| 22:02:22 | `지원금 액수가 궁금해요` | `2026 중등 기초학력 보장 추진 계획 내 두드림학교 및 기초학력보장 선도학교 지원금 액수와 예산 배분 내역` | fuse | 7336ms | 사용자 |

**21:37 회차는 배선 이전이다** — 그때 `query_log` 줄에는 `rewritten` 칸이 없었다. 뒤 둘에는 있다.

| 항목 | 배선 전 | 배선 후 | 판정 |
|---|---|---|---|
| `query_log` 칸 수 | 7 | 9 (`rewritten`·`rewrite_mode`) | 의도한 변화 |
| 답변 조각의 재작성 줄 | 모든 답변에 가짜(`관련 조항 재검색 중 (1 / 3)`) | 재작성이 걸렸을 때만 실물 | 의도한 변화 |
| `.cache/rewrite` | 78 | 81 (질의 3회 + 탐침 1회 후 삭제) | 의도한 변화 |

**PRF 가 실제로 버는 것이 세 회차에서 눈에 보인다.** 22:02 회차가 제일 뚜렷하다 —
`지원금 액수가 궁금해요` 라는 일상어에 `두드림학교` · `기초학력보장 선도학교` 라는
**코퍼스 고유어**가 붙었다. 모델이 지어낸 것이 아니라 1차 검색 상위 10에서 건진 것이고,
그것이 이 단계를 고른 근거였다(`plan_log/검색-생성.md` 21회차). **다만 세 회차뿐이라
검색 품질이 좋아졌다는 판정은 아니다** — 그것은 `run_eval` 이 이미 60건에서 답했다.

## 7. 재지 못한 것

- **재작성을 켠 화면 지연**. 위 세 회차(9223 · 11601 · 7336ms)는 캐시 상태도 서버 프로세스도
  제각각이라 **기준선이 아니다.** 재작성 O/X 를 각각 여러 회차로 잡는 측정이 다음 일이고,
  X 조건을 만들려면 `.env` 의 `REWRITE_MODEL` 을 주석 처리하고 서버를 다시 띄워야 한다
- **모양은 기계가 못 잰다.** 잘림·정렬·꼬리말이 안 잘리는지는 사람이 브라우저로 여는 것이
  최종 판정이다(헤드리스 브라우저가 없다 — `plan_log/frontend.md` 2회차가 남긴 미결과 같다)
- **`replace` 모드의 라이브 회차가 없다.** `.env` 가 `fuse` 라 화면에서 `로 바꿔 검색했습니다`
  문구는 렌더 테스트로만 확인했다
