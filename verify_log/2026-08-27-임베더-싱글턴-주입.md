## 2. 가상 데이터

무엇을 고립시켰나: **임베딩 캐시 적중 여부 한 축.** 다른 것(문서·설정·서버)을 전부 고정한
채 캐시만 비웠다 지웠다 하며 재색인을 걸었다. 4절이 그 A/B 다.

`index_document()` 의 주입 계약 자체는 실행 없이 잠갔다 — 모델을 안 올리는 가짜 임베더로
`get_embedder()` 가 안 불리는 것과 `usage` 가 이 문서 몫만 나오는 것을 본다.

```python
class _CountingEmbedder:
    def __init__(self, dim: int = 8) -> None:
        self.dim = dim
        self.usage = EmbeddingUsage()
        self.batches = 0

    def embed_documents(self, texts):
        self.batches += 1
        self.usage.api_calls += 1
        self.usage.total_tokens += 7 * len(texts)
        return [[0.1] * self.dim for _ in texts]

    def embed_query(self, text):
        return [0.1] * self.dim
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `index_document(..., embedder=fake)` | `get_embedder()` 미호출 · `batches == 1` | 그대로 | 통과 |
| 위 임베더에 `usage.api_calls=5, total_tokens=999` 를 미리 얹고 색인 | `result.usage` 는 **이번 몫만**(1 · 7×청크수) | 그대로 | 통과 |
| 〃 | 공유 카운터는 **안 줄어든다**(6 · 999+7×청크수) | 그대로 | 통과 |
| 업로드·재색인 라우트 | `kwargs["embedder"] is app.state.embedder` | 그대로 | 통과 |

### 4.5 워밍업이 실제로 도는가 (추가 측정, 무료)

HTTP 로 안 나오는 값이라 **기동 경로를 그대로 다시 태웠다** — 같은 `.env`, 같은 lifespan,
같은 `warm_up()`. 쓰기는 `QDRANT_PATH`·`ORIGINALS_DIR`·`QUERY_LOG_PATH` 를 임시 경로로 돌렸다
(qdrant 는 운영 서버가 잠금을 들고 있어 안 돌리면 여기서 죽는다).

| 항목 | 실측 |
|---|---|
| `warmup_on_startup` | `True` |
| 기동(lifespan 반환) | 0.011초 · `health=200` |
| 워밍업 완료까지 | **22.675초** |
| **`warmup_errors`** | **`[]`** |
| `state.embedder` / `state.reranker` | `LocalEmbedder` / `LocalCrossEncoderReranker` |
| VRAM | 640 → **5157 MiB** |

**운영 워커에서도 실제로 돌았다.** 워밍업 입력이 `uuid4` 라 캐시에 늘 미스로 한 줄씩 남는
것이 이 증거를 만든다 — 워커 기동 `00:04:27` → `.cache/embedding` 1건 `00:04:42`(+15초) →
`.cache/rerank` 1건 `00:04:50`(+23초). 위 22.675초와 맞는다.

**그래서 이 기록의 앞 판정 하나가 틀렸다** — *"워밍업이 모델을 안 들고 있다"* 는 VRAM 하나만
보고 세운 추측이었고, 캐시 흔적이 그것을 뒤집었다.

**안 풀린 것은 VRAM 숫자다.** 워커가 24.9분째인데 656 MiB 다. 참고로 이 머신은
`nvidia-smi --query-compute-apps` 가 프로세스별 메모리를 전부 `[N/A]` 로 낸다(WDDM) — 총량만
보이고 귀속이 안 보여 어느 프로세스 몫인지 못 가른다. 가장 싼 확인은 `--reload` 없이 새로
띄우고 25초 뒤 VRAM 을 보는 것이다.
