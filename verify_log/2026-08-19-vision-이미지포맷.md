2. 고치는 방법으로 **전부 PNG 로 굽기**와 **못 받는 것만 굽기** 중 어느 쪽인가

## 2. 가상 데이터

`tests/ingestion/loader/content/test_vision_format.py` 4건. 합성 이미지를 포맷별로 만들어
`image_vision.handle()` 에 넣고, `_make_client` 이음새로 붙잡은 **실제 data URL** 을 검사한다.

| 만든 것 | 기대 | 결과 |
|---|---|---|
| BMP 400×200 | `data:image/png` 로 나가고 바이트가 달라진다(다시 구웠다) | 통과 |
| JPEG 400×200 | `data:image/jpeg` 로 나가고 바이트가 **원본과 동일**하다 | 통과 |
| GIF 400×200, `blob_kind="png"` | 라벨이 아니라 바이트를 봐서 `gif` 로 나간다 | 통과 |
| 몸통이 잘린 BMP(200바이트) | 예외가 아니라 빈 결과 + 폴백 경고, `vision_calls=0` | 통과 |

가상이 답할 수 있는 것은 **규칙이 도는가**까지다. 어느 포맷이 실제 문서에 들어있는지와
재인코딩이 얼마나 부푸는지는 3절이 답한다.

세 번째 항목이 이 회차의 핵심을 고립시킨다 — `blob_kind` 에 일부러 거짓말(`"png"`)을 시켜도
GIF 로 나가야 한다. 로더가 실제로 하고 있던 거짓말이 그것이다.

### 재인코딩 비용 — 전부 굽기 vs 못 받는 것만 굽기

| | 최대 base64 | 상한(20MB) 대비 | 재인코딩 건수 |
|---|---:|---:|---:|
| 전부 PNG 로 굽기 | 14,743,305 B | **74%** | 197 |
| 못 받는 것만 굽기 | 5,093,256 B | 25% | 40 |

가장 부푸는 것은 학교기록물 HWPX 의 사진들이다.

```
4000x3000 jpeg   3,812,550 B  ->  PNG 11,057,479 B   (2.9배)
2016x1512 mpo    1,257,533 B  ->  PNG  3,819,942 B   (3.0배)
1233x833  bmp    3,082,154 B  ->  PNG    901,736 B   (0.29배 — bmp 는 오히려 줄어든다)
```

**JPEG 을 굽는 것이 손해의 전부다.** bmp 는 무압축이라 PNG 로 구우면 오히려 작아진다.

### 수정 후 실제 함수로 재확인

고친 `_normalize_for_vision()` 을 픽스처 197개에 그대로 돌렸다.

```
images 197 / passthru 157 / reencoded 40 / failed 0
passthru: jpeg->jpeg 111, png->png 46
reencode: bmp->png 32, jpeg2000->png 4, mpo->png 4
max after reencode: 3,819,942 B -> base64 5,093,256 B
```

**정규화 실패 0개.** `vision_calls=0` 이던 문서 셋이 정확히 `passthru == 0` 인 셋이고, 이제
전부 재인코딩 경로로 들어간다.
