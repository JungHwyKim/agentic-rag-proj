# 실패가 화면에 뜨는가, 그러면서 공개 API 의 JSON 은 그대로인가

- 검증일: 2026-08-24
- 대상: [task_log/2026-08-24-조용한-실패.md](../task_log/2026-08-24-조용한-실패.md) · 미커밋 (기준 `e00f7f6`)
- 비용: **외부 API 호출 없음.** 임베딩·생성·LlamaParse 를 한 번도 안 부른다 — 실패 경로 테스트는 예외를 `side_effect` 로 주입하고, 415·413 은 파일이 로더에 닿기도 전에 거절된다

## 1. 확인하려 한 것

**"규칙이 도는가"** 다. **임계값이 없다** — 이번 변경에 고른 수가 하나도 없다.

축은 하나다: **`HX-Request` 헤더.** 있으면 HTML 조각, 없으면 지금까지의 JSON.

1. **두 갈래가 실제로 갈리는가** — 그리고 **JSON 쪽이 한 자도 안 바뀌었는가**
2. **415·413 이 그 갈래를 타는가** — 이 둘은 `RagPipelineError` 가 아니라 `HTTPException`
   이라 **다른 핸들러**로 간다. `RagPipelineError` 쪽만 고치면 나머지가 전부 통과하는데
   업로드가 제일 자주 낼 오류만 안 보인다
3. **화면 배선이 렌더된 HTML 에 실제로 실려 나오는가**

## 2. 가상 데이터

무엇을 고립시켰나: **요청 헤더 하나.** 같은 라우트·같은 예외·같은 파일로 보내면서
`HX-Request` 만 붙였다 뗐다 한다. 앱은 `create_app()` 을 그대로 쓰고 `app.state` 에만
가짜를 꽂는다 — **lifespan 을 일부러 안 돌린다**(돌리면 테스트가 `PROJECT_ROOT/.qdrant` 를
열어 개발자의 실제 색인을 건드리고 배타 잠금까지 잡는다).

```python
HTMX = {"HX-Request": "true"}


class FakeStore:
    def iter_chunks(self):
        return iter(())

    def close(self) -> None:
        pass


def _client() -> TestClient:
    app = create_app()
    config = IngestConfig()
    # 생성 설정의 키를 지운다 — offline_config 와 같은 이유로, 안 지우면 실키가 실린다
    object.__setattr__(config, "_generation", GenerationConfig(openai_api_key=None))
    app.state.ingest_config = config
    app.state.store = FakeStore()
    app.state.embedder = object()
    app.state.bm25 = None
    app.state.answer_cache = None
    return TestClient(app)


def _files(name="안내서.docx", body=b"PK\x03\x04 not really a docx") -> dict:
    return {"file": (name, body, "application/octet-stream")}
```

기대값을 먼저 적었다.

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `/documents/index` · `EmbeddingError` · **HX 있음** | 503 · `text/html` · `user_message` 포함 | 그대로 · `class="error"` 포함 | OK |
| 같은 실패 · **HX 없음** | 503 · `application/json` · `detail == user_message` | 그대로 | OK |
| `.exe` · **HX 있음** | 415 · `text/html` · `.exe` 포함 | 그대로 | OK |
| `.exe` · **HX 없음** | 415 · `application/json` · `detail` 에 `.exe` | 그대로 | OK |
| 2MB 파일 · 상한 1MB · **HX 있음** | 413 · `text/html` | 그대로 | OK |
| `/query` · `IndexingError` · **HX 있음** | 503 · `text/html` · `user_message` 포함 | 그대로 | OK |
| 서로 다른 `user_message` 둘 | 문구가 **그대로** 실린다 | 그대로 | OK |
| 색인 성공 · **HX 있음** | 204 · **본문 빈 문자열** · `HX-Trigger` | 그대로 | OK |
| `get_settings()` 가 캐시되지 않는가 | 413 테스트가 옆 테스트를 안 깬다 | 안 깬다 | OK |

**쌍으로 잰 것이 이 표의 요점이다.** HX 있음만 봤으면 *"화면은 고쳤는데 공개 API 를
깨뜨렸다"* 가 안 잡힌다. 415·413 의 쌍이 특히 그렇다 — 그쪽은 아예 다른 핸들러다.

화면 배선은 렌더된 HTML 문자열로 넷을 더 봤다(`tests/api/test_pages.py`).

| 확인 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 오류 자리와 폼의 겨냥 | `id="upload-error"` · `hx-target="#upload-error"` · `hx-swap="innerHTML"` | 셋 다 있음 | OK |
| **reset 비대칭** | 업로드 폼은 조건 없이, composer 는 `successful` 일 때만 | 그대로 | OK |
| swap 리스너 | `id="error-swap"` · `htmx:beforeSwap` · `shouldSwap = true` | 셋 다 있음 | OK |
| `isError` 는 안 건드림 | 스크립트에 `isError` 없음 | 없음 | OK |

마지막 것을 따로 잠근 이유: `isError = false` 를 켜면 **그리기는 하는데
`htmx:responseError` 가 안 떠 콘솔 진단이 사라진다.** 그리는 것과 실패로 남기는 것은
다른 축이라, "오류가 안 그려진다"를 고치다 이걸 같이 끄기 쉽다.

**실파일 파싱은 이번 변경과 무관하다** — 고친 것이 전부 예외→응답 경로와 화면 배선이라
`tests/fixtures/` 가 답할 질문이 없다. 대신 **이미 색인된 실제 저장소**를 읽기 전용으로
관측했다. 이것이 *"업로드한 파일이 어디에 저장되나"* 에 답한 자리다.

**두 경로로 독립 대조했다.** 이쪽은 `storage.sqlite` 를 `?mode=ro` 로 직접 열어 셌고,
`defer-commit-pending-changes` 세션이 띄워 둔 서버의 `GET /api/v1/documents` 로 따로 셌다 —
**480 과 6문서가 정확히 일치**한다. 혼자 센 값이었으면 파싱 방식의 착오를 못 걸렀다.

**여기서 딸려 나온 것 둘.**

- 뒤의 둘(41·25)은 평가 코퍼스 밖이다 — **사용자가 오늘 19:37 에 브라우저 업로드 버튼으로
  올린 것**이고, 4회차가 *"브라우저에서 안 눌러봤다"* 로 남긴 자리가 이걸로 실증됐다
- **`.hwpx` 가 섞여 있다** — 확장자 1차 검증과 매직바이트 2차 검증이 한글 파일에서도
  실제로 지났다는 뜻이다(3회차가 22종 왕복으로 잰 것의 운영 쪽 옆줄)

### 실서버 관측 — 여기서 하나 걸렸다

띄워 둔 `uvicorn --reload` 에 같은 요청을 걸어 봤다.

| 요청 | 기대 | 실측 | |
|---|---|---|---|
| `.exe` + `HX-Request` | 415 · `text/html` | 415 · **`application/json`** | **불일치** |
| `GET /api/v1/nope` + `HX-Request` | HTML 조각 | **`{"detail":"Not Found"}`** | **불일치** |
| `GET /` 의 배선 6종 | 전부 있음 | 전부 있음 | 일치 |

**코드가 틀린 것이 아니라 프로세스가 옛것이었다.** 워커(PID 33260)의 생성 시각이
`19:31:27` 로 서버 기동 그대로다 — `--reload` 가 `main.py` 변경에 **한 번도 반응하지
않았다.** 배선 6종이 최신으로 보인 것은 Jinja2 가 템플릿을 mtime 으로 매 요청 새로 읽기
때문이고, **그래서 "화면은 새것, 파이썬은 옛것"** 이라는 헷갈리는 조합이 나온다.

**이것이 이번 검증에서 제일 값나가는 관측이다** — 렌더된 HTML 만 보고 "실서버에서 확인함"
이라고 적었으면 거짓이 될 뻔했다.

### 재시작 뒤 — 넷 다 실서버에서 확인됐다

사용자가 프로세스를 내렸고(권한으로 막혀 있던 자리다) 새로 띄워 같은 것을 다시 걸었다.

| 요청 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `.exe` + `HX-Request` | 415 · `text/html` · 한국어 문구 | `415 · text/html` · `<p class="error" role="alert">'.exe' 형식은 지원하지 않습니다…` | OK |
| `.exe` · 헤더 없음 | 415 · `application/json` | `415 · application/json` · `detail` 동일 문구 | OK |
| `GET /api/v1/nope` + `HX-Request` | HTML 조각 | `404 · text/html` · `<p class="error" role="alert">Not Found</p>` | OK |
| `GET /api/v1/documents` | 기존 색인 생존 | 200 · `doc-item` **6개** | OK |

셋째가 **`StarletteHTTPException` 핸들러가 실제로 산다는 증거**다 — 404 는 라우트를 아예
안 지나므로 라우트별 try/except 였다면 못 잡는 경로다. 넷째는 서버를 내렸다 올리는 사이
**qdrant 배타 잠금이 정상적으로 반납·재취득됐다**는 뜻이다.

**같은 문구가 두 갈래에 그대로 실린 것**도 여기서 보인다 — HTML 쪽은 Jinja 가 작은따옴표를
`&#39;` 로 이스케이프할 뿐 문장이 같다. `_error.html` 이 문구를 새로 짓지 않는다는 것이
합성이 아니라 실제 응답으로 확인됐다.

## 7. 재지 못한 것

- **브라우저에서 눌러보지 못했다 — 다만 남은 것이 줄었다.** 재시작 뒤 **서버 절반은 실서버
  에서 확인됐다**(위 3절). 남은 것은 순전히 **브라우저 런타임**이다: htmx 가 `beforeSwap` 을
  실제로 어떻게 처리해 `#upload-error` 에 넣는지 · `<label for>` 가 숨긴 input 을 여는지 ·
  `reset()` 뒤 같은 파일을 다시 골랐을 때 `change` 가 뜨는지 · 성공 204 의 빈 본문이 그 자리를
  실제로 비우는지. **넷 다 사람이 눌러야만 재현된다** — `TestClient` 도 `httpx` 도 htmx 를
  실행하지 않는다
- **질의 실패를 화면에서 못 만든다.** `.env` 에 키가 있어 `EmbeddingError`·`GenerationError`
  가 자연히 안 난다. 라우트 계약은 2절이 덮지만 화면에서 본 것은 아니다
- **`--reload` 가 왜 안 먹었는지 원인은 안 팠다.** `watchfiles` 부재인지 감시 경로 문제인지
  안 갈랐다 — 재시작으로 증상이 사라져 이번 범위 밖으로 뒀다. **새 서버에서 다시 발생하는지도
  아직 모른다**
- **답변 캐시가 켜진 상태의 상호작용.** `ANSWER_CACHE_THRESHOLD` 가 비어 있으면 캐시가
  통째로 꺼지고 그게 기본값이라, 이번에도 그 경로는 안 밟혔다
