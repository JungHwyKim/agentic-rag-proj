# 기동 워밍업이 서버를 안 막고 모델을 실제로 올리는가

- 검증일: 2026-08-26
- 대상: `task_log/2026-08-26-기동-워밍업.md` (「다음 승인 단위」 미결 *기동 시 미리 적재할지* 의 구현). 측정 시점 HEAD `c9e4ce1`
- 비용: **외부 API 호출 없음.** 생성 LLM 0회 · vision 0 · llamaparse 0 (질의를 한 건도 안 보냈다)

## 1. 확인하려 한 것

임계값이 아니라 **계약이 지켜지는가**다. 워밍업이 노리는 것은 첫 질의 21.8초 중 약 19초인데
(`2026-08-26-첫질의-대표값.md`), 그것을 얻으면서 **깨면 안 되는 것이 둘**이다.

1. **서버는 즉시 떠야 한다** — `local_ce.py` 의 *"로딩이 느리거나 실패해도 서버는 떠야 한다"*
2. **기본 pytest 가 가중치를 안 받아야 한다** — 이번에 새로 걸린 축이다

그리고 **워밍업이 실제로 데우는지**가 따로 확인돼야 한다. `get_embedder()`·`get_reranker()`
자체는 0.002초라, 객체만 만드는 워밍업은 **아무것도 안 하면서 다 한 것처럼 보인다.**

## 2. 가상 데이터

무엇을 고립시켰나: **가짜 임베더·리랭커**로 "워밍업이 무엇을 부르는가"만 남기고 가중치
적재를 통째로 뺐다. 실제 모델로는 *"안 데웠다"* 와 *"데웠는데 느리다"* 가 시간으로만
갈려서, 계약 위반을 시간으로 판정하게 된다.

```python
class FakeReranker:
    def __init__(self) -> None:
        self.calls: list[int] = []

    def rerank(self, query: str, candidates: list) -> list:
        self.calls.append(len(candidates))   # **후보 수를 기억하는 것이 요점**
        return candidates
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 설정 기본값 | `warmup_on_startup is False` | False | 의도한 변화 |
| lifespan · `WARMUP_ON_STARTUP=true` | 배경 스레드가 뜬다 | `Event` 5초 안에 set | 의도한 변화 |
| lifespan · `WARMUP_ON_STARTUP=false` | `warm_up` 이 안 불린다 | `assert_not_called` 통과 | 의도한 변화 |
| 같은 칸을 `.env` 를 안 덮고 재기 | (덮어야 한다) | **`.env` 를 켜자 깨졌다** — `Settings` 가 `PROJECT_ROOT/.env` 를 읽어 *기본값* 이 아니라 **개발자 설정**을 재고 있었다 | **회귀 — 고쳤다**(`monkeypatch.setenv`) |
| 워밍업 1회 | 임베더·리랭커를 **쓴다**(만들기만 하지 않는다) | `embed_query` 1회 · `rerank` 1회 | 의도한 변화 |
| 리랭커에 먹인 후보 수 | **2 이상** | 2 | 의도한 변화 |
| 리랭커가 `None`(모델명 빔) | 그 갈래만 건너뛴다 | `warmup_errors == []` | 의도한 변화 |
| 임베더가 예외를 던짐 | **안 던지고** 기록만 | `warmup_errors` 에 `embedder:` | 의도한 변화 |
| 같은 getter 2회 | 같은 인스턴스 | `first is second` | 의도한 변화 |
| 스레드 4개가 동시에 getter 진입 | **1번만 만든다** | `len(calls) == 1` | 의도한 변화 |

**후보 2개 칸은 가상만 만들 수 있다.** `local_ce.rerank()` 가 `len(candidates) <= 1` 이면
모델을 안 올리고 그대로 돌려주는데, 실파일 경로에서는 후보가 늘 50이라 이 경계가 **우연히도
안 나온다.** 하나만 먹이는 실수는 *"첫 질의가 여전히 느리다"* 로만 드러난다.

### 기동이 안 막히는가

| 항목 | 실측 |
|---|---:|
| `WARMUP_ON_STARTUP=true` 로 띄운 뒤 `GET /docs` 200 까지 | **97 ms** |

**게으름 계약이 안 깨졌다.** 동기로 올렸으면 여기가 20초대여야 한다.

### 모델이 실제로 올라오는가

질의를 **한 건도 안 보내고** GPU 메모리만 5초 간격으로 봤다.

| 시점 | VRAM |
|---|---:|
| 기동 전 | 1442~1530 MiB |
| t+05s | 1626 MiB |
| t+10s | 2725 MiB |
| t+15s | **3974 MiB** |
| t+20s | 3938 MiB |
| t+25s | 3911 MiB |
| t+30s | 3884 MiB |
| 서버 종료 후 | 1530 MiB |

**질의 없이 2.4GB 가 올라왔다는 것이 워밍업이 실제로 돌았다는 증거다.** 객체만 만들었으면
이 곡선이 평평했을 것이다. 15초쯤에 평평해지는 것도 앞 회차의 리랭커 적재분
6.2~6.5초 + 임베더 11.8~14.7초와 아귀가 맞는다.

## 7. 재지 못한 것

- **워밍업 후 첫 질의의 왕복** — 생성 LLM 과금이라 안 돌렸다. 이 회차의 가장 큰 공백이다
- **워밍업이 기동을 늦추는 정도의 상한** — 97ms 는 한 번 잰 값이고, 스레드 생성 비용이라
  분산을 안 봤다
- **워밍업 도중에 질의가 들어오는 경우의 실제 동작** — 락은 단위 테스트로 잠갔지만
  **실제 모델 적재 중에 요청을 보내 보지는 않았다.** 그때 요청은 락을 기다리므로
  *"첫 질의가 워밍업 잔여 시간만큼 기다린다"* 가 예상인데 확인 안 했다
- **CPU 전용 머신** — `RERANK_DEVICE=cpu` 에서 워밍업이 63.9초짜리를 배경에서 무는 동안
  서버가 어떻게 보이는지 안 봤다
- **메모리 상한** — VRAM 8151MiB 중 3974 까지 올라갔다. 임베딩까지 GPU 로 보낸 `86b5330`
  이후의 동시 사용량은 이 측정에 안 들어가 있다
