## 1. 확인하려 한 것

셋이고 성격이 다르다.

1. **규칙이 도는가** — 빈 `None` 자리를 *격자 칸 중심을 덮는 앵커가 있는가* 로 가르면
   진짜 병합 자리와 격자 구멍이 실제로 갈리는가. 그리고 구멍 글자 복원의 빈 열 가드가
   막을 것을 막는가. → **가상**
2. **임계값이 맞는가** — 판정 두 겹(`_MARK_INSIDE_RATIO` · `_MARK_AREA_RATIO`)을 합성 격자
   칸에도 그대로 써도 오검출이 안 쏟아지는가. → **실파일**
3. **호출이 실제로 줄어드는가** — 한 문서 안에서 표시 서명이 한 종류인가, 그리고 표 6개가
   호출 1회가 되는가. → **실파일 + 가짜 클라이언트**

## 2. 가상 데이터

무엇을 고립시켰나: **같은 표 안에 "앵커가 덮는 빈 자리"와 "아무도 안 덮는 빈 자리"를
동시에 두고**, 그 둘만으로 판정이 갈리는지 봤다. 드로잉·글자는 그 위에 얹었다.

```python
# tests/ingestion/loader/document/test_pdf.py 의 _fake_table 을 그대로 쓴다.
# cells 의 None 이 "PyMuPDF 가 셀 사각형을 안 낸 자리"이고 extract() 는 거기에 빈 문자열을 준다.
from types import SimpleNamespace

import pymupdf

from rag_pipeline.ingestion.loader.document.pdf import (
    _fill_grid_holes, _fill_merged_cells, _grid_holes, _mark_cells, _mark_signature,
)


def _fake_table(rows):
    return SimpleNamespace(
        rows=[SimpleNamespace(cells=cells) for cells, _ in rows],
        extract=lambda: [list(values) for _, values in rows],
    )


# r1c1 = 가로 병합에 덮인 자리 (앵커 (0,10,200,20) 이 중심 (150,15) 를 덮는다)
# r2c0 = 격자 구멍            (어느 앵커도 중심 (50,25) 를 안 덮는다)
table = _fake_table([
    ([(0, 0, 100, 10), (100, 0, 200, 10), (200, 0, 300, 10)], ["A", "B", "C"]),
    ([(0, 10, 200, 20), None, (200, 10, 300, 20)],            ["전체", "", ""]),
    ([None, (100, 20, 200, 30), (200, 20, 300, 30)],          ["", "F", "G"]),
])

values = _fill_merged_cells(table)
holes = _grid_holes(table, values)
print("구멍:", [(r, c) for r, c, _ in holes])

page = SimpleNamespace(
    get_textbox=lambda rect: "책임성" if tuple(rect) == (0.0, 20.0, 100.0, 30.0) else ""
)
_fill_grid_holes(page, values, holes)
print("복원:", values[2][0])

# **표를 새로 만든다.** 위에서 글자를 채운 구멍은 더 이상 빈 칸이 아니라 표시 대상이
# 아니다(로더도 같은 순서로 돈다 — 글자 복원이 먼저고 표시 판정이 나중이다)
t2 = _fake_table([
    ([(0, 0, 100, 10), (100, 0, 200, 10), (200, 0, 300, 10)], ["A", "B", "C"]),
    ([(0, 10, 200, 20), None, (200, 10, 300, 20)],            ["전체", "", ""]),
    ([None, (100, 20, 200, 30), (200, 20, 300, 30)],          ["", "F", "G"]),
])
v3 = _fill_merged_cells(t2)
h3 = _grid_holes(t2, v3)
print("표시:", _mark_cells(t2, [
    (pymupdf.Rect(40, 22, 48, 28), "hole-sig"),      # 구멍 안
    (pymupdf.Rect(140, 12, 148, 18), "merged-sig"),  # 병합에 덮인 자리 안
], v3, h3))
print("배경 음영:", _mark_cells(t2, [(pymupdf.Rect(0, 20, 100, 30), "shade")], v3, h3))

# 빈 열 가드 — 구멍이 있는 열이 표 전체에서 비어 있다
empty_col = _fake_table([
    ([(0, 0, 100, 10), (100, 0, 200, 10)], ["A", ""]),
    ([(0, 10, 100, 20), None],             ["B", ""]),
])
v2 = _fill_merged_cells(empty_col)
h2 = _grid_holes(empty_col, v2)
_fill_grid_holes(SimpleNamespace(get_textbox=lambda rect: "21"), v2, h2)
print("빈 열 가드:", repr(v2[1][1]))

# 서명 — 크기만 다른 같은 경로
small = {"items": [("l", pymupdf.Point(0, 0), pymupdf.Point(10, 10))], "fill": (0.1, 0.2, 0.3)}
large = {"items": [("l", pymupdf.Point(0, 0), pymupdf.Point(20, 20))], "fill": (0.1, 0.2, 0.3)}
white = {"items": [("l", pymupdf.Point(0, 0), pymupdf.Point(10, 10))], "fill": (1.0, 1.0, 1.0)}
print("크기 무시:", _mark_signature(small, pymupdf.Rect(0, 0, 10, 10))
      == _mark_signature(large, pymupdf.Rect(0, 0, 20, 20)))
print("색 구분:", _mark_signature(small, pymupdf.Rect(0, 0, 10, 10))
      != _mark_signature(white, pymupdf.Rect(0, 0, 10, 10)))
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 앵커가 덮는 빈 자리 `(1,1)` + 안 덮는 빈 자리 `(2,0)` | 구멍은 `[(2,0)]` 만 | `[(2, 0)]` | 통과 |
| 구멍 `(2,0)` 에 글자가 있고 그 열에 다른 값이 있다 | `values[2][0]` 이 `책임성` | `책임성` | 통과 |
| 구멍 안 드로잉 + 병합 자리 안 드로잉 | 표시는 `[(2,0)]`, 서명 `{hole-sig}` | `([(2, 0)], {'hole-sig'})` | 통과 |
| 칸을 통째로 덮는 드로잉(면적비 1.0)이 구멍 안 | 표시 없음 | `([], set())` | 통과 |
| 구멍이 있는 열이 **표 전체에서 빔**, 글자 `21` | 안 채운다 | 빈 문자열 | 통과 |
| 같은 경로 · 크기만 2배 | 같은 서명 | `True` | 통과 |
| 같은 경로 · 채움색만 다름 | 다른 서명 | `True` | 통과 |

**순서가 결과를 바꾼다 — 이 스니펫을 처음 쓸 때 틀렸다.** 같은 `values` 를 재사용해
글자 복원 뒤에 표시를 세면 `([], set())` 이 나온다. 글자가 든 칸은 빈 칸이 아니라 표시
대상이 아니기 때문이고 **동작은 맞다.** 로더도 같은 순서로 돈다(복원이 먼저, 판정이 나중).
AI가이드 17쪽에서 둘이 안 부딪히는 것은 글자가 든 구멍 `(2,0)` 과 표시가 든 구멍 `(2,7)`
이 서로 다른 자리이기 때문이다 — 같은 구멍이면 글자가 이긴다.

**이 가상 수치로 임계값을 정하지 않았다.** 두 겹의 값(0.5 / 0.5)은 11회차 실파일 실측에서
나온 것이고, 여기서 본 것은 *그 값이 합성 격자 칸에서도 같은 방향으로 도는가* 뿐이다.

**빈 열 가드는 반대로 가상만 검증한다.** 그것이 막는 유일한 실파일 사례(아동정책 p11 의
쪽 번호 `21`)가 아래 3절에서 그 문서를 빼며 코퍼스에서 사라졌다 — *"실파일에 우연히 없는
경계값은 가상만 만들 수 있다"* 가 이 자리다.

## 7. 재지 못한 것

- ~~유료 경로를 실제로 안 돌렸다~~ → **2회차에서 돌렸다**(3-7). 첫 실행 1회 · 재실행 0회 ·
  채움 75/74 로 계획의 기대값 셋이 다 맞았다
- **앞 폴더와의 A/B 가 깨끗하지 않다.** `2026-08-22-table-vision-escalation` 이 12·13회차
  이전 상태라, 그 폴더와의 6청크 차이에 세 회차가 겹쳐 있다. 14회차만의 산출 증거는 17쪽
  행 라벨 하나이고 나머지는 직접 잰 수치(73→74 · 6→1)로 받친다. **다음 변경 때는 직전
  폴더가 바로 앞 커밋 상태인지 먼저 봐야 한다**
- **`ocr` 패스를 안 돌렸다.** 무과금이지만 문서당 56초가 들고 표 경로와 무관하다.
  이미지 쪽 수치가 필요하면 따로 돌려야 한다
- **빈 열 가드의 실파일 근거가 없다.** 그것이 막는 유일한 관측 사례가 아동정책 p11 의 쪽
  번호였고 그 문서를 뺐다. 지금 이 규칙을 지키는 것은 2절의 합성 테스트 하나뿐이다
- **HWPX 에서는 이 신호를 못 잰다.** 셀 사각형이 없어 격자 구멍이라는 개념 자체가 성립하지
  않는다. '없다'가 아니라 '못 잰다'이고, 이미지 표시 크기 필터가 HWPX 에서 못 도는 것과
  같은 형태다
- **서명이 둘 이상인 문서를 못 봤다.** 표본이 AI가이드 하나뿐이라 *"서명이 갈리면 두 번
  문다"* 는 가상 테스트(`test_mixed_signatures_still_call`)로만 확인됐다
- **`regression/baseline.json` 은 이 스킬이 아니라 계획 실행 단계에서 고쳤다.** 값 갱신이
  아니라 **항목 배제**이고, 지우기 전에 3-6 의 대조로 나머지 9개가 안 움직이는 것을 먼저
  확인했다
