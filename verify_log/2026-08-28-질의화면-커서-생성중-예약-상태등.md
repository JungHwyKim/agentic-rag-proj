- 대상: `task_log/2026-08-28-질의화면-커서-생성중-예약-상태등.md` (미커밋)
- 비용: **외부 API 호출 없음.** 서버를 한 번 띄웠지만 **질의는 한 건도 안 보냈다** — 유료

## 1. 확인하려 한 것

**"규칙이 도는가" 쪽이고, 이번 작업에는 정할 임계값이 아예 없다.** 상태등의 10초는 관측값이
아니라 화면 갱신 주기이고(서버가 하는 일이 `getattr` 둘이라 분포에서 고를 것이 없다), 나머지는
전부 배선이다.

가른 것은 셋이다.

1. **서버가 내는 것** — 라우트·템플릿·CSS 가 계약대로 바뀌었나 (아래 2절, 앱을 세워 잰다)
2. **띄운 서버가 내는 것** — `.env` 를 실제로 태운 프로세스에서도 같은가 (3절)
3. **사람이 브라우저에서 밟아야만 알 수 있는 것** — 커서 모양·생성 중 줄·예약·스탑·회색등.
   **이번에도 못 쟀다**(7절). 2회차가 남긴 *"모양은 기계가 못 잰다"* 가 그대로다

## 2. 가상 데이터

무엇을 고립시켰나: **`app.state` 의 임베더 유무 한 축**이다. 상태등이 그 한 축만 보고 색을
가르는지, 그리고 **조회가 임베더를 만들어 버리지 않는지**를 본다. 뒤엣것이 이 축의 요점이다 —
`embedder_for()` 를 부르면 키가 없는 환경에서 상태 조회가 예외로 죽고, 있는 환경에서는 등이
KURE 2.27GB 를 올린다.

`tests/api/test_query_route.py` 의 `_client()` 를 그대로 쓴다(설정 핀이 이미 박혀 있다).

```python
# tests/api/test_query_route.py 에 들어간 것과 같다
def test_status_says_idle_before_the_first_query():
    client = _client()
    client.app.state.embedder = None      # lifespan 이 심는 첫 질의 전 상태
    body = client.get("/api/v1/status").text
    assert "status-idle" in body
    assert "status-ready" not in body
    assert client.app.state.embedder is None   # 조회가 임베더를 만들지 않았다

def test_status_says_ready_once_the_embedder_stands():
    client = _client()                    # _client() 가 embedder = object() 를 세워 둔다
    body = client.get("/api/v1/status").text
    assert "status-ready" in body
    assert "status-idle" not in body

def test_status_carries_the_warmup_reason_in_the_title():
    client = _client()
    client.app.state.warmup_errors = ["reranker: boom"]
    body = client.get("/api/v1/status").text
    assert 'title="reranker: boom"' in body
```

## 5. 판정

- **의도한 변화** — 위 2·3절 전부. 배선이 계약대로 붙었고 서버가 같은 것을 낸다
- **회귀** — 없음. 1496 passed 이고 실패 0
- **회귀 하나를 사용자가 잡았다(1차 판정 뒤)** — 첫 판은 말풍선을 `submit` 에서 그리고
  입력칸을 거기서 비웠는데, htmx 가 폼을 읽기 **전**이라 빈 질문이 `required` 검증에 걸려
  **요청이 아예 안 나갔다.** 단위 테스트 1496개와 서버 프로브 9항목이 **전부 통과한 채였다** —
  둘 다 브라우저의 이벤트 순서를 안 본다. 그리는 자리를 `htmx:beforeRequest` 로 옮겨 고쳤고,
  «비우는 코드가 어느 리스너 안에 있는가» 를 잠그는 테스트를 더했다(동작이 아니라 자리를
  재는 것이 브라우저 없이 할 수 있는 최대다)
- **두 번째 회귀도 사용자가 잡았다** — 예약된 질의를 `htmx:afterRequest` 안에서 곧바로
  `requestSubmit()` 했는데, htmx 가 그 이벤트를 **in-flight 잠금을 풀기 전**에 쏘므로
  `hx-sync="this:drop"` 이 떨궜다(에러 없음 · «예약은 되는데 자동 발사만 안 되는» 모양).
  `setTimeout(…, 0)` 으로 콜스택 밖에서 보내 고쳤다. **앞의 회귀와 같은 모양이다** —
  htmx 의 이벤트는 htmx 자신의 상태 정리보다 먼저 온다
- **확인 필요** — **화면에서 실제로 어떻게 보이고 어떻게 도는가.** 커서가 안 바뀌는지, 생성 중
  줄이 질문 아래에 뜨는지, 초가 오르는지, 두 번째 전송이 예약되고 스탑이 푸는지, 서버를
  내렸을 때 등이 회색이 되는지 — **여섯 다 사람이 브라우저에서 밟아야 한다**(7절)

## 7. 재지 못한 것

- **모양과 상호작용 전부.** 헤드리스 브라우저가 없어 DOM 과 라우트 계약까지가 한계다.
  2회차가 남긴 *"최종 판정은 사람이 열어본 것 하나"* 가 그대로이고, **이번에 밟을 경로가
  늘었다** — 상태가 넷(idle·busy·reserved·스탑)에 등이 3색이다
- **질의를 한 건도 안 보냈다.** 그래서 «질문이 먼저 올라간다»·«에코가 일치한다»·«실패하면
  입력값이 돌아온다» 를 실서버에서 못 봤다. 단위 테스트가 서버 쪽 절반(조각에 말풍선이 없고
  `data-echo` 가 실린다)은 잠갔고, 화면 쪽 절반은 사람 몫이다
- **에코 대조 줄이 실제로 뜨는 것을 못 봤다.** 그것을 보려면 일부러 깨진 질의를 보내야 하는데,
  그 경로가 곧 `data/queries.jsonl` 오염이다(깨진 4줄이 이미 그 파일에 있다)
- **노랑 → 초록 전이**(3절) · **회색**(서버를 내려야 한다)
