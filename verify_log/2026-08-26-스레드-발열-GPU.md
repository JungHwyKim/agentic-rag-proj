# CPU 발열의 축은 셋이고 서로 안 겹친다 — 임베딩 GPU 전환으로 CPU-초 117배

- 검증일: 2026-08-26
- 대상: `task_log/2026-08-26-스레드-발열.md` — `TORCH_NUM_THREADS`·`OCR_MAX_WORKERS` 신설,
  `EVAL_EMBEDDINGS["kure-v1-gpu"]` 추가, `EMBEDDING_DEVICE=cuda` 전환
- 비용: **외부 API 호출 0** (vision 0 · llamaparse 0 · 임베딩 API 0 — 전부 로컬 모델).
  환경 변경 없음(`torch` cu130 은 앞 회차가 이미 깔았다)

## 1. 확인하려 한 것

사용자 질문이 *"임베더·리랭커가 쓰는 스레드 수와 스레드별 성능"* 이었다. 넷으로 갈렸다.

1. **스레드 수가 몇인가** — 저장소가 안 정하므로 torch 기본값을 읽는 문제다
2. **스레드마다 성능이 얼마인가** — 저장소에 이 축의 측정이 **하나도 없었다**
3. **GPU 로 옮기면 얼마나 식나** — 앞 회차가 리랭커만 닫았고 **임베딩 색인 경로는 아무도 안 쟀다**
4. **옮겨도 되나** — `config.py` 가 *"처음 GPU 를 쓸 때 CPU 벡터와의 코사인 차이를 재기로
   했다"* 로 **예약해 둔 측정**이 있다. 캐시 salt 를 고칠지가 여기서 갈린다

3·4는 "값이 얼마인가"라 실파일이 답한다. 2도 규칙이 아니라 값이라 역시 실측이다.

## 2. 가상 데이터

**임계값을 정하는 데는 안 썼다.** 두 군데에만 썼고 역할이 다르다.

### 2-1. 스레드 상한이 실제로 먹는가 — 가짜 torch

torch 를 올리지 않고 `set_num_threads()` 호출만 본다. 실제 torch 를 부르면 기본 pytest 가
가중치 2.27GB 경로를 열게 되는데, 그것이 `local_st.py` 가 경고하는 자리다.

```python
@pytest.fixture
def fake_torch(monkeypatch):
    calls: list[int] = []
    module = SimpleNamespace(set_num_threads=calls.append)
    monkeypatch.setitem(sys.modules, "torch", module)
    return calls
```

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `torch_num_threads=4` | `set_num_threads(4)` 1회 · 반환 4 | 그대로 | 통과 |
| `torch_num_threads=None` | **torch 를 아예 안 건드림** · 반환 None | `calls == []` | 통과 |
| `torch_num_threads=0` / `-1` | 무시 · 반환 None | `calls == []` | 통과 |
| 2 → 2 → 6 연속 호출 | 첫 번만 적용(멱등) | `calls == [2]` | 통과 |
| torch 미설치 | 예외 없이 None | 그대로 | 통과 |
| 인자 없이 · `TORCH_NUM_THREADS=3` | 환경변수를 읽어 3 | 3 | 통과 |

**멱등 칸이 이 표의 이유다.** 부르는 자리가 둘(임베더·리랭커 적재)이라, 멱등이 아니면
*"나중에 부른 쪽이 이긴다"* 가 그대로 재현된다 — 설정을 하나로 만든 근거가 무효가 된다.

### 2-2. 워커 수가 셋의 최솟값인가

`os.cpu_count()` 를 고정해 축을 고립시켰다.

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| `cpu_count=16` · 상한 2 · 할 일 100 | 2 (상한이 이김) | 2 | 통과 |
| `cpu_count=16` · 상한 8 · 할 일 3 | 3 (할 일이 이김) | 3 | 통과 |
| `cpu_count=2` · 상한 8 · 할 일 100 | 2 (코어가 이김) | 2 | 통과 |
| `cpu_count=16` · 상한 0 · 할 일 100 | 1 (바닥) | 1 | 통과 |
| 기본값 | 8 | 8 | 통과 |

**가상으로 워커 수를 못 정한다.** 모킹한 sleep 은 Tesseract 의 실제 CPU 경합을 흉내내지
못한다 — 값은 `verify_log/2026-08-24-ocr-병렬화.md` 의 실측이 정했고 이번에 안 바꿨다.

### 3-3c. GPU 손잡이 — `-pl` 은 이 GPU 에서 **안 된다**. 되는 것은 `-lgc` 다

**초판이 `nvidia-smi -pl 50` 을 권고했는데 틀렸다.** `nvidia-smi -q -d POWER` 가
`Current 74.14W / Default 50.00W / Min 5 / Max 85` 을 보여주길래 조정 가능하다고 읽었다.
실제로 돌리니 이렇다.

| 시도 | 결과 |
|---|---|
| `nvidia-smi -pl 50` (일반 권한) | `Insufficient Permissions` |
| `nvidia-smi -pl 50` (**관리자**) | **`Changing power management limit is not supported for GPU`** |
| `nvidia-smi -pm 1` (지속 모드) | `not supported for GPU ... on this platform` (WDDM) |
| `nvidia-smi -lgc 210,1500` (관리자) | **`GPU clocks set to (gpuClkMin 210, gpuClkMax 1500)`** — 먹는다 |

**권한 오류가 미지원을 가리고 있었다.** 일반 권한에서 `Insufficient Permissions` 만 보고
*"권한만 있으면 된다"* 로 결론 내린 것이 실수다 — 승격하고 나서야 진짜 사유가 나왔다.
노트북 GPU 라 전력 예산을 Dynamic Boost·펌웨어가 쥐고 있어 nvidia-smi 가 못 건드린다.
**그 상한 자체가 움직인다는 것도 관측됐다** — 같은 유휴 상태에서 74.14 → 56.75 → 59.33W.

**그래서 축이 전력이 아니라 클럭이다.** 같은 임베딩 부하 45초씩, `nvidia-smi` 를 2초마다
병행 표본(부하 구간만; 앞 2표본은 아직 안 올라온 구간이라 뺐다).

| 클럭 상한 | 청크/초 | vs 무제한 | GPU W 평균 | **GPU W 최대** | GPU °C 평균/최대 | 실측 클럭 | **J/청크** |
|---|---:|---:|---:|---:|---:|---:|---:|
| 무제한 | 13.07 | 100% | 75.0 | **97.6** | 66.5 / 71 | 2,202 | 5.74 |
| 1800 | 10.92 | 84% | 53.4 | 58.5 | 65.9 / 68 | 1,789 | 4.89 |
| **1500** | 9.27 | **71%** | **38.6** | **42.2** | **59.7 / 62** | 1,487 | 4.17 |
| 1200 | 7.52 | 58% | 30.9 | 35.3 | 60.2 / 61 | 1,190 | 4.11 |

**넷이 나온다.**

1. **사용자가 원한 "50W" 를 만족하는 것은 1500 이다** — 최대 42.2W 로 50 아래다.
   1800 은 평균 53.4W · 최대 58.5W 로 **넘는다.** `-pl` 이 묶으려던 것은 *피크*라
   평균이 아니라 최대 칸으로 골라야 한다.
2. **온도는 1500 에서 바닥을 친다.** 1200 으로 더 내려도 60.2°C 로 **안 내려간다**
   (오히려 0.5°C 높은데 표본 노이즈 범위다). **1500 아래로는 온도 이득이 없다.**
3. **CPU 스레드 축과 정반대로, GPU 는 낮출수록 총 에너지도 준다.** `J/청크` 가
   5.74 → 4.11 이다. GPU 는 클럭을 낮추면 전압이 같이 내려가고 사용률이 96~99% 로
   유지돼 **노는 구간이 없다.** CPU 스레드는 코어를 놀리면서도 패키지 전력을 계속 물어
   반대로 나왔다 — **같은 "낮춘다"가 두 축에서 부호가 반대다.**
4. **효율 무릎도 1500 이다.** 1200 의 `J/청크` 가 4.11 로 1500(4.17)과 사실상 같은데
   속도는 22% 더 잃는다. 즉 1200 은 **얻는 것 없이 느려지기만 한다.**

**`-lgc` 는 재부팅하면 풀린다.** `-pm`(지속 모드)이 이 플랫폼에서 미지원이라 드라이버
수준으로 굳힐 방법이 없고, 남는 것은 작업 스케줄러(부팅 시 관리자 실행)뿐이다.
**저장소 설정으로는 만들 수 없다** — 앱이 GPU 클럭을 바꾸려면 관리자 권한이 필요하고,
적재 파이프라인이 하드웨어 상태를 건드리는 것은 경계 위반이다. `.env` 에 넣으면
**아무도 안 읽는 죽은 설정**이 된다(이 저장소가 `rerank_provider` 를 두고 세운 잣대와 같다).

### 3-5. 예약돼 있던 측정 — CPU 벡터 vs GPU 벡터

`config.py` 의 `embedding_device` 주석이 *"아직 실측이 아니다(이 저장소에 CUDA 머신이
없었다)"* 로 남겨 둔 자리다.

| 입력 | 코사인 최소 | 코사인 평균 | `1−cos` 최대 | 성분 최대 절대차 | 노름 cpu / cuda |
|---|---:|---:|---:|---:|---|
| 실제 청크 414개 | 0.9999999986 | 1.0000000000 | **1.354e-09** | 5.728e-06 | 1.00000003 / 1.00000002 |
| 합성 200개(참고) | 1.00000000 | 1.00000000 | **0.000e+00** | 4.284e-07 | 1.000000 / 1.000000 |

**합성에서는 정확히 0인데 실제 청크에서는 0이 아니다.** 둘 다 float32 오차 수준인 것은
같지만, **합성만 봤으면 "완전히 같다"로 적을 뻔했다** — 가상이 자기 확인이 되는 사례다.

### 3-6. E2E — 그런데 첫 실행은 아무것도 검증하지 않았다

같은 60건을 임베딩 축만 갈아 돌렸다. **처음에는 `--label g1-all-gpu` 로 돌려 지표 49개가

**`calls: 0` 이 갈라 준 것이다.** `cache_salt_for()` 에 device 가 없으므로 GPU 실행이
CPU 가 만든 벡터를 그대로 읽는다 — *"GPU 가 같은 결과를 낸다"* 와 *"GPU 가 안 돌았다"* 가
**에러 없이 수치로만** 같아 보이는 자리다. `EMBEDDING_CACHE_DIR`·`RERANK_CACHE_DIR` 를
스크래치패드로 돌려 다시 쟀다. 앞 회차(`2026-08-26-리랭커-GPU축.md`)가 리랭크 salt 를 두고
같은 검사를 한 것과 같은 종류이고, **임베딩 쪽은 salt 에 device 가 없어 더 잘 숨는다.**

## 7. 재지 못한 것

- **팬 RPM.** 이 HWiNFO 로그에 팬 컬럼이 **하나도 없다**(339개 중 0). 노트북 EC 를 못 읽는
  것으로 보인다. 그래서 **소음 자체는 이 데이터로 못 답한다** — 전력·온도까지가 한계이고,
  *"cuda 가 CPU 를 식히는 대신 GPU 팬을 돌리는데 그게 더 시끄러운가"* 는 **사용자 귀가
  답할 문제로 남긴다.** 전력이 팬의 원인이라 대리지표로는 쓸 만하지만 팬 커브는 모른다
- **클럭 상한이 소음을 실제로 얼마나 줄이는지.** 전력·온도는 쟀지만 팬 RPM 이 없어
  **dB 로는 못 답한다.** 1500 에서 GPU 최대 97.6W→42.2W · 66.5°C→59.7°C 이므로 팬이 덜 돌
  것으로 보이지만, **그 판단이 실측은 아니다**
- **1500 이 리랭킹·생성에 미치는 영향.** 임베딩 부하로만 쟀다. cross-encoder 는 배치
  모양이 달라 클럭 민감도가 다를 수 있다
- **클럭 잠금이 검색 품질을 바꾸는가.** 안 쟀다. 장치가 같고 연산도 같아 안 바뀔 것으로
  보이지만 `1−cos` 대조를 안 돌렸다
- **1스레드 지점의 앞 65초.** CSV 가 스윕 시작(17:53:08)보다 늦게(17:54:13) 시작해 그
  지점만 부분 관측이다. 부하 창 60초는 온전히 들어 있다
- **CPU 온도의 절대값은 이 케이스·이 냉각 상태의 값이다.** 주변 온도·먼지·전원 프로파일을
  안 통제했고 스윕 1회다. **비교(스레드 간 상대)는 같은 조건 연속 측정이라 유효**하지만
  *"이 노트북은 8스레드에서 89°C 다"* 를 일반화하면 안 된다
- **스레드 수가 벡터를 바꾸는가.** 안 쟀다. BLAS 리덕션 순서가 스레드 수에 따라 달라질 수
  있는데, CPU↔GPU 차이(1.354e-09)보다 작을 것으로 **보이나 그 판단이 실측은 아니다.**
  `EVAL_SETTINGS` 가 `torch_num_threads` 를 안 박은 것이 이 미결에 걸려 있다
- **OCR 워커를 낮췄을 때의 발열.** `OCR_MAX_WORKERS` 를 열기만 했고 값별 스윕은
  `verify_log/2026-08-24-ocr-병렬화.md` 의 벽시계를 그대로 쓴다 — 그 회차는 CPU-초를 안 쟀다
- **화면 왕복.** `answer_question()` 은 생성 LLM 을 부르고 그것이 과금이라 안 돌렸다.
  사용자 체감은 이 표의 합이 아니다
- **다른 코어 수 / 다른 GPU.** 16논리 8물리 + RTX 5060 한 대에서만 쟀다
