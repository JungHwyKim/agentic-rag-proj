# 무료 OCR 병렬화 — 속도와 결과 동치를 함께 잰다

- 검증일: 2026-08-24
- 대상: [task_log/2026-08-24-ocr-병렬화.md](../task_log/2026-08-24-ocr-병렬화.md)
  (`loader/content/` 의 `router.py` · `base.py` · `image_ocr.py` · `classify.py`, 미커밋)
- 비용: **외부 API 호출 없음.** vision 0회 · llamaparse 0회 · 임베딩 0회.
  측정 스크립트가 `ContentRoutingConfig` 의 `openai_api_key` · `llama_cloud_api_key` 를
  빈 문자열로 덮어 유료 경로를 원천 차단했고, 실측에서도 `vision_calls=0` 으로 확인됐다.
  `-m integration` 은 안 돌렸다

## 1. 확인하려 한 것

둘이고 성격이 다르다.

1. **규칙이 도는가** — 병렬 실행이 요소 순서를 안 깨는가, 공유 상태(`ctx.warn` ·
   `ctx.ocr_applied`)가 안 샜는가, 유료 Vision 이 병렬 구간에 안 들어가는가. **가상**이 답한다
2. **얼마나 빨라지고, 결과가 같은가** — 워커 수별 벽시계와 **산출물 동치**. **실파일**이 답한다

**2번의 동치가 이 검증의 중심이다.** 빨라진 것만 재고 산출물을 안 재면 "덜 읽고 빨리 끝난
것"과 구별이 안 된다.

## 2. 가상 데이터

무엇을 고립시켰나: **이미지 리전의 개수와 완료 순서**만 바꾸고 나머지는 고정했다.
Tesseract 를 모킹해 **설치 여부에 결과가 안 흔들리게** 하고, 뒤 리전일수록 빨리 끝나게
지연을 거꾸로 줘서 **완료 순서와 `order` 를 일부러 어긋나게** 만들었다.

리전 구별은 PNG 폭으로 한다 — 가짜 `extract_text` 가 `image.width` 에서 리전 번호를 되찾아
텍스트를 만들므로, **어느 리전의 결과가 어디로 갔는지**까지 검사된다.

```python
# tests/conftest.py 의 png_bytes 픽스처를 그대로 쓴다 (새 생성 방식을 만들지 않는다)
import io
from PIL import Image

def png_bytes(width=400, height=200, color="white") -> bytes:
    buffer = io.BytesIO()
    Image.new("RGB", (width, height), color).save(buffer, format="PNG")
    return buffer.getvalue()

# 리전 i 는 폭 400+i 로 만든다. 지연은 (개수 - i) 에 비례 — 뒤엣것이 먼저 끝난다
def _extract(image, config, **kwargs):
    index = image.width - 400
    time.sleep((count - index) * 0.005)
    return f"텍스트-{index}"

# 입력은 역순으로 넣어 route_all 의 정렬까지 함께 본다
regions = [_image_region(i, png_bytes(400 + i, 200)) for i in reversed(range(12))]
```

전문은 `tests/ingestion/loader/content/test_router_parallel.py` 다.

| 입력 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 이미지 12개 · 입력 역순 · 완료 역순 · 워커 8 | `order` 가 0..11, 텍스트가 `텍스트-0`..`텍스트-11` | 그대로 | 통과 |
| 이미지 10개를 워커 1 과 워커 8 로 각각 | `(order, text, page, image_source)` 전부 동일 · `warnings` 동일 · `ocr_applied` 동일 · `vision_calls` 0 동일 | 그대로 | 통과 |
| 이미지 24개가 전부 같은 경고를 남김 · 워커 8 | `ctx.warnings` 길이 **1** | 1 | 통과 |
| `LoadContext.warn` 을 스레드 16개 × 50회, 서로 다른 메시지 5종 | 정확히 5개 | 5개 | 통과 |
| `image_handler="vision"` · 리전 6개 · 상한 2 · 워커 8 | `vision_calls == 2` · 호출 스레드가 **메인 하나** | 2 · `{메인}` | 통과 |
| 텍스트·표·이미지 섞어 4개 | `order` 0,1,2,3 순서로 맞물림 | 그대로 | 통과 |
| 이미지 3개 중 1개가 열리지 않는 바이트 | 남는 요소 `order` [0,2] · 경고 1개 · `open_image` **정확히 3회** | 그대로 | 통과 |

마지막 줄이 재는 것: 병렬 구간에서 열기에 실패한 리전을 **직렬 구간이 다시 열지 않는가**.
다시 열면 호출이 3보다 커진다.

**가상으로는 임계값(워커 수)을 못 정한다.** 모킹한 `sleep` 은 Tesseract 의 실제 CPU 경합을
흉내내지 못한다 — 워커 수는 3절이 정했다.

## 7. 재지 못한 것

- **직렬 바닥 23.6초의 내부 구성** — PyMuPDF 쪽 루프 / 300dpi 래스터 / cleaner 로 안 쪼갰다.
  16워커 이론 하한 37초의 대부분이 이것이라, 42초 아래로 가려면 여기부터 재야 한다
- **화면(uvicorn) 실측** — 안 했다. `index_document()` 는 임베딩 API 를 부르고 사용자의 실제
  `.qdrant` 와 문서 목록에 쓰므로 승인 없이 안 돌렸다. 병렬화한 구간은 `ingest()` 안이라
  위 수치가 전부를 덮지만, **체감 대기 시간은 임베딩·upsert 를 더한 값**이라 아직 모른다
- **Vision 이 많이 붙는 문서에서의 이득** — 이 문서는 47/47 이 OCR 이라 유료 경로가 안 밟혔다.
  유료는 직렬로 남겼으므로 그런 문서는 **이번 변경으로 안 빨라진다**. 그 크기를 못 쟀다
- **다른 코어 수의 머신** — 16코어 한 대에서만 쟀다. `_ocr_workers()` 가
  `min(8, os.cpu_count(), 리전 수)` 라 적은 코어에서는 알아서 줄지만, 그 값이 맞는지는 안 쟀다
- **메모리 실측** — 1.2GB 는 2500x3535 RGB × 47 로 **계산한 값**이고 실제로 재지 않았다.
  설계를 바꾼 근거였으므로 적어 둔다
