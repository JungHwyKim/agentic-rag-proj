## 1. 확인하려 한 것

앞 네 판이 「흡수됨」으로 닫혔는데 **리랭커가 `cohere` 하나였다.** 그래서
**「흡수가 리랭커 종류를 타는가」에 답이 없었다** — 이 축의 제일 큰 구멍이다.

**재기 전에 박은 기준** — 앞 네 판과 **같은 문구**를 썼다(판마다 다르면 비교가 안 된다).

- **흡수됨** — 조합이 리랭커 단독을 이긴 질의 **0~1건** & 총합 안 오름
- **안 흡수됨** — **2건 이상** 이기고, **그 이득이 재작성 단독이 올린 질의에서 온다**
- **못 가름** — 사이

**이 판에만 있는 물음의 기준도 박았다** — 네 칸 모두 `cohere` 와 같은 판정이면 *종류를 안 탄다*,
한 칸이라도 갈리면 *탄다* 이고 **어느 칸인지가 곧 다음 질문**이다.

### 3-1. 회계 게이트 — **규약이 유료 갈래와 다르다**

**미리 적어 둔 게이트가 그대로는 안 먹었다.** `rerank_calls + rerank_cache_hits == 질의 수` 로
검사했더니 **네 실행 모두 `0 + 0`** 인데 `reranked` 는 3,000 / 900 이었다.

**사고가 아니라 회계 규약 차이다** — `retrieval/reranker/local_ce.py` 모듈 docstring 이
*"`RerankUsage.reranked`(점수를 매긴 후보 수)가 이쪽의 비용 지표다 — `api_calls`·`total_tokens`
는 늘 0 이다"* 라고 못 박아 뒀다. `api_calls` 는 **HTTP 호출 수**라 로컬 갈래에 존재하지 않는다.

**그래서 로컬 갈래의 게이트는 이것이다:**

```
reranked / rerank_candidates + rerank_cache_hits == 질의 수
```

**이 차이가 위험한 방향은 하나다** — 로컬 갈래에서 리랭커가 아무것도 안 한 실행도
`calls=0 · cache=0` 으로 보인다. 즉 **유료용 게이트를 그대로 쓰면 「돌았다」와 「안 돌았다」가
안 갈린다.** Cohere 429 가 품질 저하로 읽혔던 것과 같은 모양이고, 여기서는 `reranked` 열이
유일한 신호다.

| 실행 | 점수매김 | 캐시 | 합 / n | `rerank_device` | 재작성 |
|---|---|---|---|---|---|
| 60건 `fuse` × local-gpu | 3000 / 50 = 60 | 0 | **60 / 60** | `cuda` | 0 + 60 |
| 60건 `replace` × local-gpu | 3000 / 50 = 60 | 0 | **60 / 60** | `cuda` | 0 + 60 |
| 사람 `fuse` × local-gpu | 900 / 50 = 18 | 0 | **18 / 18** | `cuda` | 0 + 18 |
| 사람 `replace` × local-gpu | 900 / 50 = 18 | 0 | **18 / 18** | `cuda` | 0 + 18 |

나머지도 통과 — `rerank_model` 넷 다 `BAAI/bge-reranker-v2-m3` · `rewrite_mode` 가 라벨과 일치 ·
경고 3종 `[]` · 적재 118/71/103/122 · 사람 세트 `queries` 18 · `skipped_unanswerable` 25 ·
여섯 실행의 `per_query` 행 수와 `query_id` 집합 동일.

**`rerank_device == "cuda"` 를 따로 본 이유** — `extra="ignore"` 라 이름을 틀리면 조용히 안 먹고,
`rerank_cache_salt_for()` 가 device 를 실어 **cpu 로 돌면 캐시도 안 겹쳐 아무 신호 없이
다른 실험이 된다**(질의당 63.9초). 넷 다 `cuda` 였다.

### 3-4. 기전 (4단계 · 판정이 갈렸으므로 발동)

리랭킹 **후** 최종 상위 n 이 `off` 와 `fuse` 사이에 같은 질의 수(60건, 캐시에서만 읽음):

| 리랭커 | 상위 1 | 상위 3 | 상위 5 | 상위 10 | 상위 20 |
|---|---|---|---|---|---|
| `cohere` | **60 / 60** | 55 | 49 | **34** | **13** |
| `local-gpu` | 59 / 60 | 53 | 47 | **25** | **8** |

**`cohere` 가 더 강하게 수렴시킨다.** 리랭킹 **전** 후보 50의 집합은 두 경우가 같으므로
(0/60 같음 · 중앙 12개 교체 — 리랭커와 무관하다) 갈리는 것은 **리랭커의 성질**이다.
같은 후보를 줘도 `cohere` 는 같은 승자를 더 자주 고르고, `local-gpu` 는 후보 구성에 더 민감해
**재작성이 데려온 후보가 상위에 남는다.** 깊이가 깊어질수록 격차가 벌어진다(상위 10에서 34 vs 25).

## 5. 판정

- **흡수는 리랭커 종류를 탄다.** `local-gpu` 로 LLM 60건 두 칸이 **「안 흡수됨」**이고
  기전 연속성까지 만족한다(이긴 질의가 3/3 · 5/6 이 재작성 단독이 올린 질의다).
  **앞 네 판의 「흡수됨」은 `cohere` 의 성질이지 리랭킹 단계의 성질이 아니다.** **의도한 변화**
- **기전은 「수렴의 세기」다.** 같은 후보를 줘도 `cohere` 는 상위 1을 **60/60** 똑같이 고르는데
  `local-gpu` 는 상위 10에서 **25/60** 만 같다. 후보 구성에 덜 민감한 리랭커일수록 재작성을
  더 지운다
- **그런데 실무 결론은 안 뒤집힌다** — `local-gpu` + 재작성(`nDCG@10` **0.7448**)이
  **리랭커 하나만 좋은 것으로 바꾼 것(`cohere` 단독 0.7674)보다 낮다.**
  즉 **「재작성을 켜는 것」보다 「리랭커를 무엇으로 쓰는가」가 크다.** 이득의 크기도
  +0.0121(nDCG) · miss 8 → 7 로 작다
- **사람 세트는 여전히 흡수됨이다**(양쪽 모드 나음 1건). 다만 기준 경계(0~1)의 **위쪽 끝**이라
  단정을 세게 하지 않는다 — n=18 에서 한 건이 5.6%p 다
- **회계 게이트 규약이 갈래마다 다르다는 것이 이 판에서 처음 드러났다.** 유료용
  `rerank_calls + cache_hits` 는 로컬 갈래에서 **늘 0** 이라 「돌았다/안 돌았다」를 못 가른다.
  로컬은 `reranked / rerank_candidates + cache_hits` 를 본다

## 7. 재지 못한 것

- **왜 `cohere` 가 더 수렴하는가** — 잰 것은 *얼마나* 수렴하는가이고 *왜* 는 안 쟀다.
  모델 크기·학습·점수 분포 중 무엇인지 이 저장소에서는 못 묻는다
- **`local` (cpu) 칸** — 같은 모델의 CPU 판은 안 쟀다. `rerank_device` 가 점수를 가를 수 있다는
  것이 salt 에 device 를 실은 이유이므로, **`local-gpu` 결과를 `local` 로 미룰 수 없다**
- **`cohere-v4-fast`** — 리랭커가 셋인데 둘만 쟀다
- **생성 품질** — 다섯 판 모두 검색 지표만 쟀다
- **사람 세트에서 두 모드가 갈리는 것**(`replace` 가 `fuse` 보다 `nDCG` 0.5705 vs 0.5540)
  — 표본 18이라 안 팠다
